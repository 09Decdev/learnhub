# Chương 15 · Elastic Kubernetes Services (EKS) cơ bản

Học xong chương này, bạn **chạy được một ứng dụng nhiều tầng trên Kubernetes do AWS quản lý**: tạo cluster EKS bằng `eksctl`, đưa traffic vào qua Application Load Balancer, lưu dữ liệu MongoDB trên EBS, hiểu cách cluster tự co giãn, cấp quyền cho người khác vào cluster, và quan trọng nhất là **xoá sạch để không bị tính tiền**.

Những lệnh bạn sẽ gõ nhiều nhất cả chương:

```bash
eksctl create cluster -f cluster-config.yaml          # tạo cluster + node group (~15 phút)
aws eks update-kubeconfig --region ap-southeast-1 --name devops-test-cluster
kubectl get nodes                                    # kiểm tra node đã Ready
helm install ...                                     # cài add-on (ALB controller...)
eksctl delete cluster --name devops-test-cluster --region ap-southeast-1
```

> 💰 EKS **không có Free Tier**. Một cluster như trong lab tốn khoảng **6–8 USD mỗi ngày** nếu để chạy. Hãy làm lab theo cụm, xong là xoá ngay.

## Giới thiệu chương và AWS EKS {001-002}

**Khái niệm cốt lõi**

Ở chương Kubernetes cơ bản, bạn chạy cluster trên máy mình (minikube). Một cluster Kubernetes thật có hai phần:

- **Control plane** (bộ não): `kube-apiserver`, `etcd` (cơ sở dữ liệu lưu mọi object), `scheduler`, `controller-manager`. Mất control plane là mất khả năng điều khiển cluster.
- **Data plane** (tay chân): các **worker node** chạy `kubelet`, `kube-proxy` và container của bạn.

Tự dựng control plane có tính sẵn sàng cao (3 máy etcd, backup, nâng cấp version, cấp chứng chỉ…) rất mất công. **Amazon EKS (Elastic Kubernetes Service)** làm thay bạn phần đó: AWS chạy control plane trên nhiều AZ, tự vá lỗi và cho bạn một endpoint API. Bạn chỉ lo phần data plane và ứng dụng.

```
                 ┌─────────── AWS quản lý (tài khoản của AWS) ───────────┐
 kubectl ──────► │  API server (endpoint HTTPS)  +  etcd  (nhiều AZ)      │
                 └──────────────────────────┬────────────────────────────┘
                                            │ ENI trong VPC của bạn
 ┌──────────────────── VPC của bạn ─────────┴─────────────────────────────┐
 │  Node EC2 (AZ a)      Node EC2 (AZ b)       hoặc Fargate / Auto Mode    │
 │  [pod][pod]           [pod][pod]                                        │
 └────────────────────────────────────────────────────────────────────────┘
```

**Đi sâu hơn: 4 cách chạy data plane**

| Lựa chọn | Ai lo EC2? | Khi nào dùng |
|---|---|---|
| **Self-managed node group** (`nodeGroups` trong eksctl) | Bạn: AMI, vá lỗi, nâng cấp | Cần tuỳ biến sâu. Lab của khoá dùng kiểu này |
| **Managed node group** (`managedNodeGroups`) | AWS tạo và nâng cấp ASG, bạn chọn instance type | Lựa chọn mặc định hợp lý cho đa số người mới |
| **Fargate** | Không có node: mỗi pod chạy trên một "máy ảo nhỏ" riêng | Workload không cần DaemonSet, không cần EBS |
| **EKS Auto Mode** (ra mắt cuối 2024) | AWS lo gần hết: node (dựa trên Karpenter), load balancer, EBS CSI, Pod Identity agent | Muốn ít vận hành nhất, chấp nhận trả thêm phí quản lý theo instance |

- **Fargate** có giới hạn: không mount được EBS, không chạy DaemonSet, không dùng được EKS Pod Identity. Vì vậy lab EBS (Lab3) phải chạy trên node EC2.
- **Auto Mode** tính thêm một khoản phí quản lý trên mỗi instance nó khởi tạo, cộng với giá EC2 bình thường. Node của Auto Mode dùng AMI Bottlerocket khoá chặt, không SSH được, và bị thay sau tối đa 21 ngày.
- **Phiên bản Kubernetes:** mỗi version có khoảng 14 tháng *standard support*. Hết hạn mà chưa nâng cấp thì cluster chuyển sang *extended support*, giá control plane tăng mạnh. Đó là lý do lab1 có lệnh `--upgrade-policy supportType=STANDARD`.

**Câu hỏi tự kiểm tra**

<details><summary>1. Bạn trả 0,10 USD/giờ cho control plane EKS để đổi lấy gì?</summary>

</details>

</details>

## Lab1 · Tạo EKS Cluster bằng eksctl {003}

**Khái niệm cốt lõi**

**eksctl** là CLI chính thức cho EKS. Bên dưới, nó sinh ra **CloudFormation stack**: một stack cho cluster (VPC, subnet, NAT, IAM role, control plane) và một stack cho mỗi node group. Bạn có thể vào CloudFormation console để xem từng bước đang tạo gì.

Cài công cụ trên Fedora:

```bash
# kubectl và helm có sẵn trong kho của Fedora
sudo dnf install -y kubernetes-client helm

# eksctl: tải bản phát hành chính thức từ GitHub
PLATFORM=$(uname -s)_amd64
curl -sLO "https://github.com/eksctl-io/eksctl/releases/latest/download/eksctl_$PLATFORM.tar.gz"
tar -xzf eksctl_$PLATFORM.tar.gz -C /tmp && sudo install -m 0755 /tmp/eksctl /usr/local/bin/
eksctl version && kubectl version --client && helm version --short && aws --version
```

File lab: `EKS-basic/lab1/cluster-config.yaml`

```yaml
apiVersion: eksctl.io/v1alpha5
kind: ClusterConfig
metadata:
  name: devops-test-cluster
  region: ap-southeast-1
nodeGroups:              # self-managed node group
  - name: my-nodes
    instanceType: t3.medium
    desiredCapacity: 2
    minSize: 2
    maxSize: 4
```

```bash
cd EKS-basic/lab1
eksctl create cluster -f cluster-config.yaml                   # 15–20 phút
aws eks update-cluster-config --name devops-test-cluster \
    --upgrade-policy supportType=STANDARD                       # tránh phí extended support
aws eks update-kubeconfig --region ap-southeast-1 --name devops-test-cluster
kubectl config get-contexts
kubectl get nodes -o wide
```

- `update-kubeconfig` ghi một *context* vào `~/.kube/config`. Context đó dùng lệnh `aws eks get-token` để xin token mỗi lần bạn gõ `kubectl`. Nghĩa là **kubectl dùng danh tính IAM** hiện tại của AWS CLI.
- `nodeGroups` là node group **self-managed**. Nếu muốn AWS quản lý vòng đời node, đổi thành `managedNodeGroups:` (cú pháp gần giống).
- Mặc định eksctl tạo VPC mới `192.168.0.0/16` với subnet public và private trên các AZ, cùng **một NAT Gateway**.

**Đi sâu hơn**

- `eksctl create cluster --dry-run -f cluster-config.yaml` in ra cấu hình đầy đủ sau khi điền giá trị mặc định. Rất đáng đọc một lần để biết eksctl ngầm tạo gì.
- Có thể bật Auto Mode bằng `autoModeConfig: { enabled: true }` trong ClusterConfig, khi đó không cần khai báo node group.
- Trong công việc thật, nhiều team dựng EKS bằng **Terraform** (module `terraform-aws-modules/eks/aws`), để cluster nằm cùng chỗ với VPC, RDS… trong một bộ IaC.
- t3.medium có 2 vCPU, 4 GiB RAM, và **tối đa 17 pod mỗi node**. Giới hạn này đến từ số ENI và IP mà VPC CNI gán cho pod. t3.small chỉ được 11 pod, nên chỉ riêng pod hệ thống đã chiếm gần hết.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `AlreadyExistsException: Stack [eksctl-devops-test-cluster-cluster] already exists` | Lần tạo trước lỗi giữa chừng, stack còn sót | `eksctl delete cluster ...` hoặc xoá stack trên CloudFormation, rồi tạo lại |
| `error: You must be logged in to the server (Unauthorized)` | Bạn dùng IAM user hoặc profile khác với người tạo cluster | `aws sts get-caller-identity`, đổi đúng profile, hoặc thêm access entry cho user đó (xem Lab4) |
| `Cannot create cluster ... insufficient capacity` trong một AZ | AZ hết loại instance đó | Thêm `availabilityZones: [...]` để chọn AZ khác, hoặc đổi instance type |
| Node `NotReady` rất lâu | Node không ra Internet được để tải image (NAT/route) | Xem event của CloudFormation stack, kiểm tra route table của subnet private |

**Bài tập**

🟢 *Cơ bản*: Tạo cluster bằng file lab nhưng đổi thành `managedNodeGroups`, `desiredCapacity: 1`, `minSize: 1`. Chạy `kubectl get pods -A` và liệt kê các pod hệ thống (aws-node, coredns, kube-proxy…). Cho biết mỗi pod đó làm gì.

<details><summary>Gợi ý</summary>

`aws-node` là VPC CNI, gán IP của VPC cho pod. `kube-proxy` dựng luật iptables cho Service. `coredns` phân giải tên như `mongo.default.svc.cluster.local`. Có thể còn `metrics-server` hoặc `eks-pod-identity-agent` nếu chúng được cài dưới dạng add-on.
</details>

🟡 *Thực hành*: Chạy `eksctl create cluster --dry-run -f cluster-config.yaml > full.yaml`. Tìm trong `full.yaml`: CIDR của VPC, chế độ NAT, `authenticationMode` của access config. Thử đổi NAT thành `Disable` và giải thích vì sao node trong subnet private sẽ lỗi.

<details><summary>Gợi ý</summary>

Tìm các khoá `vpc.cidr`, `vpc.nat.gateway`, `accessConfig.authenticationMode`. Không có NAT thì node ở subnet private không kéo được image từ ECR public hay Docker Hub. Muốn tắt NAT thì node phải nằm ở subnet public (`privateNetworking: false`), hoặc dùng VPC endpoint cho ECR và S3.
</details>

🔴 *Thử thách*: Viết `cluster-config.yaml` tối ưu chi phí cho việc học: 1 managed node group dùng **Spot** (`spot: true`, `instanceTypes: ["t3.medium","t3a.medium"]`), gắn tag `owner=<tên-bạn>`. Sau khi tạo, dùng **Cost Explorer** lọc theo tag để xem chi phí 1 ngày. Xoá cluster khi xong.

<details><summary>Gợi ý</summary>

Muốn lọc theo tag trong Cost Explorer, phải bật tag đó ở **Billing → Cost allocation tags**, và dữ liệu xuất hiện sau khoảng 24 giờ. Spot có thể bị thu hồi bất cứ lúc nào, nên chỉ hợp với môi trường học và dev. Khai báo nhiều instance type giúp tăng khả năng có hàng.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>kubectl</code> lấy quyền từ đâu khi nói chuyện với EKS?</summary>

Từ danh tính IAM mà AWS CLI đang dùng. `kubectl` gọi `aws eks get-token` để lấy token ký bằng credential IAM. EKS xác thực token đó, rồi tra **access entry** (hoặc ConfigMap `aws-auth` kiểu cũ) để biết IAM identity này có quyền Kubernetes nào.
</details>

<details><summary>2. Vì sao xoá cluster nên dùng <code>eksctl delete cluster</code> thay vì xoá tay từng thứ?</summary>

eksctl biết các CloudFormation stack nó đã tạo (VPC, NAT, IAM role, node group, service account) và xoá theo đúng thứ tự phụ thuộc. Xoá tay rất dễ sót NAT Gateway hoặc ENI, khiến VPC không xoá được và tiền vẫn bị tính.
</details>

## Load Balancer và Lab2 · ALB cho EKS {004-006}

**Khái niệm cốt lõi**

Có ba cách đưa traffic từ Internet vào pod:

| Cách | Bạn khai báo | AWS tạo ra |
|---|---|---|
| `Service type: LoadBalancer` | Service | **NLB** (layer 4, TCP/UDP), mỗi Service một NLB |
| `Ingress` với `ingressClassName: alb` | Ingress + các Service | **ALB** (layer 7, HTTP), định tuyến theo path và host, nhiều Service dùng chung một ALB |
| Gateway API (`Gateway`, `HTTPRoute`) | Gateway + Route | ALB hoặc NLB. Đây là chuẩn mới thay dần cho Ingress |

Kubernetes không tự biết cách tạo ALB. Cần một **controller** là **AWS Load Balancer Controller (LBC)**: một pod trong `kube-system` theo dõi các object Ingress và Service, rồi gọi API của ELB để tạo ALB/NLB, listener, rule và target group tương ứng.

```
Internet → ALB (do LBC tạo)  ── /api ──► Target group (IP của pod backend:3000)
                             └─ /    ──► Target group (IP của pod frontend:3000)
             ▲
             │ gọi ELB API bằng IAM role (IRSA)
   aws-load-balancer-controller (pod trong kube-system)
             │ watch
          Ingress "demo-ingress"
```

**Vì sao cần IAM role cho pod?** Controller phải gọi API của AWS (`elasticloadbalancing:CreateLoadBalancer`…). Không được nhét access key vào pod. Thay vào đó, ta gắn **IAM role vào ServiceAccount** của pod. Có hai cơ chế:

| | **IRSA** (IAM Roles for Service Accounts) | **EKS Pod Identity** (2023) |
|---|---|---|
| Cách hoạt động | Cluster có OIDC provider. Pod nhận token, đổi lấy credential qua `sts:AssumeRoleWithWebIdentity` | Agent DaemonSet trên mỗi node cấp credential. Bạn tạo *association* (role ↔ namespace/serviceaccount) bằng EKS API |
| Trust policy của role | Gắn với OIDC URL **của từng cluster** | Một principal chung `pods.eks.amazonaws.com`, dùng lại cho nhiều cluster |
| Hạn chế | Phải tạo OIDC provider cho mỗi cluster | Không hỗ trợ Fargate, không hỗ trợ node Windows |
| Lab dùng | ✔ (`eksctl create iamserviceaccount`) | Nên thử ở bài tập |

**Code / lệnh mẫu** (khớp `EKS-basic/lab2/lab2-part1.sh`, `draff.txt`)

```bash
# 1. Bật OIDC provider cho cluster (cần cho IRSA)
eksctl utils associate-iam-oidc-provider --cluster devops-test-cluster --approve

# 2. Tạo IAM policy cho controller (file lab: EKS-basic/lab2/iam_policy.json)
#    Bản mới nhất: tải đúng tag release của controller, ví dụ v2.14.1
curl -O https://raw.githubusercontent.com/kubernetes-sigs/aws-load-balancer-controller/v2.14.1/docs/install/iam_policy.json
aws iam create-policy --policy-name AWSLoadBalancerControllerIAMPolicy \
    --policy-document file://iam_policy.json

# 3. Tạo IAM role + ServiceAccount có annotation role ARN
eksctl create iamserviceaccount \
  --cluster=devops-test-cluster --namespace=kube-system \
  --name=aws-load-balancer-controller \
  --attach-policy-arn=arn:aws:iam::<ACCOUNT_ID>:policy/AWSLoadBalancerControllerIAMPolicy \
  --override-existing-serviceaccounts --region ap-southeast-1 --approve

# 4. Cài controller bằng Helm
helm repo add eks https://aws.github.io/eks-charts && helm repo update eks
helm install aws-load-balancer-controller eks/aws-load-balancer-controller \
  -n kube-system --set clusterName=devops-test-cluster \
  --set serviceAccount.create=false --set serviceAccount.name=aws-load-balancer-controller
kubectl get deployment -n kube-system aws-load-balancer-controller    # READY 2/2
```

> ⚠️ Trong `draff.txt`, ARN policy chứa **account ID của giảng viên** (`430950558682`). Bạn phải thay bằng account ID của bạn (`aws sts get-caller-identity --query Account --output text`).

Ingress ở Lab2 part 2 (`EKS-basic/lab2/demo-app.yaml`):

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: demo-ingress
  annotations:
    alb.ingress.kubernetes.io/scheme: internet-facing   # ALB public (mặc định: internal)
    alb.ingress.kubernetes.io/target-type: ip           # gửi thẳng tới IP của pod
spec:
  ingressClassName: alb
  rules:
  - http:
      paths:
      - { path: /api, pathType: Prefix, backend: { service: { name: backend,  port: { number: 3000 } } } }
      - { path: /,    pathType: Prefix, backend: { service: { name: frontend, port: { number: 3000 } } } }
```

```bash
kubectl apply -f demo-app.yaml
kubectl get ingress demo-ingress          # cột ADDRESS = DNS của ALB, sau 2–3 phút
curl -I http://<DNS-của-ALB>/
```

**Đi sâu hơn: các annotation hay dùng**

| Annotation | Tác dụng |
|---|---|
| `target-type: ip` / `instance` | `ip`: đăng ký IP pod vào target group (cần VPC CNI, bắt buộc với Fargate). `instance`: đăng ký node qua NodePort |
| `healthcheck-path: /api/health` | Đường dẫn health check cho target group |
| `listen-ports: '[{"HTTP":80},{"HTTPS":443}]'` + `certificate-arn: arn:aws:acm:...` | Bật HTTPS bằng chứng chỉ ACM |
| `ssl-redirect: '443'` | Chuyển HTTP sang HTTPS |
| `group.name: shared-alb` | Nhiều Ingress dùng chung **một** ALB, giúp tiết kiệm tiền |

- LBC tìm subnet theo **tag**: subnet public cần `kubernetes.io/role/elb=1`, subnet private cần `kubernetes.io/role/internal-elb=1`. eksctl tự gắn các tag này. Nếu tự dựng VPC bằng Terraform thì bạn phải tự gắn.
- Helm chart **không tự nâng cấp**. Khi `helm upgrade`, CRD không được cập nhật, phải `kubectl apply` file CRD bằng tay.
- File `note.sh` của lab nhắc bỏ một khối `Condition` trong policy. Đây là cách giảng viên lách lỗi phân quyền với tag. Hãy ưu tiên dùng **policy đúng version của controller**, đừng tự nới quyền.

**Lỗi hay gặp & cách sửa**

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| `kubectl get ingress` mãi không có ADDRESS | Controller chưa chạy hoặc thiếu quyền | `kubectl logs -n kube-system deploy/aws-load-balancer-controller`. Thường thấy `AccessDenied` hoặc `WebIdentityErr` |
| Log: `couldn't auto-discover subnets: unable to resolve at least one subnet` | Subnet thiếu tag `kubernetes.io/role/elb` | Gắn tag cho subnet public |
| ALB trả **502/503** | Target unhealthy: sai port, health check `/` trả 404, hoặc SG chặn | Xem Target group trong EC2 console, thêm annotation `healthcheck-path` |
| `failed calling webhook "mservice.elbv2.k8s.aws"` khi apply Service | Webhook của controller chưa sẵn sàng | Chờ pod controller `Running` rồi apply lại |

💰 Mỗi Ingress (không dùng `group.name`) là **một ALB riêng**, khoảng 0,6 USD/ngày cộng IP public. Luôn `kubectl delete ingress ...` **trước** khi xoá cluster, nếu không ALB có thể bị bỏ lại và chặn việc xoá VPC.

<details><summary>Gợi ý</summary>

Các Ingress cùng `group.name` được LBC gộp vào một ALB, mỗi rule thành một listener rule. Dùng `alb.ingress.kubernetes.io/group.order` nếu cần thứ tự ưu tiên. Không có domain riêng thì phân biệt bằng path, ví dụ `/game`. Lưu ý app 2048 phục vụ ở `/`, nên đổi path có thể làm vỡ đường dẫn file tĩnh.
</details>

🔴 *Thử thách*: Cài lại LBC bằng **EKS Pod Identity** thay cho IRSA: cài add-on `eks-pod-identity-agent`, tạo role có trust `pods.eks.amazonaws.com`, rồi `eksctl create podidentityassociation`. Chứng minh controller vẫn tạo được ALB.

</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Khác nhau giữa <code>target-type: ip</code> và <code>instance</code>?</summary>

`instance`: ALB gửi tới NodePort trên node, rồi kube-proxy chuyển tiếp tới pod (có thể sang node khác, thêm một bước nhảy). `ip`: ALB gửi thẳng tới IP của pod, ít bước nhảy hơn, và là cách duy nhất dùng được với Fargate. Với `ip`, Service có thể là ClusterIP.
</details>

<details><summary>2. Vì sao không cấp quyền ELB cho controller bằng IAM role của node?</summary>

Mọi pod trên node đó đều có thể đọc credential của node role qua IMDS, nên app bất kỳ cũng tạo hoặc xoá được load balancer. IRSA hay Pod Identity chỉ cấp quyền cho đúng ServiceAccount của controller (least privilege).
</details>

## Storage và Lab3 · EBS Volume cho Mongo {007-008}

**Khái niệm cốt lõi**

Container mất dữ liệu khi bị xoá. Muốn MongoDB giữ dữ liệu, cần **persistent volume**. Có ba object liên quan:

- **StorageClass**: "loại ổ đĩa và ai tạo nó" (provisioner `ebs.csi.aws.com`, loại gp3, có mã hoá hay không).
- **PersistentVolumeClaim (PVC)**: pod "đặt hàng": "tôi cần 4Gi, ReadWriteOnce, loại `ebs-sc`".
- **PersistentVolume (PV)**: ổ đĩa thật, ở đây là một **EBS volume**, được tạo *động* khi có PVC.

```
Pod mongo ──uses──► PVC mongo-pvc (4Gi) ──bound──► PV pvc-xxxx ──► EBS vol-0abc (AZ a)
                          │
                   StorageClass ebs-sc ──► EBS CSI driver (controller gọi EC2 API: CreateVolume, AttachVolume)
```

**CSI (Container Storage Interface)** là chuẩn plugin lưu trữ. Từ Kubernetes 1.23, driver EBS "in-tree" cũ (`kubernetes.io/aws-ebs`) đã được chuyển sang driver CSI, nên **bắt buộc cài `aws-ebs-csi-driver`** thì PVC mới được cấp volume.

**Code / lệnh mẫu** (khớp `EKS-basic/lab3-ebs-volume/lab3.sh`)

```bash
# IAM role cho controller của driver (IRSA, chỉ tạo role: --role-only)
eksctl create iamserviceaccount --name ebs-csi-controller-sa --namespace kube-system \
  --cluster devops-test-cluster --role-name AmazonEKS_EBS_CSI_DriverRole --role-only \
  --attach-policy-arn arn:aws:iam::aws:policy/service-role/AmazonEBSCSIDriverPolicy \
  --approve
# Cài driver dưới dạng EKS add-on, gắn role ở trên
eksctl create addon --name aws-ebs-csi-driver --cluster devops-test-cluster \
  --service-account-role-arn arn:aws:iam::<ACCOUNT_ID>:role/AmazonEKS_EBS_CSI_DriverRole --force
```

```yaml
# EKS-basic/lab3-ebs-volume/demo-app.yaml (rút gọn), đã thêm tham số gp3 nên dùng
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: ebs-sc
provisioner: ebs.csi.aws.com
volumeBindingMode: WaitForFirstConsumer   # chờ pod được xếp lịch rồi mới tạo volume ĐÚNG AZ của node
parameters:            # (lab không ghi; driver mặc định dùng gp3)
  type: gp3
  encrypted: "true"
reclaimPolicy: Delete  # xoá PVC thì xoá luôn EBS (mặc định). Retain = giữ lại volume
allowVolumeExpansion: true
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: mongo-pvc }
spec:
  accessModes: ["ReadWriteOnce"]   # EBS chỉ gắn được vào 1 node một lúc
  storageClassName: ebs-sc
  resources: { requests: { storage: 4Gi } }
```

```bash
kubectl apply -f demo-app.yaml
kubectl get sc,pvc,pv
kubectl delete pod -l app=mongo        # pod mới được tạo lại, dữ liệu vẫn còn
```

**Đi sâu hơn**

- **EBS gắn với một AZ.** Nếu pod Mongo bị dời sang node ở AZ khác, nó sẽ `Pending` vì không gắn được volume. `WaitForFirstConsumer` chỉ giải quyết lúc *tạo* volume, không giải quyết lúc *dời* pod. Đây là lý do database trong production thường dùng **RDS / DocumentDB**, hoặc chạy StatefulSet với replica trên nhiều AZ.
- **Deployment hay StatefulSet cho database?** Lab dùng Deployment + 1 PVC. Với nhiều replica, mỗi replica cần ổ riêng, nên dùng **StatefulSet + `volumeClaimTemplates`** (bài assignment `lab5-assignment-vote-app` yêu cầu như vậy). Khi rolling update một Deployment có PVC RWO, pod mới có thể kẹt `Multi-Attach error`, nên đặt `strategy: Recreate`.
- **Quyền IAM:** tài liệu EKS hiện khuyên dùng **EKS Pod Identity** cho EBS CSI, và có thêm managed policy **`AmazonEBSCSIDriverPolicyV2`** thu hẹp quyền hơn bản cũ mà lab đang dùng.
- **EKS Auto Mode** có sẵn EBS, nhưng dùng provisioner khác là `ebs.csi.eks.amazonaws.com`. StorageClass `ebs.csi.aws.com` của lab không dùng được với Auto Mode.
- **EFS** (`efs.csi.aws.com`) cho phép `ReadWriteMany` (nhiều pod, nhiều AZ cùng đọc ghi), nhưng chậm hơn và đắt hơn tính theo GB.

**Lỗi hay gặp & cách sửa**

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| PVC `Pending`, event: `waiting for a volume to be created ... ebs.csi.aws.com` mãi | Chưa cài driver, hoặc pod chưa được xếp lịch (do `WaitForFirstConsumer`, điều này bình thường) | `kubectl get pods -n kube-system \| grep ebs`, rồi `kubectl describe pvc mongo-pvc` |
| `could not create volume in EC2: UnauthorizedOperation` | Role của driver thiếu quyền hoặc gắn sai ServiceAccount | Kiểm tra role ARN trong add-on, trust policy (OIDC id, `sub` = `system:serviceaccount:kube-system:ebs-csi-controller-sa`) |
| Pod `ContainerCreating`: `Multi-Attach error for volume` | Pod cũ ở node khác chưa nhả volume | Dùng `strategy: Recreate`, chờ pod cũ terminate |
| Pod `Pending`: `volume node affinity conflict` | Volume ở AZ a, node còn trống chỉ ở AZ b | Thêm node ở AZ a, hoặc dùng StatefulSet đa AZ |

💰 EBS gp3 khoảng 0,08–0,10 USD/GB-tháng (ước lượng, tuỳ region). 4 GiB thì rẻ, nhưng **volume mồ côi tính tiền mãi mãi**. Thứ tự dọn dẹp: `kubectl delete -f demo-app.yaml` (xoá PVC, kéo theo xoá EBS khi `reclaimPolicy: Delete`) → xoá cluster → vào EC2 → Volumes lọc trạng thái **available** để xoá phần còn sót.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab3. Thêm vài todo, xoá pod Mongo, kiểm tra dữ liệu còn. Sau đó thử **xoá PVC** và quan sát EBS volume trên console biến mất.

🟡 *Thực hành*: Tạo StorageClass `ebs-gp3-retain` với `reclaimPolicy: Retain`, `allowVolumeExpansion: true`. Tăng PVC từ 4Gi lên 6Gi bằng `kubectl edit pvc`, kiểm tra trong pod bằng `df -h /data/db`. Xoá PVC rồi giải thích vì sao volume vẫn còn, và tự xoá nó.

<details><summary>Gợi ý</summary>

Với `Retain`, PV chuyển sang trạng thái `Released`, EBS vẫn tồn tại (và vẫn tính tiền). Phải xoá PV bằng `kubectl delete pv <tên>`, sau đó xoá EBS trên console hoặc bằng `aws ec2 delete-volume`. Mở rộng volume chạy online với driver CSI, filesystem được giãn tự động.
</details>

🔴 *Thử thách*: Chuyển Mongo sang **StatefulSet** với `volumeClaimTemplates` và Service headless (`clusterIP: None`). Rồi cài **CSI snapshot controller**, tạo `VolumeSnapshot` cho PVC, xoá dữ liệu, và khôi phục từ snapshot sang PVC mới.

<details><summary>Gợi ý</summary>

Cần CRD và controller snapshot (cài được bằng EKS add-on `snapshot-controller`), một `VolumeSnapshotClass` với `driver: ebs.csi.aws.com`, rồi PVC mới có `dataSource: { kind: VolumeSnapshot, name: ..., apiGroup: snapshot.storage.k8s.io }`. Dọn dẹp: xoá VolumeSnapshot (để xoá luôn EBS snapshot), các PVC, rồi kiểm tra mục Snapshots trong EC2 console.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao StorageClass dùng <code>WaitForFirstConsumer</code> thay vì <code>Immediate</code>?</summary>

Với `Immediate`, volume được tạo ngay khi có PVC, có thể ở AZ a. Sau đó pod lại được xếp lên node ở AZ b và không gắn được volume. `WaitForFirstConsumer` chờ scheduler chọn node trước, rồi mới tạo EBS ở đúng AZ của node đó.
</details>

<details><summary>2. Có chạy được 3 replica Mongo dùng chung một PVC EBS không?</summary>

Không. EBS là `ReadWriteOnce`, chỉ gắn vào một node. Hơn nữa, ba tiến trình mongod ghi chung một thư mục dữ liệu sẽ làm hỏng dữ liệu. Muốn 3 replica thì dùng StatefulSet (mỗi pod một PVC) và cấu hình replica set của MongoDB, hoặc dùng dịch vụ managed.
</details>

## Autoscaling trong EKS {009}

**Khái niệm cốt lõi**

Có hai tầng co giãn, và bạn cần **cả hai**:

```
Tải tăng ─► HPA tăng số pod (2 → 6)
             └─► pod mới Pending vì node hết CPU/RAM
                   └─► Cluster Autoscaler / Karpenter thêm node
                         └─► pod được xếp lịch, chạy
Tải giảm ─► HPA giảm pod ─► node vắng ─► autoscaler gom pod và xoá node thừa
```

- **HPA (Horizontal Pod Autoscaler):** thay đổi `replicas` của Deployment dựa trên metric. Công thức: `desired = ceil(hiện_tại × giá_trị_đo / mục_tiêu)`. Ví dụ 2 pod, CPU trung bình 90%, mục tiêu 60% thì cần `ceil(2 × 90/60) = 3` pod.
- **metrics-server:** gom CPU và RAM từ kubelet để HPA và lệnh `kubectl top` đọc được. Không có nó thì HPA hiện `<unknown>`.
- **VPA (Vertical Pod Autoscaler):** chỉnh `requests/limits` của pod. Không nên dùng chung với HPA trên cùng metric CPU.
- **Co giãn node:** thêm hoặc bớt EC2 khi có pod `Pending` vì thiếu tài nguyên.

**Đi sâu hơn: Cluster Autoscaler vs Karpenter**

| | **Cluster Autoscaler (CA)** | **Karpenter** |
|---|---|---|
| Cơ chế | Tăng/giảm `desired` của **Auto Scaling Group** có sẵn | Tự gọi EC2 API, chọn loại instance phù hợp với pod đang chờ |
| Loại instance | Cố định theo node group | Linh hoạt (khai báo trong `NodePool`), trộn được Spot và On-Demand |
| Tốc độ | Chậm hơn (đi qua ASG) | Nhanh hơn, có **consolidation** (gom pod để tắt node thừa) |
| Dùng ở đâu | Mọi Kubernetes trên AWS, quen thuộc | Khuyên dùng cho EKS hiện nay. EKS Auto Mode chạy Karpenter bên trong |

**Code mẫu: HPA cho backend**

```bash
kubectl get deployment metrics-server -n kube-system || \
  kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml
kubectl top nodes && kubectl top pods
```

```yaml
# HPA chỉ tính được % CPU khi container có requests.cpu.
# Deployment trong demo-app.yaml của lab CHỈ có requests.memory, nên phải thêm:
#   resources: { requests: { cpu: "100m", memory: "256Mi" }, limits: { memory: "512Mi" } }
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: backend-hpa }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: backend-deployment }
  minReplicas: 2
  maxReplicas: 6
  metrics:
  - type: Resource
    resource: { name: cpu, target: { type: Utilization, averageUtilization: 60 } }
```

```bash
kubectl apply -f backend-hpa.yaml
# Tạo tải giả từ trong cluster
kubectl run load --rm -it --image=busybox:1.36 -- /bin/sh -c \
  "while true; do wget -q -O- http://backend:3000/api >/dev/null; done"
kubectl get hpa backend-hpa -w        # xem TARGETS và REPLICAS thay đổi
```

**Lỗi hay gặp & cách sửa**

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| `TARGETS <unknown>/60%`, event: `missing request for cpu` | Container không khai báo `requests.cpu` | Thêm `resources.requests.cpu` |
| `unable to get metrics for resource cpu` | Chưa có metrics-server | Cài metrics-server, chờ khoảng 1 phút |
| Pod mới `Pending`: `0/2 nodes are available: Insufficient cpu` | Node đầy và không có autoscaler cho node | Cài CA/Karpenter, hoặc `eksctl scale nodegroup --nodes 3` |
| Node không bao giờ giảm | Có pod dùng `emptyDir`/local storage, PDB quá chặt, hoặc pod không thuộc controller nào | Đọc log của CA hoặc Karpenter, nới PDB |

💰 `maxSize: 4` trong cluster-config là "cầu chì" chi phí. Đừng đặt `maxReplicas` hay `NodePool limits` quá lớn trong tài khoản học: một vòng lặp tạo tải bị quên có thể bật thêm node chạy cả đêm.

**Bài tập**

🟢 *Cơ bản*: Thêm `requests.cpu` cho backend, tạo HPA như trên, chạy pod tạo tải và quan sát `kubectl get hpa -w` từ 2 lên nhiều pod. Dừng tải, chờ khoảng 5 phút xem số pod giảm (HPA có *stabilization window* mặc định 300 giây khi giảm).

🟡 *Thực hành*: Cài **Cluster Autoscaler** cho node group (cần IRSA hoặc Pod Identity và tag ASG `k8s.io/cluster-autoscaler/enabled`). Đặt `maxReplicas: 20` để buộc thiếu node, quan sát node thứ 3 xuất hiện. Hạ tải và xem node bị gỡ.

<details><summary>Gợi ý</summary>

Dùng Helm chart `autoscaler/cluster-autoscaler` với `autoDiscovery.clusterName=devops-test-cluster`, `awsRegion=ap-southeast-1`. eksctl gắn sẵn tag auto-discovery khi node group có `iam.withAddonPolicies.autoScaler: true`. Đọc log bằng `kubectl logs -n kube-system deploy/cluster-autoscaler`. Thời gian chờ để gỡ node mặc định khoảng 10 phút.
</details>

🔴 *Thử thách*: Đọc tài liệu Karpenter, viết (chưa cần apply) một `NodePool` chỉ cho phép instance family `t3`/`t3a`, Spot ưu tiên, `limits.cpu: 8`, `consolidationPolicy: WhenEmptyOrUnderutilized`. Giải thích từng trường bảo vệ chi phí như thế nào.

**Câu hỏi tự kiểm tra**

<details><summary>1. HPA tăng pod nhưng pod mới Pending. Ai chịu trách nhiệm giải quyết?</summary>

HPA chỉ đổi số replica, không tạo node. Phải có Cluster Autoscaler, Karpenter hoặc EKS Auto Mode thấy pod `Pending` vì thiếu tài nguyên và thêm node. Nếu không có những thứ đó, bạn phải tự scale node group.
</details>

<details><summary>2. Vì sao <code>requests</code> quan trọng với cả HPA lẫn scheduler?</summary>

Scheduler dựa vào `requests` để quyết định node nào còn chỗ. HPA tính % sử dụng là `usage / requests`. Không có requests thì HPA không có mẫu số để tính, còn scheduler có thể nhồi quá nhiều pod lên một node.
</details>

## Security trong EKS, Lab4 RBAC và dọn dẹp {010-012}

**Khái niệm cốt lõi: hai cánh cửa**

Truy cập EKS luôn đi qua hai bước:

```
kubectl (IAM user developer01)
   │ 1. AUTHENTICATION: "bạn là ai?"   → EKS kiểm tra token IAM
   │                                     → tra Access Entry: IAM ARN ↔ username / group Kubernetes
   ▼
   │ 2. AUTHORIZATION: "bạn được làm gì?" → Access Policy của EKS (AmazonEKSViewPolicy…)
   │                                        và/hoặc Kubernetes RBAC (Role/ClusterRole + Binding)
   ▼
 API server cho phép / từ chối (Forbidden)
```

- **Quyền IAM ≠ quyền Kubernetes.** developer01 có `PowerUserAccess` vẫn **không xem được pod**, vì quyền IAM chỉ cho gọi EKS API (DescribeCluster…), chưa cho đọc tài nguyên *bên trong* cluster. Đây đúng là điều Lab4 cho bạn thấy.
- **Access entries** (từ cuối 2023) là cách hiện hành để ánh xạ IAM sang Kubernetes, quản lý bằng EKS API, console hoặc Terraform. Cách cũ là sửa ConfigMap **`aws-auth`** trong `kube-system`: gõ sai một dòng YAML là có thể khoá luôn chính bạn ra ngoài cluster. AWS khuyên chuyển sang access entries.
- `authenticationMode` của cluster: `CONFIG_MAP` (chỉ aws-auth), `API_AND_CONFIG_MAP` (cả hai, trạng thái chuyển tiếp), `API` (chỉ access entries). Chuyển sang `API` rồi thì không quay lại được.

**Access policy có sẵn** (gắn với scope là cả cluster hoặc một vài namespace):

| Policy | Tương đương ClusterRole | Quyền |
|---|---|---|
| `AmazonEKSClusterAdminPolicy` | `cluster-admin` | Toàn quyền |
| `AmazonEKSAdminPolicy` | `admin` | Gần toàn quyền trong namespace, kể cả RBAC |
| `AmazonEKSEditPolicy` | `edit` | Sửa phần lớn tài nguyên, không sửa RBAC |
| `AmazonEKSViewPolicy` | `view` | Chỉ đọc, **không đọc Secret** |

**Kubernetes RBAC** dùng khi cần quyền chi tiết hơn các policy có sẵn:

- **Role** (trong một namespace) / **ClusterRole** (toàn cluster): danh sách `apiGroups + resources + verbs`.
- **RoleBinding** / **ClusterRoleBinding**: gán Role cho user, group hoặc ServiceAccount.

**Code / lệnh mẫu** (Lab4 làm trên console, dưới đây là CLI tương đương, file `EKS-basic/lab4-rbac/lab4.sh`)

```bash
# Cách 1: access entry + access policy (giống lab)
aws eks create-access-entry --cluster-name devops-test-cluster \
  --principal-arn arn:aws:iam::<ACCOUNT_ID>:user/developer01 --type STANDARD
aws eks associate-access-policy --cluster-name devops-test-cluster \
  --principal-arn arn:aws:iam::<ACCOUNT_ID>:user/developer01 \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSViewPolicy \
  --access-scope type=cluster

# Dùng profile của developer01, KHÔNG cần xoá ~/.kube/config: đặt alias cho context
aws eks update-kubeconfig --name devops-test-cluster --region ap-southeast-1 \
  --profile developer01 --alias dev01
kubectl --context dev01 get pods -A              # được
kubectl --context dev01 get secrets -A           # Forbidden (ViewPolicy không đọc Secret)
kubectl --context dev01 auth can-i --list      # liệt kê quyền hiện có
```

**Đi sâu hơn: checklist bảo mật EKS**

- **Endpoint API:** mặc định public. Có thể giới hạn `publicAccessCidrs` về IP của bạn, hoặc bật endpoint private.
- **Danh tính cho pod:** IRSA hoặc Pod Identity, không dùng node role cho app. Chặn pod gọi IMDS bằng cách đặt hop limit = 1 trên node.
- **Secret:** bật mã hoá envelope bằng KMS (cluster mới mặc định đã mã hoá ở tầng etcd). Tốt hơn nữa là lưu trong Secrets Manager và đọc qua Secrets Store CSI driver.
- **Mạng:** NetworkPolicy (VPC CNI hỗ trợ) để giới hạn pod nào nói chuyện được với Mongo. Security Group cho pod khi cần.
- **Pod Security Admission:** gắn label `pod-security.kubernetes.io/enforce: restricted` cho namespace, cấm container chạy root hay privileged.
- **Image:** bật scan trên ECR, ghim tag hoặc digest thay vì `:latest`.
- **Audit:** bật control plane logging (`audit`, `authenticator`) ra CloudWatch Logs. Có tính phí theo GB log.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `error: You must be logged in to the server (Unauthorized)` | IAM identity chưa có access entry | Tạo access entry, kiểm tra ARN đúng user/role (role assume thì phải dùng ARN của **role**) |
| `pods is forbidden: User "arn:aws:iam::...:user/developer01" cannot list resource "pods" ... in the namespace "default"` | Đã xác thực nhưng chưa có quyền | Gắn access policy hoặc RoleBinding |
| `AccessDeniedException ... eks:DescribeCluster` khi `update-kubeconfig` | User thiếu quyền IAM | Cấp quyền IAM `eks:DescribeCluster` (PowerUserAccess đã có) |
| Sau Lab4, admin cũng bị `Unauthorized` | `~/.kube/config` còn context của developer01 | `aws eks update-kubeconfig` lại bằng profile admin, `kubectl config use-context` |

**Bài tập**

🟢 *Cơ bản*: Làm lại Lab4 bằng CLI (`create-access-entry`, `associate-access-policy`) thay vì console. Dùng `--alias` để giữ cả hai context. Kiểm tra `kubectl --context dev01 get secrets` bị từ chối.

🟡 *Thực hành*: Cho developer01 quyền **edit chỉ trong namespace `dev`**: access policy `AmazonEKSEditPolicy` với `--access-scope type=namespace,namespaces=dev`. Chứng minh developer01 tạo được Deployment trong `dev` nhưng bị Forbidden ở `default`.

<details><summary>Gợi ý</summary>

```bash
kubectl create namespace dev
aws eks associate-access-policy --cluster-name devops-test-cluster \
  --principal-arn arn:aws:iam::<ACCOUNT_ID>:user/developer01 \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSEditPolicy \
  --access-scope type=namespace,namespaces=dev
kubectl --context dev01 -n dev create deployment web --image=nginx
kubectl --context dev01 -n default create deployment web --image=nginx   # Forbidden
```
Nếu developer01 vẫn còn `AmazonEKSViewPolicy` ở scope cluster thì vẫn *đọc* được mọi namespace. Quyền từ các policy được cộng dồn.
</details>

🔴 *Thử thách*: Thay vì IAM user có access key dài hạn, tạo **IAM role `eks-developer`** cho phép admin assume. Gán access entry cho role (với `kubernetes-groups: dev-team`) và RBAC tự viết như ví dụ `pod-reader`. Đăng nhập bằng `aws sts assume-role` hoặc profile có `role_arn`. Viết ra 3 lý do role tốt hơn user.

<details><summary>Gợi ý</summary>

Trong `~/.aws/config`: `[profile eks-dev]` có `role_arn = arn:aws:iam::<ID>:role/eks-developer` và `source_profile = default`. Access entry phải dùng **ARN của role** (không phải ARN dạng `assumed-role/...`). Lý do: credential tạm thời tự hết hạn; không có key dài hạn để lộ; một role dùng chung cho nhiều người và có thể bắt MFA khi assume. Dọn dẹp: xoá access entry, role, và cluster.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. developer01 có PowerUserAccess nhưng vẫn không xem được pod trên console. Vì sao?</summary>

PowerUserAccess là quyền IAM, cho phép gọi API của AWS. Xem pod là gọi **Kubernetes API** bên trong cluster, và quyền này do access entry/RBAC của cluster quyết định. Chưa có access entry thì EKS không ánh xạ developer01 sang danh tính Kubernetes nào.
</details>

<details><summary>2. Access entries tốt hơn ConfigMap <code>aws-auth</code> ở điểm nào?</summary>

Được quản lý qua EKS API, nên có CloudTrail audit, làm được bằng IaC, và không lo gõ sai YAML làm hỏng việc xác thực. Ngay cả khi mất quyền vào Kubernetes API, bạn vẫn khôi phục được truy cập bằng EKS API. Còn sửa `aws-auth` sai có thể khoá mọi người khỏi cluster.
</details>

<details><summary>3. Vì sao phải xoá Ingress và PVC TRƯỚC khi xoá cluster?</summary>

ALB và EBS do controller trong cluster tạo ra, không nằm trong CloudFormation stack của eksctl. Xoá cluster trước thì không còn controller nào dọn chúng. ALB sót lại giữ ENI trong subnet làm việc xoá VPC thất bại, còn EBS sót lại thì tính tiền âm thầm.
</details>
