# Chương 13 · CICD sử dụng Github Action

Học xong chương này, bạn **viết được workflow GitHub Actions** để build Docker image và push lên ECR, deploy lên ECS, chuyển traffic blue/green trên ALB, dọn bản cũ, và gộp tất cả thành một pipeline có bước duyệt tay. Bạn cũng biết cách cho GitHub đăng nhập AWS **không cần access key dài hạn** (OIDC).

Khung sườn một workflow (file `.github/workflows/<tên>.yml` trong repo):

```yaml
name: Ten workflow
on: [push]                      # KHI NÀO chạy (trigger)
jobs:
  build:                        # một JOB = một máy runner riêng
    runs-on: ubuntu-latest
    steps:                      # các STEP chạy tuần tự trên cùng máy
      - uses: actions/checkout@v5          # step dùng action có sẵn
      - run: echo "Hello $GITHUB_REPOSITORY"   # step chạy lệnh shell
```

## Giới thiệu GitHub Actions {001}

**Khái niệm cốt lõi**

**GitHub Actions** là hệ thống CI/CD có sẵn trong GitHub. Không cần dựng server như Jenkins: bạn chỉ cần đặt file YAML vào `.github/workflows/`, và GitHub sẽ tìm máy để chạy.

| Khái niệm | Nghĩa | Ví dụ trong lab |
|---|---|---|
| **Workflow** | Một file YAML, một quy trình tự động | `build-docker.yml`, `deploy-ecs.yml` |
| **Event / trigger** | Sự kiện kích hoạt workflow | `push`, `pull_request`, `workflow_dispatch` |
| **Job** | Nhóm step chạy trên **một runner**. Các job mặc định chạy **song song** | `build-and-push`, `deploy` |
| **Step** | Một lệnh (`run`) hoặc một action (`uses`) | `docker build ...` |
| **Action** | "Hàm" đóng gói sẵn, dùng lại được | `actions/checkout`, `aws-actions/amazon-ecr-login` |
| **Runner** | Máy chạy job | `ubuntu-latest` (máy ảo GitHub cấp, xoá sau job) hoặc self-hosted |

```
push lên master
   │
   ▼
Workflow "Build and Push"
   ├─ job build-and-push (runner ubuntu #1)
   │     step: checkout → login AWS → login ECR → docker build → docker push
   └─ job deploy (runner ubuntu #2)   ← needs: build-and-push (chờ job trên xong)
```

Các job **không chia sẻ ổ đĩa**. Muốn truyền dữ liệu giữa job thì dùng `outputs` (chuỗi ngắn) hoặc `actions/upload-artifact` / `download-artifact` (file).

**Đi sâu hơn: trigger hay dùng**

```yaml
on:
  push:
    branches: [master]            # chỉ nhánh master
    tags: ['v*']                  # hoặc khi push tag v1.0.0...
    paths: ['src/**', 'Dockerfile']   # chỉ khi các file này đổi
  pull_request:
    branches: [master]            # PR nhắm vào master
  workflow_dispatch:              # nút "Run workflow" bằng tay, có form nhập
    inputs:
      version: { description: 'Tag', required: true, type: string }
  workflow_call:                  # cho phép workflow khác gọi (reusable workflow)
  schedule:
    - cron: '0 1 * * *'           # 01:00 UTC mỗi ngày (08:00 giờ Việt Nam)
```

**Đi sâu hơn: secrets, variables và environments**

| | Dùng cho | Đọc bằng | Hiện trong log? |
|---|---|---|---|
| **Secrets** | Mật khẩu, token, key | `${{ secrets.TEN }}` | Bị che `***` |
| **Variables** | Cấu hình không bí mật (region, tên repo ECR) | `${{ vars.TEN }}` | Hiện bình thường |
| **Environments** | Nhóm secrets/vars theo môi trường + **luật bảo vệ** | `environment: production` trên job | — |

- Secrets/variables đặt ở 3 cấp: **organization → repository → environment**. Cấp hẹp hơn ghi đè cấp rộng hơn.
- **Environment protection rules:**
  - *Required reviewers:* tối đa 6 người/team, chỉ cần 1 người duyệt.
  - *Wait timer:* tối đa 30 ngày.
  - *Deployment branches:* chỉ nhánh nào được deploy vào môi trường.
  - Job có `environment:` sẽ **dừng chờ duyệt**, và chỉ đọc được secret của environment sau khi được duyệt.
  - ⚠️ Với gói **GitHub Free**, required reviewers chỉ dùng được ở **repo public**. Repo private cần gói trả phí (Pro/Team/Enterprise).
- Biến có sẵn: `github.sha`, `github.ref_name`, `github.actor`, `github.event_name`, `runner.os`…

**Đi sâu hơn: an toàn chuỗi cung ứng**

- **Ghim action theo version, tốt nhất theo commit SHA.** `uses: actions/checkout@v5` tiện nhưng tag có thể bị dời sang code khác (đã có sự cố thật với action bị chiếm quyền vào năm 2025). Cách an toàn nhất là ghim theo commit SHA đầy đủ, kèm comment phiên bản:

  ```yaml
  - uses: aws-actions/configure-aws-credentials@<40-ký-tự-SHA>   # v6.x
  ```
  Bật **Dependabot** (`.github/dependabot.yml`, `package-ecosystem: github-actions`) để nó tự mở PR nâng version.
- **Node 20 đã bị gỡ khỏi runner (9/2026).** Runner giờ chạy action JavaScript bằng Node 24. Lab đang dùng `actions/checkout@v4` và `configure-aws-credentials@v4` (khai báo Node 20), nên hãy nâng lên `actions/checkout@v5` trở lên và `aws-actions/configure-aws-credentials@v6` trở lên.
- **`permissions:` tối thiểu** cho `GITHUB_TOKEN`:

  ```yaml
  permissions:
    contents: read
  ```

**Đi sâu hơn: giới hạn và chi phí**

- Repo **public**: runner chuẩn của GitHub **miễn phí**.
- Repo **private**:
  - GitHub Free có **2.000 phút/tháng**, Pro/Team có 3.000 phút/tháng.
  - Vượt mức thì Linux 2-core khoảng 0,006 USD/phút. Windows đắt hơn khoảng 1,7 lần, macOS khoảng 10 lần.
- Lưu trữ artifact: 500 MB (Free). Cache: 10 GB mỗi repo.
- Một job trên runner của GitHub chạy tối đa **6 giờ**.

**Lỗi hay gặp & cách sửa**

- Workflow không hiện trong tab Actions → file không nằm đúng `.github/workflows/` ở **nhánh mặc định**, hoặc YAML sai cú pháp (GitHub báo `Invalid workflow file`).
- Nút "Run workflow" không xuất hiện → thiếu `workflow_dispatch`, hoặc file chưa có trên nhánh mặc định.
- `Error: Unable to process file command 'env' successfully` / biến rỗng → nhầm giữa `${{ env.X }}` (biểu thức, GitHub thay giá trị *trước* khi chạy) và `$X` (biến shell, đọc *lúc* chạy).

**Bài tập**

🟡 *Thực hành*: Tạo variable `AWS_REGION=ap-southeast-1` (Settings → Secrets and variables → Actions → Variables) và secret `DEMO_TOKEN`. In cả hai ra log. Quan sát secret bị che `***`.

🔴 *Thử thách*: Thêm file `.github/dependabot.yml` cho `github-actions` (lịch weekly), rồi đổi mọi `uses:` trong repo sang ghim SHA. Giải thích vì sao ghim SHA mà không có Dependabot cũng là rủi ro.

**Câu hỏi tự kiểm tra**

<details><summary>1. Hai job trong cùng workflow có dùng chung file đã build không?</summary>

Không. Mỗi job chạy trên một runner mới, sạch. Muốn chia sẻ thì job A dùng `actions/upload-artifact`, job B dùng `actions/download-artifact`; hoặc đẩy lên nơi chung (ECR, S3). Giá trị nhỏ thì truyền qua `outputs` + `needs`.
</details>

<details><summary>2. Secret khác variable khác environment thế nào?</summary>

Secret dành cho giá trị bí mật: được mã hoá và che trong log. Variable dành cho cấu hình thường: không che. Environment là một "hộp" chứa secret/variable riêng cho từng môi trường, kèm luật bảo vệ (người duyệt, nhánh được phép, thời gian chờ).
</details>

## Lab1 · Build Docker image và push lên ECR {002-003}

**Khái niệm cốt lõi**

File lab: `github-action/lab-1-build-docker-ecr/build-docker-v1.yml` (bản tự chạy khi push) và `build-docker-v2.yml` (chạy tay, checkout theo **tag**).

```yaml
env:
  AWS_REGION: ap-southeast-1
  ECR_REGISTRY: <account-id>.dkr.ecr.ap-southeast-1.amazonaws.com
  ECR_REPOSITORY: nodejs-random-color

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: refs/tags/${{ inputs.version }}     # v2: build đúng code của tag v1.0.0
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}       # lab dùng access key của IAM user
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: ${{ env.AWS_REGION }}
      - uses: aws-actions/amazon-ecr-login@v2                    # docker login vào ECR
      - run: docker build -t nodejs-random-color:${{ inputs.version }} .
      - run: |
          docker tag nodejs-random-color:${{ inputs.version }} $ECR_REGISTRY/$ECR_REPOSITORY:${{ inputs.version }}
          docker push $ECR_REGISTRY/$ECR_REPOSITORY:${{ inputs.version }}
```

Quy trình gắn tag (trong `lab1.md`):

```bash
git tag -a v1.0.0 -m "Test v1.0.0 by Github Action"
git push origin master
git push --tags                 # tag phải lên GitHub thì checkout refs/tags/v1.0.0 mới được
```

**Đi sâu hơn: thay access key bằng OIDC**

Lab tạo IAM user với `PowerUserAccess` và dán access key vào GitHub Secrets. Cách này chạy được, nhưng key **sống mãi**: lộ một lần (log, fork, người cũ trong team) là kẻ gian dùng được đến khi bạn phát hiện. Cách được khuyên dùng hiện nay là **OIDC (OpenID Connect)**:

```
GitHub runner ──(1) xin "ID token" có chữ ký GitHub: repo=me/app, ref=master──▶ GitHub OIDC
      │ (2) AssumeRoleWithWebIdentity + token
      ▼
AWS STS ── kiểm tra: token do token.actions.githubusercontent.com ký? sub khớp điều kiện? ──▶
      │ (3) trả credentials TẠM THỜI (mặc định 1 giờ)
      ▼
Các step sau dùng aws cli / docker push bình thường
```

Thiết lập một lần, ở phía AWS:
1. IAM → Identity providers → *OpenID Connect*: URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`.
2. Tạo role với **trust policy** chỉ tin đúng repo và đúng nhánh:

```json
{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::<account-id>:oidc-provider/token.actions.githubusercontent.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
      "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:<user>/nodejs-random-color:ref:refs/heads/master" }
    }
  }]
}
```

3. Gắn quyền tối thiểu cho role: push vào **đúng một** repo ECR (`ecr:GetAuthorizationToken` trên `*`, và `ecr:BatchCheckLayerAvailability`, `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage` trên ARN của repo).

Phía workflow:

```yaml
permissions:
  id-token: write      # BẮT BUỘC để xin OIDC token
  contents: read
steps:
  - uses: aws-actions/configure-aws-credentials@v6
    with:
      role-to-assume: arn:aws:iam::<account-id>:role/github-actions-ecr-push
      aws-region: ap-southeast-1
```

- `sub` có các dạng: `repo:OWNER/REPO:ref:refs/heads/BRANCH`, `repo:OWNER/REPO:ref:refs/tags/TAG`, `repo:OWNER/REPO:environment:ENV`, `repo:OWNER/REPO:pull_request`.
- **Không bao giờ** để điều kiện `repo:*` hoặc bỏ trống `sub`. Nếu làm vậy, *bất kỳ repo nào trên GitHub* cũng assume được role của bạn.

**Đi sâu hơn: build nhanh hơn với cache**

```yaml
- uses: docker/setup-buildx-action@v3
- uses: docker/build-push-action@v6
  with:
    push: true
    tags: ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ github.sha }}
    cache-from: type=gha          # dùng cache của GitHub Actions (tính vào 10 GB/repo)
    cache-to: type=gha,mode=max
```

**Lỗi hay gặp & cách sửa**

- **Lỗi có sẵn trong `build-docker-v1.yml`:** image được build với tag `:latest`, nhưng bước tag lại dùng `nodejs-random-color:${{ inputs.version }}`. Khi chạy bằng `push`, `inputs.version` **rỗng**, nên lệnh thành `docker tag nodejs-random-color: ...` và báo `Error parsing reference: "nodejs-random-color:" is not a valid repository/tag: invalid reference format`. Sửa: tag từ `nodejs-random-color:latest`, hoặc dùng `${{ inputs.version || github.sha }}`.
- `fatal: couldn't find remote ref refs/tags/v1.0.0` → bạn quên `git push --tags`, hoặc nhập version không đúng tên tag.
- `Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity` → `sub` trong trust policy không khớp (sai tên repo, sai nhánh, chữ hoa/thường), hoặc thiếu `permissions: id-token: write`.
- `Credentials could not be loaded, please check your action inputs` → secret `AWS_ACCESS_KEY_ID` chưa tạo, hoặc gõ sai tên.
- `name unknown: The repository with name '...' does not exist in the registry` → chưa tạo repo ECR, hoặc `ECR_REPOSITORY` vẫn là tên của giảng viên (`...-0529`).

💰 **Chi phí:** workflow vài phút, nằm trong 2.000 phút free (repo public thì free hoàn toàn). ECR khoảng 0,10 USD/GB/tháng sau free tier; đặt lifecycle policy. Nếu đã dùng IAM user + access key: học xong **deactivate và xoá access key**.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab v1 và sửa lỗi `inputs.version` rỗng. Push code, kiểm tra image `latest` và image tag `${{ github.sha }}` trên ECR.

🟡 *Thực hành*: Chuyển workflow sang **OIDC**: tạo identity provider, role có trust policy giới hạn đúng repo + nhánh `master`, xoá 2 secret access key. Workflow vẫn push được.

<details><summary>Gợi ý Terraform (tuỳ chọn)</summary>

```hcl
resource "aws_iam_openid_connect_provider" "github" {
  url            = "https://token.actions.githubusercontent.com"
  client_id_list = ["sts.amazonaws.com"]
}
data "aws_iam_policy_document" "trust" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]
    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }
    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }
    condition {
      test     = "StringLike"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:<user>/nodejs-random-color:ref:refs/heads/master"]
    }
  }
}
resource "aws_iam_role" "gha" {
  name               = "github-actions-ecr-push"
  assume_role_policy = data.aws_iam_policy_document.trust.json
}
```
Một số phiên bản provider AWS cũ bắt buộc `thumbprint_list`; bản mới thì không.
</details>

🔴 *Thử thách*: Tạo nhánh `test-oidc`, push và chạy workflow từ nhánh đó. Chứng minh role **từ chối** (vì `sub` chỉ cho `master`). Sau đó mở rộng trust policy để cho phép thêm mọi tag `v*`, nhưng vẫn chặn các nhánh khác.

<details><summary>Đáp án</summary>

Thêm giá trị thứ hai vào `StringLike` của `sub`: `"repo:<user>/nodejs-random-color:ref:refs/tags/v*"`. Nhiều giá trị trong cùng một điều kiện được nối bằng phép OR.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao OIDC an toàn hơn access key trong GitHub Secrets?</summary>

Không có bí mật dài hạn nào được lưu trên GitHub. Mỗi lần chạy, AWS cấp credentials tạm thời (mặc định 1 giờ), và chỉ cấp khi token chứng minh được *đúng repo, đúng nhánh*. Lộ log hay bị fork repo cũng không lộ được key dùng lâu dài.
</details>

<details><summary>2. Vì sao lab v2 checkout <code>refs/tags/${{ inputs.version }}</code> thay vì nhánh master?</summary>

Để image `v1.0.0` được build từ **đúng code đã gắn tag v1.0.0**, kể cả khi master đã có thêm commit mới. Nhờ vậy phiên bản có thể lặp lại: build lại tag cũ lúc nào cũng ra cùng một code.
</details>

## Lab2 · Deploy lên ECS {004}

**Khái niệm cốt lõi**

Hạ tầng của chương (`github-action/terraform/`) khác chương 11. Ở đây có **hai ECS cluster**, `udemy-devops-cluster-blue` và `udemy-devops-cluster-green`, mỗi cluster có service `nodejs-service` (2 task) gắn với một target group. ALB có listener **:80 → TG blue** và **:81 → TG green**. Blue/green được làm *bằng tay* qua workflow, không dùng CodeDeploy.

```
            ALB
 :80 ──▶ target-group-blue  ──▶ cluster-blue  / nodejs-service (đang phục vụ)
 :81 ──▶ target-group-green ──▶ cluster-green / nodejs-service (deploy bản mới vào đây)
```

```bash
cd github-action/terraform/singapore-dev
# sửa terraform.tfvars: ecr_repo_url = "<account>.dkr.ecr.ap-southeast-1.amazonaws.com/nodejs-random-color:latest"
terraform init && terraform apply --var-file "terraform.tfvars"
```

Workflow `lab-2-deploy-ecr/deploy-ecs.yml` (chạy tay, nhập `version` và `cluster_name`):

```bash
# 1. Lấy task definition hiện tại
TASK_DEFINITION=$(aws ecs describe-task-definition --task-definition nodejs-task-definition)
# 2. Đổi image, xoá các trường chỉ-đọc (register-task-definition sẽ từ chối nếu còn)
NEW_TASK_DEFINITION=$(echo $TASK_DEFINITION | jq --arg IMAGE "$FULL_IMAGE" '
  .taskDefinition | .containerDefinitions[0].image = $IMAGE |
  del(.taskDefinitionArn, .revision, .status, .requiresAttributes, .compatibilities, .registeredAt, .registeredBy)')
# 3. Đăng ký revision mới, 4. Cập nhật service
aws ecs register-task-definition --cli-input-json "$NEW_TASK_DEFINITION"
aws ecs update-service --cluster $CLUSTER --service nodejs-service --task-definition nodejs-task-definition:$NEW_REVISION --force-new-deployment
aws ecs update-service --cluster $CLUSTER --service nodejs-service --desired-count 2
```

⚠️ Chỉ deploy vào cluster **đang không nhận traffic production** (xem *Resource map* của ALB). Kiểm tra bản mới qua `http://<alb>:81`.

**Đi sâu hơn**

- **Cách "chính chủ" thay cho jq:** AWS có 2 action làm đúng việc này, và chúng **chờ service ổn định** rồi mới báo xanh:

  ```yaml
  - name: Render task definition
    id: render
    uses: aws-actions/amazon-ecs-render-task-definition@v1
    with:
      task-definition-family: nodejs-task-definition   # hoặc task-definition: taskdef.json trong repo
      container-name: nodejs-container
      image: ${{ env.ECR_REGISTRY }}/${{ env.ECR_REPOSITORY }}:${{ inputs.version }}
  - name: Deploy
    uses: aws-actions/amazon-ecs-deploy-task-definition@v2
    with:
      task-definition: ${{ steps.render.outputs.task-definition }}
      cluster: ${{ inputs.cluster_name }}
      service: nodejs-service
      wait-for-service-stability: true      # đợi task mới healthy, lỗi thì job đỏ
  ```
  Kiểm tra phiên bản mới nhất của các action trên GitHub trước khi dùng.
- **`aws ecs update-service` trả về ngay**, không đợi deploy xong. Workflow của lab báo "xanh" kể cả khi task mới crash liên tục. Tự thêm `aws ecs wait services-stable --cluster ... --services nodejs-service`.
- **`outputs` giữa step và job:**

  ```yaml
  jobs:
    build:
      outputs:
        image: ${{ steps.meta.outputs.image }}      # khai báo output của JOB
      steps:
        - id: meta
          run: echo "image=$ECR_REGISTRY/$ECR_REPOSITORY:${{ github.sha }}" >> "$GITHUB_OUTPUT"
    deploy:
      needs: build
      steps:
        - run: echo "Deploy ${{ needs.build.outputs.image }}"
  ```
  Lab1 có ghi `IMAGE_URI` vào `$GITHUB_OUTPUT`, nhưng job không khai báo `outputs:` nên job khác không đọc được.
- Hai cluster dùng **chung một task definition family**, nên mỗi lần deploy tạo revision mới cho cả họ. Revision cũ vẫn còn, rollback bằng cách chọn lại revision trước.

**Lỗi hay gặp & cách sửa**

- `Parameter validation failed: Unknown parameter in input: "<tên-trường>"` → output của `describe-task-definition` có trường chỉ-đọc mà jq chưa xoá (AWS thỉnh thoảng thêm trường mới, hoặc bạn dùng `--include TAGS` nên có thêm `tags` ở ngoài). Xoá thêm trường đó, hoặc dùng action `render-task-definition`.
- `ServiceNotFoundException` → sai `cluster_name` (phải là `udemy-devops-cluster-blue` hoặc `-green`), hoặc sai region.
- Task mới `STOPPED` với lý do `CannotPullContainerError: ... not found` → tag `version` chưa có trên ECR (bạn chưa chạy lab1 với tag đó).
- `AccessDeniedException ... iam:PassRole` → user/role của GitHub thiếu quyền *pass* execution role `nodejs-task-execution-role` khi đăng ký task definition.

## Lab3 · Switch traffic Blue-Green trên ALB {005}

**Khái niệm cốt lõi**

Sau khi kiểm tra bản mới trên `:81`, workflow `lab-3-switch-traffic/switch-traffic.yml` **hoán đổi** target group của hai listener:

```
Trước:  :80 → TG blue (v1)     :81 → TG green (v2)
Sau:    :80 → TG green (v2)    :81 → TG blue (v1)    ← v1 vẫn chạy, quay lại chỉ cần chạy lại workflow
```

```bash
LISTENERS=$(aws elbv2 describe-listeners --load-balancer-arn $ALB_ARN)
LISTENER_1_ARN=$(echo "$LISTENERS" | jq -r '.Listeners[0].ListenerArn')
LISTENER_1_TG=$(echo "$LISTENERS"  | jq -r '.Listeners[0].DefaultActions[0].TargetGroupArn')
# ... tương tự Listeners[1]
aws elbv2 modify-listener --listener-arn "$LISTENER_1_ARN" --default-actions Type=forward,TargetGroupArn="$LISTENER_2_TG"
aws elbv2 modify-listener --listener-arn "$LISTENER_2_ARN" --default-actions Type=forward,TargetGroupArn="$LISTENER_1_TG"
```

Workflow có `workflow_dispatch: {}` (chạy tay, không có input) và `workflow_call: {}` (để lab5 gọi).

**Đi sâu hơn**

- **Đừng dựa vào thứ tự `Listeners[0]` / `Listeners[1]`.** API không cam kết trả listener theo thứ tự cổng. Nếu thứ tự đảo thì script vẫn chạy, nhưng log in ra nhầm "listener 1 / listener 2", và nếu ALB có thêm listener thứ ba (ví dụ :443) thì script sẽ hoán sai. Hãy lọc theo port:

  ```bash
  PROD_ARN=$(aws elbv2 describe-listeners --load-balancer-arn "$ALB_ARN" \
    --query 'Listeners[?Port==`80`].ListenerArn' --output text)
  TEST_ARN=$(aws elbv2 describe-listeners --load-balancer-arn "$ALB_ARN" \
    --query 'Listeners[?Port==`81`].ListenerArn' --output text)
  ```
- **Hai lệnh `modify-listener` không nằm trong một giao dịch (transaction).** Giữa lệnh 1 và lệnh 2 có một khoảnh khắc cả hai cổng cùng trỏ vào TG green. Với bài lab thì không sao, nhưng cần biết.
- **Đổi hẳn hay chia dần?** `modify-listener` hỗ trợ *weighted forward* (ví dụ 90% blue / 10% green). Đó là cách tự làm canary mà không cần CodeDeploy:

  ```bash
  aws elbv2 modify-listener --listener-arn "$PROD_ARN" --default-actions '[{"Type":"forward","ForwardConfig":{"TargetGroups":[
    {"TargetGroupArn":"'"$TG_BLUE"'","Weight":90},{"TargetGroupArn":"'"$TG_GREEN"'","Weight":10}]}}]'
  ```
- **Không hard-code ARN của ALB trong YAML:** lấy theo tên bằng `aws elbv2 describe-load-balancers --names udemy-devops-alb`, hoặc lưu ở `vars.ALB_ARN`.
- **Kiểm tra trước khi đổi:** chỉ switch khi target group mới có đủ target `healthy` (`aws elbv2 describe-target-health --target-group-arn $TG_GREEN`). Như vậy tránh đẩy production vào một TG rỗng.

**Lỗi hay gặp & cách sửa**

- `❌ Error: Could not extract listener information` → `ALB_ARN` sai (ALB tạo lại sau mỗi lần `terraform apply` sẽ có ARN mới), hoặc ALB chỉ có một listener.
- `AccessDenied ... elasticloadbalancing:ModifyListener` → role/user thiếu quyền ELB.
- Switch xong `:80` trả **503** → target group mới không có target healthy (cluster đó đã bị scale về 0 ở lab4, hoặc task đang crash).

💰 **Chi phí:** đổi listener miễn phí. Chi phí vẫn là ALB + NAT + task đang chạy.

**Bài tập**

🟢 *Cơ bản*: Chạy workflow switch, mở `:80` và `:81`, xác nhận hai phiên bản đã đổi chỗ. Chạy lại lần nữa để quay về như cũ.

🟡 *Thực hành*: Viết lại script: tìm listener theo **port**, lấy ALB ARN theo **tên**, và kiểm tra TG đích có ít nhất 1 target `healthy` trước khi đổi (không có thì `exit 1`).

## Lab4 · Dọn bản cũ (Clear old resources) {006}

**Khái niệm cốt lõi**

Sau khi switch và chắc chắn bản mới ổn, cluster cũ vẫn chạy 2 task, tốn tiền vô ích. Workflow `lab-4-clear-old-resource/clear-resources.yml` scale service của cluster cũ về **0 task**:

```bash
TASK_ARNS=$(aws ecs list-tasks --cluster "$CLUSTER" --query 'taskArns[]' --output text)
for task_arn in $TASK_ARNS; do aws ecs stop-task --cluster "$CLUSTER" --task "$task_arn"; done

```

Service, cluster và task definition vẫn còn, chỉ không có task nào chạy. Lần deploy sau (lab2) sẽ đặt lại `desired-count 2`.

**Đi sâu hơn**

- **Thứ tự lệnh nên đảo lại.** Nếu `stop-task` *trước* khi hạ `desired-count`, ECS thấy service thiếu task và **khởi động task mới để bù**.  
  ```bash
  aws ecs update-service --cluster "$CLUSTER" --service nodejs-service --desired-count 0
  aws ecs wait services-stable --cluster "$CLUSTER" --services nodejs-service
  ```
- **Chặn chạy nhầm cluster production.** Đây là workflow nguy hiểm: nhập nhầm tên là tắt production. Trước khi scale, kiểm tra target group của cluster này **không** đang gắn với listener :80; nếu đang gắn thì `exit 1`.
- **`concurrency`** để không chạy hai lần chồng nhau:

  ```yaml
  concurrency:
    group: ecs-${{ inputs.cluster_name }}
    cancel-in-progress: false      # không huỷ giữa chừng thao tác hạ tầng
  ```
- **Dọn cả task definition revision cũ** (tuỳ chọn): `aws ecs deregister-task-definition --task-definition nodejs-task-definition:<rev>`. Revision đã deregister không bị tính tiền, chỉ giúp danh sách gọn hơn.
- Từ 2025, ECS có blue/green *built-in* trong một service. Mô hình "hai cluster + tự đổi listener" của lab rất tốt để **hiểu bản chất**, nhưng hệ thống thật thường dùng ECS built-in hoặc CodeDeploy.

**Lỗi hay gặp & cách sửa**

- Sau khi chạy, task lại xuất hiện vài giây rồi mới biến mất → do thứ tự `stop-task` trước `desired-count` (xem trên).

## Lab5 · Kết hợp tất cả trong một pipeline {007}

**Khái niệm cốt lõi**

`lab-5-combine-all-actions/blue-green-deployment.yml` không tự làm việc gì. Nó **gọi lại 4 workflow** của lab1–4 (gọi là *reusable workflow*), nối với nhau bằng `needs:` và `if:`:

```
workflow_dispatch(version, target_cluster, switch_traffic, cleanup_old_cluster)
      │
      ▼
build-and-push  (uses: ./.github/workflows/build-docker.yml)
      │ needs
      ▼
deploy-to-target (uses: deploy-ecs.yml, cluster = blue|green)
      │ needs                     if: switch_traffic
      ▼
manual-approval  (environment: production-approval  ← DỪNG chờ người duyệt)
      │ needs
      ▼
switch-traffic   (uses: switch-traffic.yml)
      │ needs                     if: cleanup_old_cluster && switch_traffic
      ▼
cleanup-old-cluster (uses: clear-resources.yml, cluster = bên còn lại)

deployment-summary (if: always())  → ghi bảng tóm tắt vào $GITHUB_STEP_SUMMARY
```

```yaml
jobs:
  build-and-push:
    uses: ./.github/workflows/build-docker.yml     # gọi workflow khác (cần có on: workflow_call)
    with:
      version: ${{ inputs.version }}
    secrets: inherit                                # truyền toàn bộ secrets của repo xuống

  deploy-to-target:
    needs: build-and-push
    uses: ./.github/workflows/deploy-ecs.yml
    with:
      version: ${{ inputs.version }}
      cluster_name: ${{ inputs.target_cluster == 'blue' && 'udemy-devops-cluster-blue' || 'udemy-devops-cluster-green' }}
      #              └─ biểu thức "a && b || c" = toán tử 3 ngôi (if/else) của GitHub Actions
```

**Đi sâu hơn: reusable workflow**

- File được gọi **phải** có `on: workflow_call` và phải nằm trực tiếp trong `.github/workflows/` (không hỗ trợ thư mục con).
- `inputs` chỉ nhận kiểu `string`, `number`, `boolean`. Secret truyền qua `secrets:` từng cái, hoặc `secrets: inherit` (chỉ dùng được trong cùng owner/organization).
- **Biến `env:` ở cấp workflow của file gọi KHÔNG được truyền xuống** workflow được gọi. Vì vậy `BLUE_CLUSTER`/`GREEN_CLUSTER` trong `env:` của lab5 không có tác dụng ở các file con; tên cluster được viết cứng trong biểu thức `cluster_name`.
- Nối tối đa **10 cấp** workflow (file gọi + 9 cấp reusable), không được gọi vòng tròn.
- Muốn lấy kết quả từ reusable workflow: khai báo `on.workflow_call.outputs.<tên>.value: ${{ jobs.<job>.outputs.<tên> }}` ở file con, rồi đọc bằng `needs.<job-gọi>.outputs.<tên>` ở file cha.
- **Reusable workflow** khác **composite action**: reusable workflow là cả một chuỗi *job* (có `runs-on` riêng, có `environment`). Composite action là một chuỗi *step*, chạy bên trong job của bạn.

**Đi sâu hơn: duyệt tay bằng environment**

- Job `manual-approval` có `environment: production-approval`. Vào *Settings → Environments → production-approval*, thêm *Required reviewers*. Khi chạy tới đây, workflow dừng chờ, người duyệt bấm *Review deployments → Approve*.
- ⚠️ Với GitHub Free, required reviewers **chỉ có ở repo public**. Repo private trên gói Free thì environment vẫn tạo được, nhưng job **không dừng lại chờ ai**, nên bước "approval" này thực chất không có tác dụng.
- Bật *Prevent self-review* để người bấm chạy workflow không tự duyệt được.
- Thời gian chờ duyệt **không** tính phút runner.

**Đi sâu hơn: `concurrency` cho pipeline deploy**

```yaml
concurrency:
  group: blue-green-production
  cancel-in-progress: false    # run sau xếp hàng chờ run trước, không chạy chồng lên ALB
```

Thiếu `concurrency`, hai người chạy cùng lúc có thể cùng switch listener, và kết quả là traffic quay về chỗ cũ.

**Lỗi hay gặp & cách sửa**

- `error parsing called workflow ".github/workflows/build-docker.yml": workflow is not reusable as it is missing a "on.workflow_call" trigger` → file con thiếu `workflow_call`, hoặc tên file khác (lab gọi `build-docker.yml`, nhưng file mẫu tên `build-docker-v2.yml`).
- `Invalid input, version is not defined in the referenced workflow` → file con không khai báo input `version` trong `on.workflow_call.inputs`.
- Job `switch-traffic` bị *skipped* dù đã tick → vì `needs: manual-approval`, mà job đó bị skip hoặc bị reject. Một job phụ thuộc vào job bị skip cũng bị skip, trừ khi dùng `if: always()` hoặc `!cancelled()`.
- Chọn nhầm `target_cluster` là cluster **đang** phục vụ → deploy đè lên production. Thêm bước kiểm tra như ở lab4.

💰 **Chi phí:** một lần chạy đầy đủ khoảng 5–10 phút runner (build Docker là lâu nhất). Repo public thì miễn phí.

**Bài tập**

🟢 *Cơ bản*: Copy 4 workflow lab1–4 với đúng tên file mà lab5 gọi, chạy `Complete Blue-Green Deployment` với `v1.0.2`, `switch_traffic = true`, `cleanup_old_cluster = true`.

🟡 *Thực hành*: Thêm `concurrency` cho lab5. Cho `build-docker.yml` trả output `image_uri` (khai báo trong `on.workflow_call.outputs`), rồi in ra ở `deployment-summary` bằng `needs.build-and-push.outputs.image_uri`.

<details><summary>Gợi ý</summary>

Trong `build-docker.yml`:
```yaml
on:
  workflow_call:
    inputs: { version: { type: string, required: true } }
    outputs:
      image_uri:
        value: ${{ jobs.build-and-push.outputs.image_uri }}
jobs:
  build-and-push:
    outputs:
      image_uri: ${{ steps.build-output.outputs.IMAGE_URI }}
```
Ở lab5, `deployment-summary` đã có `needs: [build-and-push, ...]`, nên đọc được `${{ needs.build-and-push.outputs.image_uri }}`.
</details>

🔴 *Thử thách*: Bỏ input `target_cluster`. Thêm một job đầu tiên **tự phát hiện** cluster nào đang *không* nhận traffic (listener :80 trỏ TG nào → cluster còn lại), xuất ra output `idle_cluster` và `active_cluster`, rồi các job sau dùng output đó. Người chạy không thể chọn nhầm nữa.

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>secrets: inherit</code> làm gì? Có rủi ro gì?</summary>

Nó truyền *mọi* secret mà workflow gọi có quyền đọc xuống workflow con. Tiện, nhưng trái nguyên tắc quyền tối thiểu: workflow con nhận cả những secret nó không cần. Khi workflow con là của bên thứ ba hoặc dùng chung rộng rãi, nên truyền từng secret cụ thể.
</details>

<details><summary>2. Vì sao job <code>deployment-summary</code> có <code>if: always()</code>?</summary>

Để job luôn chạy và ghi tóm tắt, kể cả khi build hoặc deploy **thất bại**. Không có `always()`, job phụ thuộc sẽ bị skip ngay khi một job trong `needs` lỗi, và bạn mất bảng tóm tắt đúng lúc cần nó nhất.
</details>

## Lab6 · Unit test trên nhánh develop và xoá resources {008-009}

**Khái niệm cốt lõi**

`lab-6-add-test-step/test-on-develop.yml` chạy mỗi khi **push vào `develop`** hoặc có **pull request nhắm vào `develop`**. Đây là phần **CI**: kiểm tra code trước khi nó được merge.

```yaml
on:
  push:         { branches: [develop] }
  pull_request: { branches: [develop] }
jobs:
  build-and-test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '18'
          cache: 'npm'                 # cache ~/.npm theo hash package-lock.json
      - run: npm install
      - run: |                         # chạy server nền, lưu PID để tắt sau
          npm run dev &
          echo $! > server.pid
      - run: ...                       # chờ tối đa 60s tới khi curl localhost:3000 OK
      - run: ...                       # kiểm tra HTTP 200 và HTML hợp lệ
      - if: always()                   # luôn dọn dẹp, kể cả khi test lỗi
        run: kill $(cat server.pid) || true
```

**Luồng làm việc nhánh điển hình:**

```
feature/x ──PR──▶ develop  (test-on-develop.yml chạy, PR hiện ✓/✗)
develop   ──PR──▶ master   (merge xong → build + deploy, lab1–5)
```

**Đi sâu hơn**

- **Bắt buộc CI xanh mới được merge:** Settings → Branches (hoặc *Rulesets*) → nhánh `develop` → *Require status checks to pass* → chọn job `build-and-test`. Như vậy nút Merge bị khoá cho tới khi test xanh.
- **Đây là smoke test, chưa phải unit test.** Lab kiểm tra "server có lên và trả HTML không". Unit test thật kiểm tra từng hàm (Jest/Vitest, `npm test`). Nên có cả hai: `npm test` trước, smoke test sau.
- **`npm ci`** thay `npm install`; và nâng Node 18 (đã hết hỗ trợ) lên **Node 20/22**.
- **Matrix:** test trên nhiều phiên bản cùng lúc, mỗi tổ hợp là một job song song:

  ```yaml
  strategy:
    fail-fast: false               # một bản lỗi không huỷ các bản khác
    matrix:
      node: [20, 22]
      os: [ubuntu-latest]
  runs-on: ${{ matrix.os }}
  steps:
    - uses: actions/setup-node@v4
      with: { node-version: '${{ matrix.node }}', cache: 'npm' }
  ```
- **Cache:** `setup-node` với `cache: 'npm'` lưu thư mục cache của npm theo hash `package-lock.json`. Cache tuỳ ý dùng `actions/cache` với `key: ${{ runner.os }}-x-${{ hashFiles('**/package-lock.json') }}` và `restore-keys`.
- **Huỷ run cũ khi push liên tục lên PR:**

  ```yaml
  concurrency:
    group: ci-${{ github.workflow }}-${{ github.ref }}
    cancel-in-progress: true       # với CI thì huỷ run cũ cho tiết kiệm phút
  ```
- **Bảo mật với PR từ fork:** event `pull_request` từ fork **không** nhận secrets, đó là thiết kế đúng. Đừng đổi sang `pull_request_target` để "lấy secret" khi chưa hiểu rủi ro: nó chạy với quyền của repo gốc, và có thể bị code trong PR lợi dụng.

**Lỗi hay gặp & cách sửa**

- `Error: Dependencies lock file is not found in /home/runner/work/... Supported file patterns: package-lock.json,npm-shrinkwrap.json,yarn.lock` → bạn dùng `cache: 'npm'` nhưng repo không commit `package-lock.json`. Commit lock file (nên làm), hoặc bỏ `cache:`.
- `Server failed to start within 60 seconds` → script `dev` nghe port khác 3000, hoặc chỉ nghe `127.0.0.1` trong khi bạn curl `localhost` qua IPv6 (`::1`). Kiểm tra log của `npm run dev`; thử `curl http://127.0.0.1:3000`.
- Workflow không chạy khi push lên `develop` → file workflow chưa có **trên nhánh develop**. Với `push`, GitHub đọc file workflow *từ chính commit được push*.
- Bước cleanup báo lỗi `kill: (1234) - No such process` → server đã tự tắt. Lab đã có `|| true` để bỏ qua.

<details><summary>Gợi ý cấu trúc</summary>

```yaml
    steps: [ ... ]
```

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao CI chạy trên PR quan trọng hơn chạy sau khi đã merge?</summary>

Chạy trên PR thì lỗi bị chặn **trước** khi vào nhánh chung, nên người khác không bị kéo code hỏng về. Kết hợp với *required status checks*, nhánh `develop`/`master` luôn ở trạng thái build được. Chạy sau merge chỉ báo cho bạn biết là đã hỏng.
</details>

<details><summary>2. <code>cancel-in-progress: true</code> hợp với CI nhưng nguy hiểm với deploy. Vì sao?</summary>

Với CI, run cũ của cùng PR là vô ích khi đã có commit mới, nên huỷ đi để tiết kiệm phút. Với deploy, huỷ giữa chừng có thể để hạ tầng dở dang: đã đăng ký task definition nhưng chưa update service, hoặc mới đổi một trong hai listener. Deploy nên xếp hàng (`cancel-in-progress: false`).
</details>
