# Chương 08 · Thao tác cơ bản với Docker & Docker compose

Học xong chương này, bạn **đóng gói một ứng dụng thành image**, chạy nó ở mọi máy bằng một lệnh, ghép nhiều container (web, cache, database, load balancer) bằng Docker Compose, rồi **đẩy image lên Amazon ECR và chạy trên Amazon ECS (Fargate)** mà không cần quản lý server.

Các lệnh bạn sẽ gõ nhiều nhất cả chương:

```bash
docker build -t my-app:1.0 .          # build image từ Dockerfile
docker run -d -p 8080:80 my-app:1.0   # chạy container, map port máy → container
docker ps -a / docker logs <id>       # xem container, xem log
docker compose up -d --build          # dựng cả cụm service trong compose.yaml
docker compose down                   # dừng và xoá cụm
docker push <account>.dkr.ecr.<region>.amazonaws.com/my-app:1.0   # đẩy image lên ECR
```

## Container là gì, Docker là gì {001-004}

**Vấn đề container giải quyết:** "Trên máy em chạy được mà!" Ứng dụng chạy tốt trên laptop, lên server thì lỗi vì khác phiên bản Node, thiếu thư viện, khác biến môi trường. **Container** đóng gói *ứng dụng + mọi thứ nó cần* (runtime, thư viện, file cấu hình) thành một khối chạy giống hệt nhau ở mọi nơi.

Ví dụ đời thường: container giống **thùng hàng tiêu chuẩn** ở cảng. Bên trong chứa gì cũng được, nhưng kích thước chuẩn nên cần cẩu, tàu, xe tải nào cũng chở được.

**Container khác máy ảo (VM) thế nào:**

```
        Máy ảo (VM)                           Container
┌─────────┬─────────┐               ┌─────────┬─────────┐
│  App A  │  App B  │               │  App A  │  App B  │
│ Thư viện│ Thư viện│               │ Thư viện│ Thư viện│
│ Guest OS│ Guest OS│ ← mỗi VM 1 OS └─────────┴─────────┘
├─────────┴─────────┤               │  Docker Engine    │
│    Hypervisor     │               │  Kernel Linux CHUNG│ ← dùng chung kernel
│     Host OS       │               │     Host OS       │
└───────────────────┘               └───────────────────┘
  khởi động: phút, GB                 khởi động: giây, MB
```

| | Máy ảo | Container |
|---|---|---|
| Cô lập | Rất mạnh (kernel riêng) | Đủ dùng (chung kernel host) |
| Kích thước | Vài GB | Vài MB đến vài trăm MB |
| Khởi động | Vài chục giây đến phút | Dưới 1 giây đến vài giây |
| Chạy OS khác | Được (Windows trên Linux) | Không: container Linux cần kernel Linux |

**Docker là gì:** nền tảng để **build, chia sẻ và chạy** container. Các thành phần:

```
docker CLI  ──REST API──►  dockerd (Docker daemon)
(bạn gõ lệnh)                  │  quản lý image, network, volume
                               ▼
                          containerd ──► runc ──► container (process Linux)
                               ▲
              pull / push      │
                     Registry (Docker Hub, Amazon ECR, GHCR…)
```

- **Image:** "khuôn" chỉ đọc, gồm nhiều **layer** (lớp). Ví dụ `nginx:1.27`.
- **Container:** một *bản chạy* của image. Một image chạy được nhiều container.
- **Registry:** kho chứa image. **Repository** là một thư mục trong registry chứa nhiều **tag** (phiên bản) của cùng một image.
- **Dockerfile:** file công thức để build image.

**Bốn bước triển khai ứng dụng bằng Docker (bài 004):**

```
1. Viết Dockerfile → 2. docker build → 3. docker push lên registry → 4. docker run / ECS / Kubernetes kéo về chạy
```

**Đi sâu hơn: container thực chất chỉ là process Linux bị "nhốt"**

Container không phải công nghệ ảo hoá. Nó là **một process bình thường** trên host, được kernel Linux che mắt và giới hạn bằng hai cơ chế:

- **Namespace (cô lập "nhìn thấy gì"):**
  - `pid`: container chỉ thấy process của nó, app trong container là PID 1.
  - `net`: có card mạng, IP, bảng route riêng.
  - `mnt`: có cây thư mục `/` riêng (lấy từ image).
  - `uts`: hostname riêng. `ipc`: bộ nhớ chia sẻ riêng. `user`: ánh xạ UID (root trong container có thể là user thường ngoài host, gọi là *rootless*).
- **cgroup (control group, giới hạn "được dùng bao nhiêu"):** CPU, RAM, số process, I/O. Fedora dùng **cgroup v2**.

```bash
docker run -d --name limited --memory 256m --cpus 0.5 nginx
docker stats limited          # thấy MEM LIMIT = 256MiB
ps -ef | grep nginx           # ngoài host vẫn thấy process nginx: container = process
```

- **Union filesystem (overlay2):** các layer image chỉ đọc chồng lên nhau, trên cùng là một **lớp ghi được** riêng của container. Xoá container là mất lớp này, nên dữ liệu cần giữ phải để trong **volume**.
- **OCI (Open Container Initiative):** chuẩn chung cho image và runtime. Nhờ vậy image build bằng Docker chạy được trên Podman, containerd, ECS, Kubernetes.

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao không chạy được container Windows trực tiếp trên Fedora?</summary>

Container dùng **chung kernel với host**. Container Windows cần kernel Windows, Fedora chỉ có kernel Linux. Docker Desktop trên Windows/Mac chạy được container Linux là nhờ chạy ngầm một máy ảo Linux nhỏ (WSL2 hoặc VM).
</details>

<details><summary>2. Image và container khác nhau thế nào? Ví dụ.</summary>

Image là **khuôn** chỉ đọc (giống file cài đặt hoặc "class"). Container là **bản đang chạy** của khuôn đó (giống "object"). Từ image `nginx` bạn có thể chạy 3 container `web1`, `web2`, `web3` cùng lúc, mỗi cái có lớp ghi và IP riêng.
</details>

<details><summary>3. Namespace và cgroup, cái nào giúp chặn một container "ăn" hết RAM của máy?</summary>

**cgroup**. Namespace chỉ quyết định container *nhìn thấy* gì. cgroup mới giới hạn *tài nguyên được dùng*, ví dụ `--memory 256m`. Vượt giới hạn, kernel sẽ kill process (lỗi OOMKilled, exit code 137).
</details>

## Cài đặt Docker và đăng ký Docker Hub {005-008}

Video hướng dẫn cài trên Windows, Mac và Cloud9. Bạn dùng **Fedora**, nên cài **Docker Engine** trực tiếp, không cần Docker Desktop.

**Cài Docker Engine trên Fedora (theo docs.docker.com, Fedora 43 trở lên dùng dnf5):**

```bash
# 1. Gỡ gói docker cũ/không chính thức (nếu có)
sudo dnf remove docker docker-client docker-client-latest docker-common \
  docker-latest docker-latest-logrotate docker-logrotate docker-selinux \
  docker-engine-selinux docker-engine

# 2. Thêm repo chính thức của Docker
sudo dnf config-manager addrepo --from-repofile https://download.docker.com/linux/fedora/docker-ce.repo

# 3. Cài Engine + Buildx + Compose v2 (plugin)
sudo dnf install docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 4. Bật service, chạy cả khi khởi động máy
sudo systemctl enable --now docker

# 5. Cho user hiện tại dùng docker không cần sudo, rồi đăng xuất/đăng nhập lại
sudo usermod -aG docker $USER
newgrp docker            # hoặc logout/login
docker run hello-world
docker compose version   # Compose v2: "docker compose" có dấu cách
```

- Khi dnf hỏi GPG key, đối chiếu fingerprint trên trang cài đặt của Docker trước khi gõ `y`.
- ⚠️ **Nhóm `docker` tương đương quyền root**: ai trong nhóm này có thể mount `/` của host vào container và sửa mọi thứ. Chỉ thêm user của chính bạn.
- Nếu `journalctl -u docker` báo `failed to find iptables`, tài liệu Docker hướng dẫn: `sudo alternatives --set iptables /usr/bin/iptables-nft` rồi restart docker.

**Podman: có sẵn trên Fedora**

Fedora cài sẵn **Podman**, một công cụ container tương thích lệnh Docker:

| | Docker Engine | Podman |
|---|---|---|
| Kiến trúc | Có daemon `dockerd` chạy nền (root) | Không daemon, mỗi lệnh là một process |
| Rootless | Có thể cấu hình | Mặc định rootless |
| Lệnh | `docker run …` | `podman run …` (gần như y hệt) |
| Compose | `docker compose` | `podman compose` / `podman-compose` |

Khoá học dùng Docker, nên bạn hãy theo Docker để khớp video. Lưu ý: gói `podman-docker` tạo lệnh giả `docker` trỏ sang Podman và xung đột với `docker-ce-cli`. Đừng cài cả hai. Kiểm tra bằng `docker version`: nếu thấy chữ "Podman" là bạn đang dùng Podman.

**Windows / Mac (bài 005, 006):** dùng **Docker Desktop**. Trên Windows cần bật WSL2. Docker Desktop miễn phí cho cá nhân, học tập và doanh nghiệp nhỏ; công ty lớn phải mua license.

**Đăng ký Docker Hub (bài 008):**

```bash
docker login            # nhập username + Personal Access Token (không dùng mật khẩu)
```

- Tạo **Personal Access Token** trong Account settings của Docker Hub, dùng token đó khi `docker login`. Token thu hồi được, mật khẩu thì không nên lộ.
- Docker Hub **giới hạn số lần pull**. Người dùng chưa đăng nhập bị giới hạn chặt hơn nhiều so với người đã đăng nhập. Gặp lỗi `toomanyrequests` thì hãy `docker login`.

**Lỗi hay gặp**

- `permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock`: user chưa thuộc nhóm `docker`, hoặc đã thêm nhưng chưa đăng nhập lại. Chạy `id` để kiểm tra có `docker` chưa.
- `Cannot connect to the Docker daemon … Is the docker daemon running?`: service chưa chạy. `sudo systemctl status docker`, rồi `sudo systemctl start docker`.
- `docker: 'compose' is not a docker command`: thiếu gói `docker-compose-plugin`.

🟡 *Thực hành*: Chạy cùng image nginx bằng cả Docker và Podman, so sánh: process chạy dưới user nào ngoài host?

</details>

**Câu hỏi tự kiểm tra**

v1 là chương trình Python riêng, đã hết hỗ trợ. v2 là plugin viết bằng Go, nằm trong Docker CLI, được cập nhật cùng Docker và hỗ trợ đầy đủ Compose Specification (`depends_on` có điều kiện, `develop.watch`, profiles…).

## Lab1 · Thao tác cơ bản với Docker {009}

File lab: `docker-basic-operation/lab1-docker-basic-command/lab1-docker-basic-command.sh`.

**Vòng đời container:**

```
docker pull → image
docker run  → created → running ──docker stop──► exited ──docker rm──► (biến mất)
                          ▲  └──docker restart──┘   │
                          └────── docker start ─────┘
```

```bash
docker pull nginx:latest                 # tải image
docker images                            # liệt kê image
docker run -d -p 8080:80 --name web nginx:latest
#          │   │    └─ port container (nginx nghe 80)
#          │   └─ port trên máy bạn
#          └─ detached: chạy nền
curl localhost:8080                      # thấy trang "Welcome to nginx!"

docker ps          # container đang chạy
docker ps -a       # tất cả, kể cả đã dừng
docker logs -f web # xem log (stdout/stderr của app)
docker exec -it web /bin/bash   # "vào" container đang chạy (không phải SSH)
docker stop web && docker rm web
docker rmi nginx:latest
```

**`-it` và `-dit`:**
- `docker run -it ubuntu`: `-i` giữ stdin mở, `-t` cấp terminal. Bạn vào thẳng shell bash. Gõ `exit` thì bash (PID 1) kết thúc nên **container cũng dừng**.
- `docker run -dit ubuntu`: chạy nền nhưng vẫn giữ terminal, nên bash không thoát và container sống. Sau đó `docker exec -it <id> bash` để vào.
- Thoát khỏi `docker run -it` mà **không** dừng container: bấm `Ctrl+P` rồi `Ctrl+Q`.

**Quy tắc quan trọng nhất:** *container sống chừng nào process chính (PID 1) còn sống.* `ubuntu` mặc định chạy `bash`; không có terminal thì bash thoát ngay, nên `docker run -d ubuntu` dừng liền.

**Đi sâu hơn**

- Lab dùng chữ "SSH login" cho `docker exec`. Thực ra `docker exec` **không dùng SSH**: nó chạy thêm một process mới bên trong các namespace của container. Container không cần cài SSH server.
- Tag `latest` chỉ là một cái tên, **không có nghĩa là mới nhất**. Hôm nay `nginx:latest` là bản này, tháng sau là bản khác. Khi triển khai thật, hãy ghim tag cụ thể (`nginx:1.27-alpine`).
- Lệnh dọn dẹp hữu ích:

```bash
docker system df                 # image/container/volume chiếm bao nhiêu dung lượng
docker container prune           # xoá mọi container đã dừng
docker image prune               # xoá image "dangling" (không có tag)
docker system prune              # cả hai + network không dùng (hỏi trước khi xoá)
docker inspect web               # mọi thông tin: IP, mount, env, lệnh chạy
docker run --rm alpine echo hi   # --rm: tự xoá container khi chạy xong
```

**Lỗi hay gặp**

- `Bind for 0.0.0.0:8080 failed: port is already allocated`: port 8080 trên máy đang bị container khác (hoặc app khác) dùng. Đổi `-p 8081:80` hoặc dừng container cũ (`docker ps` để tìm).
- `Error response from daemon: conflict: unable to remove repository reference "nginx" … container … is using its referenced image`: còn container (kể cả đã dừng) dùng image này. `docker rm` container trước, hoặc `docker rmi -f`.
- `Conflict. The container name "/web" is already in use`: tên đã tồn tại (container cũ đã dừng nhưng chưa xoá). `docker rm web`.

**Bài tập**

🟢 *Cơ bản*: Chạy 2 container nginx tên `web1`, `web2` trên port 8081 và 8082. Dùng `docker exec` sửa trang chủ của `web2` thành "Hello web2" và kiểm tra bằng curl.

<details><summary>Lời giải</summary>

```bash
docker run -d --name web1 -p 8081:80 nginx
docker run -d --name web2 -p 8082:80 nginx
docker exec web2 sh -c 'echo "Hello web2" > /usr/share/nginx/html/index.html'
curl localhost:8081; curl localhost:8082
docker rm -f web1 web2
```

Thay đổi chỉ nằm trong lớp ghi của `web2`. Xoá container là mất, image không hề bị sửa.
</details>

🟡 *Thực hành*: Chạy `docker run -d --name oom --memory 20m nginx`, rồi tìm hiểu xem `docker inspect` cho biết gì về `OOMKilled` và `ExitCode` khi container bị giới hạn bộ nhớ quá thấp.

<details><summary>Gợi ý</summary>

`docker inspect oom --format '{{.State.OOMKilled}} {{.State.ExitCode}}'`. Nếu nginx vượt 20 MB, kernel kill nó với exit code 137 (128 + 9, tức SIGKILL). Nginx nhỏ có thể vẫn sống; khi đó thử `--memory 6m`. Dọn: `docker rm -f oom`.
</details>

🔴 *Thử thách*: Container `ubuntu` chạy bằng `docker run -d ubuntu` dừng ngay lập tức. Giải thích bằng khái niệm PID 1 và đưa ra 2 cách làm nó chạy mãi.

<details><summary>Lời giải</summary>

PID 1 của image ubuntu là `bash`. Không có terminal (`-t`) và stdin (`-i`) thì bash đọc thấy EOF và thoát, PID 1 chết nên container dừng. Cách 1: `docker run -dit ubuntu`. Cách 2: cho nó một lệnh chạy mãi: `docker run -d ubuntu sleep infinity`. Kiểm tra bằng `docker ps`, rồi `docker rm -f` để dọn.
</details>

**Câu hỏi tự kiểm tra**

<details><summary><code>docker stop</code> và <code>docker kill</code> khác gì nhau?</summary>

`stop` gửi **SIGTERM** để app tự dọn dẹp và thoát, chờ mặc định 10 giây, quá hạn mới gửi **SIGKILL**. `kill` gửi SIGKILL ngay, app không kịp đóng kết nối hay ghi dữ liệu.
</details>

## Dockerfile và Lab2 · Build image đầu tiên {010-011}

**Dockerfile** là công thức để build image: mỗi dòng là một **chỉ thị** (instruction).

File lab: `docker-basic-operation/lab2-Dockerfile/Dockerfile`

```dockerfile
FROM httpd                                  # image gốc: Apache HTTP Server
COPY ./web/index.html /usr/local/apache2/htdocs/   # chép file từ máy vào image
RUN chown www-data:www-data /usr/local/apache2/htdocs/index.html   # chạy lệnh lúc BUILD
ENV LOGFILE=/var/log/httpd/access.log       # biến môi trường, có cả lúc chạy
EXPOSE 80                                   # ghi chú: app nghe port 80
CMD ["httpd-foreground"]                    # lệnh chạy khi container START
```

```bash
cd lab2-Dockerfile
docker build -t my-httpd-image .      # "." là build context: thư mục gửi cho Docker
docker run -d -p 8080:80 --name my-httpd-container my-httpd-image
curl localhost:8080/index.html
```

**Các chỉ thị hay dùng:**

| Chỉ thị | Ý nghĩa | Chạy lúc |
|---|---|---|
| `FROM` | Image gốc | build |
| `WORKDIR` | Thư mục làm việc (tự tạo nếu chưa có) | build + run |
| `COPY` / `ADD` | Chép file vào image. Ưu tiên `COPY`; `ADD` có thêm giải nén tar, tải URL | build |
| `RUN` | Chạy lệnh, kết quả thành một layer mới | build |
| `ENV` | Biến môi trường, còn trong container | build + run |
| `ARG` | Biến chỉ dùng lúc build (`--build-arg`) | build |
| `EXPOSE` | Chỉ là **tài liệu**, không tự mở port. Port do `-p` quyết định | — |
| `USER` | Đổi user cho các lệnh sau và lúc chạy | build + run |
| `HEALTHCHECK` | Lệnh kiểm tra container còn khoẻ không | run |
| `CMD` / `ENTRYPOINT` | Lệnh mặc định khi start (xem Lab3) | run |

**Đi sâu hơn: layer và build cache**

Mỗi `RUN`, `COPY`, `ADD` tạo một **layer**. Docker **cache** từng layer: nếu chỉ thị và file đầu vào không đổi thì dùng lại layer cũ, build nhanh hơn nhiều. Nhưng khi **một layer đổi, mọi layer phía sau đều phải build lại**.

```dockerfile
# CHƯA TỐI ƯU: sửa 1 dòng code → npm install chạy lại từ đầu
COPY . .
RUN npm install

# TỐI ƯU: thứ ít thay đổi đặt trước, thứ hay thay đổi đặt sau
COPY package*.json ./      # chỉ đổi khi thêm/bớt thư viện
RUN npm ci                 # được cache nếu package*.json không đổi
COPY . .                   # code thay đổi thường xuyên → đặt cuối
```

Các lab 5–7 trong repo đã viết đúng thứ tự này. Xem layer của một image: `docker history my-httpd-image`.

**`.dockerignore`**: giống `.gitignore`, loại file khỏi **build context**. Không có nó, `COPY . .` sẽ chép cả `node_modules`, `.git`, file `.env` chứa bí mật vào image, vừa nặng vừa lộ thông tin, và làm hỏng cache vì `.git` thay đổi liên tục.

```text
# .dockerignore
node_modules
npm-debug.log
.git
.env
build
Dockerfile*
```

Repo hiện **chưa có** file `.dockerignore` nào. Đây là việc nên bổ sung.

**Các best practice hiện hành (theo docs.docker.com):**

- **Image gốc nhỏ và tin cậy:** Docker Official Image hoặc Verified Publisher. So sánh kích thước ước lượng: `node:18` khoảng 1 GB, `node:18-slim` khoảng 200 MB, `node:18-alpine` khoảng 130–180 MB. **Distroless** (`gcr.io/distroless/nodejs…`) chỉ có runtime, không có shell, ít lỗ hổng nhất nhưng khó debug.
- **Ghim phiên bản:** `FROM node:22-alpine` thay vì `node`. Muốn chắc chắn tuyệt đối thì ghim digest: `FROM node:22-alpine@sha256:…`.
- **`apt-get update` và `apt-get install` chung một `RUN`**, thêm `--no-install-recommends` và xoá `/var/lib/apt/lists/*`.
- **Chạy non-root:** mặc định process trong container là **root**. App bị khai thác thì kẻ tấn công có root trong container. Thêm `USER`:

```dockerfile
FROM node:22-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --chown=node:node . .
USER node                      # image node có sẵn user "node" (UID 1000)
ENV NODE_ENV=production
EXPOSE 3000
HEALTHCHECK --interval=30s --timeout=3s --retries=3 \
  CMD wget -qO- http://localhost:3000/ || exit 1
CMD ["node", "index.js"]
```

- **`HEALTHCHECK`**: Docker chạy lệnh định kỳ; exit 0 là `healthy`, khác 0 là `unhealthy`. `docker ps` hiện trạng thái trong cột STATUS. Compose dùng nó cho `depends_on: condition: service_healthy`.
- **`ARG` và `ENV`:** `ARG VERSION=1.0` chỉ tồn tại lúc build, `ENV` còn lại trong container. **Không truyền mật khẩu qua `ARG` hay `ENV`**: chúng nằm lộ trong `docker history`/`docker inspect`. Dùng `RUN --mount=type=secret` của BuildKit khi cần bí mật lúc build.
- Build lại sạch hoàn toàn (lấy bản vá mới của image gốc): `docker build --pull --no-cache -t app .`

**Quét lỗ hổng image**

```bash

docker scout cves my-httpd-image           # chi tiết từng CVE
docker scout recommendations my-httpd-image   # gợi ý image gốc ít lỗ hổng hơn

# Trivy (mã nguồn mở), chạy bằng container nên không cần cài

  aquasec/trivy image --severity HIGH,CRITICAL my-httpd-image
```

`docker scout` cần đăng nhập Docker Hub. Amazon ECR cũng có tính năng scan khi push (xem phần ECR).

**Lỗi hay gặp**

- `COPY failed: file not found in build context` hoặc `"/web/index.html": not found`: bạn đứng sai thư mục khi build. Đường dẫn trong `COPY` tính **từ build context** (dấu `.` cuối lệnh), không phải từ vị trí Dockerfile. Phải `cd lab2-Dockerfile` trước.
- Sửa `index.html` rồi chạy lại container nhưng trang không đổi: bạn chưa **build lại** image. Image là ảnh chụp lúc build. Phải `docker build` rồi xoá và chạy lại container.
- Build rất chậm, `Sending build context to Docker daemon 500MB`: thiếu `.dockerignore`, Docker đang gửi cả `node_modules`.

**Bài tập**

🟢 *Cơ bản*: Sửa `lab2-Dockerfile/web/index.html` (thêm tên bạn), build image với tag `my-httpd-image:v2`, chạy ở port 8090 song song với bản cũ.

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>EXPOSE 80</code> có làm truy cập được <code>localhost:80</code> từ máy bạn không?</summary>

Không. `EXPOSE` chỉ là **ghi chú** cho người đọc và công cụ. Muốn truy cập từ máy thì phải publish port bằng `-p 8080:80` (hoặc `-P` để Docker tự chọn port ngẫu nhiên cho mọi port đã EXPOSE).
</details>

<details><summary>2. Trong Dockerfile có 2 dòng <code>RUN apt-get update</code> và <code>RUN apt-get install -y curl</code> tách riêng. Vấn đề là gì?</summary>

Layer `apt-get update` được cache. Vài tháng sau thêm gói mới vào dòng `install`, Docker vẫn dùng danh sách gói cũ từ cache, có thể cài bản cũ hoặc lỗi "not found". Gộp thành một `RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*`.
</details>

## Lab3 · CMD và ENTRYPOINT {012}

File lab: `docker-basic-operation/lab3-CMD-and-ENTRYPOINT/` (Dockerfile-1, -2, -3 và `command.sh`).

**Quy tắc một câu:** `ENTRYPOINT` là **chương trình** chạy, `CMD` là **tham số mặc định**. Tham số bạn gõ sau `docker run <image> …` sẽ **thay thế CMD**, còn ENTRYPOINT giữ nguyên.

| Dockerfile | `docker run img` | `docker run img -alh` |
|---|---|---|
| 1: `ENTRYPOINT ["ls"]` | `ls` | `ls -alh` (đúng) |
| 2: `CMD ["ls"]` | `ls` | `-alh` → lỗi: không có chương trình tên `-alh` |
| 3: `ENTRYPOINT ["ls"]` + `CMD ["-alh"]` | `ls -alh` | `ls -alh` (CMD bị thay bằng `-alh`) |

```bash
cd lab3-CMD-and-ENTRYPOINT
docker build -t alpine-3 -f Dockerfile-3 .     # -f: chọn Dockerfile khác tên mặc định
docker run --rm alpine-3                       # ls -alh
docker run --rm alpine-3 -p --full-time        # ls -p --full-time
docker run --rm --entrypoint cat alpine-3 /etc/os-release   # thay luôn ENTRYPOINT
docker inspect alpine-3 --format '{{.Config.Entrypoint}} {{.Config.Cmd}}'
```

Lỗi của Dockerfile-2 khi chạy `docker run alpine-2 -alh` có dạng:

```text
docker: Error response from daemon: failed to create task for container: ... exec: "-alh": executable file not found in $PATH
```

**Đi sâu hơn: exec form và shell form**

```dockerfile
CMD ["node", "index.js"]   # exec form (JSON): node chạy trực tiếp, là PID 1
CMD node index.js          # shell form: thực chất là /bin/sh -c "node index.js", sh là PID 1
```

- Với **shell form**, PID 1 là `sh`, và `sh` **không chuyển tiếp tín hiệu** SIGTERM cho app. `docker stop` phải chờ hết 10 giây rồi SIGKILL, app không kịp đóng kết nối database.
- **ENTRYPOINT shell form còn bỏ qua hoàn toàn CMD và tham số `docker run`.** Vì vậy luôn dùng exec form (dấu ngoặc vuông, nháy kép).
- Exec form **không** thay biến kiểu `$HOME` vì không có shell. Cần thì viết `["sh", "-c", "echo $HOME"]`.
- `ENTRYPOINT` hợp với image đóng vai **một công cụ** (`aws`, `terraform`, `trivy`). Image app web thường chỉ cần `CMD`.
- Mẫu hay gặp: `ENTRYPOINT ["/docker-entrypoint.sh"]` (script chuẩn bị cấu hình) + `CMD ["nginx", "-g", "daemon off;"]`. Cuối script phải có `exec "$@"` để CMD trở thành PID 1.
- Nếu image gốc có CMD mà bạn khai báo ENTRYPOINT mới, CMD của image gốc bị **xoá**. Cần thì khai báo lại CMD.

**Bài tập**

🟢 *Cơ bản*: Viết `Dockerfile-4` để `docker run alpine-4` in ra `Hello Docker`, còn `docker run alpine-4 Vy` in ra `Hello Vy`.

<details><summary>Lời giải</summary>

```dockerfile
FROM alpine:3.20
ENTRYPOINT ["echo", "Hello"]
CMD ["Docker"]
```
</details>

🟡 *Thực hành*: Build hai image chạy `sleep 300`, một bằng shell form, một bằng exec form. Đo thời gian `time docker stop <container>` của mỗi cái và giải thích.

<details><summary>Gợi ý</summary>

Shell form: `CMD sleep 300`; exec form: `CMD ["sleep", "300"]`. Với shell form, PID 1 là `sh` (hoặc có trường hợp sh tự `exec` lệnh đơn, tuỳ shell). Nếu SIGTERM không tới được `sleep`, stop mất khoảng 10 giây. Kiểm tra PID 1 bằng `docker exec <id> ps`. Kết luận: dùng exec form, hoặc `docker run --init` để có một init nhỏ chuyển tín hiệu.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Image có <code>ENTRYPOINT ["python", "app.py"]</code>. Làm sao mở shell bên trong để debug?</summary>

`docker run -it --entrypoint sh <image>`. Tham số sau tên image chỉ thay CMD, nên phải dùng `--entrypoint` để thay chương trình chính.
</details>

## Multistage Dockerfile và Lab4 {013-014}

File lab: `docker-basic-operation/lab4-multi-stage-docker-file/Dockerfile` (và `Dockerfile-tmp` để so sánh).

**Vấn đề:** để *build* frontend cần Node.js, npm, webpack và hàng trăm MB `node_modules`. Nhưng để *chạy* thì chỉ cần vài file HTML/JS/CSS tĩnh. Đưa cả bộ công cụ build vào image chạy thật là lãng phí và tăng bề mặt tấn công.

**Multistage build:** một Dockerfile có nhiều `FROM`. Stage sau chỉ **chép kết quả** từ stage trước, mọi thứ khác bị bỏ lại.

```
Stage 1 "buildstep" (node:14, ~900 MB)        Stage 2 (httpd, ~140 MB)  ← image cuối
  package.json → npm install                    COPY --from=buildstep /app/build
  COPY . . → npm run build → /app/build ──────►   /usr/local/apache2/htdocs/
  (bị bỏ đi, không vào image cuối)
```

```dockerfile
#Stage 1
FROM node:14 as buildstep
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm install
COPY . .
RUN npm run build              # webpack → thư mục /app/build

#Stage 2
FROM httpd
COPY --from=buildstep /app/build /usr/local/apache2/htdocs/
...
CMD ["httpd-foreground"]
```

```bash
cd lab4-multi-stage-docker-file
docker build -t tmp-nodejs -f Dockerfile-tmp .   # chỉ stage 1
docker build -t custom-httpd .                    # đủ 2 stage
docker images | grep -E 'tmp-nodejs|custom-httpd' # ~900MB so với ~140MB
docker run -d -p 8080:80 custom-httpd
```

**Đi sâu hơn**

- **Cập nhật phiên bản:** `node:14` đã hết hỗ trợ (EOL) từ 2023, không còn bản vá bảo mật. Nên dùng bản LTS hiện hành, ví dụ `node:22-alpine`, cho stage build.
- **Chữ hoa/thường:** BuildKit hiện cảnh báo `FromAsCasing: 'as' and 'FROM' keywords' casing do not match`. Viết `FROM node:22-alpine AS build` cho sạch cảnh báo.
- **Image chạy còn nhỏ hơn nữa:** file tĩnh chỉ cần web server. `nginx:alpine` hoặc `httpd:2.4-alpine` chỉ vài chục MB.
- **`--target`:** build tới một stage cụ thể, ví dụ `docker build --target build -t debug .` để debug stage build.
- **`npm ci` thay `npm install`** trong CI: cài đúng theo `package-lock.json`, nhanh hơn và lặp lại được.
- **Cache mount** của BuildKit giữ cache npm giữa các lần build:
  `RUN --mount=type=cache,target=/root/.npm npm ci`
- **Thư mục `build/` đã nằm sẵn trong repo**, và không có `.dockerignore`, nên `COPY . .` chép cả nó vào stage 1 (sau đó webpack ghi đè). Thêm `build` và `node_modules` vào `.dockerignore`.
- Multistage cũng là cách chuẩn cho ngôn ngữ biên dịch: stage 1 `golang` biên dịch ra một file nhị phân, stage 2 `FROM scratch` hoặc distroless chỉ chứa file đó, image chỉ vài MB.

Phiên bản cải tiến của lab4:

```dockerfile
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/build /usr/share/nginx/html
EXPOSE 80
```

**Lỗi hay gặp**

- `COPY --from=buildstep … not found`: tên stage gõ sai, hoặc thư mục output của build không phải `/app/build` (xem `output.path` trong `webpack.config.js`).
- Lỗi build webpack trên node mới (ví dụ `error:0308010C:digital envelope routines::unsupported`): webpack/công cụ cũ không tương thích OpenSSL 3 của Node 17+. Cập nhật webpack (lab dùng webpack 5 nên thường ổn) hoặc tạm đặt `ENV NODE_OPTIONS=--openssl-legacy-provider`.
- `npm ci` báo lỗi `package-lock.json` không khớp `package.json`: chạy `npm install` ở máy để cập nhật lock file rồi commit.

**Bài tập**

🟢 *Cơ bản*: Build cả `Dockerfile-tmp` và `Dockerfile`, ghi lại kích thước hai image. Dùng `docker history custom-httpd` để chỉ ra layer nào đến từ `COPY --from`.

<details><summary>Gợi ý</summary>

Layer có lệnh `COPY /app/build /usr/local/apache2/htdocs/` chỉ vài trăm KB. Không có layer nào của node:14 trong image cuối. Dọn: `docker rmi tmp-nodejs custom-httpd`.
</details>

🟡 *Thực hành*: Viết bản Dockerfile cải tiến ở trên (node 22 + nginx alpine), thêm `.dockerignore`. So sánh kích thước và thời gian build lần 2 khi chỉ sửa `app/index.html`.

<details><summary>Gợi ý</summary>

Lần build thứ 2, layer `npm ci` phải hiện `CACHED` vì `package*.json` không đổi. Image cuối nhỏ hơn bản httpd. Nhớ đổi port container sang 80 của nginx: `docker run -p 8080:80`.
</details>

🔴 *Thử thách*: Chuyển image chạy sang **non-root**: dùng `nginxinc/nginx-unprivileged:alpine` (nghe port 8080). Chứng minh process không chạy bằng root.

<details><summary>Gợi ý</summary>

`FROM nginxinc/nginx-unprivileged:alpine`, chép vào `/usr/share/nginx/html`, chạy `docker run -p 8080:8080`. Kiểm tra: `docker exec <id> id` phải ra `uid=101(nginx)`. Process không phải root thì không mở được port dưới 1024 theo mặc định, đó là lý do image này nghe 8080.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Multistage giúp gì về bảo mật, ngoài việc giảm dung lượng?</summary>

Image cuối không chứa compiler, npm, mã nguồn, `.npmrc` có token hay `node_modules` dev. Ít phần mềm hơn thì ít CVE hơn, và nếu container bị chiếm thì kẻ tấn công có ít công cụ hơn để khai thác tiếp.
</details>

## Docker Compose và Lab5 · Compose đơn giản {015-016}

**Docker Compose** mô tả *nhiều container và cách chúng kết nối* trong **một file YAML**, rồi dựng tất cả bằng một lệnh. Thay vì gõ lệnh `docker run` dài với `-p`, `-v`, `-e`, `--network` cho từng container, bạn ghi hết vào file và commit lên Git.

File lab: `docker-basic-operation/lab5-docker-compose/docker-compose.yaml`

```yaml
version: '3'                 # đã lỗi thời, Compose v2 bỏ qua (xem bên dưới)
services:
  web:                       # tên service = tên DNS trong mạng compose
    build:
      context: web           # build image từ thư mục ./web
      dockerfile: Dockerfile
    ports:
      - 8080:3000            # máy:container
    volumes:
      - ./web:/app           # bind mount: code trên máy ↔ /app trong container
      - /app/node_modules    # volume ẩn danh: giữ node_modules của image
    environment:
      - NODE_ENV=development
```

```bash
cd lab5-docker-compose
docker compose up -d --build     # build (nếu cần) rồi chạy nền
docker compose ps                # trạng thái các service
docker compose logs -f web       # log của service web
docker compose exec web sh       # vào container của service
docker compose down              # dừng + xoá container và network (giữ volume)
docker compose down -v           # xoá luôn named volume (mất dữ liệu!)
```

**Volume và bind mount, mẹo `/app/node_modules`:**

```
Máy bạn ./web  ──bind mount──►  /app            (code bạn sửa thấy ngay trong container)
volume ẩn danh ─────────────►   /app/node_modules (giữ thư viện đã npm install lúc build)
```

Bind mount `./web:/app` **che** toàn bộ `/app` của image, kể cả `node_modules` mà `RUN npm install` đã cài. Dòng `- /app/node_modules` tạo một volume riêng cho đúng thư mục con đó, nên thư viện trong image vẫn còn.

**Đi sâu hơn**

- **Dòng `version:` đã lỗi thời.** Compose v2 theo *Compose Specification* và in cảnh báo `the attribute 'version' is obsolete, it will be ignored`. Cứ xoá dòng đó. Tên file mặc định hiện nay là `compose.yaml` (`docker-compose.yaml` vẫn được nhận), nên không cần `-f` nếu đặt đúng tên.
- **"Auto reload" trong comment của lab chỉ đúng một nửa.** Sửa file trong `public/` thì thấy ngay (Express đọc file tĩnh từ đĩa mỗi request). Nhưng sửa `index.js` thì **không** tự reload vì `npm start` chạy `node index.js`. Muốn reload code phải dùng `node --watch index.js` (Node 18.11+) hoặc `nodemon`, hoặc tính năng `develop.watch` + `docker compose watch` của Compose v2.
- **Ba loại mount:**

| | Volume (named) | Bind mount | tmpfs |
|---|---|---|---|
| Cú pháp | `dbdata:/var/lib/mysql` | `./web:/app` | `tmpfs: /tmp` |
| Nằm ở đâu | Docker quản lý (`/var/lib/docker/volumes/`) | Thư mục bất kỳ trên máy | RAM |
| Dùng cho | Dữ liệu database, cần bền | Code khi dev, file cấu hình | Dữ liệu tạm |
| Xoá khi `down` | Không (trừ `down -v`) | Không bao giờ | Có |

- **Fedora dùng SELinux.** Bind mount một thư mục ở home vào container có thể bị `Permission denied` dù quyền file đúng. Thêm hậu tố `:Z` (nhãn riêng cho container này) hoặc `:z` (dùng chung giữa nhiều container): `- ./web:/app:Z`. Đừng tắt SELinux.
- Compose tự đặt **tên project** theo tên thư mục (`lab5-docker-compose`), container tên `lab5-docker-compose-web-1`, network `lab5-docker-compose_default`.
- `docker compose config` in ra file đã gộp và chuẩn hoá. Dùng để kiểm tra lỗi cú pháp YAML trước khi `up`.

**Lỗi hay gặp**

- `Error: Cannot find module 'express'`: bind mount che mất `node_modules` vì thiếu dòng `- /app/node_modules`, hoặc chưa `--build` lại sau khi thêm thư viện.
- `EACCES: permission denied, open '/app/index.js'` trên Fedora: SELinux chặn bind mount. Thêm `:Z`.
- `yaml: line 8: did not find expected key`: YAML thụt lề sai hoặc lẫn tab. YAML chỉ dùng dấu cách.
- Lab ghi `docker-composse ps -a` (sai chính tả) sẽ báo `command not found`. Lệnh đúng: `docker compose ps -a`.

**Bài tập**

🟢 *Cơ bản*: Xoá dòng `version`, đổi tên file thành `compose.yaml`, chạy `docker compose up -d` không cần `-f`. Sửa `web/public/index.html` và kiểm tra trình duyệt thấy thay đổi mà không cần build lại.

<details><summary>Gợi ý</summary>

Nếu trên Fedora bị lỗi quyền, đổi thành `- ./web:/app:Z`. Dọn: `docker compose down`.
</details>

🟡 *Thực hành*: Làm cho sửa `index.js` cũng tự reload: dùng `develop.watch` của Compose (tra docs "Compose Watch") hoặc đổi lệnh chạy sang `node --watch`.

<details><summary>Gợi ý</summary>

Cách nhanh: trong service web thêm `command: ["node", "--watch", "index.js"]`. Cách của Compose v2: bỏ bind mount, thêm

```yaml
    develop:
      watch:
        - action: sync+restart
          path: ./web
          target: /app
          ignore: [node_modules/]
```

rồi chạy `docker compose watch`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary><code>docker compose down</code> có xoá dữ liệu MySQL lưu trong named volume không?</summary>

Không. `down` chỉ xoá container và network. Named volume chỉ bị xoá khi thêm `-v` (`docker compose down -v`) hoặc `docker volume rm`. Bind mount thì không bao giờ bị Docker xoá, vì đó là thư mục của bạn.
</details>

## Lab6 · Compose nhiều service (web + Redis + MySQL) {017}

File lab: `docker-basic-operation/lab6-docker-compose-multi/docker-compose.yaml`

```
           máy bạn
  :8080 ─► web (Node, scale: 3?)     ← cùng network lab6_default
  :6379 ─► cache (redis:alpine)        web gọi Redis bằng host "cache"
  :3306 ─► db (mysql:5.7)              web gọi MySQL bằng host "db"
                └─ ./db (bind mount) → /var/lib/mysql
```

```yaml
  cache:
    image: redis:alpine
  db:
    image: mysql:5.7
    environment:
      - MYSQL_ROOT_PASSWORD=Linh#4321
      - MYSQL_DATABASE=testdb
    volumes:
      - ./db:/var/lib/mysql   # dữ liệu còn sau khi xoá container
```

Kiểm tra MySQL và nạp dữ liệu mẫu `test-db.sql`:

```bash
docker compose up -d
docker compose exec -T db mysql -uroot -p'Linh#4321' testdb < test-db.sql
docker compose exec db mysql -uroot -p'Linh#4321' -e 'SELECT * FROM testdb.employee;'
docker compose exec cache redis-cli ping      # PONG
```

**Đi sâu hơn: mạng và DNS giữa container**

- Compose tạo **một network bridge riêng** cho project. Mọi service trong đó gọi nhau bằng **tên service** nhờ DNS nội bộ của Docker (địa chỉ `127.0.0.11` trong container). Trong code Node, host Redis là `cache`, host MySQL là `db`, **không phải `localhost`**. `localhost` trong container là chính container đó.
- Mạng `bridge` **mặc định** của `docker run` (không có `--network`) **không** phân giải tên container. Tài liệu Docker khuyên dùng **user-defined bridge**: có DNS theo tên và cô lập tốt hơn.

```bash
docker network create mynet
docker run -d --name redis1 --network mynet redis:alpine
docker run --rm --network mynet alpine ping -c1 redis1   # phân giải được tên
```

- **`ports` chỉ cần khi truy cập từ máy bạn.** Các container trong cùng network gọi nhau qua port gốc mà không cần publish. Lab publish 6379 và 3306 ra máy là tiện để thử, nhưng ở môi trường thật đó là lỗ hổng: database lộ ra ngoài. Nếu cần, chỉ mở trên loopback: `127.0.0.1:3306:3306`.
- **Mật khẩu đang viết cứng trong file YAML.** Tách ra file `.env` (Compose tự đọc) và đưa `.env` vào `.gitignore`:

```yaml
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?chưa đặt biến}
```

- **Volume khai báo nhưng không dùng:** cuối file có `volumes: db:` (named volume), nhưng service lại dùng bind mount `./db`. Muốn dùng named volume thì viết `- db:/var/lib/mysql`. Trên Fedora, bind mount thư mục dữ liệu MySQL còn gặp thêm vấn đề quyền/SELinux, nên named volume ít rắc rối hơn.
- **`mysql:5.7` đã hết hỗ trợ (EOL 10/2023).** Dùng `mysql:8.4` (LTS) cho bài mới.

**Lỗi hay gặp**

- `Bind for 0.0.0.0:8080 failed: port is already allocated` khi `scale: 3`: ba bản sao của `web` **cùng muốn chiếm port 8080 của máy**. Chỉ một cái thắng. Cách sửa: bỏ port cố định (`- 3000` để Docker tự chọn port máy) hoặc đặt một load balancer phía trước (đó là Lab7).
- Web báo `connect ECONNREFUSED 127.0.0.1:3306`: code dùng `localhost` thay vì `db`.
- `Access denied for user 'root'` dù đã đổi mật khẩu trong YAML: MySQL chỉ đọc `MYSQL_ROOT_PASSWORD` **lần khởi tạo đầu tiên**, khi thư mục dữ liệu trống. Thư mục `./db` đã có dữ liệu cũ thì mật khẩu cũ vẫn giữ nguyên. Xoá dữ liệu (`rm -rf ./db` hoặc `down -v`) để khởi tạo lại.
- Web khởi động trước khi MySQL sẵn sàng và lỗi kết nối: xem `depends_on` + healthcheck ở Lab7.

**Bài tập**

🟢 *Cơ bản*: Chạy lab6 (bỏ `scale` hoặc bỏ port cố định), nạp `test-db.sql`, đếm số nhân viên phòng IT bằng SQL.

<details><summary>Lời giải</summary>

`docker compose exec db mysql -uroot -p'…' -e "SELECT COUNT(*) FROM testdb.employee WHERE department='IT';"` → 2. Dọn: `docker compose down`, rồi `sudo rm -rf ./db` nếu muốn xoá dữ liệu.
</details>

🟡 *Thực hành*: Chuyển mật khẩu ra `.env`, đổi sang named volume `dbdata`, đổi image `mysql:8.4`, và bỏ publish port 3306/6379. Chứng minh web vẫn gọi được `db` bằng tên.

<details><summary>Gợi ý</summary>

`docker compose exec web getent hosts db` phải in ra IP của container db. Từ máy bạn, `nc -zv localhost 3306` phải thất bại. Dọn: `docker compose down -v`.
</details>

🔴 *Thử thách*: Sửa `web/index.js` để route `/visits` tăng bộ đếm trong Redis (`INCR visits`) và trả về số lượt. Chạy 3 bản sao `web` không publish port, dùng `docker compose exec web` gọi curl nhiều lần. Bộ đếm có đúng không? Vì sao?

## Lab7 · Load balancer và Auto-restart {018}

File lab: `docker-basic-operation/lab7-docker-compose-load-balance/` (`docker-compose-load-balance.yaml`, `nginx.conf`).

```
trình duyệt :8080 ─► nginx (reverse proxy, restart: always)
                         │ upstream "web:3000"
                         ├──► web-1 (màu chữ ngẫu nhiên)
                         └──► web-2 (màu chữ khác)
```

```yaml
  web:
    build: { context: web }
    ports:
      - 3000              # chỉ ghi port container → Docker chọn port máy ngẫu nhiên
    deploy:
      replicas: 2         # 2 bản sao
      restart_policy:
        condition: always # ⚠️ không phải giá trị hợp lệ, xem bên dưới
    networks: [mynetwork]
  nginx:
    image: nginx
    restart: 'always'
    ports: ["8080:80"]
    volumes: ["./nginx.conf:/etc/nginx/nginx.conf"]
    depends_on: [web]
    networks: [mynetwork]
```

```nginx
http {
  upstream all { server web:3000; }    # "web" phân giải ra IP của CẢ 2 bản sao
  server { listen 80; location / { proxy_pass http://all/; } }
}
```

```bash
cd lab7-docker-compose-load-balance
docker compose -f docker-compose-load-balance.yaml up -d --build
for i in 1 2 3 4; do curl -s localhost:8080/index.html | grep welcome; done   # màu thay đổi
docker compose -f docker-compose-load-balance.yaml ps
```

Mỗi bản sao `web` khi khởi động sửa `index.html` với **màu ngẫu nhiên**, nên tải lại trang thấy màu đổi là bằng chứng nginx đang chia tải. Hàm "crash sau 15 giây" (đang comment cuối `index.js`) dùng để thử restart policy.

**Đi sâu hơn: restart policy**

| `restart:` (cấp service, giống `docker run --restart`) | Ý nghĩa |
|---|---|
| `no` (mặc định) | Không tự khởi động lại |
| `always` | Luôn khởi động lại, kể cả sau khi Docker daemon/máy khởi động lại |
| `on-failure[:N]` | Chỉ khi exit code khác 0, tối đa N lần |
| `unless-stopped` | Như `always`, trừ khi bạn đã `docker stop` thủ công |

- Trong `deploy.restart_policy`, Compose Specification chỉ chấp nhận `condition` là **`none`, `on-failure`, `any`** (mặc định `any`). `always` là giá trị của khoá `restart`, không phải của `deploy`. Viết cho rõ: ở service `web` dùng `restart: always` giống `nginx`.
- **Restart policy không phải health check.** Docker chỉ restart khi **process thoát**. App bị treo nhưng process vẫn sống thì Docker không làm gì; `HEALTHCHECK` chỉ đánh dấu `unhealthy`, Docker Engine thường không tự restart theo đó. Orchestrator như ECS, Kubernetes mới thay container unhealthy.
- **`depends_on` mặc định chỉ chờ container *start*, không chờ app *sẵn sàng*.** Muốn chờ thật sự, kết hợp healthcheck:

```yaml
services:
  web:
    depends_on:
      db:
        condition: service_healthy   # chờ healthcheck của db pass
        restart: true                # db restart thì web restart theo
  db:
    image: mysql:8.4
    healthcheck:
      test: ["CMD", "mysqladmin", "ping", "-h", "localhost"]
      interval: 10s
      retries: 5
```

Các điều kiện khác: `service_started` (mặc định), `service_completed_successfully` (cho job chạy một lần như migrate database).

- **Nginx chỉ phân giải DNS lúc khởi động.** Nếu bạn scale `web` từ 2 lên 4 khi nginx đang chạy, nginx vẫn chỉ biết 2 IP cũ. Phải `docker compose restart nginx`. Muốn tự động, dùng `resolver 127.0.0.11` kèm biến trong `proxy_pass`, hoặc proxy hiểu Docker như Traefik.
- **Network:** `web` và `nginx` chỉ nằm trong `mynetwork`. `cache` và `db` không khai báo `networks` nên nằm ở network `default`. Nghĩa là **web không gọi được db/cache** trong lab này. Muốn gọi được, thêm `mynetwork` cho db và cache (hoặc bỏ hết khai báo `networks` để mọi service chung `default`).

**Lỗi hay gặp**

- `502 Bad Gateway` từ nginx: nginx chạy nhưng không tới được `web:3000`. Kiểm tra: web có cùng network với nginx không, app có nghe port 3000 không (`docker compose logs web`).
- Nginx lỗi `host not found in upstream "web:3000"` rồi thoát: lúc nginx khởi động, `web` chưa có trong DNS. `restart: always` sẽ khởi động lại nginx cho tới khi được; cách sạch hơn là `depends_on` với `condition: service_healthy`.
- Trên Fedora, nginx báo `open() "/etc/nginx/nginx.conf" failed (13: Permission denied)`: SELinux chặn bind mount file. Viết `./nginx.conf:/etc/nginx/nginx.conf:ro,Z`.

**Bài tập**

🟢 *Cơ bản*: Bỏ comment đoạn "crash sau 15 giây" trong `web/index.js`, đặt `restart: always` cho web, build lại. Quan sát `docker compose ps` và cột `RESTARTS` / `STATUS` trong 1 phút.

<details><summary>Gợi ý</summary>

`watch -n2 docker compose -f docker-compose-load-balance.yaml ps`. Container thoát với code 101 và được khởi động lại liên tục. Docker tăng dần khoảng chờ giữa các lần restart để tránh vòng lặp quá nhanh. Đổi sang `restart: on-failure:3` để thấy nó dừng hẳn sau 3 lần.
</details>

🟡 *Thực hành*: Thêm `HEALTHCHECK`/`healthcheck` cho `web` và `depends_on: condition: service_healthy` cho nginx. Scale web lên 4 (`docker compose up -d --scale web=4`) và làm cho nginx nhận đủ 4 bản sao.

<details><summary>Gợi ý</summary>

Healthcheck dùng được vì image `node:18` có `curl`: `test: ["CMD", "curl", "-f", "http://localhost:3000/"]`. Sau khi scale, `docker compose restart nginx` (nginx chỉ phân giải DNS lúc khởi động). Kiểm tra bằng vòng lặp curl, đếm số màu khác nhau.
</details>

🔴 *Thử thách*: Sửa compose để `web` thực sự kết nối được `db` và `cache` (đang khác network), đồng thời không publish port database ra máy. Viết lý do cho từng thay đổi.

<details><summary>Gợi ý</summary>

Thêm `networks: [mynetwork]` cho `db` và `cache`, xoá `ports` của chúng. Kiểm tra: `docker compose exec web getent hosts db cache`. Lý do: DNS của Docker chỉ phân giải tên trong cùng network; DB không cần lộ ra máy vì chỉ web gọi nó.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Container có <code>restart: always</code>. Bạn chạy <code>docker stop</code>, rồi khởi động lại máy. Container có chạy lại không? Với <code>unless-stopped</code> thì sao?</summary>

`always`: **có**, khi daemon khởi động lại nó bật lại container dù bạn đã stop thủ công. `unless-stopped`: **không**, vì bạn đã chủ động dừng nó.
</details>

- `docker compose config`, `docker inspect`, `docker logs` là ba công cụ gỡ lỗi đầu tiên.
- Dùng AI để hỏi cũng được, nhưng kiểm tra lại với `--help` hoặc docs chính thức: AI hay gợi ý cú pháp cũ.

## Giới thiệu Amazon ECR và ECS {020-021}

**Amazon ECR (Elastic Container Registry):** registry **private** của AWS, giống Docker Hub nhưng nằm trong tài khoản AWS của bạn, phân quyền bằng IAM.

**Amazon ECS (Elastic Container Service):** dịch vụ **điều phối container** (orchestration) của AWS: quyết định chạy container ở đâu, thay container chết, gắn vào load balancer, cập nhật phiên bản mới.

```
Laptop ──docker push──► ECR repository (my-httpd:abc1234)
                              │ pull (dùng task execution role)
                              ▼
ECS Cluster ──► Service (desired count = 2) ──► Task ── container httpd
                                           └──► Task ── container httpd
     chạy trên: Fargate (serverless) hoặc EC2 (máy của bạn)
```

**Các khái niệm ECS:**

| Khái niệm | Giải thích | Tương đương bên Docker |
|---|---|---|
| **Cluster** | Nhóm logic chứa task và service | Một "máy Docker" lớn |
| **Task definition** | Bản mô tả JSON: image, CPU/RAM, port, biến môi trường, log, IAM role. Mỗi lần sửa tạo một **revision** mới (`my-task:1`, `my-task:2`) | Một file compose cho 1 nhóm container |
| **Task** | Một bản chạy của task definition, gồm 1 hoặc nhiều container | `docker compose up` một lần |
| **Service** | Giữ **N task luôn chạy**, thay task chết, gắn ALB, rolling update | `restart: always` + `replicas` + load balancer |

**Chạy trên đâu (capacity):**

| | **Fargate** | **EC2** |
|---|---|---|
| Quản lý server | Không: AWS lo | Bạn lo EC2, AMI, vá lỗi, scale máy |
| Tính tiền | Theo vCPU và GB RAM của **task**, tính theo giây (tối thiểu 1 phút) | Theo **EC2 instance**, dù chạy ít hay nhiều task |
| Hợp với | Người mới, tải biến động, ít vận hành | Tải lớn ổn định, cần GPU, muốn tối ưu chi phí bằng Reserved/Spot |

AWS còn có **ECS Managed Instances** (AWS quản lý EC2 hộ bạn). Với người mới, **Fargate** là lựa chọn đơn giản nhất và là thứ khoá học dùng.

**ECS khác EKS (Kubernetes, sẽ học ở chương sau):** ECS đơn giản, chỉ có trên AWS, không tốn phí control plane. EKS dùng Kubernetes chuẩn, chạy được ở mọi nơi nhưng phức tạp hơn và tốn phí control plane theo giờ.

**Các bài lab tiếp theo (bài 021):**
1. Build image và push lên ECR (máy local, thay cho Cloud9).
2. Chạy **Task** đơn giản trên ECS Fargate.
3. Chạy **Service** để task luôn có mặt.
4. Tìm hiểu **Cloud Map** để các service tìm thấy nhau.
5. Xoá toàn bộ resource.

**Câu hỏi tự kiểm tra**

<details><summary>Sửa biến môi trường trong task definition. Task đang chạy có tự nhận thay đổi không?</summary>

Không. Sửa task definition tạo **revision mới**; task đang chạy vẫn dùng revision cũ. Với service, bạn phải *update service* sang revision mới (ECS sẽ rolling deploy: chạy task mới, rồi dừng task cũ). Với task chạy lẻ, phải chạy task mới.
</details>

<details><summary>Service đặt desired count = 2, bạn "Stop" một task bằng tay. Chuyện gì xảy ra?</summary>

Service scheduler thấy chỉ còn 1 task, nhỏ hơn 2, nên **tự chạy task mới** thay thế. Muốn dừng hẳn phải đặt desired count = 0 hoặc xoá service.
</details>

## Lab · Build image và push lên ECR {022-023}

File lab: `docker-basic-operation/lab8-ecs-ecr-lab/build-custom-docker-image/` (Dockerfile httpd + `index.html`) và `hello-docker.sh`.

Video 023 dùng Cloud9. Vì Cloud9 không còn cho tài khoản mới, bạn làm **ngay trên Fedora** (đã có Docker + AWS CLI), hoặc trên một EC2 có gắn IAM role.

**Bước 1: build và chạy thử ở máy**

```bash
cd lab8-ecs-ecr-lab/build-custom-docker-image
docker build -t my-httpd .
docker run -dit --name my-httpd-app -p 8080:80 my-httpd
curl -s localhost:8080 | grep "first Docker app"
docker rm -f my-httpd-app
```

**Bước 2: tạo repository ECR và đăng nhập**

```bash
export AWS_REGION=ap-southeast-1
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export REPO=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/my-httpd

aws ecr create-repository --repository-name my-httpd --region $AWS_REGION \
  --image-scanning-configuration scanOnPush=true \
  --image-tag-mutability IMMUTABLE        # không cho ghi đè một tag đã có

aws ecr get-login-password --region $AWS_REGION \
  | docker login --username AWS --password-stdin $ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com
```

- Username luôn là chữ `AWS`. Mật khẩu là **token tạm thời, hết hạn sau 12 giờ**, nên phải chạy lại lệnh login khi hết hạn.
- `--password-stdin` để mật khẩu không nằm trong lịch sử shell.

**Bước 3: tag theo commit SHA và push**

```bash
TAG=$(git rev-parse --short HEAD)       # ví dụ 17d61f3
docker tag my-httpd:latest $REPO:$TAG
docker push $REPO:$TAG
aws ecr describe-images --repository-name my-httpd --region $AWS_REGION
aws ecr describe-image-scan-findings --repository-name my-httpd --image-id imageTag=$TAG --region $AWS_REGION
```

**Đi sâu hơn**

- **Vì sao tag theo commit SHA, không dùng `latest`:**
  - Nhìn tag là biết image build từ code nào, dễ truy vết khi lỗi.
  - Rollback chỉ là trỏ task definition về tag cũ.
  - `latest` bị ghi đè liên tục: hai task cùng `latest` có thể chạy hai phiên bản khác nhau. Bật **tag immutability** để ECR từ chối push đè tag đã có.
  - Trong CI/CD (các chương sau), pipeline tự lấy SHA của commit để làm tag.
- **Lifecycle policy:** ECR tính phí theo dung lượng lưu trữ, image cũ tích tụ rất nhanh. Lifecycle policy tự xoá image theo quy tắc, ECR áp dụng trong vòng 24 giờ sau khi image thoả điều kiện. Rule có `rulePriority` nhỏ hơn thì ưu tiên cao hơn.

```json
{
  "rules": [
    {
      "rulePriority": 1,
      "description": "Xoa image khong co tag sau 7 ngay",
      "selection": { "tagStatus": "untagged", "countType": "sinceImagePushed", "countUnit": "days", "countNumber": 7 },
      "action": { "type": "expire" }
    },
    {
      "rulePriority": 2,
      "description": "Chi giu 10 image moi nhat",
      "selection": { "tagStatus": "any", "countType": "imageCountMoreThan", "countNumber": 10 },
      "action": { "type": "expire" }
    }
  ]
}
```

```bash
aws ecr put-lifecycle-policy --repository-name my-httpd \
  --lifecycle-policy-text file://lifecycle.json --region $AWS_REGION
```

  Trên console có nút **preview** để xem trước image nào sẽ bị xoá trước khi áp dụng. Nên dùng.
- **Kiến trúc CPU:** build trên laptop x86_64 thì task Fargate phải chọn `X86_64`. Muốn chạy Fargate ARM (Graviton, rẻ hơn khoảng 20%) thì build `--platform linux/arm64`.

**Lỗi hay gặp**

- `no basic auth credentials` hoặc `denied: Your authorization token has expired`: chưa login hoặc token quá 12 giờ. Chạy lại lệnh `get-login-password | docker login`.
- `name unknown: The repository with name 'my-httpd' does not exist in the registry`: chưa tạo repo, hoặc sai **region** (repo ở ap-southeast-1, login/push ở region khác).
- `tag invalid: The image tag '…' already exists … and cannot be overwritten because the repository is immutable`: đúng như thiết kế; hãy dùng tag mới (commit mới).
- `AccessDeniedException … ecr:InitiateLayerUpload`: IAM user thiếu quyền push. Cần các quyền như `ecr:InitiateLayerUpload`, `ecr:UploadLayerPart`, `ecr:CompleteLayerUpload`, `ecr:PutImage` (managed policy `AmazonEC2ContainerRegistryPowerUser` có đủ).

💰 **Chi phí:** ECR private tính theo GB lưu trữ mỗi tháng (ước lượng khoảng 0,10 USD/GB-tháng) cộng phí truyền dữ liệu ra ngoài region. Image httpd khoảng vài chục MB nên gần như không đáng kể, nhưng hãy đặt lifecycle policy và xoá repo khi học xong.

**Bài tập**

🟢 *Cơ bản*: Push image `my-httpd` lên ECR với 2 tag: SHA commit hiện tại và `v1`. Kiểm tra trên console thấy cả hai tag trỏ cùng một digest.

<details><summary>Gợi ý</summary>

`docker tag my-httpd $REPO:v1 && docker push $REPO:v1`. Push lần 2 rất nhanh vì mọi layer đã có (`Layer already exists`). Cùng digest nghĩa là cùng một image.
</details>

🟡 *Thực hành*: Áp dụng lifecycle policy ở trên, dùng tính năng preview trên console để xem kết quả. Đọc kết quả scan on push và liệt kê các CVE mức HIGH/CRITICAL (nếu có).

<details><summary>Gợi ý</summary>

🔴 *Thử thách*: Viết script `push.sh` nhận tham số region, tự tạo repo nếu chưa có, login, build với tag `git rev-parse --short HEAD`, và **dừng lại với thông báo lỗi** nếu thư mục Git còn thay đổi chưa commit (để tag luôn khớp đúng code).

</details>

<details><summary>Vì sao không nên lưu image triển khai thật trên Docker Hub public mà dùng ECR?</summary>

</details>

## Lab · Chạy Task và Service trên ECS {025-026}

File lab dùng image đã push ở phần trước (`lab8-ecs-ecr-lab/ecs-ecr-lab/Dockerfile`). Các bước làm trên console như video; dưới đây là các khái niệm cần nắm và CLI tương ứng để bạn hiểu console làm gì phía sau.

**Bước 1: Cluster.** ECS → Clusters → Create, chọn **AWS Fargate (serverless)**. Cluster rỗng không tốn tiền.

**Bước 2: Task definition** (phần cốt lõi):

```json
{
  "family": "my-httpd-task",
  "requiresCompatibilities": ["FARGATE"],
  "networkMode": "awsvpc",
  "cpu": "256",
  "memory": "512",
  "runtimePlatform": { "cpuArchitecture": "X86_64", "operatingSystemFamily": "LINUX" },
  "executionRoleArn": "arn:aws:iam::<ACCOUNT_ID>:role/ecsTaskExecutionRole",
  "containerDefinitions": [
    {
      "name": "httpd",
      "image": "<ACCOUNT_ID>.dkr.ecr.ap-southeast-1.amazonaws.com/my-httpd:<SHA>",
      "portMappings": [{ "containerPort": 80, "protocol": "tcp" }],
      "essential": true,
      "logConfiguration": {
        "logDriver": "awslogs",
        "options": {
          "awslogs-group": "/ecs/my-httpd-task",
          "awslogs-region": "ap-southeast-1",
          "awslogs-stream-prefix": "ecs"
        }
      }
    }
  ]
}
```

- `cpu: 256` là 0,25 vCPU, nhỏ nhất của Fargate. Đi kèm memory 512 MiB, 1 GB hoặc 2 GB. CPU và RAM phải theo **các cặp hợp lệ** của Fargate.
- `essential: true`: container này chết thì cả task dừng.

**Bước 3: Run Task (bài 025).** Chọn cluster, launch type Fargate, VPC/subnet **public**, security group mở port 80, **Public IP: ENABLED**. Khi task `RUNNING`, mở tab Networking của task lấy public IP rồi truy cập `http://<ip>`.

```bash
aws ecs run-task --cluster my-cluster --launch-type FARGATE \
  --task-definition my-httpd-task \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-xxx],securityGroups=[sg-xxx],assignPublicIp=ENABLED}'
```

**Bước 4: Service (bài 026).** Task chạy lẻ dừng là thôi. **Service** giữ `desired count` task luôn chạy, thay task hỏng, có thể gắn **ALB** (Application Load Balancer) để có một địa chỉ cố định và chia tải.

```bash
aws ecs create-service --cluster my-cluster --service-name my-httpd-svc \
  --task-definition my-httpd-task --desired-count 2 --launch-type FARGATE \
  --network-configuration 'awsvpcConfiguration={subnets=[subnet-a,subnet-b],securityGroups=[sg-xxx],assignPublicIp=ENABLED}'
```

**Đi sâu hơn**

- **Task execution role và task role: hai role khác nhau, rất hay nhầm.**

| | **Task execution role** (`executionRoleArn`) | **Task role** (`taskRoleArn`) |
|---|---|---|
| Ai dùng | ECS/Fargate **agent**, trước và trong khi khởi động container | **Code app** bên trong container |
| Để làm gì | Pull image từ ECR, ghi log lên CloudWatch Logs, lấy secret từ Secrets Manager/SSM để nạp vào biến môi trường | Gọi AWS API: đọc S3, ghi DynamoDB, gửi SQS… |
| Policy thường dùng | `AmazonECSTaskExecutionRolePolicy` (AWS managed) | Tự viết theo least privilege |
| Trust | `ecs-tasks.amazonaws.com` | `ecs-tasks.amazonaws.com` |

  Ví dụ: app cần đọc file từ S3 thì cấp quyền S3 vào **task role**, không phải execution role. Container **không** nhìn thấy credentials của execution role.

- **awsvpc networking:** mỗi task có **ENI (card mạng ảo) và IP riêng trong VPC**, có security group riêng, giống một EC2 thu nhỏ. Fargate **bắt buộc** dùng `awsvpc`. Vì vậy:
  - Container trong cùng task gọi nhau qua `localhost` (chung network namespace, giống các container trong một Pod của Kubernetes).
  - Task ở **public subnet** cần **public IP** (hoặc NAT) để kéo image từ ECR. Task ở **private subnet** cần **NAT Gateway** hoặc **VPC endpoint** cho ECR/S3/CloudWatch Logs.
  - Security group của task phải mở port container (80) cho nguồn cần truy cập. Khi có ALB, chỉ mở cho SG của ALB.
- **Deployment của service:** mặc định là **rolling update**: chạy task revision mới, đợi healthy, rồi dừng task cũ. Bật **deployment circuit breaker** để ECS tự rollback khi task mới liên tục lỗi.
- **Log:** stdout/stderr của container đi vào CloudWatch Logs qua driver `awslogs`. Xem log ở tab *Logs* của task, hoặc `aws logs tail /ecs/my-httpd-task --follow`.

**Lỗi hay gặp**

- **Thiếu quyền tạo CloudWatch log group khi start task** (tài liệu 024 của khoá học). Task dừng ngay, *Stopped reason* có dạng:

  ```text
  ResourceInitializationError: failed to validate logger args: create stream has been retried 1 times:
  failed to create Cloudwatch log group: AccessDeniedException: User: arn:aws:sts::<id>:assumed-role/ecsTaskExecutionRole/...
  is not authorized to perform: logs:CreateLogGroup ...
  ```

  Nguyên nhân: console bật tuỳ chọn tự tạo log group (`"awslogs-create-group": "true"`), nhưng managed policy `AmazonECSTaskExecutionRolePolicy` chỉ có `logs:CreateLogStream` và `logs:PutLogEvents`, **không có `logs:CreateLogGroup`**. Cách sửa (chọn một):
  1. Tạo trước log group: `aws logs create-log-group --log-group-name /ecs/my-httpd-task`, nên đặt luôn retention: `aws logs put-retention-policy --log-group-name /ecs/my-httpd-task --retention-in-days 7`.
  2. Hoặc thêm inline policy cho `ecsTaskExecutionRole` cho phép `logs:CreateLogGroup` (giới hạn resource ở `arn:aws:logs:<region>:<account>:log-group:/ecs/*`).
- `CannotPullContainerError: … i/o timeout` hoặc `ResourceInitializationError: unable to pull secrets or registry auth`: task không ra được Internet để kéo image. Task ở public subnet nhưng **quên bật Public IP**, hoặc ở private subnet mà không có NAT/VPC endpoint.
- `CannotPullContainerError: … not found`: sai tên image/tag, hoặc image ở region khác.
- `Essential container in task exited` với exit code 1/137: app lỗi khi chạy (xem CloudWatch Logs) hoặc bị OOM vì RAM quá ít. Với lỗi `exec format error`: image ARM nhưng task chọn X86_64 (hoặc ngược lại).
- Task `RUNNING` nhưng không truy cập được IP: security group chưa mở port 80 cho IP của bạn.

💰 **Chi phí / an toàn**

- Fargate tính theo **vCPU-giờ và GB-giờ**, theo giây, tối thiểu 1 phút. Giá tham khảo ở US East (N. Virginia), Linux/x86: khoảng 0,0405 USD/vCPU-giờ và 0,0044 USD/GB-giờ; ARM rẻ hơn khoảng 20%. Singapore đắt hơn một chút.
- Một task 0,25 vCPU + 0,5 GB: khoảng 0,0123 USD/giờ, tức khoảng **0,30 USD/ngày, 9 USD/tháng** nếu quên tắt (ước lượng theo giá US East). Service 2 task thì gấp đôi.
- Cộng thêm **public IPv4** khoảng 0,005 USD/giờ cho mỗi task bật public IP, và **ALB** (nếu tạo) khoảng 0,02–0,03 USD/giờ cộng phí LCU.
- 20 GB ephemeral storage mỗi task đã được tính sẵn.
- ⚠️ Fargate **không có Free Tier** thường trực. Học xong lab nào, dừng lab đó: đặt desired count = 0 hoặc xoá service.

**Bài tập**

🟢 *Cơ bản*: Chạy task `my-httpd-task` bằng console, truy cập trang qua public IP, xem log truy cập của httpd trong CloudWatch Logs, rồi **Stop task**.

<details><summary>Gợi ý</summary>

Nếu task dừng với lỗi `logs:CreateLogGroup`, áp dụng cách sửa ở mục Lỗi hay gặp. Mỗi request vào trang tạo một dòng access log trong log stream `ecs/httpd/<task-id>`.

**Câu hỏi tự kiểm tra**

<details><summary>1. App trong container báo <code>AccessDenied</code> khi đọc S3, nhưng bạn đã thêm quyền S3 vào <code>ecsTaskExecutionRole</code>. Sai ở đâu?</summary>

</details>

## Cloud Map, tổng kết và xoá resources {027-028}

**Bài toán:** service `web` cần gọi service `api`. IP của task Fargate **thay đổi** mỗi lần task được thay mới. Hardcode IP thì hỏng ngay sau lần deploy tiếp theo.

**AWS Cloud Map** là dịch vụ **service discovery** (đăng ký và tìm kiếm dịch vụ): ECS tự đăng ký IP của từng task vào Cloud Map khi task chạy, và gỡ ra khi task dừng. Service khác tìm bằng **tên DNS**.

```
namespace private "local" (= Route 53 private hosted zone trong VPC)
   api.local  ──► A record: 10.0.1.23, 10.0.2.45  (IP của các task api, tự cập nhật)
web task: curl http://api.local:8080
```

- Giống DNS nội bộ của Docker Compose (gọi `db`, `cache` bằng tên) mà bạn đã dùng ở Lab6/Lab7, nhưng ở quy mô VPC.
- Namespace **private DNS** tạo ra một **Route 53 private hosted zone** gắn với VPC.
- **Đi sâu hơn:** với ứng dụng ECS mới, AWS giới thiệu **ECS Service Connect**, dùng Cloud Map làm namespace bên dưới và thêm một proxy (Envoy) do AWS quản lý: có retry, metric kết nối, tên ngắn (`http://api:8080`). Khi cần kết nối giữa nhiều VPC hoặc nhiều tài khoản, có thêm **Amazon VPC Lattice**. Cloud Map DNS thuần vẫn hữu ích cho client chỉ cần tra DNS.
- DNS có **TTL**: client có thể còn dùng IP cũ trong vài giây sau khi task bị thay. App nên có retry.

**Tổng kết chương**

| Bạn đã học | Dùng để |
|---|---|
| Container, namespace, cgroup | Hiểu container là process bị cô lập |
| Dockerfile, layer, cache, multistage, non-root | Build image nhỏ, nhanh, an toàn |
| Compose, network, volume, healthcheck, restart | Chạy cụm nhiều service ở máy local |
| ECR + tag SHA + lifecycle | Lưu image private, có phiên bản rõ ràng |
| ECS Fargate: task definition, task, service, IAM role, awsvpc | Chạy container trên AWS không cần quản lý server |

**Xoá resources (làm theo thứ tự, ở đúng region đã dùng):**

```bash
R=ap-southeast-1
# 1. Service: hạ về 0 rồi xoá
aws ecs update-service --cluster my-cluster --service my-httpd-svc --desired-count 0 --region $R
aws ecs delete-service --cluster my-cluster --service my-httpd-svc --force --region $R
# 2. Task chạy lẻ còn sót
aws ecs list-tasks --cluster my-cluster --region $R
aws ecs stop-task --cluster my-cluster --task <task-arn> --region $R
# 3. Cluster
aws ecs delete-cluster --cluster my-cluster --region $R
# 4. Task definition: deregister từng revision (rồi có thể delete)
aws ecs deregister-task-definition --task-definition my-httpd-task:1 --region $R
# 5. ECR repo (kèm mọi image)
aws ecr delete-repository --repository-name my-httpd --force --region $R
# 6. CloudWatch log group
aws logs delete-log-group --log-group-name /ecs/my-httpd-task --region $R
# 7. Cloud Map: xoá service trong namespace, rồi xoá namespace
aws servicediscovery list-namespaces --region $R
aws servicediscovery delete-namespace --id <ns-id> --region $R
```

- Còn phải kiểm tra: **ALB và target group**, **security group** tự tạo, **NAT Gateway / VPC endpoint** (nếu đã tạo ở bài thử thách).
- Cluster tạo bằng console có thể đi kèm một **CloudFormation stack**. Kiểm tra CloudFormation xem còn stack nào của ECS không.
- 💰 Route 53 hosted zone do namespace Cloud Map tạo ra tính phí theo tháng (khoảng 0,50 USD/hosted zone/tháng). Nhỏ, nhưng sẽ tính mãi nếu quên.
- Ở máy local: `docker compose down -v` trong từng thư mục lab, rồi `docker system prune -a` nếu muốn lấy lại dung lượng đĩa (xoá mọi image không dùng).

**Bài tập**

🟢 *Cơ bản*: Làm đủ danh sách xoá ở trên. Sau đó vào **Billing → Bills** (hoặc Cost Explorer) xem chi phí ECS/ECR của chương này là bao nhiêu.

<details><summary>Gợi ý</summary>

Mở console ECS, ECR, CloudWatch Logs, Cloud Map, EC2 (Load Balancers, Security Groups, Network Interfaces) ở **đúng region**. ENI của task Fargate tự biến mất khi task dừng. ENI nào còn "in-use" nghĩa là còn task hoặc endpoint đang chạy.
</details>

🟡 *Thực hành*: Tạo hai service `web` và `api` trong cùng cluster, dùng service discovery (Cloud Map) hoặc Service Connect để `web` gọi được `api` bằng tên. Kiểm tra bằng **ECS Exec** (`aws ecs execute-command`) chạy `curl` từ trong task `web`.

<details><summary>Gợi ý</summary>

ECS Exec cần: service bật `--enable-execute-command`, **task role** có quyền `ssmmessages:*` cần thiết, và Session Manager plugin cài trên máy bạn. Đây là bài tốt để phân biệt task role và execution role. Dọn dẹp xong nhớ xoá namespace.
</details>

🔴 *Thử thách*: Đưa ứng dụng `lab7` (web Node + nginx) lên ECS: build và push 2 image lên ECR, viết một task definition chứa **cả hai container** (nginx proxy sang `localhost:3000` vì chung awsvpc), chạy thành service. Ghi lại những gì phải đổi so với file compose.

<details><summary>Gợi ý</summary>

Những điểm phải đổi: (1) `nginx.conf` dùng `server localhost:3000` thay vì `web:3000`, vì các container trong một task chung network namespace. (2) Không bind mount `nginx.conf` từ máy được: phải `COPY` nó vào image nginx riêng. (3) `restart`/`replicas` của compose được thay bằng `desiredCount` của service. (4) Đặt `dependsOn` với `condition: HEALTHY` trong container definition để nginx chờ web. (5) Fargate x86 hay ARM phải khớp kiến trúc image.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao không gọi service khác bằng IP của task?</summary>

IP của task Fargate thay đổi mỗi lần task được tạo lại (deploy, scale, task chết được thay). Gọi bằng tên DNS (Cloud Map) hoặc qua Service Connect/ALB thì địa chỉ ổn định, còn danh sách IP phía sau được cập nhật tự động.
</details>
