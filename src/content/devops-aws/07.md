# Chương 07 · Thao tác cơ bản với Git

Học xong chương này, bạn **quản lý code bằng Git như trong một team thật**: tạo repository, kết nối GitHub bằng SSH key, làm việc theo nhánh `develop` / `feature` / `release`, gửi pull request để review, giải quyết conflict, và quan trọng nhất là **sửa sai an toàn** (revert, reset, stash, reflog) mà không làm mất code của ai.

Những lệnh bạn sẽ gõ nhiều nhất cả chương:

```bash
git status                     # đang ở nhánh nào, file nào đã sửa / đã stage
git add <file>                 # đưa thay đổi vào staging area
git commit -m "feat: ..."      # chụp một snapshot
git switch -c feature/F001     # tạo và chuyển sang nhánh mới
git push -u origin feature/F001
git pull                       # lấy code mới về (fetch + merge)
git log --oneline --graph --all
```

Code lab của chương: `devops-for-beginner/git-basic-operation/` (lab1 … lab4 `.sh`, là ghi chú lệnh để gõ từng bước).

## Git là gì, các mô hình workflow và nhà cung cấp Git {001-004}

**Khái niệm cốt lõi**

**Git** là hệ thống quản lý phiên bản *phân tán*: mỗi người clone về đều có **toàn bộ lịch sử** của dự án trên máy mình. Bạn commit, xem lịch sử, tạo nhánh mà không cần mạng; chỉ khi `push`/`pull` mới cần nói chuyện với server.

Ví dụ đời thường: commit giống như **chụp ảnh** toàn bộ thư mục dự án tại một thời điểm, kèm ghi chú "ảnh này chụp gì". Bạn có thể quay lại bất kỳ tấm ảnh nào.

**Ba khu vực của Git**

```
 Working tree            Staging area (index)          Repository (.git)
 (file bạn đang sửa)     (những gì SẼ vào commit)       (các commit đã chụp)
        │   git add  ───────────▶ │   git commit ─────────────▶ │
        │ ◀─────────── git restore --staged                     │
        │ ◀──────────────────────────────── git restore / switch│
                                                    git push ──▶ Remote (GitHub)
```

- **Staging area** cho phép bạn chọn *một phần* thay đổi để commit, ví dụ sửa 5 file nhưng chỉ commit 2 file liên quan.

**Đi sâu hơn: Git lưu dữ liệu thế nào**

- Git không lưu "đoạn khác nhau" giữa các phiên bản, mà lưu **snapshot**. File không đổi thì commit mới chỉ trỏ lại bản cũ, không tốn thêm chỗ.
- Bên trong `.git/objects` có 3 loại object chính, mỗi object được đặt tên bằng **mã băm** (hash SHA-1, 40 ký tự hex):
  - **blob**: nội dung một file.
  - **tree**: một thư mục (danh sách tên file → blob, thư mục con → tree).
  - **commit**: trỏ tới một tree gốc + commit cha + tác giả + thông điệp.
- **Branch** chỉ là một file nhỏ chứa hash của một commit (`.git/refs/heads/develop`). Tạo nhánh vì thế gần như tức thì.
- **HEAD** là con trỏ "bạn đang đứng ở đâu", thường trỏ vào một branch. Khi bạn commit, branch đó tiến lên commit mới.

```
            HEAD
             │
             ▼
           develop
             │
 A ◀── B ◀── C ◀── D          (mỗi commit trỏ về commit cha)
       ▲
     master
```

```bash
git cat-file -p HEAD          # xem nội dung commit: tree, parent, author
git cat-file -p HEAD^{tree}   # xem tree: danh sách file và hash của chúng
cat .git/HEAD                 # ref: refs/heads/develop
```

**Các mô hình workflow (video 003)**

| Mô hình | Nhánh chính | Hợp với | Điểm yếu |
|---|---|---|---|
| **GitFlow** | `master` (bản đã phát hành), `develop` (tích hợp), `feature/*`, `release/*`, `hotfix/*` | Phần mềm phát hành theo phiên bản (app mobile, bản cài đặt), cần hỗ trợ nhiều phiên bản song song | Nhiều nhánh, merge nhiều, nhánh feature sống lâu dễ conflict |
| **GitHub Flow** | `main` + nhánh feature ngắn, merge qua PR, deploy liên tục | Web app, API, deploy nhiều lần mỗi ngày | Cần CI/CD và test tự động tốt |
| **Trunk-based** | Mọi người commit vào `main` (trực tiếp hoặc nhánh rất ngắn, dưới 1–2 ngày), tính năng chưa xong ẩn bằng *feature flag* | Team trưởng thành, CI/CD mạnh | Đòi hỏi kỷ luật và test tự động rất tốt |

Ngay tác giả của GitFlow (Vincent Driessen) năm 2020 đã thêm ghi chú: với web app được deploy liên tục, nên dùng mô hình đơn giản hơn như GitHub Flow. Khoá học dùng GitFlow vì nó dạy được *đủ mọi loại nhánh*; khi đi làm, hãy theo quy ước của team.

**Các nhà cung cấp Git (video 004)**

| Nhà cung cấp | Điểm nổi bật |
|---|---|
| **GitHub** | Phổ biến nhất, GitHub Actions cho CI/CD, cộng đồng mã nguồn mở |
| **GitLab** | CI/CD tích hợp rất mạnh, có thể tự cài (self-hosted) |
| **Bitbucket** | Hệ sinh thái Atlassian (Jira, Confluence) |
| **AWS CodeCommit** | Nằm trong AWS, xác thực bằng IAM. Từng ngừng nhận khách mới 7/2024, **mở lại từ 11/2025** (xem phần CodeCommit) |

Git là công cụ, GitHub/GitLab là *dịch vụ lưu trữ* Git kèm thêm pull request, issue, CI/CD. Chuyển nhà cung cấp chỉ cần `git push` sang remote mới, lịch sử giữ nguyên.

## Lab1–Lab2 · Cài Git, tạo repository và thêm SSH key lên GitHub {005-006}

**Lab1 · Cài đặt Git và công cụ giao diện**

Video hướng dẫn trên Windows (Git Bash + Sourcetree). Trên **Fedora** của bạn:

```bash
sudo dnf install -y git
git --version

# Cấu hình một lần trên mỗi máy
git config --global user.name  "Tên Của Bạn"
git config --global user.email "email-dùng-cho-github@example.com"
git config --global init.defaultBranch main      # nhánh mặc định khi git init
git config --global core.editor "nano"           # hoặc vim, "code --wait"
git config --global pull.rebase false            # git pull = fetch + merge (dễ hiểu cho người mới)
git config --list --show-origin                  # xem mọi cấu hình và nằm ở file nào

git clone https://github.com/cloudacademy/react-webapp.git    # lab1: clone repo public
```

- **Sourcetree không có bản cho Linux.** Thay thế trên Fedora: tab *Source Control* của **VS Code** (kèm extension *Git Graph*), `gitk --all` và `git gui` (gói `gitk`, `git-gui`), hoặc GitKraken. Dạng dòng lệnh: `git log --oneline --graph --all --decorate` là đủ để xem cây nhánh.
- Thứ tự ưu tiên cấu hình: `--system` (cả máy) → `--global` (`~/.gitconfig`) → `--local` (`.git/config` của từng repo). Cấp sau thắng.

**Lab2 · Tạo repository và kết nối bằng SSH key**

GitHub đã bỏ đăng nhập bằng mật khẩu cho lệnh Git từ 2021. Bạn chọn một trong hai:
- **HTTPS + Personal Access Token** (hoặc lệnh `gh auth login` của GitHub CLI).
- **SSH key**: tạo một lần, dùng mãi, không phải gõ token. Lab dùng cách này.

```bash
ssh-keygen -t ed25519 -C "email-dùng-cho-github@example.com"   # Enter chọn ~/.ssh/id_ed25519, NÊN đặt passphrase
eval "$(ssh-agent -s)"            # Fedora desktop thường đã có agent chạy sẵn
ssh-add ~/.ssh/id_ed25519         # nạp key để không phải gõ passphrase mỗi lần
cat ~/.ssh/id_ed25519.pub         # copy dòng này
# GitHub → Settings → SSH and GPG keys → New SSH key → dán vào
ssh -T git@github.com             # mong đợi: "Hi <user>! You've successfully authenticated..."
git clone git@github.com:<user>/<repo>.git
```

Phần PowerShell trong `lab2-create-repo-add-SSH-key.sh` chỉ dành cho Windows. Trên Linux, các bước tương đương là `eval "$(ssh-agent -s)"` và `ssh-add` như trên.

**Đi sâu hơn**

- **ed25519** là loại key GitHub khuyên dùng: ngắn, nhanh, an toàn. Chỉ dùng RSA (`-t rsa -b 4096`) khi hệ thống cũ không hỗ trợ ed25519.
- **Remote** là tên viết tắt cho địa chỉ server. `origin` là tên mặc định khi clone.

```bash
git remote -v                                         # xem remote đang dùng
git remote set-url origin git@github.com:<user>/<repo>.git   # đổi từ HTTPS sang SSH
```

- Tạo repo từ thư mục có sẵn trên máy, thay vì clone:

```bash
mkdir demo-git && cd demo-git
git init
echo "# Demo" > README.md
git add README.md && git commit -m "chore: initial commit"
git remote add origin git@github.com:<user>/demo-git.git
git push -u origin main          # -u: ghi nhớ nhánh upstream, lần sau chỉ cần git push
```

- **`.gitignore`**: liệt kê những thứ không bao giờ được commit. Tạo ngay từ commit đầu tiên:

```gitignore
# .gitignore
.env
*.pem
*.tfstate*
.terraform/
node_modules/
*.log
.DS_Store
```

  `.gitignore` chỉ có tác dụng với file **chưa được track**. File đã commit rồi thì phải gỡ khỏi index: `git rm --cached <file>` rồi commit. Mẫu sẵn cho từng ngôn ngữ: repo `github/gitignore`.

**Lỗi hay gặp & cách sửa**

- `git@github.com: Permission denied (publickey).` → chưa thêm public key lên GitHub, hoặc agent chưa nạp key. Chạy `ssh-add -l` và `ssh -vT git@github.com` để xem key nào đang được thử.
- `remote: Support for password authentication was removed …` → bạn đang dùng HTTPS kèm mật khẩu. Chuyển remote sang SSH hoặc dùng token.
- `Author identity unknown *** Please tell me who you are.` → chưa cấu hình `user.name` / `user.email`.
- `error: src refspec main does not match any` → chưa có commit nào, hoặc nhánh của bạn tên `master` chứ không phải `main` (`git branch` để xem).

**Bài tập**

🟢 *Cơ bản*: Trên Fedora, tạo SSH key ed25519 có passphrase, thêm lên GitHub, tạo repo **private** `demo-git`, clone về bằng SSH và push một commit README.

🟡 *Thực hành*: Bạn có 2 tài khoản GitHub (cá nhân và công ty) với 2 key khác nhau. Cấu hình `~/.ssh/config` để `git clone git@github-work:org/repo.git` dùng key công ty, còn `git@github.com:...` dùng key cá nhân.

<details><summary>Gợi ý</summary>

```bash
# ~/.ssh/config
Host github.com
    IdentityFile ~/.ssh/id_ed25519
    IdentitiesOnly yes
Host github-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_work
    IdentitiesOnly yes
```

Trong repo công ty, đặt email riêng: `git config user.email "ban@congty.com"` (không có `--global`).
</details>

🔴 *Thử thách*: Commit trên GitHub hiện "Unverified" hay không có nhãn gì? Tìm cách **ký commit bằng chính SSH key** để GitHub hiện nhãn *Verified*.

<details><summary>Gợi ý</summary>

```bash
git config --global gpg.format ssh
git config --global user.signingkey ~/.ssh/id_ed25519.pub
git config --global commit.gpgsign true
```

Trên GitHub, thêm cùng public key đó một lần nữa với loại **Signing Key** (*Settings → SSH and GPG keys*). Commit mới sẽ hiện *Verified*.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Bạn lỡ commit file <code>.env</code>, rồi mới thêm <code>.env</code> vào <code>.gitignore</code>. File có biến mất khỏi repo không?</summary>

Không. `.gitignore` không ảnh hưởng file đã được track. Phải `git rm --cached .env` rồi commit. Và vì file đã nằm trong **lịch sử**, nếu chứa secret thì phải coi như secret đã lộ (xem phần cuối chương).

## Lab3–Lab5 · Nhánh develop, feature, release và Pull Request {007-009}

**Khái niệm cốt lõi: GitFlow trong 3 lab**

```
master   ●─────────────────────────────────●  v1.0.0 (tag)
          \                               / \
release    \                    ●───●────●   \        ← chỉ sửa bug, chuẩn bị phát hành
            \                  /          \   \
develop      ●────●──────●────●────────────●───●      ← nhánh tích hợp
                   \    /
feature/F001        ●──●                              ← mỗi tính năng một nhánh
```

| Lab | Việc làm | Lệnh chính |
|---|---|---|
| Lab3 (`lab3-create-develop-branch.sh`) | Tạo `develop` từ `master`, push lên | `git switch -c develop`, `git push -u origin develop` |
| Lab4 (`lab4-protect-branch-develop-and-master.sh`) | Protect `master` và `develop`, làm `feature/F001`, mở PR vào `develop`, review rồi merge | `git switch -c feature/F001 develop` |
| Lab5 | Tạo `release/1.0.0` từ `develop`, chốt bản, merge vào `master` + gắn tag, merge ngược về `develop` | `git tag -a v1.0.0` |

```bash
# Lab3
git switch -c develop                     # = git checkout -b develop (cú pháp cũ trong lab)
git add index.html README.md              # nên add từng file thay vì "git add ."
git commit -m "feat: add index page"
git push -u origin develop

# Lab4
git switch develop && git pull
git switch -c feature/F001
# ... sửa code ...
git commit -am "feat(F001): add login form"
git push -u origin feature/F001
# Trên GitHub: Compare & pull request, base: develop ← compare: feature/F001

# Lab5
git switch develop && git pull
git switch -c release/1.0.0
# ... chỉ sửa bug nhỏ, cập nhật version, changelog ...
git push -u origin release/1.0.0
# PR release/1.0.0 → master, merge xong:
git switch master && git pull
git tag -a v1.0.0 -m "Release 1.0.0"
git push origin v1.0.0                    # tag KHÔNG tự lên theo git push thường
# PR (hoặc merge) master → develop để develop có các bản sửa từ release
```

**Pull Request (PR) và Protect branch**

- **PR** là đề nghị "hãy merge nhánh của tôi vào nhánh kia", kèm chỗ để review, bình luận từng dòng và chạy CI.
- **Protect branch** (GitHub: *Settings → Branches* hoặc *Rules → Rulesets*) cho `master`/`develop`:
  - Cấm push trực tiếp, bắt buộc qua PR.
  - Bắt buộc ít nhất 1 người **approve**.
  - Bắt buộc CI (status check) xanh.
  - Cấm force push và cấm xoá nhánh.
- Thử `git push origin develop` sau khi đã protect: bạn sẽ nhận `remote: error: GH006: Protected branch update failed`. Đó là kết quả mong muốn.

> ⚠️ Với gói **GitHub Free**, luật protect branch/ruleset chỉ được *áp dụng* cho repo **public**. Repo private cần gói trả phí (Pro, Team…). Nếu lab của bạn là repo private trên tài khoản free mà protect "không có tác dụng", hãy tạo một repo public để tập (không chứa gì bí mật), hoặc kiểm tra lại trang tài liệu vì chính sách có thể thay đổi.

**Đi sâu hơn: merge, squash hay rebase**

GitHub cho 3 cách merge PR:

| Cách | Lịch sử trên nhánh đích | Khi nào dùng |
|---|---|---|
| **Create a merge commit** | Giữ mọi commit + 1 commit merge | GitFlow, muốn thấy rõ "feature này vào lúc nào" |
| **Squash and merge** | Gộp cả PR thành **1 commit** | Nhánh feature có nhiều commit lặt vặt ("fix typo", "wip") |
| **Rebase and merge** | Đặt lại từng commit lên đầu nhánh đích, không có commit merge | Muốn lịch sử thẳng, mỗi commit đều sạch |

- **Fast-forward**: nếu nhánh đích không có gì mới, Git chỉ "kéo con trỏ" lên mà không tạo commit merge. GitFlow dùng `git merge --no-ff` để luôn có commit merge đánh dấu.
- **`git rebase develop`** (trên nhánh feature của bạn) viết lại commit của bạn để nằm trên đầu `develop` mới nhất. Lịch sử đẹp, nhưng **đổi hash** của commit.
- **Quy tắc vàng của rebase:** chỉ rebase nhánh *của riêng bạn* và chưa ai khác dùng. Rebase nhánh chung rồi `push --force` sẽ làm hỏng lịch sử của đồng nghiệp. Nếu buộc phải force push, dùng `git push --force-with-lease` (từ chối nếu trên remote có commit mới bạn chưa thấy).

**Đi sâu hơn: đặt tên commit và phiên bản**

- **Conventional Commits**: `<type>(scope): mô tả`. Type hay dùng: `feat` (tính năng), `fix` (sửa lỗi), `docs`, `refactor`, `test`, `chore`, `ci`. Thay đổi phá vỡ tương thích: thêm `!` (`feat!: ...`) hoặc dòng `BREAKING CHANGE:` ở phần thân. Công cụ có thể từ đó tự sinh changelog và tự tăng version.
- **Semantic Versioning** `MAJOR.MINOR.PATCH`: tăng MAJOR khi phá vỡ tương thích, MINOR khi thêm tính năng tương thích, PATCH khi chỉ sửa lỗi. Ví dụ `1.4.2 → 1.5.0` (thêm tính năng), `1.5.0 → 2.0.0` (đổi API).
- **Tag**: *annotated tag* (`-a`, có người tạo, ngày, thông điệp) cho bản phát hành; *lightweight tag* chỉ là cái tên. Xem: `git tag -n`, `git show v1.0.0`.

**Lỗi hay gặp & cách sửa**

- `! [rejected] develop -> develop (fetch first)` → trên remote có commit bạn chưa có. Chạy `git pull` (giải quyết conflict nếu có) rồi push lại. **Đừng** `--force` trên nhánh chung.
- `fatal: The current branch feature/F001 has no upstream branch.` → lần đầu push nhánh mới, dùng `git push -u origin feature/F001`.
- Mở PR thấy cả chục commit lạ → bạn tạo feature từ `master` thay vì `develop`, hoặc chọn sai *base branch* trong PR.
- Đã merge `release` vào `master` nhưng quên merge về `develop` → bản sửa bug sẽ "biến mất" ở lần release sau. Luôn merge ngược.

🟡 *Thực hành*: Bật protect cho `develop` (cần PR + 1 approval + cấm force push). Chứng minh push thẳng bị chặn. Thêm một file `.github/CODEOWNERS` để mọi PR sửa thư mục `infra/` phải được bạn review.

<details><summary>Gợi ý</summary>

Nội dung `CODEOWNERS`: `/infra/ @<tên-github-của-bạn>`. Trong luật protect, bật *Require review from Code Owners*. Lưu ý chính bạn không tự approve được PR của mình; hãy nhờ một tài khoản thứ hai, hoặc chỉ quan sát rằng nút Merge bị khoá.
</details>

🔴 *Thử thách*: Đang có `release/1.0.0` thì production phát hiện lỗi nghiêm trọng ở `v1.0.0`. Làm **hotfix** theo GitFlow ra `v1.0.1`, đảm bảo bản sửa có mặt ở `master`, `develop` *và* nhánh release đang mở.

<details><summary>Hướng giải</summary>

```bash
git switch -c hotfix/1.0.1 v1.0.0      # tạo từ tag đang chạy trên production
# sửa lỗi, commit "fix: ..."
# PR hotfix/1.0.1 → master, merge, rồi:
git switch master && git pull && git tag -a v1.0.1 -m "Hotfix 1.0.1" && git push origin v1.0.1
# merge hotfix vào develop và release/1.0.0 (hoặc cherry-pick commit sửa lỗi):
git switch release/1.0.0 && git cherry-pick <hash-commit-fix>
```

Điểm mấu chốt: hotfix tạo từ **tag production**, không phải từ `develop` (vì `develop` chứa tính năng chưa phát hành).
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. PR có 15 commit "wip", "fix typo". Bạn chọn cách merge nào?</summary>

**Squash and merge**: cả PR thành một commit sạch trên nhánh đích, đặt tên theo Conventional Commits. Lịch sử chi tiết vẫn xem được trong PR.
</details>

<details><summary>2. Vì sao không nên <code>git rebase</code> rồi <code>push --force</code> lên <code>develop</code>?</summary>

Rebase đổi hash các commit. Đồng nghiệp đã có commit cũ trên máy họ; khi họ pull, Git thấy hai lịch sử khác nhau và tạo commit trùng lặp hoặc conflict hàng loạt, thậm chí làm mất commit của người khác bị ghi đè trên remote.
</details>

## Lab6 · Revert một commit {010}

**Khái niệm cốt lõi**

`git revert <commit>` tạo **một commit mới có nội dung ngược lại** commit cũ. Commit lỗi vẫn nằm trong lịch sử, chỉ là tác dụng của nó bị huỷ.

```
Trước:  A ── B ── C(lỗi) ── D                       ← develop (đã push, cả team đang dùng)
Revert: A ── B ── C(lỗi) ── D ── C'(revert của C)   ← lịch sử chỉ TIẾN lên, không viết lại
```

Đây là cách **an toàn duy nhất** để huỷ commit **đã push lên nhánh chung**, vì không ai phải sửa lại lịch sử trên máy của họ.

```bash
git log --oneline                     # tìm hash commit lỗi, ví dụ a1b2c3d
git revert a1b2c3d                    # mở editor để sửa thông điệp, mặc định: Revert "..."
git revert --no-edit a1b2c3d          # dùng luôn thông điệp mặc định
git revert HEAD~2..HEAD               # revert 2 commit gần nhất (mỗi commit một commit revert)
git revert -n a1b2c3d b4c5d6e         # -n: gộp nhiều revert, tự commit một lần
git push
```

Trên GitHub, PR đã merge có sẵn nút **Revert**, tạo ra một PR mới đảo ngược PR cũ.

**Đi sâu hơn**

- **Revert một commit merge** phải chỉ rõ "giữ phía cha nào": `git revert -m 1 <hash-merge>`. `-m 1` nghĩa là giữ nhánh đích (nhánh bạn đã merge vào), bỏ đi những gì nhánh feature mang vào.
- ⚠️ Sau khi revert một merge, nếu sau này merge lại *cùng nhánh feature đó*, Git coi các commit cũ "đã có rồi" và **không mang lại**. Phải *revert cái revert* trước (`git revert <hash-của-commit-revert>`), rồi mới merge phần sửa mới.
- Revert cũng có thể conflict (nếu các commit sau đã sửa cùng dòng). Cách xử lý giống phần Resolve conflict, rồi `git revert --continue`.
- So với các lệnh khác (chi tiết ở phần reset):

| Lệnh | Tác động | Đã push lên nhánh chung? |
|---|---|---|
| `git revert` | Thêm commit mới đảo ngược | **An toàn** |
| `git reset` | Kéo con trỏ nhánh lùi, "xoá" commit khỏi nhánh | Chỉ dùng trên nhánh riêng, chưa push |
| `git restore` | Bỏ thay đổi *chưa commit* của file | Không liên quan lịch sử |

**Lỗi hay gặp & cách sửa**

- `error: commit 9f8e7d6 is a merge but no -m option was given.` → bạn revert commit merge, thêm `-m 1`.
- `error: could not revert a1b2c3d... hint: after resolving the conflicts, mark the corrected paths` → có conflict. Sửa file, `git add`, rồi `git revert --continue` (hoặc `git revert --abort` để huỷ).
- Revert xong push bị chặn vì nhánh được protect → làm revert trên một nhánh mới (`revert/xxx`) rồi mở PR, đúng quy trình.

**Bài tập**

🟢 *Cơ bản*: Trên `develop`, tạo 3 commit (A, B, C), mỗi commit thêm một dòng vào `index.html`. Revert commit B. Kiểm tra file chỉ mất dòng của B.

🟡 *Thực hành*: Merge `feature/F002` vào `develop` bằng `--no-ff`, rồi revert cả commit merge đó. Sau đó thêm một commit sửa lỗi vào `feature/F002` và tìm cách đưa *toàn bộ* tính năng trở lại `develop`.

<details><summary>Gợi ý</summary>

`git revert -m 1 <hash-merge>`. Muốn đưa lại: trên `develop` chạy `git revert <hash-của-commit-revert>` (revert cái revert), rồi `git merge feature/F002` để lấy thêm commit sửa lỗi mới.
</details>

🔴 *Thử thách*: Một PR làm hỏng production đã được merge vào `master` 3 commit trước, và sau nó đã có 2 PR khác (không liên quan) được merge. Đưa production về trạng thái tốt nhanh nhất **mà không mất 2 PR kia**, theo đúng quy trình protect branch.

<details><summary>Hướng giải</summary>

`git switch -c revert/bad-pr master`, `git revert -m 1 <hash-merge-của-PR-lỗi>`, push, mở PR vào `master`, nhờ review gấp và merge (hoặc dùng nút *Revert* trên giao diện PR). Không dùng `reset --hard` vì sẽ mất 2 PR sau và phải force push lên nhánh được bảo vệ.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao revert an toàn với nhánh chung còn reset thì không?</summary>

Revert chỉ *thêm* commit, lịch sử cũ giữ nguyên, nên mọi người `pull` bình thường. Reset *viết lại* lịch sử: muốn đưa lên remote phải `push --force`, và máy đồng nghiệp vẫn còn các commit "đã bị xoá", dễ đẩy ngược chúng lên lại.
</details>

## Lab7 · Resolve conflict {011}

**Khái niệm cốt lõi**

**Conflict** xảy ra khi hai nhánh **sửa cùng một vùng** của cùng một file (hoặc một bên sửa, một bên xoá file), và Git không tự biết giữ bên nào. Git dừng lại, đánh dấu chỗ xung đột, và chờ bạn quyết định.

```html
<<<<<<< HEAD
<h1>Chào mừng tới LearnHub</h1>          ← phiên bản ở nhánh bạn ĐANG đứng (vd: develop)
=======
<h1>Welcome to LearnHub</h1>             ← phiên bản từ nhánh đang được merge vào
>>>>>>> feature/F003
```

**Các bước giải quyết**

```bash
git switch develop
git merge feature/F003                 # CONFLICT (content): Merge conflict in index.html
git status                             # liệt kê file "both modified"
# mở file, giữ lại nội dung đúng, XOÁ HẾT các dòng <<<<<<<, =======, >>>>>>>
git add index.html                     # đánh dấu đã giải quyết
git commit                             # Git đã soạn sẵn thông điệp "Merge branch ..."
# Muốn huỷ và quay về như trước khi merge:
git merge --abort
```

**Cách làm trong team (qua PR):** khi GitHub báo PR *"This branch has conflicts that must be resolved"*, cách gọn nhất là cập nhật nhánh feature của bạn:

```bash
git switch feature/F003
git fetch origin
git merge origin/develop               # giải quyết conflict ngay trên nhánh của bạn
git push                               # PR tự cập nhật, hết conflict
```

**Đi sâu hơn**

- **Công cụ giúp đỡ**: VS Code hiện nút *Accept Current / Accept Incoming / Accept Both* và có *Merge Editor* 3 cột. `git mergetool` mở công cụ merge bạn cấu hình (meld, vimdiff…).
- Xem conflict kèm cả phiên bản gốc chung (rất có ích để hiểu *ai đã đổi gì*): `git config --global merge.conflictstyle zdiff3`.
- Chọn hẳn một bên cho cả file: `git checkout --ours index.html` hoặc `--theirs`. ⚠️ Khi **rebase**, ý nghĩa `ours`/`theirs` bị đảo ngược so với merge.
- **Giảm conflict từ gốc**: nhánh feature ngắn ngày, merge `develop` vào nhánh mình thường xuyên, chia nhỏ PR, thống nhất formatter (Prettier, `terraform fmt`) để không có "conflict do khoảng trắng".
- `git config --global rerere.enabled true`: Git ghi nhớ cách bạn đã giải quyết một conflict và tự áp dụng lại khi gặp đúng conflict đó lần nữa.
- **Sau khi giải quyết, luôn chạy lại test/build.** Một file hết dấu `<<<<<<<` không có nghĩa code đúng: hai thay đổi đều hợp lệ có thể kết hợp lại thành lỗi logic.

**Lỗi hay gặp & cách sửa**

- `error: Your local changes to the following files would be overwritten by merge` → bạn có thay đổi chưa commit. Commit chúng, hoặc `git stash` trước khi merge.
- Commit lên rồi mới phát hiện còn sót `<<<<<<< HEAD` trong file → tìm bằng `git grep -n '<<<<<<<'`, sửa và commit tiếp. Có thể thêm pre-commit hook `check-merge-conflict` để chặn.
- `fatal: You have not concluded your merge (MERGE_HEAD exists).` → bạn đang ở giữa một lần merge. Hoặc hoàn tất (`git add` + `git commit`), hoặc `git merge --abort`.

**Bài tập**

🟢 *Cơ bản*: Tạo conflict có chủ đích: `develop` và `feature/F003` cùng sửa dòng `<h1>` trong `index.html`. Merge, giải quyết bằng tay, commit.

🟡 *Thực hành*: Làm lại tình huống trên nhưng qua PR trên GitHub. Giải quyết conflict bằng cách merge `origin/develop` vào nhánh feature trên máy, rồi push để PR hết báo lỗi. Thử thêm một lần giải quyết bằng trình soạn thảo web của GitHub.

🔴 *Thử thách*: Bật `merge.conflictstyle zdiff3`, tạo conflict 3 bên: gốc là `port = 80`, nhánh A đổi thành `port = 8080`, nhánh B đổi thành `port = 80 # web`. Giải thích từng khối trong file conflict, và chọn kết quả đúng ý cả hai người.

<details><summary>Gợi ý</summary>

Với `zdiff3` sẽ có thêm khối `||||||| base` chứa `port = 80`. Nhìn vào base, bạn thấy A đổi *giá trị*, B chỉ thêm *chú thích*. Kết quả hợp lý: `port = 8080 # web`. Đây là lý do zdiff3 giúp bạn quyết định chính xác hơn nhiều so với chỉ nhìn 2 bên.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Hai người sửa hai hàm khác nhau trong cùng một file. Có conflict không?</summary>

Thường là **không**. Git merge theo từng vùng dòng; nếu các vùng sửa không chồng lên nhau (và không sát nhau), Git tự gộp được.
</details>

<details><summary>2. Đang giải quyết conflict thì rối quá, muốn làm lại từ đầu. Lệnh gì?</summary>

`git merge --abort` (với rebase: `git rebase --abort`). Repo quay về đúng trạng thái trước khi bắt đầu merge.
</details>

## Lab8 · AWS CodeCommit {012-013}

**Khái niệm cốt lõi**

**AWS CodeCommit** là dịch vụ lưu trữ Git riêng (private) do AWS quản lý. Điểm khác biệt so với GitHub: quyền truy cập được quản lý bằng **IAM** (cùng chỗ với mọi quyền AWS khác), dữ liệu nằm trong tài khoản AWS của bạn, tích hợp với CodeBuild / CodePipeline.

**Tình trạng hiện tại (cập nhật 10/2026)**

| Thời điểm | Sự kiện |
|---|---|
| 25/7/2024 | AWS **ngừng nhận khách hàng mới** cho CodeCommit; khách cũ dùng bình thường. AWS hướng dẫn di chuyển sang nhà cung cấp Git khác. |
| 24–25/11/2025 | AWS thông báo CodeCommit **trở lại General Availability**: tài khoản mới lại tạo được repo qua console, CLI, API. Giá giữ nguyên. |
| Lộ trình AWS công bố | Hỗ trợ **Git LFS** (dự kiến Q1/2026), mở rộng thêm region (từ Q3/2026). Hãy kiểm tra trang tài liệu để biết đã ra mắt chưa. |

Vì vậy video quay khi CodeCommit còn bình thường vẫn làm theo được. Nếu tài khoản của bạn vẫn không tạo được repo, hãy làm phần thay thế bên dưới với GitHub/GitLab.

**Ba cách kết nối Git với CodeCommit**

| Cách | Hợp với | Ghi chú |
|---|---|---|
| **HTTPS + git-remote-codecommit (GRC)** | **Khuyên dùng**, nhất là khi dùng IAM role / SSO / credential tạm thời | Dùng chính credential của AWS CLI, không cần mật khẩu riêng |
| HTTPS + Git credentials | IAM user, công cụ chỉ hỗ trợ username/password | Tạo trong *IAM → User → Security credentials → HTTPS Git credentials for CodeCommit* |
| SSH | IAM user quen dùng SSH | Upload public key vào IAM user, dùng *SSH key ID* làm username |

```bash
# Chuẩn bị: AWS CLI đã cấu hình (chương 05), IAM user/role có quyền CodeCommit
pip install --user git-remote-codecommit

aws codecommit create-repository --repository-name demo-git \
    --repository-description "Lab CodeCommit" --region ap-southeast-1
git clone codecommit::ap-southeast-1://demo-git          # cú pháp của GRC
# Dùng profile khác: codecommit::ap-southeast-1://<profile>@demo-git

# Đẩy repo GitHub sẵn có sang CodeCommit (mirror toàn bộ nhánh và tag):
git clone --mirror git@github.com:<user>/demo-git.git
cd demo-git.git
git push --mirror codecommit::ap-southeast-1://demo-git
```

- **Approval rule template**: tương đương "bắt buộc N người approve" của GitHub.
- Muốn chặn push trực tiếp vào `main`, dùng IAM policy `Deny` cho `codecommit:GitPush` với điều kiện `codecommit:References` là `refs/heads/main`.
- **Notification rule / trigger**: gửi sự kiện push, PR sang SNS, Lambda, hoặc kích hoạt CodePipeline.

**Đi sâu hơn: chọn nhà cung cấp nào?**

- **Học và dự án cá nhân**: **GitHub** (GitHub Actions miễn phí nhiều phút cho repo public, cộng đồng lớn). Các chương CI/CD sau của khoá vẫn dùng được GitHub qua *CodeConnections* (trước đây là CodeStar Connections) để nối với CodePipeline.
- **Công ty muốn tự host hoặc CI/CD tích hợp sâu**: **GitLab**.
- **Đã gắn chặt với AWS, cần IAM, VPC endpoint, dữ liệu trong tài khoản AWS**: CodeCommit vẫn là lựa chọn hợp lệ sau khi được mở lại. Đổi qua lại rất dễ vì Git là chuẩn chung: `git push --mirror` sang remote mới là mang theo toàn bộ lịch sử.
- Bài học rút ra: **đừng khoá chặt quy trình vào một nhà cung cấp**. Dịch vụ có thể ngừng nhận khách (như năm 2024) rồi quay lại (như năm 2025).

**Lỗi hay gặp & cách sửa**

- `git: 'remote-codecommit' is not a git command` → chưa cài GRC, hoặc `~/.local/bin` chưa nằm trong `PATH` (`pip install --user` cài vào đó).
- `fatal: unable to access ...: The requested URL returned error: 403` → IAM user/role thiếu quyền (thử policy `AWSCodeCommitPowerUser`), sai region trong URL, hoặc credential trong Keychain/credential helper cũ bị lưu sai.
- Repo không hiện trên console → bạn đang xem **khác region** với region đã tạo repo.

💰 **Chi phí / an toàn**
- CodeCommit có gói miễn phí không hết hạn, áp dụng cả khách mới và cũ: khoảng **5 active user đầu tiên mỗi tháng** kèm dung lượng và số request Git nhất định; vượt mức thì tính khoảng 1 USD/user/tháng và phí theo GB, theo request (xem trang giá để biết con số hiện tại). Một người tự học gần như chắc chắn ở mức 0 USD.
- Dọn dẹp: `aws codecommit delete-repository --repository-name demo-git --region ap-southeast-1`. Xoá Git credentials hoặc SSH key đã tạo trong IAM nếu không dùng nữa.

**Bài tập**

🟢 *Cơ bản*: Tạo repo `demo-git` trên CodeCommit (region `ap-southeast-1`), clone bằng GRC, push một commit, xem commit trên console.

🟡 *Thực hành*: Mirror repo GitHub của Lab3–5 (đủ nhánh `develop`, `feature/*`, tag `v1.0.0`) sang CodeCommit. Tạo một PR trên CodeCommit kèm approval rule bắt buộc 1 người duyệt.

<details><summary>Gợi ý</summary>

Dùng `git clone --mirror` + `git push --mirror` như trên. Approval rule: *Repository → Approval rule templates → Create*, gắn template vào repo, rồi mở PR để thấy trạng thái "Approval rules not satisfied".
</details>

🔴 *Thử thách*: Viết IAM policy cho nhóm `developers`: được push mọi nhánh **trừ** `main` và `develop` (phải đi qua PR). Kiểm tra bằng một IAM user thử nghiệm, rồi xoá user, policy và repo khi xong.

<details><summary>Hướng giải</summary>

Gắn `AWSCodeCommitPowerUser` (hoặc quyền tự viết), cộng một statement `Deny` cho các action `codecommit:GitPush`, `codecommit:PutFile`, `codecommit:DeleteBranch`, `codecommit:MergeBranchesBy*` với `Condition` `StringEqualsIfExists` trên `codecommit:References` gồm `refs/heads/main` và `refs/heads/develop`, và điều kiện `Null` để chặn cả trường hợp không có reference. Tài liệu CodeCommit có ví dụ mẫu ở mục *Limit pushes and merges to branches*.
</details>

## git reset, git stash, reflog, giữ bí mật ngoài Git và tổng kết {014-015}

**git reset: kéo con trỏ nhánh lùi lại**

`git reset <commit>` di chuyển nhánh hiện tại (và HEAD) về commit đó. Ba chế độ khác nhau ở chỗ *có đụng tới staging và working tree hay không*:

| Chế độ | Con trỏ nhánh | Staging (index) | Working tree (file) | Dùng khi |
|---|---|---|---|---|
| `--soft` | Lùi | Giữ nguyên (thay đổi vẫn *đã stage*) | Giữ nguyên | Gộp vài commit gần nhất thành một |
| `--mixed` (**mặc định**) | Lùi | Đặt lại (thay đổi thành *chưa stage*) | Giữ nguyên | Commit nhầm, muốn chọn lại file |
| `--hard` | Lùi | Đặt lại | **Ghi đè, mất thay đổi chưa commit** | Muốn bỏ hết, quay về đúng commit cũ |

```bash
git reset --soft HEAD~3 && git commit -m "feat: login form"   # gộp 3 commit cuối thành 1
git reset HEAD~1                 # huỷ commit cuối, giữ code để sửa tiếp
git reset --hard origin/develop  # vứt mọi thứ local, khớp đúng remote  ⚠️
```

`HEAD~1` là commit cha của HEAD, `HEAD~3` là lùi 3 commit.

**git restore và git switch (cú pháp mới, dễ hiểu hơn `checkout`)**

```bash
git restore index.html             # bỏ thay đổi CHƯA stage của file
git restore --staged index.html    # bỏ stage, giữ thay đổi trong file
git restore --source=HEAD~2 a.txt  # lấy nội dung file từ 2 commit trước
git switch develop                 # chuyển nhánh (thay cho git checkout develop)
```

**git stash: cất tạm việc đang làm dở**

Tình huống: đang code dở `feature/F004` thì phải chuyển sang sửa gấp `hotfix`. Chưa muốn commit dở dang:

```bash
git stash push -u -m "F004: form đang làm dở"   # -u: cất cả file mới chưa track
git switch -c hotfix/1.0.2 master
# ... sửa, commit, push ...
git switch feature/F004
git stash list                    # stash@{0}: On feature/F004: F004: form đang làm dở
git stash pop                     # lấy ra và xoá khỏi danh sách (apply = lấy ra nhưng vẫn giữ)
git stash show -p stash@{0}       # xem trước nội dung một stash
git stash drop stash@{0}          # xoá một stash
```

**reflog: lưới an toàn khi lỡ tay**

Mỗi lần HEAD di chuyển (commit, reset, rebase, switch), Git ghi lại vào **reflog** trên máy bạn. Commit "biến mất" sau `reset --hard` thường **vẫn còn**, chỉ là không nhánh nào trỏ tới.

```bash
git reset --hard HEAD~3           # ôi, lỡ tay xoá 3 commit!
git reflog                        # a1b2c3d HEAD@{1}: commit: feat: login form ...
git reset --hard a1b2c3d          # đưa nhánh quay lại; hoặc an toàn hơn:
git branch cuu-ho a1b2c3d         # tạo nhánh mới trỏ vào commit cần cứu
```

- reflog chỉ có **ở máy local**, không được push. Mặc định các mục giữ khoảng 90 ngày (commit không còn ai trỏ tới thì khoảng 30 ngày) trước khi bị dọn.
- Thứ duy nhất reflog **không cứu được**: thay đổi *chưa từng commit hoặc stash* mà bị `reset --hard` / `restore` ghi đè. Vì vậy: commit thường xuyên, kể cả commit "wip" trên nhánh riêng.

**Giữ secret ngoài Git**

> ⚠️ Bot quét GitHub tìm access key, private key, mật khẩu trong vài phút sau khi bạn push. Coi như **mọi secret từng nằm trong lịch sử Git đều đã lộ**, kể cả khi repo private hoặc bạn đã xoá ở commit sau.

Ví dụ thật ngay trong repo lab: thư mục `linux-basic-operation/` có file `dev01`, là **private key SSH đã được commit**. Ai đọc được repo đều dùng được key này.

**Phòng ngừa:**
- `.gitignore` cho `.env`, `*.pem`, private key, `*.tfstate`.
- Add từng file (`git add <file>`) và xem lại `git diff --cached` trước khi commit, hạn chế `git add .`.
- Quét bằng công cụ trước khi commit:
  - **gitleaks**: `gitleaks git -v` quét toàn bộ lịch sử repo (bản cũ dùng `gitleaks detect`), có thể gắn vào pre-commit hook.
  - **git-secrets** (của AWS Labs): `git secrets --install && git secrets --register-aws` để chặn commit có AWS access key.
- Bật **push protection / secret scanning** trên GitHub để chặn push chứa secret đã biết dạng.
- Secret thật để ở biến môi trường, AWS Secrets Manager / SSM Parameter Store, hoặc GitHub Actions secrets.

**Đã lỡ commit secret, làm theo thứ tự:**
1. **Thu hồi / đổi secret ngay lập tức** (xoá access key trong IAM, sinh SSH key mới và xoá dòng key cũ khỏi `authorized_keys`). Đây là bước quan trọng nhất; nhiều khi chỉ cần bước này.
2. Xoá secret khỏi **toàn bộ lịch sử** bằng `git-filter-repo` (GitHub khuyên dùng bản 2.47 trở lên với cờ `--sensitive-data-removal`):

```bash
git clone --mirror git@github.com:<user>/devops-for-beginner.git   # thao tác trên bản clone mới
cd devops-for-beginner.git
git filter-repo --sensitive-data-removal --invert-paths --path linux-basic-operation/dev01
git push --force --mirror origin
```

3. Báo cả team **clone lại** (hoặc rebase, không được merge lịch sử cũ vào, vì sẽ đưa secret quay lại). Trên GitHub, các commit cũ vẫn có thể còn trong PR, fork và cache; liên hệ GitHub Support nếu cần xoá triệt để.

Viết lại lịch sử là thao tác phá huỷ, ảnh hưởng mọi người dùng repo. Hãy cân nhắc và chỉ làm sau khi đã thu hồi secret.

**Lỗi hay gặp & cách sửa**

- Lỡ `git reset --hard` mất commit → `git reflog`, rồi `git branch cuu-ho <hash>`.
- `git stash pop` báo conflict → stash *không bị xoá* khi pop gặp conflict. Giải quyết như conflict thường, `git add`, rồi tự `git stash drop`.
- `reset` xong push bị `! [rejected] (non-fast-forward)` → bạn đã viết lại lịch sử *đã push*. Trên nhánh chung, hãy dùng `revert` thay vì reset. Trên nhánh riêng: `git push --force-with-lease`.
- Đổi nhánh mà thấy file sửa đi theo → thay đổi chưa commit không thuộc nhánh nào, nó "đi theo" bạn. Commit hoặc stash trước khi đổi nhánh.

**Tổng kết chương**

| Muốn… | Lệnh |
|---|---|
| Bỏ thay đổi chưa commit của một file | `git restore <file>` |
| Bỏ stage | `git restore --staged <file>` |
| Sửa thông điệp / thêm file vào commit cuối (chưa push) | `git commit --amend` |
| Huỷ commit cuối, giữ code (chưa push) | `git reset HEAD~1` |
| Huỷ commit **đã push** lên nhánh chung | `git revert <hash>` |
| Cất tạm việc dở dang | `git stash push -u -m "..."` |
| Cứu commit tưởng đã mất | `git reflog` + `git branch cuu-ho <hash>` |
| Đánh dấu phiên bản phát hành | `git tag -a v1.2.0 -m "..."` + `git push origin v1.2.0` |

💰 **Dọn dẹp cuối chương**: xoá repo CodeCommit thử nghiệm, xoá Git credentials / SSH key thử nghiệm trong IAM, xoá IAM user thử nghiệm. Repo GitHub cá nhân để lại không tốn tiền, nhưng hãy chắc chắn nó không chứa secret.

**Bài tập**

🟢 *Cơ bản*: Tạo 3 commit nhỏ trên một nhánh riêng. Lần lượt thử `reset --soft HEAD~1`, `reset --mixed HEAD~1`, `reset --hard HEAD~1`, mỗi lần ghi lại `git status` khác nhau thế nào. Cuối cùng dùng `git reflog` để lấy lại commit bị `--hard` xoá.

🟡 *Thực hành*: Đang sửa dở 2 file trên `feature/F004` (một file đã track, một file mới), dùng stash để chuyển sang sửa `hotfix`, rồi quay lại và lấy đủ cả hai file. Thử lại mà không có `-u` và giải thích chuyện gì xảy ra với file mới.

<details><summary>Gợi ý</summary>

Không có `-u`, file mới (untracked) **không được cất**, nó vẫn nằm trong working tree và đi theo bạn sang nhánh `hotfix`. Nếu lỡ `git add` file đó trên hotfix thì nó sẽ lọt vào commit sửa lỗi.
</details>

🔴 *Thử thách*: Áp dụng vào chính repo `devops-for-beginner` của bạn: (1) chạy gitleaks (hoặc `git log --all --name-only | grep -E 'dev01$|udemy-key$|\.pem$'`) để liệt kê mọi private key từng được commit; (2) với mỗi key, ghi lại nó đang được dùng ở đâu (key pair AWS, `authorized_keys` trên server nào) và thu hồi; (3) thêm luật `.gitignore` phù hợp; (4) lên kế hoạch (chưa cần thực hiện) xoá chúng khỏi lịch sử bằng `git-filter-repo`, kèm danh sách những ai phải clone lại.

<details><summary>Gợi ý</summary>

Thứ tự đúng luôn là **thu hồi trước, dọn lịch sử sau**. Với key pair AWS: tạo key mới, cập nhật Terraform (`aws_key_pair`) hoặc EC2, rồi xoá key pair cũ. Luật `.gitignore` gợi ý: `**/keypair/*` kèm ngoại lệ `!**/keypair/*.pub`, và `linux-basic-operation/dev01`. Thử `--dry-run` của git-filter-repo trên một bản clone mirror trước khi làm thật. Nhớ rằng kế hoạch này ảnh hưởng tới các thay đổi chưa commit trong máy bạn, nên commit hoặc sao lưu trước.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Bạn <code>git reset --hard HEAD~2</code> trên nhánh local, chưa push. Hai commit đó mất vĩnh viễn chưa?</summary>

Chưa. Chúng vẫn nằm trong `.git` và hiện trong `git reflog` (mặc định vài tuần tới vài tháng trước khi bị dọn). Tìm hash rồi `git reset --hard <hash>` hoặc tạo nhánh trỏ vào đó.
</details>

<details><summary>2. Lỡ push AWS access key lên GitHub, bạn đã xoá file và commit tiếp. Đủ chưa?</summary>

Chưa. Key vẫn nằm trong lịch sử và có thể đã bị bot sao chép. Việc đầu tiên là **vô hiệu hoá và xoá access key trong IAM**, kiểm tra CloudTrail/Billing xem có hoạt động lạ, tạo key mới. Sau đó mới dọn lịch sử bằng `git-filter-repo` nếu cần.
</details>

<details><summary>3. Khác nhau giữa <code>git stash pop</code> và <code>git stash apply</code>?</summary>

Cả hai đều đưa thay đổi đã cất trở lại working tree. `pop` xoá stash khỏi danh sách nếu áp dụng thành công; `apply` giữ lại, hữu ích khi muốn áp cùng một stash lên nhiều nhánh.
</details>
