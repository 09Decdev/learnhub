# Chương 14 · Giới thiệu về Kubernetes (k8s)

Học xong chương này, bạn **chạy ứng dụng container trên Kubernetes**: dựng cluster học tập bằng minikube trên Fedora, viết YAML cho Pod, Deployment, Service, Ingress, PersistentVolume, ConfigMap, Secret, biết gỡ lỗi khi Pod không chạy. Cuối chương bạn dựng một cluster thật trên AWS bằng kops và deploy ứng dụng React + Express + MongoDB lên đó.

Các lệnh bạn sẽ gõ nhiều nhất cả chương:

```bash
kubectl apply -f file.yaml        # tạo/cập nhật tài nguyên theo file (declarative)
kubectl get pods -o wide          # liệt kê, xem Pod nằm trên node nào, IP gì
kubectl describe pod <tên>        # xem chi tiết + Events (nơi đầu tiên để tìm lỗi)
kubectl logs <pod> [-f]           # log của container
kubectl exec -it <pod> -- sh      # vào bên trong container
kubectl delete -f file.yaml       # xoá những gì file đã tạo
```

> Phiên bản tại thời điểm viết (10/2026): Kubernetes **1.37** là bản mới nhất; dự án hỗ trợ 3 bản minor gần nhất (1.37, 1.36, 1.35). Video khoá học quay trên bản cũ hơn (khoảng 1.27), nhưng các khái niệm trong chương này không đổi.

## Kubernetes là gì, kiến trúc và các concept {001-003}

**Khái niệm cốt lõi**

Ở chương Docker bạn đã chạy container trên **một** máy. Khi có hàng chục container trên nhiều máy, bạn gặp ngay các câu hỏi: container chết thì ai khởi động lại? Máy hỏng thì chuyển container sang đâu? Làm sao tăng từ 2 lên 10 bản sao khi tải tăng? Cập nhật phiên bản mới mà không gián đoạn thế nào?

**Kubernetes (k8s)** là hệ thống *điều phối container* (container orchestration) trả lời các câu hỏi đó. Bạn có thể hình dung nó như **người quản lý kho**: bạn chỉ nói "tôi cần 3 bản nginx luôn chạy", người quản lý tự tìm chỗ, tự thay bản hỏng, tự cân bằng.

**Kiến trúc cluster**

```
                 kubectl  (bạn)
                    │ HTTPS (REST API)
┌───────────── CONTROL PLANE ─────────────────────────────┐
│  kube-apiserver  ◄──► etcd (CSDL key-value lưu mọi thứ)  │
│      ▲     ▲                                             │
│  scheduler  controller-manager   (cloud-controller-mgr)  │
└──────┼──────────────────────────────────────────────────┘
       │ watch / cập nhật
┌──── WORKER NODE 1 ─────────┐   ┌──── WORKER NODE 2 ─────────┐
│ kubelet → containerd       │   │ kubelet → containerd       │
│ kube-proxy                 │   │ kube-proxy                 │
│  [Pod] [Pod]               │   │  [Pod] [Pod] [Pod]         │
└────────────────────────────┘   └────────────────────────────┘
```

| Thành phần | Nằm ở | Làm gì |
|---|---|---|
| **kube-apiserver** | Control plane | "Cửa chính" duy nhất. Mọi thứ (kubectl, kubelet, controller) đều nói chuyện qua đây. Kiểm tra quyền, validate YAML, ghi vào etcd. |
| **etcd** | Control plane | CSDL key-value phân tán, lưu **toàn bộ trạng thái** cluster. Mất etcd là mất cluster, nên phải backup. |
| **kube-scheduler** | Control plane | Chọn node cho Pod mới, dựa trên CPU/RAM còn trống, label, taint/toleration, affinity. |
| **kube-controller-manager** | Control plane | Chạy nhiều *controller* (ReplicaSet, Deployment, Node, Job…), mỗi cái lo một loại tài nguyên. |
| **kubelet** | Mỗi node | "Quản đốc" của node: nhận danh sách Pod cần chạy, gọi container runtime, báo cáo trạng thái, chạy probe. |
| **kube-proxy** | Mỗi node | Lập trình luật mạng (iptables / nftables) để IP ảo của Service chuyển tới đúng Pod. |
| **Container runtime** | Mỗi node | Thực sự chạy container, thường là **containerd** hoặc CRI-O, giao tiếp qua chuẩn CRI. |

**Các concept chính** (bạn sẽ gặp lần lượt trong chương)

- **Pod**: đơn vị nhỏ nhất k8s quản lý. Gồm 1 hoặc vài container dùng chung IP và volume.
- **ReplicaSet**: giữ đúng N bản sao Pod.
- **Deployment**: quản lý ReplicaSet, lo cập nhật phiên bản (rolling update) và rollback.
- **Service**: địa chỉ ổn định (IP + DNS) đứng trước một nhóm Pod.
- **Ingress**: định tuyến HTTP theo domain/path từ ngoài vào Service.
- **PersistentVolume / PVC**: ổ đĩa sống lâu hơn Pod.
- **ConfigMap / Secret**: cấu hình và dữ liệu nhạy cảm tách khỏi image.
- **Namespace**: chia cluster thành các "phòng" riêng.

**Đi sâu hơn**

- **Declarative và vòng lặp reconcile (đối chiếu).** Bạn không ra lệnh "tạo 3 Pod". Bạn khai báo `spec` (trạng thái mong muốn), k8s ghi lại `status` (trạng thái thực tế). Mỗi controller chạy một vòng lặp vô tận: *quan sát → so sánh spec với status → hành động cho khớp*. Đây cùng tư tưởng với Terraform ở chương 05, chỉ khác là k8s **liên tục** đối chiếu chứ không đợi bạn gõ `apply`.
- **Không còn Docker bên trong k8s.** Từ bản 1.24, k8s bỏ *dockershim*, nghĩa là node không dùng Docker Engine làm runtime nữa mà dùng containerd/CRI-O. Image bạn build bằng Docker vẫn chạy bình thường, vì image theo chuẩn OCI chung.
- **Labels và selectors** là "keo dán" của k8s. Label là cặp key/value gắn lên đối tượng (`app: nginx`). ReplicaSet, Service, NetworkPolicy đều tìm Pod **bằng label selector**, không bằng tên. Hiểu điều này giúp bạn gỡ 50% lỗi kiểu "Service không có endpoint".
- **Managed vs tự dựng.** Trên cloud thật, người ta thường dùng dịch vụ có sẵn control plane (EKS, GKE, AKS). Tự dựng (kubeadm, kops) giúp hiểu sâu nhưng tốn công vận hành.

**Câu hỏi tự kiểm tra**

<details><summary>1. Bạn xoá một Pod do ReplicaSet quản lý. Thành phần nào phát hiện và tạo Pod mới, thành phần nào chọn node cho nó?</summary>

ReplicaSet controller (trong **kube-controller-manager**) thấy số Pod thực tế (2) ít hơn mong muốn (3) nên tạo đối tượng Pod mới qua apiserver. **kube-scheduler** gán Pod đó cho một node. **kubelet** trên node đó gọi containerd để chạy container.
</details>

<details><summary>2. Vì sao etcd quan trọng nhất trong control plane?</summary>

Mọi đối tượng (Deployment, Secret, Service…) chỉ "tồn tại" vì được lưu trong etcd. apiserver, scheduler, controller đều không lưu trạng thái riêng. Mất etcd mà không có backup thì phải dựng lại toàn bộ cluster. Đây cũng là lý do Secret trong etcd cần được mã hoá (xem phần Secret).
</details>

<details><summary>3. "Declarative" trong k8s giống và khác Terraform ở điểm nào?</summary>

Giống: cả hai đều mô tả trạng thái mong muốn, công cụ tự tính phải làm gì. Khác: Terraform chỉ đối chiếu khi bạn chạy `plan/apply`. Kubernetes có controller chạy **liên tục**, nên nếu ai đó xoá Pod bằng tay, nó tự sửa lại ngay mà không cần bạn làm gì.
</details>

## Lab1 · Cài minikube và kubectl trên Fedora {004}

**Khái niệm cốt lõi**

- **kubectl**: công cụ dòng lệnh để nói chuyện với apiserver của *bất kỳ* cluster nào.
- **minikube**: tạo một cluster k8s **một node** trên máy bạn (node vừa là control plane vừa là worker), chạy trong container Docker/Podman hoặc trong máy ảo KVM.
- **kubeconfig** (`~/.kube/config`): file lưu danh sách cluster, user, và **context** (cặp cluster + user + namespace). kubectl gửi lệnh tới context hiện tại.

**Cài đặt trên Fedora**

```bash
# 1. kubectl từ repo chính thức pkgs.k8s.io (đổi v1.37 thành bản bạn muốn)
cat <<EOF | sudo tee /etc/yum.repos.d/kubernetes.repo
[kubernetes]
name=Kubernetes
baseurl=https://pkgs.k8s.io/core:/stable:/v1.37/rpm/
enabled=1
gpgcheck=1
gpgkey=https://pkgs.k8s.io/core:/stable:/v1.37/rpm/repodata/repomd.xml.key
EOF
sudo dnf install -y kubectl
kubectl version --client

# 2. minikube (gói RPM chính thức)
curl -LO https://storage.googleapis.com/minikube/releases/latest/minikube-latest.x86_64.rpm
sudo rpm -Uvh minikube-latest.x86_64.rpm

# 3. Khởi động cluster - chọn MỘT driver
minikube start --driver=docker     # cần Docker Engine (docker-ce) đã chạy, user trong nhóm docker
minikube start --driver=kvm2       # máy ảo KVM, cần libvirt: sudo dnf install @virtualization
minikube start --driver=podman     # Podman có sẵn trên Fedora, nhưng driver này còn "experimental"

minikube config set driver docker  # nhớ driver mặc định
kubectl get nodes                  # phải thấy node "minikube" Ready
```

**Đi sâu hơn**

- **Version skew:** kubectl chỉ nên lệch tối đa **1 bản minor** với cluster (kubectl 1.37 dùng được với cluster 1.36–1.38). Nếu lười cài, dùng `minikube kubectl -- get pods`, minikube tự tải kubectl đúng phiên bản.
- **Các lựa chọn khác để luyện miễn phí:**
  - **kind** (Kubernetes IN Docker): mỗi node là một container, tạo cluster nhiều node rất nhanh (`kind create cluster`). Hay dùng trong CI.
  - **k3d**: chạy **k3s** (bản k8s rút gọn của Rancher) trong Docker, nhẹ hơn, có sẵn Traefik làm ingress.
  - **Killercoda**: cluster trên trình duyệt, miễn phí, không cần cài gì. Rất hợp để luyện đề CKA/CKAD.
- **Addons minikube** hay dùng: `minikube addons enable ingress`, `metrics-server`, `dashboard`. Xem tất cả: `minikube addons list`.
- `minikube stop` giữ lại cluster, `minikube delete` xoá sạch. Cluster minikube khá tốn RAM; mặc định nó tự chọn CPU/RAM, có thể đặt `--cpus=2 --memory=4096`.

**Làm việc với context** (khớp `lab1-install-minikube.sh`)

```bash
kubectl config get-contexts          # dấu * là context đang dùng
kubectl config use-context minikube  # chuyển về minikube
kubectl cluster-info
```

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `Exiting due to PROVIDER_DOCKER_NOT_RUNNING` | Docker daemon chưa chạy | `sudo systemctl enable --now docker` |
| `permission denied while trying to connect to the Docker daemon socket` | User chưa thuộc nhóm docker | `sudo usermod -aG docker $USER` rồi đăng xuất/đăng nhập lại |
| `The connection to the server localhost:8080 was refused` | kubectl không có kubeconfig/context | `minikube start` lại, hoặc `kubectl config use-context minikube` |
| `kubectl get nodes` ra node lạ | Đang trỏ tới cluster khác (kops, EKS) | Kiểm tra `get-contexts`, đổi context |

**Bài tập**

🟢 *Cơ bản*: Cài minikube với driver docker, chạy `kubectl get nodes` và `kubectl get pods -A`. Kể tên các Pod trong namespace `kube-system` và đối chiếu với bảng thành phần ở phần trước.

<details><summary>Gợi ý</summary>

Bạn sẽ thấy `etcd-minikube`, `kube-apiserver-minikube`, `kube-scheduler-minikube`, `kube-controller-manager-minikube`, `kube-proxy-xxxxx`, `coredns-xxxxx`, `storage-provisioner`. Các thành phần control plane chạy dưới dạng **static Pod** do kubelet đọc từ thư mục manifest trên node (`minikube ssh` rồi `ls /etc/kubernetes/manifests`).
</details>

🟡 *Thực hành*: Cài **kind** và tạo cluster 1 control plane + 2 worker bằng file config. Dùng `kubectl config get-contexts` để chuyển qua lại giữa minikube và kind.

<details><summary>Gợi ý</summary>

```yaml
# kind-3nodes.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

`kind create cluster --name lab --config kind-3nodes.yaml`, context sẽ tên `kind-lab`. Dọn dẹp: `kind delete cluster --name lab`.
</details>

🔴 *Thử thách*: Chạy `minikube start --kubernetes-version=v1.35.0` trong một profile riêng (`-p old`) rồi thử kubectl 1.37 với nó. Có cảnh báo gì không? Giải thích bằng chính sách version skew.

<details><summary>Lời giải</summary>

`minikube start -p old --kubernetes-version=v1.35.0`. Lệch 2 bản minor, `kubectl version` sẽ in cảnh báo vượt quá skew được hỗ trợ. Phần lớn lệnh vẫn chạy, nhưng không được đảm bảo. Dùng `minikube -p old kubectl -- ...` để có kubectl đúng bản. Dọn: `minikube delete -p old`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Context trong kubeconfig gồm những gì? Vì sao trước khi xoá tài nguyên nên xem context?</summary>

Context = cluster + user + namespace mặc định. Nếu bạn quên đang trỏ vào cluster kops/EKS thật, `kubectl delete -f ...` sẽ xoá trên cluster đó. Thói quen tốt: hiện context trên prompt shell, hoặc luôn chạy `kubectl config current-context` trước lệnh nguy hiểm.
</details>

## Lab2–Lab3 · Pod: chạy bằng lệnh và bằng YAML {005-006}

**Khái niệm cốt lõi**

**Pod** là "căn hộ" cho container: các container trong cùng Pod dùng chung địa chỉ IP (gọi nhau qua `localhost`) và có thể dùng chung volume. Thường 1 Pod = 1 container ứng dụng; đôi khi thêm container phụ (*sidecar*, ví dụ đẩy log).

Có hai cách tạo Pod:

| Imperative (ra lệnh) – Lab2 | Declarative (khai báo) – Lab3 |
|---|---|
| `kubectl run nginx-pod --image=nginx` | `kubectl apply -f nginx-pod.yaml` |
| Nhanh, hợp để thử nghiệm | Lưu trong Git, review được, lặp lại được |
| Khó biết đã tạo với tham số gì | Chạy `apply` nhiều lần vẫn ra cùng kết quả |

File `kubernetes-basic/lab3-simple-pod-using-yaml/nginx-pod.yaml`:

```yaml
apiVersion: v1          # nhóm API + phiên bản (Pod thuộc core "v1")
kind: Pod               # loại đối tượng
metadata:
  name: nginx-pod       # tên, duy nhất trong namespace
spec:                   # trạng thái MONG MUỐN
  containers:
    - name: nginx-container
      image: nginx
      ports:
        - containerPort: 80   # chỉ mang tính mô tả, không mở port ra ngoài
```

Mọi manifest đều có 4 phần `apiVersion`, `kind`, `metadata`, `spec`. Khi lấy về bằng `kubectl get pod nginx-pod -o yaml`, bạn sẽ thấy thêm phần `status` do k8s ghi.

**Bộ lệnh kubectl cần thuộc**

```bash
kubectl get pods -o wide                     # IP Pod, node chứa Pod
kubectl describe pod nginx-pod               # xem Events ở cuối
kubectl logs nginx-pod                       # log; thêm -f để theo dõi, --previous xem lần chạy trước
kubectl exec -it nginx-pod -- bash           # vào container
kubectl port-forward pod/nginx-pod 8080:80   # mở http://localhost:8080 trên máy bạn
kubectl run tmp --rm -it --image=busybox -- sh   # Pod tạm để thử mạng, thoát là tự xoá
kubectl explain pod.spec.containers          # tra cứu trường YAML ngay trong terminal
kubectl diff -f nginx-pod.yaml               # xem apply sẽ thay đổi gì (như terraform plan)
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml   # sinh YAML mẫu
```

**Đi sâu hơn**

- **Vòng đời Pod:** `Pending` (chưa được xếp node hoặc đang tải image) → `Running` → `Succeeded`/`Failed`. Cột STATUS của `kubectl get pods` còn hiện lý do chi tiết như `ContainerCreating`, `CrashLoopBackOff`.
- **Pod tạo trực tiếp không tự hồi sinh.** Xoá là mất, node chết là mất. Thực tế gần như không ai tạo Pod trần; người ta dùng Deployment (phần sau).
- **`restartPolicy`** (mặc định `Always`): kubelet tự khởi động lại *container* chết trong Pod, với thời gian chờ tăng dần (10s, 20s, 40s… tối đa 5 phút). Đó chính là trạng thái `CrashLoopBackOff`.
- **Tag `latest`:** `image: nginx` nghĩa là `nginx:latest`, và k8s sẽ luôn pull lại (`imagePullPolicy: Always`). Trong thực tế nên ghim tag cụ thể (`nginx:1.27`) để biết chính xác đang chạy gì.

**Gỡ lỗi Pod: ba trạng thái hay gặp nhất**

```
kubectl get pods  →  STATUS bất thường?
   │
   ├─ Pending ............ kubectl describe pod → Events:
   │                        "0/1 nodes are available: Insufficient cpu"  → giảm requests / thêm node
   │                        "pod has unbound immediate PersistentVolumeClaims" → xem PVC
   ├─ ImagePullBackOff /
   │  ErrImagePull ....... sai tên/tag image, repo private chưa có imagePullSecrets, hết quota Docker Hub
   └─ CrashLoopBackOff ... container chạy rồi chết: kubectl logs <pod> --previous
                            thiếu biến môi trường, sai lệnh, app lỗi, bị OOMKilled (exit 137)
```

`kubectl get events --sort-by=.lastTimestamp` cho bạn cái nhìn toàn namespace. Với image không có shell, dùng `kubectl debug -it <pod> --image=busybox --target=<container>` để gắn container debug tạm thời.

**Lỗi hay gặp & cách sửa**

- `Error from server (AlreadyExists): pods "nginx-pod" already exists`: chạy `kubectl run` hai lần. Dùng `kubectl apply` (cập nhật được) hoặc xoá Pod cũ.
- `The Pod "nginx-pod" is invalid: spec: Forbidden: pod updates may not change fields other than ...`: hầu hết trường của Pod **không sửa được** sau khi tạo (đổi port, thêm env…). Phải xoá rồi tạo lại, hoặc dùng Deployment.
- `error: error parsing nginx-pod.yaml: ... did not find expected key`: lỗi thụt lề YAML. Chỉ dùng dấu cách, không dùng Tab.

**Bài tập**

🟢 *Cơ bản*: Tạo Pod nginx bằng YAML, `port-forward` để xem trang chào mừng trên trình duyệt, rồi `exec` vào sửa `/usr/share/nginx/html/index.html` thành tên bạn. Tải lại trang.

<details><summary>Gợi ý</summary>

`kubectl exec -it nginx-pod -- sh -c 'echo "Xin chao" > /usr/share/nginx/html/index.html'`. Sau đó xoá và tạo lại Pod, nội dung sửa sẽ mất, vì filesystem container là tạm thời. Đây là lý do cần volume (phần PV/PVC). Dọn: `kubectl delete -f nginx-pod.yaml`.
</details>

🟡 *Thực hành*: Viết Pod có 2 container: `nginx` và `busybox` chạy `sh -c 'while true; do wget -qO- localhost; sleep 5; done'`. Xem log của từng container.

<details><summary>Gợi ý</summary>

Hai container chung network namespace nên busybox gọi được nginx qua `localhost:80`. Xem log: `kubectl logs <pod> -c <tên-container>`. Đây chính là mô hình sidecar.
</details>

🔴 *Thử thách*: Cố tình tạo 3 Pod lỗi: (a) `image: nginx:khongtontai`, (b) `image: busybox` với `command: ["sh","-c","exit 1"]`, (c) Pod yêu cầu `resources.requests.cpu: "64"`. Với mỗi Pod, ghi lại STATUS, dòng Event quan trọng và cách sửa.

<details><summary>Lời giải</summary>

(a) `ErrImagePull` → `ImagePullBackOff`, Event `manifest unknown` hoặc `not found`. Sửa tag. (b) `CrashLoopBackOff`, `kubectl logs --previous` trống, `describe` cho thấy `Exit Code: 1`. Sửa command. (c) `Pending`, Event `0/1 nodes are available: 1 Insufficient cpu`. Giảm requests. Dọn: `kubectl delete pod --all` (chỉ trong namespace học tập).
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>containerPort: 80</code> trong YAML có làm Pod truy cập được từ ngoài không?</summary>

Không. Nó chỉ là thông tin mô tả (và đặt tên port). Pod đã có IP nội bộ cluster và nghe port 80 dù có khai báo hay không. Để truy cập từ ngoài cần `port-forward`, Service NodePort/LoadBalancer hoặc Ingress.
</details>

<details><summary>2. CrashLoopBackOff là lỗi của Kubernetes hay của ứng dụng?</summary>

Gần như luôn là của **ứng dụng hoặc cấu hình** (lệnh sai, thiếu env, không kết nối được DB, hết RAM). Kubernetes chỉ đang làm đúng việc: khởi động lại và chờ lâu dần. Hãy đọc `kubectl logs --previous` và `describe` (Last State, Exit Code).
</details>

## Namespace {007}

**Khái niệm cốt lõi**

**Namespace** chia một cluster thành nhiều "phòng" logic. Tên tài nguyên chỉ cần duy nhất *trong một namespace*: `dev` và `prod` đều có thể có Deployment tên `web`. Ví dụ đời thường: một toà nhà (cluster) có nhiều phòng ban (namespace), mỗi phòng có người tên "Minh" mà không nhầm.

Namespace có sẵn:

| Namespace | Chứa gì |
|---|---|
| `default` | Nơi tài nguyên rơi vào khi bạn không chỉ định |
| `kube-system` | Thành phần hệ thống (coredns, kube-proxy…). Đừng tự ý sửa |
| `kube-public` | Dữ liệu đọc công khai, hiếm dùng |
| `kube-node-lease` | Heartbeat của các node |

Lệnh trong `kubernetes-basic/namespace.sh`:

```bash
kubectl create namespace demo-namespace
kubectl config set-context --current --namespace=demo-namespace   # đổi namespace mặc định
kubectl config view --minify | grep namespace:                    # đang ở namespace nào
kubectl get pods -n kube-system                                   # xem namespace khác một lần
kubectl get pods -A                                               # mọi namespace
kubectl config set-context --current --namespace=default
```

**Đi sâu hơn**

- **Namespace không phải ranh giới mạng.** Mặc định Pod ở namespace `dev` vẫn gọi được Pod ở `prod`. Muốn chặn phải dùng **NetworkPolicy** (và CNI hỗ trợ nó).
- Thứ thường gắn theo namespace: **RBAC** (Role/RoleBinding: ai được làm gì trong namespace), **ResourceQuota** (giới hạn tổng CPU/RAM/số Pod), **LimitRange** (requests/limits mặc định cho container).
- Không phải tài nguyên nào cũng thuộc namespace: Node, PersistentVolume, StorageClass, Namespace, ClusterRole là tài nguyên *cluster-scoped*. Xem: `kubectl api-resources --namespaced=false`.
- Có thể khai báo `metadata.namespace: dev` trong YAML, nhưng nhiều team để trống và dùng `kubectl apply -n dev` để cùng một file deploy được nhiều môi trường.
- Xoá namespace sẽ **xoá mọi thứ bên trong**. Rất tiện để dọn dẹp bài lab, và rất nguy hiểm nếu gõ nhầm.

**Bài tập**

🟢 *Cơ bản*: Tạo namespace `lab`, chạy Pod nginx trong đó, rồi chứng minh `kubectl get pods` (ở `default`) không thấy nó.

🟡 *Thực hành*: Tạo `ResourceQuota` cho namespace `lab` chỉ cho phép tối đa 2 Pod. Thử tạo Pod thứ 3 và đọc thông báo lỗi.

<details><summary>Gợi ý</summary>

```yaml
apiVersion: v1
kind: ResourceQuota
metadata: { name: pod-quota, namespace: lab }
spec:
  hard:
    pods: "2"
```

Lỗi sẽ có dạng `exceeded quota: pod-quota, requested: pods=1, used: pods=2, limited: pods=2`. Dọn: `kubectl delete namespace lab`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Hai namespace <code>dev</code> và <code>prod</code> có cô lập hoàn toàn với nhau không?</summary>

Không. Namespace chỉ cô lập **tên** và là đơn vị để gắn RBAC/quota. Về mạng, Pod vẫn gọi nhau được qua `<service>.<namespace>.svc.cluster.local`. Cần NetworkPolicy để chặn, và về tài nguyên node, Pod của hai namespace vẫn chạy chung node.
</details>

## ReplicaSet: luôn giữ đủ N bản sao {008-009}

**Khái niệm cốt lõi**

**ReplicaSet** đảm bảo *luôn có đúng N Pod* khớp với một label selector. Pod chết, bị xoá, hay node hỏng: ReplicaSet tạo Pod mới. Thừa Pod (ví dụ bạn tạo tay một Pod có cùng label): nó xoá bớt.

File `kubernetes-basic/lab4-replica-set-simple/nginx-replicaset.yaml`:

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-replicaset
spec:
  replicas: 5                 # số Pod mong muốn
  selector:
    matchLabels:
      app: nginx              # "Pod nào có label app=nginx là của tôi"
  template:                   # khuôn để tạo Pod mới
    metadata:
      labels:
        app: nginx            # PHẢI khớp selector ở trên
        service_name: service_a
    spec:
      containers:
      - name: nginx-container
        image: nginx
```

```bash
kubectl apply -f nginx-replicaset.yaml
kubectl get rs                                  # DESIRED / CURRENT / READY
kubectl get pods --show-labels
kubectl delete pod nginx-replicaset-<xxxxx>     # xoá 1 Pod...
kubectl get pods -w                             # ...và xem Pod mới xuất hiện ngay (Ctrl+C để thoát)
kubectl scale rs nginx-replicaset --replicas=2
```

**Đi sâu hơn**

- **Selector là thứ quyết định quyền sở hữu, không phải tên.** Pod mới được đặt tên `nginx-replicaset-<5 ký tự ngẫu nhiên>` và có trường `metadata.ownerReferences` trỏ về ReplicaSet. Xem bằng `kubectl get pod <tên> -o yaml | grep -A5 ownerReferences`.
- **Template không áp dụng lại cho Pod cũ.** Đổi `image` trong ReplicaSet rồi `apply`: Pod đang chạy **vẫn dùng image cũ**. Chỉ Pod tạo mới sau đó mới dùng image mới. Đây chính là lý do cần Deployment.
- Selector của ReplicaSet (và Deployment) **không đổi được** sau khi tạo.
- Gần như không ai tạo ReplicaSet trực tiếp. Bạn học nó để hiểu Deployment hoạt động thế nào bên dưới.

**Lỗi hay gặp & cách sửa**

- `The ReplicaSet "x" is invalid: spec.template.metadata.labels: Invalid value: ... selector does not match template labels`: label trong template phải chứa đủ các label của selector.
- Tạo tay một Pod trần có label `app: nginx` trong lúc ReplicaSet đang chạy: Pod đó bị ReplicaSet "nhận nuôi" và có thể bị xoá ngay vì thừa số lượng.

**Bài tập**

🟢 *Cơ bản*: Chạy lab4, xoá cùng lúc 2 Pod (`kubectl delete pod <a> <b>`) và đếm thời gian đến khi đủ lại 5 Pod.

🟡 *Thực hành*: Gỡ label `app` khỏi một Pod đang chạy: `kubectl label pod <tên> app-`. Chuyện gì xảy ra với Pod đó và với ReplicaSet?

<details><summary>Lời giải</summary>

Pod đó không còn khớp selector, nên bị ReplicaSet "bỏ rơi" (ownerReference bị gỡ) nhưng **vẫn chạy**. ReplicaSet thấy chỉ còn 4 Pod nên tạo thêm 1. Kết quả có 6 Pod. Kỹ thuật này dùng để tách một Pod lỗi ra điều tra mà không ảnh hưởng số bản sao. Nhớ xoá Pod "mồ côi" bằng tay khi xong.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Đổi <code>image: nginx</code> thành <code>nginx:1.27</code> trong ReplicaSet rồi apply. Bao nhiêu Pod chạy bản mới?</summary>

Không Pod nào, cho đến khi có Pod bị xoá và được tạo lại. ReplicaSet chỉ đếm số lượng, không so sánh nội dung template với Pod đang chạy.
</details>

## Deployment: rolling update, rollback, probe và tài nguyên {010-011}

**Khái niệm cốt lõi**

**Deployment** quản lý ReplicaSet để **đổi phiên bản mà không gián đoạn**. Mỗi lần template Pod thay đổi, Deployment tạo một ReplicaSet mới, rồi từ từ tăng Pod mới và giảm Pod cũ.

```
Deployment nginx-deployment
   ├── ReplicaSet ...-7f9c (image nginx:1.17.10)  replicas 4 → 3 → 2 → 1 → 0
   └── ReplicaSet ...-5b8d (image nginx:1.27)     replicas 0 → 1 → 2 → 3 → 4
```

File `kubernetes-basic/lab5-deployment-simple/nginx-deployment.yaml`:

```yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # được tạo dư tối đa 1 Pod so với replicas trong lúc update
      maxUnavailable: 0    # không bao giờ để thiếu Pod sẵn sàng → an toàn nhất, chậm hơn
```

```bash
kubectl apply -f nginx-deployment.yaml
kubectl rollout status deployment/nginx-deployment
kubectl set image deployment/nginx-deployment nginx-container=nginx:1.27   # đổi image nhanh
kubectl rollout history deployment/nginx-deployment
kubectl rollout undo deployment/nginx-deployment                 # về bản trước
kubectl rollout undo deployment/nginx-deployment --to-revision=2
kubectl rollout restart deployment/nginx-deployment              # tạo lại toàn bộ Pod (vd: sau khi đổi ConfigMap)
kubectl scale deployment/nginx-deployment --replicas=5
```

**Đi sâu hơn**

*Chiến lược deploy*

- `RollingUpdate` (mặc định, `maxSurge` và `maxUnavailable` mặc định 25%).
- `Recreate`: xoá hết Pod cũ rồi mới tạo Pod mới, có downtime. Dùng khi 2 phiên bản không được chạy song song (ví dụ app ghi vào volume RWO).
- Blue/green và canary không có sẵn trong Deployment; thường làm bằng 2 Deployment + Service/Ingress, hoặc công cụ như Argo Rollouts.
- `rollout history` chỉ giữ 10 ReplicaSet cũ (`revisionHistoryLimit`). Để cột `CHANGE-CAUSE` có nội dung, gắn annotation `kubernetes.io/change-cause` (cờ `--record` cũ đã bị bỏ).
- **Rollback chỉ quay về template Pod cũ**, không quay lại database hay ConfigMap.

*Probe: k8s biết app "khoẻ" bằng cách nào?*

| Probe | Câu hỏi | Khi thất bại |
|---|---|---|
| **startupProbe** | App khởi động xong chưa? | Chưa xong thì tạm hoãn 2 probe kia; quá ngưỡng thì restart container |
| **readinessProbe** | Có nhận request được không? | Pod bị **gỡ khỏi Service** (không restart) |
| **livenessProbe** | Có bị treo không? | kubelet **restart** container |

Không có readinessProbe, rolling update coi Pod là "sẵn sàng" ngay khi container chạy, dù app chưa nghe port, và người dùng bị lỗi trong lúc deploy. Đừng cho livenessProbe kiểm tra database: DB chậm sẽ làm mọi Pod restart dây chuyền.

*Requests, limits và QoS*

- **requests**: lượng CPU/RAM *đặt chỗ*. Scheduler dùng nó để chọn node.
- **limits**: mức trần. Vượt CPU limit thì bị *bóp* (throttle). Vượt memory limit thì bị **OOMKilled** (exit code 137).
- **QoS class** (k8s tự gán, xem trong `kubectl describe pod`): **Guaranteed** (mọi container có requests = limits cho cả CPU và RAM), **Burstable** (có đặt ít nhất một request/limit), **BestEffort** (không đặt gì, bị đuổi khỏi node đầu tiên khi node thiếu RAM).

```yaml
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.27
          resources:
            requests: { cpu: "100m", memory: "64Mi" }   # 100m = 0,1 vCPU
            limits:   { memory: "128Mi" }
          readinessProbe:
            httpGet: { path: /, port: 80 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /, port: 80 }
            initialDelaySeconds: 10
            periodSeconds: 10
```

**Lỗi hay gặp & cách sửa**

- `Waiting for deployment "x" rollout to finish: 1 out of 4 new replicas have been updated...` treo mãi: Pod mới lỗi (ImagePullBackOff, readiness fail). Với `maxUnavailable: 0`, Pod cũ vẫn phục vụ nên không sập. Sửa bằng `kubectl rollout undo`.
- Rollout bị đánh dấu thất bại sau `progressDeadlineSeconds` (mặc định 600 giây): `ProgressDeadlineExceeded` trong `kubectl describe deployment`.
- Pod restart liên tục với `Reason: OOMKilled`: memory limit quá thấp so với app (Java, Node.js hay gặp). Tăng limit hoặc giới hạn heap trong app.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab5: update lên `nginx:1.27`, chạy `kubectl get rs` để thấy 2 ReplicaSet, rồi rollback và xác nhận image bằng `kubectl describe deployment`.

🟡 *Thực hành*: Thêm readinessProbe và requests/limits như mẫu trên. Sau đó cố tình đổi image thành `nginx:9.9.9`. Quan sát `kubectl get pods` và chứng minh bằng `port-forward` rằng trang web vẫn chạy.

<details><summary>Gợi ý</summary>

Với `maxSurge: 1, maxUnavailable: 0`, chỉ 1 Pod mới được tạo và kẹt ở `ImagePullBackOff`; 4 Pod cũ không bị xoá. `kubectl port-forward deployment/nginx-deployment 8080:80` vẫn trả trang nginx. Sửa: `kubectl rollout undo deployment/nginx-deployment`.
</details>

🔴 *Thử thách*: Tạo Deployment với image `polinux/stress` chạy `stress --vm 1 --vm-bytes 200M`, memory limit `128Mi`. Giải thích chuỗi trạng thái bạn thấy, QoS class của Pod, và sửa để Pod chạy ổn định ở class Guaranteed.

<details><summary>Lời giải</summary>

Container cấp phát 200M vượt limit 128Mi → kernel giết tiến trình → `OOMKilled` (exit 137) → restart → `CrashLoopBackOff`. Nếu chỉ đặt limits thì k8s tự gán requests = limits; đặt requests thấp hơn limits thì là Burstable. Để Guaranteed và chạy ổn: đặt cả CPU và memory với requests = limits, memory ≥ 256Mi (hoặc giảm `--vm-bytes`). Dọn: `kubectl delete deployment <tên>`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. readinessProbe thất bại và livenessProbe thất bại khác nhau thế nào?</summary>

Readiness thất bại: Pod vẫn chạy nhưng bị gỡ khỏi danh sách endpoint của Service, không nhận traffic. Liveness thất bại: kubelet giết và khởi động lại container.
</details>

<details><summary>2. Vì sao <code>maxUnavailable: 0</code> cần cluster có thêm tài nguyên trống?</summary>

Vì không được giảm Pod cũ trước, k8s phải tạo Pod mới **dư ra** (maxSurge) rồi mới xoá Pod cũ. Nếu node không còn chỗ cho Pod dư đó, nó nằm `Pending` và rollout bị kẹt.
</details>

## Service NodePort {012-013}

**Khái niệm cốt lõi**

Pod sinh ra và chết đi liên tục, mỗi lần một IP mới. **Service** cho bạn một **địa chỉ cố định** đứng trước một nhóm Pod (chọn bằng label selector) và chia tải giữa chúng. Ví dụ đời thường: số tổng đài 1900 của công ty không đổi, dù nhân viên trực đổi ca liên tục.

Bốn loại Service:

| Loại | Truy cập từ | Ghi chú |
|---|---|---|
| **ClusterIP** (mặc định) | Chỉ trong cluster | IP ảo nội bộ + tên DNS |
| **NodePort** | `<IP-node>:<30000–32767>` | Mở cùng một port trên **mọi node** |
| **LoadBalancer** | IP/DNS của load balancer cloud | Cloud tự tạo LB (trên AWS là NLB/CLB) |
| **ExternalName** | Trong cluster | Chỉ là bí danh DNS (CNAME) trỏ ra tên ngoài |

Mỗi loại "chồng" lên loại trước: NodePort có sẵn ClusterIP, LoadBalancer có sẵn NodePort.

File `kubernetes-basic/lab6-service-NodePort-simple/nginx-nodeport.yaml`:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  type: NodePort
  selector:
    app: nginx            # gửi traffic tới Pod có label này
  ports:
    - protocol: TCP
      port: 80            # port của Service (ClusterIP)
      targetPort: 80      # port container đang nghe
      nodePort: 30099     # port mở trên node; bỏ trống thì k8s tự chọn
```

```
Trình duyệt → <minikube ip>:30099 (nodePort) → Service :80 (port) → Pod :80 (targetPort)
```

```bash
kubectl apply -f nginx-nodeport.yaml
kubectl get svc nginx-service -o wide
kubectl get endpointslices -l kubernetes.io/service-name=nginx-service   # IP các Pod phía sau
minikube ip                          # IP của node minikube
curl http://$(minikube ip):30099     # với driver docker trên Linux, gọi thẳng được
minikube service nginx-service --url # tạo đường hầm; bắt buộc trên macOS/Windows
```

**Đi sâu hơn**

- **kube-proxy** trên mỗi node theo dõi Service và EndpointSlice rồi viết luật iptables (hoặc nftables, chế độ mới GA từ 1.33) để gói tin gửi tới IP:port của Service được chuyển ngẫu nhiên tới một Pod. Service không phải một tiến trình proxy thật, nên `ping` IP Service thường không trả lời.
- **EndpointSlice** thay cho đối tượng Endpoints cũ (Endpoints bị đánh dấu deprecated từ 1.33). Chỉ Pod *Ready* mới nằm trong endpoint, đây là lúc readinessProbe phát huy tác dụng.
- Trên cloud thật, NodePort ít dùng trực tiếp: phải mở Security Group cho dải port cao và client phải biết IP node. Nó hay đóng vai "cửa sau" cho một load balancer bên ngoài, đúng như lab13 làm với ALB.

**Lỗi hay gặp & cách sửa**

- `curl` timeout, `kubectl get endpointslices` trống: selector của Service không khớp label Pod (gõ nhầm `app: ngnix`). So sánh `kubectl get pods --show-labels` với `kubectl describe svc`.
- `Connection refused`: `targetPort` sai so với port app thật sự nghe.
- `spec.ports[0].nodePort: Invalid value: 30099: provided port is already allocated`: Service khác đã dùng port này (lab9 và lab13 cũng dùng 30088/30099). Xoá Service cũ hoặc đổi port.

**Bài tập**

## Service ClusterIP, DNS nội bộ và LoadBalancer {014-016}

**Khái niệm cốt lõi**

**ClusterIP** là loại Service dành cho giao tiếp **bên trong cluster**: backend gọi MongoDB, frontend gọi backend. Không ai ở ngoài truy cập được, đây là điều bạn muốn cho database.

File `kubernetes-basic/lab7-service-ClusterIP-simple/mongo-cluster.yaml` tạo Deployment `mongo` và Service `mongo-service` (port 27017). Ứng dụng trong cluster chỉ cần chuỗi kết nối `mongodb://mongo-service:27017`.

**DNS nội bộ (CoreDNS)**

Mỗi Service có tên DNS theo mẫu:

```
<service>.<namespace>.svc.cluster.local
mongo-service.default.svc.cluster.local  → ClusterIP của Service
```

- Cùng namespace: gọi tắt `mongo-service`.
- Khác namespace: `mongo-service.default` (hoặc tên đầy đủ).
- Pod có file `/etc/resolv.conf` với các *search domain* nên tên ngắn tự được nối đuôi.

```bash
kubectl apply -f mongo-cluster.yaml
kubectl describe svc mongo-service       # xem IP, Endpoints
kubectl run dnstest --rm -it --image=busybox:1.36 -- nslookup mongo-service
kubectl run mongosh --rm -it --image=mongo -- mongosh "mongodb://mongo-service:27017" --eval "db.runCommand({ping:1})"
kubectl port-forward svc/mongo-service 27017:27017   # mở Mongo cho máy bạn khi cần debug, không cần NodePort
```

**Service LoadBalancer** (video 016)

```yaml
spec:
  type: LoadBalancer
  selector: { app: nginx }
  ports: [{ port: 80, targetPort: 80 }]
```

- Trên AWS, controller sẽ tạo một load balancer thật và ghi DNS của nó vào cột `EXTERNAL-IP`. Trên EKS hiện nay nên cài **AWS Load Balancer Controller** để tạo NLB (cùng annotation như `service.beta.kubernetes.io/aws-load-balancer-type`); controller cũ sẵn có trong k8s chỉ tạo Classic LB.
- Trên minikube, `EXTERNAL-IP` sẽ là `<pending>` mãi, cho đến khi bạn chạy `minikube tunnel` ở một terminal riêng.
- 💰 Mỗi Service LoadBalancer = một load balancer tính tiền riêng (ước lượng 0,0225–0,025 USD/giờ mỗi LB ở Singapore, chưa kể phí LCU và IPv4 public). 10 Service là 10 LB. Đây là lý do người ta dùng **Ingress**: một LB cho nhiều app.

**Đi sâu hơn**

- **Headless Service** (`clusterIP: None`): không có IP ảo, DNS trả về **thẳng IP từng Pod**. Dùng cho StatefulSet (database cần gọi đúng từng bản sao).
- `externalTrafficPolicy: Local` giữ IP nguồn của client và tránh nhảy qua node khác, đổi lại phân tải có thể không đều.
- `sessionAffinity: ClientIP` để cùng một client luôn vào cùng Pod (chỉ nên dùng khi app chưa stateless).

**Lỗi hay gặp & cách sửa**

- `getaddrinfo ENOTFOUND mongo` trong log backend: tên Service sai, hoặc Service nằm namespace khác. Thử `nslookup` từ Pod busybox trong *cùng namespace* với backend.
- Mọi DNS lookup đều lỗi: Pod CoreDNS hỏng. `kubectl get pods -n kube-system -l k8s-app=kube-dns`.
- `EXTERNAL-IP <pending>` trên minikube hoặc kops không có cloud controller đúng: không có ai tạo LB. Dùng `minikube tunnel`, hoặc kiểm tra quyền IAM/controller trên AWS.

## Ingress: định tuyến theo sub-domain và path {017-018}

**Khái niệm cốt lõi**

**Ingress** là bộ luật định tuyến HTTP/HTTPS: *host nào, path nào* thì chuyển tới Service nào. Nhưng bản thân Ingress chỉ là "tờ giấy ghi luật". Cần một **Ingress controller** (một reverse proxy chạy trong cluster, như nginx) đọc luật đó và thực sự nhận traffic. Không có controller thì Ingress không làm gì cả.

```
                     ┌─ host service-a.localhost ─► Service service-a ─► Pod A
Client ─► LB/NodePort ─► Ingress controller ─┤
                     └─ host service-b.localhost ─► Service service-b ─► Pod B
```

Lab8 có hai file trong `kubernetes-basic/lab8-ingress-simple/`:

```yaml
# ingress-demo.yaml - định tuyến theo SUB-DOMAIN (host)
spec:
  rules:
  - host: "service-a.localhost"
    http:
      paths:
      - pathType: Prefix
        path: "/"
        backend:
          service: { name: service-a, port: { number: 3000 } }
  - host: "service-b.localhost"
    # ... tương tự cho service-b
```

```yaml
# ingress-demo-path.yaml - định tuyến theo PATH trên cùng host
metadata:
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /   # /service-a/xyz → gửi "/" tới app
spec:
  rules:
  - host: "localhost"
    http:
      paths:
      - { pathType: Prefix, path: "/service-a", backend: { service: { name: service-a, port: { number: 3000 } } } }
      - { pathType: Prefix, path: "/service-b", backend: { service: { name: service-b, port: { number: 3000 } } } }
```

```bash
minikube addons enable ingress          # cài ingress-nginx controller vào namespace ingress-nginx
kubectl apply -f ingress-demo.yaml
kubectl get ingress                     # đợi cột ADDRESS có IP
curl -H "Host: service-a.localhost" http://$(minikube ip)/   # Linux + driver docker: gọi thẳng IP node
minikube tunnel                         # hoặc mở tunnel, rồi vào http://service-a.localhost trên trình duyệt
```

Trình duyệt hiện đại tự phân giải mọi tên `*.localhost` về `127.0.0.1`, nên không cần sửa `/etc/hosts` khi dùng `minikube tunnel`. Với domain khác (ví dụ `app.test`), thêm dòng `<minikube ip> app.test` vào `/etc/hosts`.

**Đi sâu hơn**

*pathType*: `Prefix` khớp theo từng đoạn path (`/api` khớp `/api` và `/api/users`, không khớp `/apix`). `Exact` khớp chính xác. `ImplementationSpecific` tuỳ controller.

*IngressClass*: trường `spec.ingressClassName: nginx` chọn controller nào xử lý Ingress này. File lab8 không ghi, vẫn chạy vì addon minikube đặt nginx làm IngressClass mặc định. Lab13 thì ghi rõ, đó là cách nên làm.

⚠️ *Tình trạng ingress-nginx (quan trọng, cập nhật 2026)*

- Tháng 11/2025, Kubernetes SIG Network thông báo **nghỉ hưu dự án ingress-nginx**. Bảo trì "best-effort" chỉ kéo dài đến **tháng 3/2026**. Sau đó: không có bản phát hành mới, không sửa lỗi, **không vá lỗ hổng bảo mật**.
- Các cài đặt hiện có vẫn chạy, Helm chart và image vẫn tải được, repo GitHub chuyển sang read-only. Bạn vẫn dùng được trong lab trên minikube, nhưng **không nên chọn cho hệ thống mới**.
- **Ingress API** (`networking.k8s.io/v1`) thì **không bị xoá**, chỉ "đóng băng tính năng". Bạn có thể giữ YAML Ingress và đổi sang controller khác (Traefik, HAProxy, Kong, NGINX của F5, AWS Load Balancer Controller…).
- Hướng được khuyến nghị: **Gateway API**, bộ API thế hệ mới (GA từ 2023) tách vai trò rõ ràng: `GatewayClass` (loại hạ tầng) → `Gateway` (điểm vào, do đội platform quản lý) → `HTTPRoute` (luật định tuyến, do đội app quản lý). Có công cụ `ingress2gateway` để chuyển đổi YAML.

```bash

```

Ví dụ HTTPRoute tương đương luật host của lab8 (cần đã cài một Gateway implementation như Envoy Gateway, NGINX Gateway Fabric, Traefik…):

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: service-a
spec:
  parentRefs:
    - name: my-gateway          # Gateway do đội platform tạo
  hostnames: ["service-a.localhost"]
  rules:
    - backendRefs:
        - name: service-a
          port: 3000
```

**Lỗi hay gặp & cách sửa**

- `503 Service Temporarily Unavailable`: khớp luật nhưng Service không có Pod Ready phía sau.

## Persistent Volume & PVC: dữ liệu sống lâu hơn Pod {019-020}

**Khái niệm cốt lõi**

Filesystem của container là tạm thời: Pod bị xoá thì dữ liệu mất. Với MySQL, điều đó là thảm hoạ. Kubernetes tách bài toán lưu trữ thành hai vai:

- **PersistentVolume (PV)**: một "ổ đĩa" thật trong cluster (đĩa trên node, EBS, EFS, NFS…). Tài nguyên cấp **cluster**, thường do admin hoặc hệ thống tạo.
- **PersistentVolumeClaim (PVC)**: **phiếu yêu cầu** của app: "tôi cần 1Gi, đọc-ghi từ một node". Tài nguyên thuộc **namespace**.
- k8s **bind** (ghép) PVC với một PV phù hợp. Pod chỉ tham chiếu tới PVC, không cần biết ổ đĩa thật là gì.

Ví dụ đời thường: PV là căn phòng trong khách sạn, PVC là phiếu đặt phòng, Pod là khách. Khách trả phòng (Pod bị xoá) thì đồ đạc trong phòng (dữ liệu) vẫn còn nếu phiếu đặt chưa huỷ.

File `kubernetes-basic/lab9-persistent-volume/persistent-volume.yaml`:

```yaml
kind: PersistentVolume
spec:
  capacity: { storage: 1Gi }
  accessModes: [ReadWriteOnce]
  hostPath: { path: /data/mysql }      # thư mục trên node minikube (chỉ dùng để học)
---
kind: PersistentVolumeClaim
spec:
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
---
# Deployment MySQL
      volumeMounts:
        - name: mysql-persistent-storage
          mountPath: /var/lib/mysql      # nơi MySQL lưu dữ liệu
      volumes:
        - name: mysql-persistent-storage
          persistentVolumeClaim: { claimName: my-pvc }
```

```bash
kubectl create -f persistent-volume.yaml
kubectl get pv,pvc            # STATUS phải là Bound
minikube service mysql-service --url
# kết nối bằng MySQL Workbench / mysql client, chạy script.sql
kubectl delete pod mysql-deployment-<xxxxx>   # Pod mới được tạo lại, dữ liệu vẫn còn
```

**Đi sâu hơn**

*StorageClass và dynamic provisioning*

Thực tế không ai tạo PV bằng tay. Admin tạo **StorageClass** (mô tả *loại* ổ đĩa), app chỉ tạo PVC, và **CSI driver** (plugin lưu trữ) tự tạo ổ đĩa + PV tương ứng.

```bash
kubectl get storageclass
# minikube: "standard (default)", provisioner k8s.io/minikube-hostpath
```

⚠️ Điều thú vị trong lab9: PVC `my-pvc` **không ghi `storageClassName`**, nên k8s gán StorageClass mặc định `standard` cho nó. Kết quả là minikube **tự tạo một PV mới** (tên kiểu `pvc-1a2b...`) thay vì dùng `my-pv`, và `my-pv` vẫn nằm ở trạng thái `Available`. Kiểm chứng bằng `kubectl get pv`. Muốn PVC bind vào đúng PV tĩnh, đặt `storageClassName: ""` ở cả hai (hoặc cùng một tên), hoặc dùng `volumeName: my-pv` trong PVC.

Trên AWS: cài **Amazon EBS CSI driver** và tạo StorageClass `gp3`. Lưu ý một ổ EBS chỉ nằm trong **một AZ**, Pod dùng nó phải chạy ở node cùng AZ; đặt `volumeBindingMode: WaitForFirstConsumer` để ổ được tạo đúng AZ với Pod.

*Access modes*

| Mode | Ý nghĩa | Ví dụ |
|---|---|---|
| `ReadWriteOnce` (RWO) | Đọc-ghi, gắn vào **một node** | EBS, hostPath |
| `ReadOnlyMany` (ROX) | Chỉ đọc, nhiều node | NFS |
| `ReadWriteMany` (RWX) | Đọc-ghi, nhiều node | EFS, NFS |
| `ReadWriteOncePod` (RWOP) | Đọc-ghi, chỉ **một Pod** | CSI hỗ trợ |

RWO giới hạn theo *node*, không phải theo Pod: 2 Pod trên cùng node vẫn gắn được, nên với database hãy dùng `replicas: 1` hoặc RWOP để tránh 2 MySQL cùng ghi một thư mục.

*Reclaim policy*: khi PVC bị xoá, PV làm gì? `Delete` (mặc định với dynamic provisioning: **xoá luôn ổ đĩa và dữ liệu**) hoặc `Retain` (giữ lại, admin tự xử lý). Với dữ liệu quan trọng, dùng StorageClass `reclaimPolicy: Retain` và vẫn phải **backup** (snapshot EBS, `mysqldump`).

**Lỗi hay gặp & cách sửa**

- PVC `Pending` mãi, Event `no persistent volumes available for this claim and no storage class is set`: không có PV phù hợp và không có StorageClass mặc định. Kiểm tra dung lượng/accessModes/storageClassName.
- Pod `Pending` với `pod has unbound immediate PersistentVolumeClaims`: hệ quả của lỗi trên.
- Pod MySQL `CrashLoopBackOff`, log `--initialize specified but the data directory has files in it`: thư mục volume còn dữ liệu cũ hoặc của phiên bản khác. Với lab, xoá PVC/PV rồi tạo lại.
- Pod mới kẹt `ContainerCreating`, Event `Multi-Attach error for volume`: volume RWO vẫn đang gắn vào node cũ (hay gặp với EBS khi rolling update). Dùng strategy `Recreate` cho Deployment có volume RWO.

<details><summary>Lời giải</summary>

PV tĩnh mặc định có `persistentVolumeReclaimPolicy: Retain`. Xoá PVC thì PV chuyển sang `Released` (không tự bind lại cho PVC mới), dữ liệu trong `/data/mysql` vẫn còn. Muốn dùng lại PV phải xoá trường `claimRef` hoặc xoá rồi tạo lại PV. Dọn: `kubectl delete -f persistent-volume.yaml` và `minikube ssh -- sudo rm -rf /data/mysql`.
</details>

🔴 *Thử thách*: Đổi Deployment MySQL sang `replicas: 2` (vẫn dùng chung PVC RWO). Chuyện gì xảy ra trên minikube (1 node)? Trên cluster nhiều node với EBS thì sao? Vì sao đây không phải cách nhân bản database?

<details><summary>Lời giải</summary>

Trên minikube cả 2 Pod cùng node nên đều gắn được volume, nhưng Pod thứ hai không khởi động được vì InnoDB khoá file (`Unable to lock ./ibdata1`) hoặc tệ hơn là làm hỏng dữ liệu. Trên nhiều node với EBS, Pod thứ hai kẹt `Multi-Attach error`. Nhân bản DB cần mỗi bản sao có **volume riêng** và cơ chế replication của chính DB, tức là StatefulSet (phần sau) hoặc dịch vụ managed như RDS.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao Pod tham chiếu PVC chứ không tham chiếu thẳng PV?</summary>

Để tách vai trò: dev chỉ nói "cần 10Gi RWO" (PVC), không cần biết hạ tầng là EBS hay NFS. Cùng một YAML chạy được trên minikube, EKS hay GKE, mỗi nơi tự cấp PV theo StorageClass của mình.
</details>

## ConfigMap: tách cấu hình khỏi image {021-022}

**Khái niệm cốt lõi**

Nguyên tắc 12-factor: **cùng một image** chạy cho dev, staging, prod; chỉ cấu hình khác nhau. **ConfigMap** lưu cấu hình dạng key/value (hoặc cả file) và đưa vào Pod theo hai cách: **biến môi trường** hoặc **file trong volume**.

File `kubernetes-basic/lab10-config-map/configmap-simple.yaml`:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: my-configmap
data:
  MYSQL_ROOT_PASSWORD: "123456789"   # ⚠️ chỉ để học - mật khẩu KHÔNG nên nằm trong ConfigMap
  name: "Linh"
  age: "20"                          # giá trị luôn là chuỗi, số phải để trong ngoặc kép
---
# trong Deployment:
          envFrom:
            - configMapRef:
                name: my-configmap   # mọi key thành biến môi trường
```

```bash
kubectl apply -f configmap-simple.yaml
kubectl get configmap my-configmap -o yaml
kubectl exec deploy/mysql-deployment -- env | grep -E 'name|age'
kubectl create configmap app-config --from-literal=LOG_LEVEL=debug --from-file=nginx.conf   # tạo nhanh
```

**Đi sâu hơn**

*Ba cách dùng ConfigMap*

```yaml
env:                                   # 1. lấy từng key, đổi tên được
  - name: APP_NAME
    valueFrom: { configMapKeyRef: { name: my-configmap, key: name } }
envFrom:                               # 2. lấy toàn bộ key
  - configMapRef: { name: my-configmap }
volumeMounts:                          # 3. mỗi key thành một file
  - { name: cfg, mountPath: /etc/app }
volumes:
  - name: cfg
    configMap: { name: my-configmap }
```

- **Cập nhật ConfigMap không tự đổi biến môi trường** của Pod đang chạy. Biến env chỉ đọc lúc container khởi động. Cần `kubectl rollout restart deployment/<tên>`.
- ConfigMap gắn dạng **volume** thì file được kubelet cập nhật sau một khoảng trễ (khoảng dưới một phút), *trừ khi* gắn bằng `subPath`. App phải tự đọc lại file.
- Giới hạn kích thước 1 MiB. Có thể đặt `immutable: true` để tránh sửa nhầm và giảm tải cho apiserver.
- Mẹo trong thực tế: đặt tên ConfigMap có hậu tố phiên bản (`app-config-v2`), hoặc dùng Kustomize `configMapGenerator` (tự thêm hash vào tên), để mỗi thay đổi cấu hình tạo ra một rollout mới và rollback được.

**Lỗi hay gặp & cách sửa**

- Pod kẹt `CreateContainerConfigError`, Event `configmap "my-configmap" not found`: ConfigMap chưa tạo hoặc ở namespace khác. ConfigMap phải **cùng namespace** với Pod.
- `couldn't find key age in ConfigMap`: gõ sai key. Thêm `optional: true` nếu key không bắt buộc.
- `cannot unmarshal number into Go struct field ConfigMap.data of type string`: viết `age: 20` không có ngoặc kép.

**Bài tập**

🟢 *Cơ bản*: Chạy lab10, kết nối MySQL bằng mật khẩu trong ConfigMap. Đổi `name` thành tên bạn, `apply`, rồi kiểm tra env trong Pod: đã đổi chưa? Làm gì để đổi?

🟡 *Thực hành*: Tạo ConfigMap chứa file `index.html`, gắn dạng volume vào `/usr/share/nginx/html` của một Deployment nginx. Sửa ConfigMap và đo xem bao lâu sau trang web đổi nội dung (không restart Pod).

<details><summary>Gợi ý</summary>

`kubectl create configmap web --from-file=index.html`, rồi `kubectl create configmap web --from-file=index.html --dry-run=client -o yaml | kubectl apply -f -` để cập nhật. Nội dung thường đổi sau vài chục giây. Nếu bạn dùng `subPath: index.html` thì sẽ không bao giờ tự đổi.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao lab10 để mật khẩu MySQL trong ConfigMap là không nên?</summary>

ConfigMap được thiết kế cho dữ liệu không nhạy cảm: hiển thị thẳng khi `kubectl get -o yaml`, quyền đọc thường được cấp rộng rãi, và không có cơ chế bảo vệ riêng. Mật khẩu nên nằm trong Secret (lab11), tốt hơn nữa là trong secret manager bên ngoài.
</details>

## Secret: base64 không phải là mã hoá {023-024}

**Khái niệm cốt lõi**

**Secret** giống ConfigMap nhưng dành cho dữ liệu nhạy cảm (mật khẩu, token, chứng chỉ TLS). k8s đối xử với Secret cẩn thận hơn một chút: có thể bật mã hoá trong etcd, kubelet giữ nó trong RAM (tmpfs) khi gắn vào Pod, và RBAC có thể tách quyền đọc Secret khỏi quyền đọc ConfigMap.

File `kubernetes-basic/lab11-secret-simple/secret-simple.yaml`:

```yaml
apiVersion: v1
kind: Secret
metadata: { name: my-secret }
type: Opaque
data:
  MYSQL_ROOT_USER: cm9vdA==                          # base64 của "root"
  MYSQL_ROOT_PASSWORD: VmVyeVN0cm9uZ1Bhc3N3b3JkMTIz  # base64 của "VeryStrongPassword123"
---
          env:
            - name: MYSQL_ROOT_PASSWORD
              valueFrom:
                secretKeyRef: { name: my-secret, key: MYSQL_ROOT_PASSWORD }
```

```bash
echo -n "root" | base64                 # -n: không thêm ký tự xuống dòng (quên là sai mật khẩu!)
kubectl get secret my-secret -o jsonpath="{.data.MYSQL_ROOT_PASSWORD}" | base64 --decode
# Cách gọn hơn, không phải tự base64:
kubectl create secret generic my-secret \
  --from-literal=MYSQL_ROOT_PASSWORD='VeryStrongPassword123' --dry-run=client -o yaml
```

⚠️ **Base64 là mã hoá *định dạng* (encoding), không phải mã hoá *bảo mật* (encryption).** Ai đọc được YAML là giải ra mật khẩu trong một giây, như lệnh `base64 --decode` ở trên. Commit file `secret-simple.yaml` lên Git công khai = công khai mật khẩu.

**Đi sâu hơn**

Tài liệu chính thức lưu ý: mặc định Secret được lưu **không mã hoá** trong etcd; ai có quyền API hoặc quyền vào etcd đều đọc được; và **ai được tạo Pod trong namespace là đọc được mọi Secret của namespace đó** (chỉ cần tạo Pod gắn Secret vào). Cách bảo vệ, từ dễ đến khó:

1. **Không commit Secret thô vào Git.** Dùng trường `stringData` khi viết tay (k8s tự base64), và tạo Secret qua pipeline thay vì lưu file.
2. **RBAC least privilege**: chỉ cho đúng ServiceAccount/người cần quyền `get` Secret. Quyền `list` Secret cũng lộ toàn bộ nội dung.
3. **Bật encryption at rest** cho etcd (`EncryptionConfiguration`, tốt nhất là provider KMS). Trên EKS, bật mã hoá envelope bằng AWS KMS.
4. **Dùng secret store bên ngoài**: AWS Secrets Manager / SSM Parameter Store, đưa vào cluster qua **External Secrets Operator** hoặc **Secrets Store CSI Driver**. Hoặc mã hoá trước khi commit bằng **Sealed Secrets** / **SOPS**.
5. Gắn Secret dạng **file** thay vì env khi có thể: biến môi trường dễ lộ qua log crash, `env` dump, tiến trình con.

Các `type` hay gặp: `Opaque` (tuỳ ý), `kubernetes.io/tls` (cert + key cho Ingress), `kubernetes.io/dockerconfigjson` (đăng nhập registry private, dùng với `imagePullSecrets`). Giới hạn 1 MiB, có `immutable: true` như ConfigMap.

Lưu ý về lab11: image `mysql` chính thức chỉ đọc các biến như `MYSQL_ROOT_PASSWORD`, `MYSQL_DATABASE`, `MYSQL_USER`, `MYSQL_PASSWORD`. Biến `MYSQL_ROOT_USER` không có tác dụng gì (user root luôn tên `root`), nó chỉ để minh hoạ cách đọc nhiều key.

**Lỗi hay gặp & cách sửa**

- Đăng nhập MySQL báo `Access denied for user 'root'`: tạo base64 bằng `echo` thiếu `-n`, mật khẩu thật có thêm `\n` ở cuối. Hoặc PVC còn dữ liệu cũ từ lab9/lab10 với mật khẩu khác (MySQL chỉ đặt mật khẩu root ở **lần khởi tạo đầu tiên**).
- `Error from server (BadRequest): error when creating "secret-simple.yaml": Secret in version "v1" cannot be handled as a Secret: illegal base64 data`: giá trị trong `data` không phải base64 hợp lệ. Dùng `stringData` nếu muốn viết chữ thường.
- `CreateContainerConfigError: secret "my-secret" not found`: Secret khác namespace hoặc chưa tạo.

**Bài tập**

🟢 *Cơ bản*: Chạy lab11 với mật khẩu mới của bạn, viết bằng `stringData` thay vì `data`. Xác nhận `kubectl get secret -o yaml` vẫn hiện dạng base64.

🟡 *Thực hành*: Gắn Secret dạng volume vào `/etc/mysql-secret` (chỉ đọc) và dùng biến `MYSQL_ROOT_PASSWORD_FILE=/etc/mysql-secret/MYSQL_ROOT_PASSWORD` (image mysql hỗ trợ hậu tố `_FILE`). Kiểm tra `env` trong Pod không còn lộ mật khẩu.

<details><summary>Gợi ý</summary>

```yaml
env:
  - { name: MYSQL_ROOT_PASSWORD_FILE, value: /etc/mysql-secret/MYSQL_ROOT_PASSWORD }
volumeMounts:
  - { name: secret, mountPath: /etc/mysql-secret, readOnly: true }
volumes:
  - name: secret
    secret: { secretName: my-secret }
```

Nhớ xoá dữ liệu PVC cũ trước, vì mật khẩu chỉ áp dụng khi MySQL khởi tạo lần đầu.
</details>

🔴 *Thử thách*: Lưu mật khẩu trong **AWS SSM Parameter Store** (SecureString, miễn phí với tham số standard), cài External Secrets Operator trên minikube bằng Helm, cấu hình `SecretStore` + `ExternalSecret` để tự sinh Secret `my-secret`. Tối thiểu hoá quyền IAM của access key dùng cho việc này.

<details><summary>Gợi ý</summary>

IAM policy chỉ cần `ssm:GetParameter` (và `kms:Decrypt` nếu dùng key KMS riêng) trên đúng ARN tham số. Trên minikube không có IAM role nên bạn phải đưa access key vào một Secret cho ESO đọc. Đó chính là "bài toán con gà quả trứng" mà trên EKS được giải bằng IRSA/EKS Pod Identity. Dọn: `helm uninstall`, xoá tham số SSM, xoá access key.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Đồng nghiệp nói "Secret an toàn vì đã base64". Bạn phản biện thế nào?</summary>

Base64 ai cũng giải được, không cần khoá. An toàn của Secret đến từ RBAC chặt, mã hoá etcd (encryption at rest), không đưa vào Git, và tốt nhất là nguồn gốc nằm ở secret manager bên ngoài.
</details>

<details><summary>2. User chỉ có quyền tạo Deployment trong namespace <code>dev</code>, không có quyền <code>get secrets</code>. Họ có đọc được Secret không?</summary>

Có. Họ tạo một Deployment gắn Secret vào env hoặc volume, rồi đọc log hay `exec`. Vì vậy quyền tạo workload trong một namespace gần như tương đương quyền đọc Secret của namespace đó. Hãy tách Secret quan trọng sang namespace mà ít người có quyền.
</details>

## StatefulSet: khi Pod cần danh tính riêng {025}

**Khái niệm cốt lõi**

Deployment coi các Pod là **như nhau, thay thế được** (gia súc). Database cụm (MySQL replication, MongoDB replica set, Kafka, Elasticsearch) thì mỗi bản sao **có vai trò và dữ liệu riêng** (thú cưng). **StatefulSet** cho mỗi Pod:

| | Deployment | StatefulSet |
|---|---|---|
| Tên Pod | `web-7f9c-x2k4p` (ngẫu nhiên) | `mysql-0`, `mysql-1`, `mysql-2` (cố định) |
| DNS từng Pod | Không | `mysql-0.mysql.default.svc.cluster.local` (qua headless Service) |
| Volume | Thường dùng chung 1 PVC | **Mỗi Pod một PVC riêng** (`volumeClaimTemplates`) |
| Thứ tự tạo/xoá | Song song | Tuần tự: 0 → 1 → 2, xoá ngược lại |
| Pod chết rồi tạo lại | Tên mới, có thể volume khác | **Cùng tên, cùng PVC** |

```yaml
apiVersion: v1
kind: Service
metadata: { name: mongo }
spec:
  clusterIP: None              # headless: DNS trả về IP từng Pod
  selector: { app: mongo }
  ports: [{ port: 27017 }]
---
apiVersion: apps/v1
kind: StatefulSet
metadata: { name: mongo }
spec:
  serviceName: mongo           # gắn với headless Service ở trên
  replicas: 3
  selector: { matchLabels: { app: mongo } }
  template:
    metadata: { labels: { app: mongo } }
    spec:
      containers:
        - name: mongo
          image: mongo:7
          volumeMounts: [{ name: data, mountPath: /data/db }]
  volumeClaimTemplates:        # tự sinh PVC data-mongo-0, data-mongo-1, data-mongo-2
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 1Gi } }
```

**Đi sâu hơn**

- StatefulSet **không tự biến app thành cụm**. Nó chỉ cho tên, DNS và ổ đĩa ổn định; việc cấu hình replication (ai là primary, ai là secondary) vẫn do app hoặc một **Operator** lo (ví dụ MongoDB Community Operator, CloudNativePG cho PostgreSQL).
- Scale từ 3 xuống 1 **không xoá PVC** của `mongo-1`, `mongo-2` theo mặc định, để bạn không mất dữ liệu. Có thể đổi hành vi bằng `persistentVolumeClaimRetentionPolicy`. Nhớ xoá PVC bằng tay khi dọn lab.
- Rolling update đi theo thứ tự ngược (từ Pod số lớn nhất), có thể dùng `partition` để chỉ cập nhật một phần (kiểu canary).
- Trên AWS, câu hỏi đầu tiên nên là: **có cần tự chạy DB trong k8s không?** RDS/DocumentDB/ElastiCache lo backup, failover, vá lỗi. Tự chạy StatefulSet chỉ đáng khi bạn có lý do rõ (chi phí, phiên bản đặc biệt, môi trường không có dịch vụ managed).

**Bài tập**

🟢 *Cơ bản*: Apply YAML trên vào minikube. Xem thứ tự Pod được tạo (`kubectl get pods -w`) và PVC sinh ra (`kubectl get pvc`). Xoá `mongo-1` và xác nhận Pod mới vẫn tên `mongo-1` và dùng lại `data-mongo-1`.

🟡 *Thực hành*: Từ Pod busybox, `nslookup mongo` (headless) và `nslookup mongo-0.mongo`. So sánh với `nslookup` một Service ClusterIP thường.

<details><summary>Lời giải</summary>

Service headless trả về **3 bản ghi A**, mỗi cái là IP một Pod. `mongo-0.mongo` trả về đúng IP của Pod `mongo-0`. Service ClusterIP thường chỉ trả về **1 IP ảo**. Dọn dẹp: `kubectl delete statefulset mongo; kubectl delete svc mongo; kubectl delete pvc -l app=mongo` (hoặc xoá từng PVC `data-mongo-N`).
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Lab13 chạy MongoDB bằng Deployment không có volume. Rủi ro là gì?</summary>

Pod Mongo bị xoá, bị đuổi khỏi node hay node chết là **mất toàn bộ dữ liệu**, vì dữ liệu nằm trong filesystem tạm của container. Bản tối thiểu nên có PVC; bản tốt hơn là StatefulSet có `volumeClaimTemplates` hoặc dùng dịch vụ managed.
</details>

## Kops: dựng cluster Kubernetes thật trên AWS {026-027}

**Khái niệm cốt lõi**

minikube chỉ có 1 node trên máy bạn. Để có cluster nhiều node trên AWS, có ba hướng:

| Cách | Ai lo control plane | Mức công sức | Chi phí control plane |
|---|---|---|---|
| **kubeadm** trên EC2 tự tạo | Bạn, từng bước | Cao nhất | Tiền EC2 |
| **kops** (Kubernetes Operations) | kops tạo EC2 + cấu hình giúp, bạn vận hành | Trung bình | Tiền EC2 chạy control plane |
| **Amazon EKS** | AWS | Thấp nhất | 0,10 USD/giờ mỗi cluster (bản k8s trong thời gian hỗ trợ chuẩn) |

**kops** giống "Terraform dành riêng cho cluster k8s": bạn khai báo cluster (bao nhiêu node, loại máy, AZ nào), kops lưu cấu hình trong **S3 (state store)**, rồi tạo VPC, subnet, Auto Scaling Group, IAM role, bản ghi DNS và cài Kubernetes lên EC2.

Luồng lệnh của `kubernetes-basic/lab12-kops/lab12.sh`:

```bash
# Trên một EC2 Ubuntu làm "kops admin server"
aws s3api create-bucket --bucket udemy-devops-kops-<tên-bạn> --region ap-southeast-1 \
  --create-bucket-configuration LocationConstraint=ap-southeast-1   # ngoài us-east-1 bắt buộc có tham số này
aws s3api put-bucket-versioning --bucket udemy-devops-kops-<tên-bạn> --versioning-configuration Status=Enabled
export KOPS_STATE_STORE=s3://udemy-devops-kops-<tên-bạn>      # khỏi phải gõ --state mỗi lệnh

kops create cluster --name=<domain-của-bạn> \
  --zones=ap-southeast-1a,ap-southeast-1c \
  --node-count=2 --node-size=t3.small \
  --control-plane-size=t3.small \
  --dns-zone=<domain-của-bạn> --node-volume-size=10
kops update cluster --name=<domain> --yes --admin   # tạo tài nguyên thật + ghi ~/.kube/config
kops validate cluster --wait 10m
kubectl get nodes
kops delete cluster --name=<domain> --yes           # XOÁ khi học xong
```

Video dùng `--master-size`, `--master-volume-size`: đó là tên cờ cũ. Trang CLI của kops bản hiện hành dùng `--control-plane-size` (và các cờ `--control-plane-*` tương tự).

`create cluster` chỉ **ghi cấu hình vào S3**, chưa tạo gì. `update cluster --yes` mới tạo tài nguyên, giống `terraform plan` rồi `apply`.

**Đi sâu hơn**

- **Không có domain?** Đặt tên cluster kết thúc bằng `.k8s.local` (ví dụ `udemy.k8s.local`) và dùng `--dns=none`. kops sẽ không cần Route53 hosted zone. Đây là cách rẻ nhất để học; bạn không phải mua domain như video.
- **State store S3:** tài liệu kops khuyến nghị **bật versioning** để khôi phục cấu hình cũ. Bucket chứa thông tin nhạy cảm (cấu hình, chứng chỉ) nên phải chặn public access.
- **Quyền IAM:** video cấp `AdministratorAccess` cho EC2 kops cho nhanh. Tài liệu kops liệt kê các quyền thực sự cần: EC2, Route53, S3, IAM, VPC, SQS, EventBridge (full access). Dù vậy đây vẫn là quyền rất lớn; chỉ dùng trong tài khoản học tập và xoá role khi xong.
- **CNI mặc định của kops hiện là Cilium.** Phiên bản kops đi theo phiên bản k8s (kops 1.37 cho k8s 1.37).
- **Ubuntu 24.04 không còn gói `awscli` trong apt** như lệnh trong lab. Cài AWS CLI v2 bằng bộ cài chính thức của AWS (hoặc `sudo snap install aws-cli --classic`).
- **kubeconfig hết hạn:** `--admin` tạo chứng chỉ admin có hạn (mặc định 18 giờ). Hôm sau gặp lỗi `You must be logged in to the server (Unauthorized)` thì chạy `kops export kubecfg --admin` (như ghi chú trong `lab13.md`).
- **Khi nào dùng kops, khi nào EKS?** kops cho bạn toàn quyền control plane và hiểu sâu hệ thống, nhưng bạn tự nâng cấp, tự backup etcd, tự xử lý sự cố. Trong doanh nghiệp trên AWS, **EKS** là lựa chọn mặc định (chương sau của khoá học). Lưu ý EKS tính 0,60 USD/giờ nếu cluster chạy bản k8s đã hết hỗ trợ chuẩn (extended support), nên phải nâng cấp đúng hạn.

💰 **Chi phí (ước lượng, ap-southeast-1)**

- 3 EC2 `t3.small` (1 control plane + 2 node): khoảng 0,026 USD/giờ mỗi máy → khoảng **1,9 USD/ngày**.
- Cộng thêm: EC2 kops admin server, EBS (gp3, vài GB mỗi máy), IPv4 public (0,005 USD/giờ mỗi IP), Route53 hosted zone (0,50 USD/tháng) và domain nếu bạn mua.
- Nếu kops tạo load balancer cho API, hoặc bạn tạo ALB ở lab13: thêm khoảng 0,6 USD/ngày mỗi LB.
- Tổng cộng có thể **3–5 USD/ngày** nếu quên xoá. Làm lab trong một buổi và chạy `kops delete cluster --yes` ngay sau đó.

**Lỗi hay gặp & cách sửa**

- `IllegalLocationConstraintException` khi tạo bucket: thiếu `--create-bucket-configuration LocationConstraint=<region>`.
- `kops validate` báo node `NotReady` hoặc `machine ... has not yet joined cluster` quá 10 phút: kiểm tra quota vCPU của tài khoản, AMI/instance type có ở AZ đó không, DNS đã delegate đúng chưa (`dig NS <domain>`).
- `error reading cluster configuration: ... NoSuchBucket` hoặc `cluster not found`: sai `--state`, hoặc biến `KOPS_STATE_STORE` chưa export trong shell mới.
- `dial tcp: lookup api.<domain>: no such host`: DNS chưa lan truyền; với domain mới mua phải đợi, hoặc dùng `.k8s.local`.

<details><summary>1. <code>kops create cluster</code> và <code>kops update cluster --yes</code> khác nhau thế nào?</summary>

## Lab13 · Triển khai React + Express + MongoDB lên Kubernetes, tổng kết {028-032}

**Khái niệm cốt lõi**

Đây là bài tổng hợp toàn chương: đưa ứng dụng 3 tầng từ `docker-compose` lên cluster kops.

```
Internet
   │ HTTP :80
ALB (tạo tay)  ── Target Group (instance, port = NodePort của ingress-nginx, vd 30927)
   │
Node EC2 :30927 → ingress-nginx controller ──┬─ /api → Service backend (3000) → 2 Pod backend
                                             └─ /    → Service frontend (3000) → 2 Pod frontend
Pod backend → Service mongo (ClusterIP 27017) → 1 Pod mongo:4.2.0
Image backend/frontend kéo từ ECR
```

Các bước trong `kubernetes-basic/lab13-deploy-resources-to-kubernetes/lab13.md`:

1. Chạy thử bằng Docker Compose (nhớ thêm rồi bỏ dòng `"proxy": "http://backend:3000"` trong `frontend/package.json`).
2. Tạo 2 repo ECR, build và push image backend, frontend.
3. Viết `lab13.yaml`: 3 Deployment, 3 Service, 1 Ingress.
4. Cài ingress-nginx controller bản bare-metal (Service kiểu NodePort).
5. `kubectl apply -f lab13.yaml`, kiểm tra Pod, Service, Ingress.
6. Tạo ALB + Target Group trỏ tới NodePort của controller, mở Security Group của node cho SG của ALB.
7. Dọn dẹp toàn bộ.

```bash
# ECR (thay <account-id> bằng ID tài khoản CỦA BẠN, không dùng 430950558682 của giảng viên)
aws ecr create-repository --repository-name devops-lab13-backend --region ap-southeast-1
aws ecr get-login-password --region ap-southeast-1 | \
  docker login --username AWS --password-stdin <account-id>.dkr.ecr.ap-southeast-1.amazonaws.com
docker build -t <account-id>.dkr.ecr.ap-southeast-1.amazonaws.com/devops-lab13-backend:v1 ./backend
docker push <account-id>.dkr.ecr.ap-southeast-1.amazonaws.com/devops-lab13-backend:v1

kubectl apply -f lab13.yaml
kubectl get pods,svc,ingress
kubectl get svc -n ingress-nginx          # lấy NodePort của cổng 80 cho Target Group
kubectl logs deploy/backend-deployment    # backend có kết nối được "mongo" không?
```

**Đi sâu hơn: nâng `lab13.yaml` lên chuẩn thực tế**

Bản lab chạy được, nhưng còn nhiều điểm bạn nên tự cải thiện bằng kiến thức của chương:

| Điểm trong lab | Rủi ro | Cải thiện |
|---|---|---|
| Image tag `:latest` | Không biết đang chạy bản nào, rollback vô nghĩa | Tag theo version/commit SHA (`:v1`, `:a1b2c3d`) |
| Mongo là Deployment, không volume | Mất dữ liệu khi Pod bị tạo lại | PVC (gp3 qua EBS CSI) hoặc StatefulSet, hay dùng DocumentDB/MongoDB Atlas |
| Không có probe | Rolling update gửi request vào Pod chưa sẵn sàng | Thêm `readinessProbe` (vd `GET /api/health`) và `livenessProbe` |
| Chỉ có memory requests/limits | Scheduler không biết app cần bao nhiêu CPU, không dùng được HPA theo CPU | Thêm `cpu` requests |
| backend, frontend là NodePort | Mở port thừa trên node, đi vòng qua Ingress là đủ | Đổi thành ClusterIP |
| ingress-nginx `controller-v1.10.0` | Bản cũ; dự án đã ngừng bảo trì từ 3/2026 | Dùng controller còn bảo trì, hoặc AWS Load Balancer Controller (Ingress → ALB trực tiếp) hay Gateway API |
| ALB tạo tay trên console | Dễ quên xoá, không tái tạo được | Terraform (chương 05) hoặc để controller tự tạo |

**HorizontalPodAutoscaler (HPA)**: tự tăng giảm số Pod theo tải. HPA cần **metrics-server** (trên minikube: `minikube addons enable metrics-server`) và Pod **phải có CPU requests**, vì mức dùng được tính theo phần trăm của requests.

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: backend }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: backend-deployment }
  minReplicas: 2
  maxReplicas: 5
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: { type: Utilization, averageUtilization: 60 }   # giữ CPU trung bình ~60% của requests
```

`kubectl get hpa` cột `TARGETS` hiện `<unknown>` nghĩa là chưa có metrics-server hoặc Pod thiếu CPU requests. Lưu ý: HPA tăng số Pod, nhưng nếu node hết chỗ thì Pod mới nằm `Pending`; cần thêm **Cluster Autoscaler** hoặc Karpenter để tăng số node.

**Quy trình debug khi "web không lên"** (đi từ trong ra ngoài)

```bash
kubectl get pods                               # 1. Pod Running và READY 1/1?
kubectl logs deploy/backend-deployment         # 2. App có lỗi kết nối Mongo?
kubectl get endpointslices                     # 3. Service có endpoint không (selector khớp)?
kubectl port-forward svc/frontend 3000:3000    # 4. Gọi thẳng Service, bỏ qua Ingress
kubectl describe ingress ingress-nginx         # 5. Luật /api và / đúng backend chưa?
kubectl logs -n ingress-nginx deploy/ingress-nginx-controller   # 6. Controller nhận request chưa?
# 7. Target Group trên console: target healthy? SG node có cho SG ALB vào NodePort?
```

**Lỗi hay gặp & cách sửa**

- `ImagePullBackOff`, Event `no basic auth credentials` hoặc `403 Forbidden` từ ECR: image ghi account ID của người khác, hoặc IAM role của node không có quyền đọc ECR (`AmazonEC2ContainerRegistryReadOnly`). Kiểm tra lại đường dẫn image và role của instance group.
- `CrashLoopBackOff`, log chỉ có `exec format error`: image build trên máy ARM (Mac M-series) nhưng node là x86_64. Build bằng `docker buildx build --platform linux/amd64`.
- Frontend gọi `/api` bị `ECONNREFUSED`/`ENOTFOUND backend`: còn sót dòng `proxy` trong `package.json` (lab13.md có nhắc).
- Target Group báo `unhealthy` hết: sai NodePort (lấy cổng ứng với `80:xxxxx` của `ingress-nginx-controller`), hoặc SG node chưa cho SG của ALB vào dải NodePort. Health check path `/` phải trả về 200 hoặc 404 (cấu hình "success codes" cho phù hợp).

<details><summary>1. Vì sao lab13 cần cả Ingress lẫn ALB? Có cách nào bỏ bớt một lớp không?</summary>
