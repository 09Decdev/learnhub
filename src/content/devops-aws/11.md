# Chương 11 · CodeBuild, CodeCommit, CodeDeploy, CodePipeline

Học xong chương này, bạn **dựng được một pipeline CI/CD hoàn toàn bằng dịch vụ của AWS**: lấy code từ GitHub, build Java/Node.js/Docker bằng CodeBuild, rồi tự động deploy lên Elastic Beanstalk hoặc ECS theo kiểu rolling, blue/green và canary, có bước duyệt tay trước khi lên production.

Bốn dịch vụ và một câu tóm tắt cho mỗi cái:

```
CodeCommit   → chỗ chứa code (Git repo của AWS). Lab dùng GitHub thay thế.
CodeBuild    → máy build tạm thời: chạy lệnh trong buildspec.yml, xong thì tự huỷ.
CodeDeploy   → đưa bản mới lên máy chủ / ECS / Lambda, điều khiển cách chuyển traffic.
CodePipeline → "nhạc trưởng": nối Source → Build → (Approval) → Deploy thành một luồng tự động.
```

## Giới thiệu bộ Code* và Lab1 tạo repository {002-004}

**Khái niệm cốt lõi**

CI/CD là viết tắt của *Continuous Integration / Continuous Delivery (hoặc Deployment)*. Hiểu đơn giản:

- **CI:** mỗi lần ai đó push code, máy tự build và chạy test. Lỗi được phát hiện ngay, không đợi đến cuối tuần.
- **CD:** bản build đạt yêu cầu được tự động đưa lên môi trường (dev, staging, production). *Delivery* là sẵn sàng để deploy (có thể còn bước bấm duyệt). *Deployment* là tự deploy hết, không cần người.

Ở chương Jenkins bạn tự dựng máy Jenkins và phải tự lo vá lỗi, nâng cấp, sao lưu. Bộ Code* của AWS là **dịch vụ được quản lý (managed)**: không có server để chăm sóc, trả tiền theo phút dùng, và tích hợp sẵn với IAM, S3, ECR, ECS, CloudWatch.

```
 Developer ──git push──▶ GitHub / CodeCommit
                              │ (webhook / CodeConnections)
                              ▼
                     ┌──── CodePipeline ─────────────────────────────┐
                     │ Source ─▶ Build (CodeBuild) ─▶ Approval ─▶ Deploy │
                     └──────────────┬───────────────────────────┬───┘
                                    │ artifact (zip trên S3)    │
                                    ▼                           ▼
                             S3 / ECR (image)     CodeDeploy / Beanstalk / ECS
```

**Đi sâu hơn: số phận của CodeCommit**

- Tháng 7/2024 AWS ngừng nhận khách hàng mới cho CodeCommit (và Cloud9). Vì vậy khoá học chuyển sang GitHub, file 001 và 011 của chương là thông báo về chuyện này.
- **Tháng 11/2025 AWS đảo ngược quyết định:** CodeCommit trở lại *General Availability*, tài khoản mới lại tạo được repository. AWS cũng công bố lộ trình hỗ trợ Git LFS. Giá giữ nguyên.
- Thực tế đi làm: đa số công ty vẫn dùng GitHub/GitLab để chứa code, và dùng CodePipeline/CodeBuild để build và deploy lên AWS. Kỹ năng bạn cần nhất trong chương là **kết nối GitHub với AWS** một cách an toàn.

**Lab1 (file `(new)codepipeline/lab1.sh`)** chỉ yêu cầu: tạo repo trên GitHub, thêm SSH key, clone về, sửa, commit, push. Đây là bước ôn lại chương Git.

```bash
ssh-keygen -t ed25519 -C "ban@example.com"     # tạo key mới (nếu chưa có)
cat ~/.ssh/id_ed25519.pub                       # dán vào GitHub → Settings → SSH and GPG keys
ssh -T git@github.com                           # kiểm tra: "Hi <user>! You've successfully authenticated"
git clone git@github.com:<user>/<repo>.git
cd <repo> && echo "test" >> README.md
git add . && git commit -m "test push" && git push origin master
```

Nếu muốn thử CodeCommit (giờ đã mở lại):

```bash
aws codecommit create-repository --repository-name demo-repo --region ap-southeast-1
# Cách dễ nhất để xác thực: cài git-remote-codecommit, dùng luôn credentials của AWS CLI
pip install --user git-remote-codecommit
git clone codecommit::ap-southeast-1://demo-repo
```

**Lỗi hay gặp & cách sửa**

- `git@github.com: Permission denied (publickey).` → chưa thêm public key lên GitHub, hoặc SSH agent dùng key khác. Chạy `ssh -vT git@github.com` để xem key nào đang được thử.
- `remote: Support for password authentication was removed` → bạn clone bằng HTTPS rồi gõ mật khẩu GitHub. GitHub chỉ nhận **SSH key** hoặc **Personal Access Token**.
- Push lên nhánh `main` nhưng lab ghi `master` → kiểm tra bằng `git branch -a`. Pipeline sau này lắng nghe **đúng tên nhánh**, sai một chữ là không chạy.

**Câu hỏi tự kiểm tra**

<details><summary>1. CI khác CD thế nào? Pipeline của chương này phần nào là CI, phần nào là CD?</summary>

CI là tự động build + test mỗi lần push (phần **Source → Build**, do CodeBuild làm). CD là tự động đưa bản build lên môi trường (phần **Deploy**, do CodeDeploy / Beanstalk / ECS action làm). Khi có bước Manual Approval trước Deploy thì đó là *Continuous Delivery*; bỏ bước duyệt thì thành *Continuous Deployment*.
</details>

<details><summary>2. Vì sao dùng CodeBuild thay vì một EC2 cài sẵn Jenkins?</summary>

CodeBuild không có server để vá lỗi hay nâng cấp. Mỗi lần build là một container sạch, chạy xong thì huỷ, nên không bị "rác" từ lần build trước. Bạn trả tiền theo phút build, không build thì không tốn. Đổi lại, bạn ít quyền tuỳ biến hơn Jenkins và bị gắn với AWS.
</details>

## Lab2 · CodeBuild build project Java {005-006}

**Khái niệm cốt lõi**

Một **build project** trong CodeBuild gồm 5 phần:

| Phần | Ý nghĩa | Trong lab |
|---|---|---|
| Source | Lấy code ở đâu | GitHub repo `java-elasticbeanstalk-sample-...`, nhánh `master` |
| Environment | Image Docker để chạy build | `aws/codebuild/standard:7.0` (Ubuntu 22.04) |
| Service role | IAM role mà CodeBuild "đeo" khi chạy | `udemy-devops-codebuild-role` |
| Buildspec | Danh sách lệnh | `buildspec.yml` |
| Artifacts | Kết quả build để ở đâu | S3 bucket, tên `demo_java_artifact` |

Hai video là cùng một lab với hai nguồn code: bản CodeCommit (005) và bản GitHub (006).

**Buildspec chạy như thế nào**

```
SUBMITTED → PROVISIONING (dựng container) → DOWNLOAD_SOURCE
   → INSTALL → PRE_BUILD → BUILD → POST_BUILD
   → UPLOAD_ARTIFACTS → FINALIZING → COMPLETED
```

File lab: `(new)codepipeline/lab2-codebuild-java/buildspec.yml`

```yaml
version: 0.2                 # luôn dùng 0.2: mọi lệnh chạy chung 1 shell (cd, export giữ được)

phases:
  install:
    runtime-versions:
      java: corretto17       # chọn JDK có sẵn trong image, không phải tự cài
  pre_build:
    commands:
      - echo Nothing to do in the pre_build phase...
  build:
    commands:
      - mvn clean install    # compile + test + đóng gói .jar vào target/
  post_build:
    commands:
      - echo Build completed on `date`
artifacts:
  files:
    - target/**/*.jar        # chỉ lấy file .jar
  discard-paths: yes         # bỏ thư mục target/, jar nằm ngay gốc file zip
```

**Đi sâu hơn**

- **Ghim runtime.** Không ghi `runtime-versions` thì CodeBuild dùng phiên bản mặc định của image, và mặc định này có thể đổi khi phiên bản cũ hết hạn hỗ trợ. Ghi rõ `java: corretto17` để build không tự nhiên hỏng.
- **Chọn image mới.** `standard:5.0` (Ubuntu 20.04) đã cũ. Hiện có `standard:7.0` (Ubuntu 22.04) và `standard:8.0` (Ubuntu 24.04), cùng `amazonlinux-x86_64-standard:5.0/6.0` (Amazon Linux 2023).
- **`finally` và `on-failure`.** Mỗi phase có thể có khối `finally` (luôn chạy, kể cả khi lệnh trước lỗi) và `on-failure: ABORT | CONTINUE | RETRY-3`.
- ⚠️ **`post_build` vẫn chạy khi `build` lỗi.** Theo luồng chuyển phase của CodeBuild, lỗi ở `build` không chặn `post_build`. Nếu `post_build` có lệnh deploy/push, hãy kiểm tra biến `CODEBUILD_BUILD_SUCCEEDING` (bằng `1` nếu mọi thứ đang thành công):

  ```yaml
  post_build:
    commands:
      - if [ "$CODEBUILD_BUILD_SUCCEEDING" = "0" ]; then echo "Build lỗi, bỏ qua upload"; exit 1; fi
  ```
- **Cache để build nhanh hơn.** Maven tải lại hàng trăm thư viện mỗi lần build. Thêm cache (bật "Amazon S3 cache" hoặc "Local cache" trong project):

  ```yaml
  cache:
    paths:
      - '/root/.m2/**/*'
  ```
- **Test report.** Khối `reports:` đọc file JUnit XML (`target/surefire-reports/*.xml`) và hiện kết quả test ngay trên console CodeBuild.
- **Service role làm được gì thì build làm được nấy.** Mọi lệnh `aws ...` trong buildspec chạy bằng quyền của role này. Lab dùng `AmazonS3FullAccess` cho nhanh; khi làm thật, chỉ cho `s3:PutObject` vào đúng bucket artifact.

**Kết nối GitHub: CodeConnections**

Nút "Connect to GitHub" tạo một **connection** (trước 2024 tên là *CodeStar Connections*, nay đổi thành **AWS CodeConnections**). Bên dưới, AWS cài một GitHub App ("AWS Connector for GitHub") vào tài khoản/tổ chức GitHub của bạn và chỉ cấp quyền cho các repo bạn chọn. Cách này an toàn hơn cách cũ là dán Personal Access Token: không có token dài hạn nằm trong AWS, và thu hồi quyền ngay trên GitHub được.

```bash
aws codeconnections list-connections --region ap-southeast-1   # xem connection, trạng thái phải là AVAILABLE
```

**Lỗi hay gặp & cách sửa**

- `ACCESS_DENIED: Service role ... does not allow logs:CreateLogStream` → service role thiếu quyền CloudWatch Logs. Thêm policy log, hoặc chọn lại "New service role" để console tự tạo quyền đúng.
- `Error while executing command: mvn clean install. Reason: exit status 1` → lỗi trong chính code (test fail, sai phiên bản Java). Đọc log ngay phía trên dòng này, thường là `[ERROR] ... release version 17 not supported` khi `pom.xml` đòi Java 17 mà runtime là Java 11.
- `CLIENT_ERROR: no matching artifact paths found` → đường dẫn `files:` sai (ví dụ project build ra `.war` chứ không phải `.jar`). Thêm `- ls -R target` vào `post_build` để xem thực tế có gì.
- Connection ở trạng thái `PENDING` → bạn tạo connection bằng CLI/Terraform nhưng chưa bấm "Update pending connection" trên console để hoàn tất bắt tay với GitHub.

💰 **Chi phí:** CodeBuild free tier có **100 phút build/tháng** với `general1.small`. Vượt mức thì khoảng 0,005 USD/phút (Linux, `general1.small`). Một lần build Maven 2–3 phút gần như không đáng kể. Artifact trên S3 vài MB, gần như miễn phí, nhưng nhớ xoá bucket cuối chương.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab, sau đó đổi `discard-paths: no` và build lại. So sánh cấu trúc file zip trên S3.

🟡 *Thực hành*: Thêm cache Maven và một report group JUnit vào buildspec. Build 2 lần liên tiếp, so thời gian phase `BUILD` giữa lần 1 và lần 2.

<details><summary>Gợi ý buildspec</summary>

```yaml
reports:
  junit-report:
    files:
      - 'target/surefire-reports/*.xml'
    file-format: JUNITXML
cache:
  paths:
    - '/root/.m2/**/*'
```
Nhớ bật cache trong project: Edit → Artifacts → Additional configuration → Cache type: Amazon S3 (chọn bucket) hoặc Local (Custom cache). Service role cần quyền tạo report (`codebuild:CreateReportGroup`, `CreateReport`, `UpdateReport`, `BatchPutTestCases`).
</details>

🔴 *Thử thách*: Đặt tên artifact có ngày giờ và commit để không bị ghi đè: `name: java-$(date +%Y%m%d-%H%M)-${CODEBUILD_RESOLVED_SOURCE_VERSION:0:7}`. Bật "Enable semantic versioning" trong project và kiểm tra trên S3 có nhiều phiên bản artifact. Vì sao giữ nhiều phiên bản giúp rollback dễ hơn?

<details><summary>Đáp án ngắn</summary>

Mỗi build tạo một file riêng, nên khi bản mới lỗi bạn deploy lại file của build trước là xong, không phải build lại từ code cũ (có thể đã đổi thư viện). Nhớ đặt S3 Lifecycle rule xoá artifact cũ hơn 30 ngày để khỏi tốn tiền lưu trữ.
</details>

<details><summary>1. Vì sao buildspec nên để trong repo thay vì gõ "Insert build commands" trên console?</summary>

Không cần. CodeBuild tự cấp credentials tạm thời của **service role** cho container. Lệnh có chạy được hay không phụ thuộc vào policy gắn với role đó.

## Lab3 · CodeBuild build project Node.js {007-008}

**Khái niệm cốt lõi**

Cùng ý tưởng với lab2, nhưng project là app Vue + webpack. Kết quả build là thư mục `dist/` gồm HTML/JS/CSS tĩnh. Điểm khác: lab chọn **No artifacts** và tự upload bằng `aws s3 cp` trong `post_build`.

File lab: `(new)codepipeline/lab3-codebuild-nodejs-webpack/buildspec.yml`

```yaml
version: 0.2
phases:
  install:
    runtime-versions:
      nodejs: latest          # ⚠️ "latest" tiện nhưng dễ vỡ khi Node lên major mới
    commands:
      - npm install
  build:
    commands:
      - npm run build         # webpack đóng gói ra dist/
  post_build:
    commands:
      - aws s3 cp --recursive ./dist s3://udemy-devops-codebuild-linh/nodejs_artifacts/   # đổi tên bucket của bạn
artifacts:
  files:
    - dist/**
  discard-paths: yes
```

**Đi sâu hơn**

- **`npm ci` thay cho `npm install`.** `npm ci` cài *đúng* phiên bản trong `package-lock.json`, nhanh hơn và lặp lại được. `npm install` có thể âm thầm nâng phiên bản và sửa lock file.
- **Ghim Node theo major:** `nodejs: 20` hoặc `nodejs: 22` thay vì `latest`. Webpack 4 cũ chạy trên Node 17+ sẽ lỗi `ERR_OSSL_EVP_UNSUPPORTED`; ghim phiên bản giúp tránh bất ngờ kiểu này.
- **Cache `node_modules`** với khoá theo nội dung lock file (cú pháp cache mới của CodeBuild):

  ```yaml
  cache:
    key: npm-$(codebuild-hash-files package-lock.json)
    paths:
      - 'node_modules/**/*'
  ```
- **Hai cách đưa kết quả ra ngoài:**
  - *Artifacts của CodeBuild:* CodeBuild tự nén và upload. Đây là cách CodePipeline cần để chuyển kết quả sang stage sau.
  - *Tự chạy `aws s3 cp` / `aws s3 sync`:* linh hoạt hơn, phù hợp để host web tĩnh trên S3. Dùng `aws s3 sync ./dist s3://bucket/ --delete` để xoá file cũ không còn dùng.
- **Biến môi trường có sẵn hữu ích:** `CODEBUILD_SRC_DIR` (thư mục code), `CODEBUILD_BUILD_NUMBER`, `CODEBUILD_RESOLVED_SOURCE_VERSION` (commit SHA), `AWS_REGION`.
- **Đừng hard-code tên bucket.** Đưa vào biến để dùng lại cho nhiều môi trường:

  ```yaml
  env:
    variables:
      ARTIFACT_BUCKET: "udemy-devops-codebuild-<tên-bạn>"
  # ...
      - aws s3 sync ./dist "s3://$ARTIFACT_BUCKET/nodejs_artifacts/" --delete
  ```
  Biến đặt trong project (console) hoặc khi `start-build` sẽ **ghi đè** biến trong buildspec.

**Lỗi hay gặp & cách sửa**

- `upload failed: ... An error occurred (AccessDenied) when calling the PutObject operation` → service role chưa có quyền ghi bucket, hoặc bạn quên đổi tên bucket `...-linh` của giảng viên.
- `npm ERR! code ERESOLVE` → xung đột phiên bản peer dependency. Tạm thời dùng `npm install --legacy-peer-deps`; về lâu dài nâng thư viện cho khớp.
- `Error: error:0308010C:digital envelope routines::unsupported` → webpack cũ trên Node mới. Ghim `nodejs: 16`/`18` hoặc thêm `export NODE_OPTIONS=--openssl-legacy-provider`.
- `Skipping install of runtimes. Runtime version selection is not supported by this build image` → image quá cũ. Chọn `amazonlinux-x86_64-standard:5.0` trở lên.

💰 **Chi phí:** như lab2, nằm trong 100 phút free. Bucket S3 nếu bật static website hosting và để public thì cẩn thận: chỉ public những gì bạn muốn công khai.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab, đổi `nodejs: latest` thành `nodejs: 20` và `npm install` thành `npm ci`. Build thành công.

🟡 *Thực hành*: Bật **Static website hosting** cho một bucket mới, sửa `post_build` dùng `aws s3 sync --delete` vào bucket đó. Mở URL website và thấy app Vue chạy.

<details><summary>Gợi ý</summary>

Bucket cần: tắt "Block all public access", bucket policy cho `s3:GetObject` với `Principal: "*"` trên `arn:aws:s3:::<bucket>/*`, Index document `index.html`. Cách chuyên nghiệp hơn: giữ bucket private và đặt CloudFront phía trước với Origin Access Control. Dọn dẹp: `aws s3 rb s3://<bucket> --force`.
</details>

🔴 *Thử thách*: Chuyển tên bucket sang **SSM Parameter Store** (`/learnhub/artifact-bucket`) và đọc bằng khối `env: parameter-store:`. Build sẽ lỗi lần đầu. Đọc log, tìm quyền IAM còn thiếu và thêm vào service role.

<details><summary>Đáp án</summary>

```yaml
env:
  parameter-store:
    ARTIFACT_BUCKET: /learnhub/artifact-bucket
```
Lỗi lần đầu là role không có `ssm:GetParameters`. Thêm inline policy cho phép `ssm:GetParameters` trên `arn:aws:ssm:ap-southeast-1:<account-id>:parameter/learnhub/*`. Parameter Store loại Standard miễn phí.
</details>

<details><summary>1. Lab chọn "No artifacts" nhưng buildspec vẫn có khối <code>artifacts:</code>. Chuyện gì xảy ra?</summary>

## Lab4 · CodeBuild build Docker image và push lên ECR {009-010}

**Khái niệm cốt lõi**

Lần này kết quả build không phải file mà là **Docker image**, được push lên **ECR (Elastic Container Registry, kho image riêng của bạn trên AWS)**. Image này là đầu vào cho các lab ECS phía sau.

```
GitHub ─▶ CodeBuild (privileged) ─ docker build ─▶ image
                │                                   │ docker push
   Secrets Manager (user/pass Docker Hub)           ▼
                                        ECR: nodejs-random-color:latest
                                                   :<7 ký tự commit>
```

File lab: `(new)codepipeline/lab4-codebuild-docker/buildspec.yml` (rút gọn, có chú thích)

```yaml
version: 0.2
env:
  secrets-manager:                       # đọc secret, gán vào biến môi trường
    DOCKERHUB_USERNAME: dockerhub-username-secret
    DOCKERHUB_PASSWORD: dockerhub-password-secret
phases:
  pre_build:
    commands:
      - docker login -u "$DOCKERHUB_USERNAME" -p "$DOCKERHUB_PASSWORD"   # tránh giới hạn pull của Docker Hub
      - aws ecr get-login-password --region ap-southeast-1 | docker login --username AWS --password-stdin <account-id>.dkr.ecr.ap-southeast-1.amazonaws.com
      - REPOSITORY_URI=<account-id>.dkr.ecr.ap-southeast-1.amazonaws.com/nodejs-random-color
      - COMMIT_HASH=$(echo $CODEBUILD_RESOLVED_SOURCE_VERSION | cut -c 1-7)   # tag theo commit
  build:
    commands:
      - docker build -t nodejs-random-color .
      - docker tag nodejs-random-color:latest $REPOSITORY_URI:latest
      - docker tag nodejs-random-color:latest $REPOSITORY_URI:$COMMIT_HASH
  post_build:
    commands:
      - docker push $REPOSITORY_URI:latest
      - docker push $REPOSITORY_URI:$COMMIT_HASH
```

Hai thiết lập bắt buộc trên project:
- **Privileged mode** (Additional configuration → Privileged): cho phép chạy Docker daemon bên trong container build. Không bật thì không `docker build` được.
- **Quyền của service role:** push lên ECR và đọc Secrets Manager.

**Đi sâu hơn**

- **Tag theo commit, đừng chỉ dùng `latest`.** `latest` bị ghi đè mỗi lần build, nên không biết production đang chạy code nào và không rollback được. Tag `a1b2c3d` (7 ký tự commit) chỉ đúng một phiên bản code. Bật **tag immutability** trên ECR để không ai ghi đè tag cũ.
- **`secrets-manager` và `parameter-store` trong buildspec:**
  - Cú pháp đầy đủ: `BIẾN: <secret-id>:<json-key>:<version-stage>:<version-id>`. Nếu một secret lưu JSON `{"username":"a","password":"b"}`, bạn chỉ cần **một** secret: `DOCKERHUB_USERNAME: dockerhub:username` và `DOCKERHUB_PASSWORD: dockerhub:password`.
  - CodeBuild **che giá trị** secret trong log. Nhưng nếu bạn biến đổi giá trị (base64, nối chuỗi) thì chuỗi mới không bị che.
  - Parameter Store loại `SecureString` miễn phí (tier Standard). Secrets Manager khoảng 0,40 USD/secret/tháng nhưng có xoay vòng (rotation) tự động.
- **`--password-stdin` thay cho `-p`.** `docker login -p` để mật khẩu lộ trong danh sách tiến trình và in cảnh báo. Viết `echo "$DOCKERHUB_PASSWORD" | docker login -u "$DOCKERHUB_USERNAME" --password-stdin`.
- **Bỏ hard-code account ID:**

  ```bash
  AWS_ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
  REPOSITORY_URI=$AWS_ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com/nodejs-random-color
  ```
- **Tránh Docker Hub hoàn toàn:** đổi `FROM node:18` thành `FROM public.ecr.aws/docker/library/node:18`. ECR Public chứa bản sao các image chính thức, không bị giới hạn pull như Docker Hub. Hoặc dùng **ECR pull through cache**.
- **Docker layer cache:** bật *Local cache → Docker layer cache* để không build lại những layer không đổi.
- **Cách mới:** CodePipeline V2 có action **ECRBuildAndPublish**, tự build và push image mà không cần viết buildspec. Bạn vẫn nên hiểu buildspec vì đó là thứ bạn sẽ gỡ lỗi.

**Lỗi hay gặp & cách sửa**

- `Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Is the docker daemon running?` → chưa bật **Privileged**.
- `toomanyrequests: You have reached your pull rate limit` → Docker Hub giới hạn số lần pull ẩn danh theo IP, và IP của CodeBuild dùng chung với rất nhiều người. Đăng nhập Docker Hub trước khi build (như lab), hoặc đổi sang ECR Public.
- `AccessDeniedException: ... is not authorized to perform: secretsmanager:GetSecretValue` → role thiếu quyền, hoặc tên secret gõ sai (CodeBuild báo lỗi ngay ở phase `DOWNLOAD_SOURCE`/`INSTALL`).
- `denied: Your authorization token has expired` / `no basic auth credentials` → chưa chạy lệnh `aws ecr get-login-password ...`, hoặc đăng nhập vào **sai region / sai account**.
- `name unknown: The repository with name 'nodejs-random-color-1107' does not exist` → tên repo trong buildspec của giảng viên khác tên repo của bạn.

💰 **Chi phí:** ECR có 500 MB lưu trữ private free trong 12 tháng đầu với tài khoản cũ (tài khoản mới từ 15/7/2025 dùng mô hình credit Free Tier), sau đó khoảng 0,10 USD/GB/tháng. Đặt **Lifecycle policy** "chỉ giữ 10 image gần nhất". 2 secret Secrets Manager ≈ 0,80 USD/tháng: xoá khi học xong (mặc định secret bị xoá sau 7–30 ngày chờ; dùng `--force-delete-without-recovery` nếu muốn xoá ngay).

**Bài tập**

🟢 *Cơ bản*: Làm lại lab với repo ECR của bạn. Sửa `docker login -p` thành `--password-stdin`, và lấy account ID bằng `aws sts get-caller-identity`.

🟡 *Thực hành*: Gộp 2 secret thành 1 secret JSON `dockerhub` (`{"username": "...", "password": "..."}`), sửa buildspec dùng cú pháp `dockerhub:username`. Bật tag immutability và lifecycle policy giữ 5 image.

## Lab5 · CodePipeline deploy Java lên Elastic Beanstalk {012-014}

**Khái niệm cốt lõi: Elastic Beanstalk là gì?**

**Elastic Beanstalk (EB)** là dịch vụ **PaaS** (Platform as a Service): bạn đưa file `.jar`, EB tự tạo EC2, Security Group, Auto Scaling Group, Load Balancer (nếu chọn), cài Java, chạy app và gắn CloudWatch. Bạn không phải viết Terraform cho từng thứ.

- **Application:** "thư mục" chứa mọi thứ của một app.
- **Application version:** một bản code đã upload (file zip/jar trên S3).
- **Environment:** một bộ máy đang chạy một version, ví dụ `myapp-dev`, `myapp-prod`. Mỗi environment có một domain `xxx.elasticbeanstalk.com`.
- **Platform:** bộ "hệ điều hành + runtime", ví dụ *Corretto 17 running on 64bit Amazon Linux 2023*.

Bản thân EB **miễn phí**, bạn chỉ trả tiền EC2, ELB, EBS… mà nó tạo ra.

**Pipeline của lab** (file `(new)codepipeline/lab5-codepipeline-java-beanstalk/lab5-codepipeline-java-beanstalk.sh`)

```
Source (GitHub qua CodeConnections, nhánh master)
   │ SourceArtifact (zip code)
   ▼
Build (CodeBuild project Java của lab2)
   │ BuildArtifact (zip chứa .jar)
   ▼
Deploy (Elastic Beanstalk: application + environment)
```

Mỗi stage nhận **input artifact** và trả **output artifact**. CodePipeline lưu chúng thành file zip trong **artifact bucket** trên S3 (tên dạng `codepipeline-ap-southeast-1-...`).

**Đi sâu hơn: CodePipeline V2**

| | V1 | V2 (mặc định, console chỉ còn cho chọn V2) |
|---|---|---|
| Giá | 1 USD / pipeline hoạt động / tháng | 0,002 USD / **phút thực thi action** |
| Free tier | 1 pipeline hoạt động/tháng | 100 phút action/tháng (chung cho mọi pipeline V2) |
| Trigger lọc theo branch/tag/file/PR | Không | Có |
| Biến cấp pipeline (variables) | Không | Có |
| Execution mode | Superseded | Superseded, Queued, Parallel |

- **Execution mode:**
  - *Superseded* (lab chọn): đang chạy mà có commit mới thì bản mới "vượt lên", bản cũ đang chờ ở stage sau bị bỏ.
  - *Queued*: xếp hàng chạy lần lượt, không bỏ commit nào.
  - *Parallel*: mỗi commit một luồng riêng, hợp với nhánh feature.
- **Trigger (V2):** lọc theo `push` (branch, tag, file path) hoặc `pullRequest` (OPEN, UPDATED, CLOSED). Ví dụ chỉ chạy khi push vào `master` và có thay đổi trong `src/**`. Nếu filter cả branch lẫn file path, lần đầu push một **nhánh mới** sẽ không kích hoạt pipeline.
- **Variables:**
  - Action có *namespace* xuất biến, ví dụ `#{SourceVariables.CommitId}`.
  - CodeBuild xuất biến qua `env: exported-variables:`.
  - Pipeline-level variable truyền lúc start: `#{variables.DEPLOY_ENV}`.
- Manual approval không bị tính phút ở V2.

**Deployment policy của Beanstalk** (Configuration → Rolling updates and deployments):
- *All at once:* nhanh nhất, nhưng app chết một lúc.
- *Rolling / Rolling with additional batch:* cập nhật từng nhóm máy.
- *Immutable:* tạo máy mới hoàn toàn, ổn rồi mới bỏ máy cũ. An toàn nhất.
- *Traffic splitting:* kiểu canary, chia % traffic cho bản mới.
- Blue/green "kiểu Beanstalk": tạo environment thứ hai rồi **Swap environment URLs**.

**Lỗi hay gặp & cách sửa**

- Web báo **502 Bad Gateway** sau khi deploy → platform Java SE của EB đặt nginx phía trước và chuyển request tới **port 5000**. App Spring Boot mặc định nghe 8080. Sửa: thêm biến môi trường `SERVER_PORT=5000` (hoặc `PORT=5000`) trong Configuration → Environment properties, hoặc đặt `server.port=5000`.
- `Deployment failed: ... Unable to download the artifact` / pipeline đỏ ở Deploy → service role của pipeline thiếu quyền EB hoặc S3. Xem tab *Events* của environment để biết chi tiết.
- Environment chuyển **Severe/Degraded** → đọc log: Environment → Logs → Request last 100 lines, tìm stacktrace Java (`/var/log/web.stdout.log`).
- Pipeline không tự chạy khi push → trigger đang lọc sai branch, hoặc connection mất quyền với repo (vào GitHub → Settings → Applications → AWS Connector, xem repo đã được chọn chưa).

💰 **Chi phí / an toàn:**
- Chọn **Single instance** (không có Load Balancer) với `t3.micro` để rẻ nhất. Load-balanced environment tạo thêm ALB (~0,0252 USD/giờ + phí LCU) và có thể tạo nhiều EC2.
- Mỗi lần chạy pipeline này tốn khoảng 3–6 phút action (source + build + deploy), nằm trong 100 phút free.
- Dọn dẹp: **Terminate environment** (xoá EC2/ELB), sau đó xoá application, pipeline, artifact bucket. Bucket `elasticbeanstalk-ap-southeast-1-<account>` cũng nên được dọn.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab. Sửa một dòng text trong controller, push, và xem pipeline tự chạy đến khi domain EB hiện nội dung mới.

🟡 *Thực hành*: Sửa trigger của pipeline để **chỉ chạy khi có thay đổi trong `src/**`** trên nhánh `master`. Push một commit chỉ sửa `README.md`: pipeline không được chạy.

## Lab6 · Deploy lên ECS kiểu Rolling update và dọn dẹp {015-016}

**Khái niệm cốt lõi**

Dùng Terraform dựng sẵn hạ tầng ECS (VPC, ALB, ECS cluster Fargate, service `nodejs-service`). Sau đó CodePipeline nối: **GitHub → CodeBuild (build image + tạo `imagedefinitions.json`) → Deploy "Amazon ECS"**.

**Rolling update** (deployment controller `ECS`): ECS tạo task mới với image mới, đợi task mới *healthy* trên Target Group, rồi tắt dần task cũ. Hai tham số điều khiển:
- `minimumHealthyPercent` (mặc định 100%): luôn giữ ít nhất bấy nhiêu % task chạy.
- `maximumPercent` (mặc định 200%): cho phép tạm thời chạy gấp đôi số task.

```
Trước:  [v1][v1]
Giữa:   [v1][v1][v2][v2]   ← ALB gửi traffic cho cả v1 và v2
Sau:    [v2][v2]
```

**`imagedefinitions.json` là gì?** Đây là "phiếu giao hàng" cho action *Amazon ECS*: *container tên gì thì dùng image nào*. Action đọc file này, tạo **revision mới của task definition** với image mới, rồi cập nhật service.

File lab: `(new)codepipeline/lab6-codepipeline-docker-ecs/buildspec.yml` (phần thêm so với lab4)

```yaml
  post_build:
    commands:
      - docker push $REPOSITORY_URI:$COMMIT_HASH
      - printf '[{"name":"nodejs-container","imageUri":"%s"}]' $REPOSITORY_URI:$COMMIT_HASH > imagedefinitions.json
      - cat imagedefinitions.json
artifacts:
  files:
    - imagedefinitions.json      # BuildArtifact chỉ cần đúng file này
```

`"name"` phải **trùng tên container** trong task definition (`nodejs-container` trong `modules/ecs_cluster/main.tf`).

Dựng hạ tầng (file `terraform/command.sh`):

```bash
cd "(new)codepipeline/lab6-codepipeline-docker-ecs/terraform/singapore-dev"
# sửa terraform.tfvars: ecr_repo_url = "<account>.dkr.ecr.ap-southeast-1.amazonaws.com/nodejs-random-color:<tag>"
terraform init
terraform plan  --var-file "terraform.tfvars"
terraform apply --var-file "terraform.tfvars"
```

**Đi sâu hơn**

- **Deployment circuit breaker:** bật `deployment_circuit_breaker { enable = true, rollback = true }` trên service. Nếu task mới liên tục chết (image lỗi), ECS tự dừng deployment và quay về revision cũ, thay vì thử mãi.
- **Health check grace period:** app Node khởi động chậm thì đặt `health_check_grace_period_seconds` để ECS không giết task trước khi app kịp sẵn sàng.
- **Terraform và CodePipeline cùng quản lý service sẽ "giành nhau".** Pipeline tạo revision mới (`nodejs-task-definition:7`), còn Terraform vẫn nhớ revision cũ. Lần `terraform apply` sau sẽ kéo service về revision cũ, tức là **deploy ngược**. Cách xử lý phổ biến:

  ```hcl
  resource "aws_ecs_service" "nodejs_service" {
    # ...
    lifecycle {
      ignore_changes = [task_definition, desired_count]
    }
  }
  ```
- **Pipeline đọc `imagedefinitions.json` từ BuildArtifact.** Nếu bạn đổi tên file, phải khai báo lại ở ô *Image definitions file* của action Deploy.

**Lỗi hay gặp & cách sửa**

- Deploy báo `The AWS ECS container nodejs-container does not exist` (hoặc thông báo tương tự) → `name` trong `imagedefinitions.json` không trùng tên container trong task definition.
- Deploy treo rất lâu rồi fail, task liên tục `STOPPED` với lý do `CannotPullContainerError` → task ở private subnet không ra được Internet/ECR (thiếu NAT hoặc VPC endpoint), hoặc execution role thiếu quyền `ecr:GetAuthorizationToken`/`ecr:BatchGetImage`.
- Target Group báo unhealthy → Security Group của task chưa cho phép port 3000 *từ SG của ALB*, hoặc health check path trả về khác 200.
- `terraform destroy` lỗi `DependencyViolation` khi xoá VPC/subnet → vẫn còn ENI của task chưa giải phóng. Đợi vài phút rồi chạy lại.

💰 **Chi phí / an toàn (video 016 – xoá resource):** stack này **tốn tiền theo giờ**. Ước lượng ở Singapore:
- NAT Gateway: khoảng 0,059 USD/giờ.
- ALB: khoảng 0,025 USD/giờ.
- Task Fargate (0,5 vCPU, 1 GB): khoảng 0,03 USD/giờ mỗi task.
- Public IPv4: 0,005 USD/giờ mỗi IP.

## Lab7 · ECS Blue/Green với CodeDeploy {017-020}

**Khái niệm cốt lõi**

**Blue/Green** nghĩa là chạy song song hai bộ: **Blue** (bản đang phục vụ) và **Green** (bản mới). Bạn kiểm tra Green trên một cổng test, ổn rồi mới chuyển toàn bộ traffic production sang. Có sự cố thì chuyển ngược lại gần như tức thì.

```
                    ALB
   Listener :80 (production) ──▶ Target Group Blue  ──▶ task set v1
   Listener :81 (test)       ──▶ Target Group Green ──▶ task set v2 (mới)

   "Reroute traffic": CodeDeploy đổi listener :80 sang TG Green
   "Terminate original task set": xoá task set v1
```

Khác với rolling (lab6), không có lúc nào người dùng production thấy lẫn hai phiên bản (trừ khi bạn chọn canary/linear ở lab8).

**Thay đổi Terraform so với lab6** (`lab7-.../terraform/modules/`):
- Service: `deployment_controller { type = "CODE_DEPLOY" }`. Từ đây, **chỉ CodeDeploy** được đổi task definition của service.
- Load balancer: thêm Target Group `green` và listener port **81**.

**CodeDeploy gồm gì:**
- **Application** (compute platform: Amazon ECS).
- **Deployment group:** cluster + service + ALB + listener 80/81 + 2 target group + cách chuyển traffic + service role (`AWSCodeDeployRoleForECS`).
- **Deployment configuration:** chuyển traffic thế nào (all-at-once, canary, linear).

**Ba file mà action "Amazon ECS (Blue/Green)" cần** (file lab: `lab7-.../buildspec.yml`):

| File | Ai tạo | Nội dung |
|---|---|---|
| `imageDetail.json` | CodeBuild (`printf`) | `{"ImageURI":"<repo>:<commit>"}` |
| `taskdef.json` | Có sẵn trong repo | Task definition, trường image là placeholder `<IMAGE1_NAME>` |
| `appspec.yaml` | Có sẵn trong repo | Container nào, port nào nhận traffic, hook nào chạy |

```yaml
# appspec.yaml (trong repo app)
version: 0.0
Resources:
  - TargetService:
      Type: AWS::ECS::Service
      Properties:
        TaskDefinition: <TASK_DEFINITION>     # pipeline tự thay bằng ARN revision mới
        LoadBalancerInfo:
          ContainerName: "nodejs-container"
          ContainerPort: 3000
```

`taskdef.json` (trích): trường `image` là placeholder, pipeline thay bằng `ImageURI` lấy từ `imageDetail.json`.

```json
{ "family": "nodejs-task-definition",
  "containerDefinitions": [ { "name": "nodejs-container", "image": "<IMAGE1_NAME>" } ] }
```

Trong action Deploy, ô *Dynamically update task definition image* nhập đúng **tên placeholder** đang dùng trong `taskdef.json` (tài liệu AWS dùng `IMAGE1_NAME`; lab ghi `IMAGE_NAME`, khi đó `taskdef.json` phải chứa `<IMAGE_NAME>`).

**So sánh nhanh hai loại file:**
- `imagedefinitions.json` (mảng `name` + `imageUri`) → action **Amazon ECS** (rolling).
- `imageDetail.json` (một trường `ImageURI`) → action **Amazon ECS (Blue/Green)**. Nếu source là ECR thì action source ECR tự sinh file này.

**Đi sâu hơn**

- **Thời gian chờ:**
  - *Reroute traffic:* "ngay lập tức" hoặc "chờ tôi bấm" (lab đặt 5 phút).
  - *Terminate original task set:* mặc định chờ **1 giờ** sau khi chuyển traffic mới xoá bản cũ. Trong 1 giờ đó bạn có thể *Stop and roll back* về Blue tức thì.
- **Lifecycle hooks:** `BeforeInstall`, `AfterInstall`, `AfterAllowTestTraffic`, `BeforeAllowTraffic`, `AfterAllowTraffic` gọi được Lambda để **test tự động**. Ví dụ `AfterAllowTestTraffic` gọi `curl` vào port 81, test fail thì CodeDeploy tự rollback.
- **Rollback tự động bằng CloudWatch alarm:** trong deployment group → *Advanced* → *Alarms*, thêm alarm như `HTTPCode_Target_5XX_Count > 10` trên Target Group, và bật *Roll back when alarm thresholds are met*. Khi alarm kêu trong lúc deploy, CodeDeploy chuyển traffic về task set cũ. Lưu ý: rollback là **một deployment mới** dùng revision cũ, có deployment ID mới.
- **Điểm mới 2025: ECS có blue/green "built-in".** Từ 2025, ECS tự làm blue/green, và từ 10/2025 cả linear/canary, ngay trong deployment controller `ECS`, có bake time, lifecycle hook và alarm rollback, **không cần CodeDeploy**. Dự án mới nên cân nhắc cách này vì ít thành phần hơn. Hiểu CodeDeploy vẫn cần thiết vì rất nhiều hệ thống đang chạy dùng nó.
- 💰 **Phút action của pipeline V2:** action Deploy blue/green ở trạng thái "đang chạy" cho tới khi CodeDeploy xong, tức là gồm cả thời gian chờ reroute và chờ terminate. Nếu để chờ terminate 1 giờ thì mỗi lần deploy có thể tốn hơn 60 phút action, hết gần sạch 100 phút free. Trong môi trường học, đặt thời gian chờ terminate ngắn (ví dụ 5 phút).

**Lỗi hay gặp & cách sửa**

- `terraform apply` báo `InvalidParameterException: Unable to update task definition on services with a CODE_DEPLOY deployment controller. Use AWS CodeDeploy to trigger a new deployment.` → Terraform cố đổi task definition của service do CodeDeploy quản lý. Thêm `lifecycle { ignore_changes = [task_definition, load_balancer] }` (CodeDeploy còn đổi target group của service).
- Pipeline báo không tìm thấy `taskdef.json` / `appspec.yaml` trong `BuildArtifact` → khai báo 2 file trong `artifacts.files` nhưng chúng **không có trong repo app**. Copy 2 file vào gốc repo `nodejs-random-color`.
- Deployment lỗi `The deployment failed because the ... container name ... in the AppSpec file ... does not match` → `ContainerName`/`ContainerPort` trong appspec phải khớp task definition (`nodejs-container`, `3000`).
- Port 81 không vào được → Security Group của ALB chỉ mở port 80. Thêm inbound 81 (chỉ cho IP của bạn).
- Lỗi IAM khi tạo task definition mới (`iam:PassRole`) → role của CodeDeploy/CodePipeline phải được phép *pass* execution role của task.

💰 **Chi phí:** lab này có `desired_count = 4` task Fargate (0,5 vCPU/1 GB), và trong lúc deploy sẽ có thêm 4 task Green, cộng ALB và NAT Gateway. Ước lượng **0,2–0,3 USD/giờ**. Làm xong là destroy ngay (xem phần cuối chương).

**Bài tập**

🟢 *Cơ bản*: Làm lại lab, bấm "Reroute traffic" bằng tay. Mở `:80` và `:81` trước và sau khi reroute, ghi lại mỗi cổng hiện phiên bản nào.

🟡 *Thực hành*: Tạo một CloudWatch alarm trên `HTTPCode_Target_5XX_Count` của Target Group (Sum ≥ 5 trong 1 phút). Gắn alarm vào deployment group và bật rollback khi alarm kêu. Deploy một bản cố tình trả 500 ở `/`, rồi dùng vòng lặp `curl` tạo traffic. Quan sát rollback.

<details><summary>Gợi ý</summary>

```bash
for i in $(seq 1 200); do curl -s -o /dev/null -w "%{http_code}\n" http://<alb-dns>/; sleep 0.5; done
```
Nhớ đặt *Treat missing data* là `notBreaching` để alarm không kêu nhầm khi không có traffic. Kiểm tra ở CodeDeploy → Deployments: trạng thái *Stopped/Rolled back*, lý do là alarm.
</details>

🔴 *Thử thách*: Viết một Lambda (Python) cho hook `AfterAllowTestTraffic`: gọi `http://<alb>:81/` và nếu khác 200 thì báo `Failed` cho CodeDeploy bằng `put_lifecycle_event_hook_execution_status`. Thêm hook vào `appspec.yaml`, deploy một bản lỗi và chứng minh traffic production **chưa bao giờ** chạm bản lỗi.

<details><summary>Gợi ý khung code</summary>

```python
import boto3, urllib.request
cd = boto3.client("codedeploy")
def handler(event, context):
    status = "Succeeded"
    try:
        with urllib.request.urlopen("http://<alb-dns>:81/", timeout=5) as r:
            if r.status != 200: status = "Failed"
    except Exception:
        status = "Failed"
    cd.put_lifecycle_event_hook_execution_status(
        deploymentId=event["DeploymentId"],
        lifecycleEventHookExecutionId=event["LifecycleEventHookExecutionId"],
        status=status)
```
Role của Lambda cần `codedeploy:PutLifecycleEventHookExecutionStatus`. Trong appspec: `Hooks: - AfterAllowTestTraffic: "<tên-hoặc-ARN-lambda>"`. Tên Lambda nên bắt đầu bằng `CodeDeployHook_` để khớp quyền của policy `AWSCodeDeployRoleForECS`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao blue/green cần 2 target group và 2 listener?</summary>

Mỗi target group chứa một bộ task (Blue hoặc Green). Listener production (:80) trỏ vào bộ đang phục vụ. Listener test (:81) trỏ vào bộ mới để bạn (hoặc hook test) kiểm tra trước. "Chuyển traffic" thực chất là đổi target group mà listener :80 trỏ tới, nên diễn ra gần như tức thì và quay lại cũng nhanh.
</details>

<details><summary>2. Pipeline rolling dùng <code>imagedefinitions.json</code>, pipeline blue/green dùng <code>imageDetail.json</code>. Vì sao blue/green cần thêm taskdef.json và appspec.yaml?</summary>

Action rolling tự lấy task definition hiện tại của service và chỉ thay image. Action blue/green giao việc cho CodeDeploy: nó cần một *mẫu* task definition đầy đủ (`taskdef.json`) để đăng ký revision mới, và một `appspec.yaml` để biết container/port nào gắn với load balancer và hook nào cần chạy.
</details>

## Lab8 · ECS Canary deployment {021}

**Khái niệm cốt lõi**

**Canary** (chim hoàng yến, ngày xưa thợ mỏ mang theo để phát hiện khí độc): đưa bản mới cho **một phần nhỏ** người dùng trước, theo dõi một lúc, ổn thì mới chuyển hết.

```
t=0     : 10% traffic → Green, 90% → Blue       (CodeDeployDefault.ECSCanary10Percent5Minutes)
t=5 phút: 100% → Green
```

**Linear** thì chia đều theo bước: 10% mỗi phút trong 10 phút (`ECSLinear10PercentEvery1Minutes`).

**Deployment config có sẵn cho ECS:**

| Tên | Cách chuyển |
|---|---|
| `CodeDeployDefault.ECSAllAtOnce` | 100% một lần (lab7) |
| `CodeDeployDefault.ECSCanary10Percent5Minutes` | 10%, 5 phút sau chuyển 90% còn lại |
| `CodeDeployDefault.ECSCanary10Percent15Minutes` | 10%, 15 phút sau chuyển phần còn lại |
| `CodeDeployDefault.ECSLinear10PercentEvery1Minutes` | +10% mỗi phút |
| `CodeDeployDefault.ECSLinear10PercentEvery3Minutes` | +10% mỗi 3 phút |

Lab yêu cầu **25% rồi chờ 5 phút**. Không có config sẵn nào như vậy, nên bạn phải tạo **custom deployment config**:

```bash
aws deploy create-deployment-config \
  --deployment-config-name Canary25Percent5Minutes \
  --compute-platform ECS \
  --traffic-routing-config '{
    "type": "TimeBasedCanary",
    "timeBasedCanary": { "canaryPercentage": 25, "canaryInterval": 5 }
  }'
# Rồi: CodeDeploy → deployment group → Edit → Deployment configuration: Canary25Percent5Minutes
```

Lab tăng service lên **4 task** để thấy rõ: với 25%, khoảng 1/4 số request trả về bản mới.

**Đi sâu hơn**

- Bên dưới, CodeDeploy dùng **weighted target groups** của ALB: listener :80 forward tới cả TG Blue (trọng số 75) và TG Green (25). Phân chia theo request, không theo người dùng. Cùng một người F5 có thể lúc thấy bản cũ, lúc thấy bản mới (trừ khi bật *stickiness* trên target group).
- Canary chỉ có ý nghĩa khi **có tín hiệu để quyết định**: CloudWatch alarm về lỗi 5xx, độ trễ (latency) p95, hoặc lỗi nghiệp vụ. Có canary mà không có alarm thì chỉ là deploy chậm hơn mà thôi.
- Với NLB, CodeDeploy chỉ hỗ trợ `ECSAllAtOnce`.
- CodeDeploy cũng làm canary/linear cho **Lambda** (`LambdaCanary10Percent5Minutes`…), bằng cách chuyển trọng số giữa hai version của alias. SAM làm việc này bằng `DeploymentPreference` (chương 12).

**Lỗi hay gặp & cách sửa**

- Không thấy 25% traffic sang bản mới khi F5 trình duyệt → trình duyệt giữ kết nối (keep-alive) và cache. Dùng `curl` trong vòng lặp và đếm kết quả.
- Custom config báo lỗi khi tạo → `--compute-platform` phải là `ECS`, và `canaryInterval` tính bằng **phút**.
- Deployment group vẫn chạy all-at-once → bạn tạo config xong nhưng chưa gán vào deployment group, hoặc pipeline đang dùng deployment group khác.

```bash
# Đếm phiên bản trả về trong 100 request (giả sử trang có chữ "v2" ở bản mới)
for i in $(seq 1 100); do curl -s http://<alb-dns>/ | grep -o 'v[0-9]' | head -1; done | sort | uniq -c
```

💰 **Chi phí:** như lab7, cộng thêm 4 task Green trong lúc deploy. Custom deployment config thì miễn phí.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab với custom config 25%/5 phút. Dùng vòng `curl` đếm tỉ lệ bản cũ/mới ở phút thứ 2 và phút thứ 6.

🟡 *Thực hành*: Tạo custom config **Linear 20% mỗi 2 phút** (`TimeBasedLinear`). Vẽ (trên giấy) tỉ lệ traffic theo thời gian và so sánh với kết quả đếm thực tế.

<details><summary>Gợi ý</summary>

```json
{"type":"TimeBasedLinear","timeBasedLinear":{"linearPercentage":20,"linearInterval":2}}
```
Kỳ vọng: 20% → 40% → 60% → 80% → 100% sau khoảng 8 phút.
</details>

🔴 *Thử thách*: Kết hợp canary + alarm từ lab7. Deploy bản mà 1/3 request trả về 500. Ở giai đoạn 25%, alarm có kịp kêu và rollback trước khi chuyển 100% không? Điều chỉnh ngưỡng alarm và `canaryInterval` để chắc chắn bắt được lỗi.

<details><summary>Hướng suy nghĩ</summary>

Ở 25% traffic, chỉ khoảng 8% tổng request lỗi. Nếu traffic thấp, alarm với ngưỡng "Sum ≥ 5/phút" có thể không đạt kịp trong 5 phút. Bạn có thể dùng tỉ lệ lỗi (metric math: 5xx / RequestCount) thay vì số tuyệt đối, kéo dài `canaryInterval`, hoặc chủ động tạo traffic kiểm thử. Bài học: thời gian canary phải đủ dài để có đủ dữ liệu.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Canary khác Linear khác All-at-once thế nào? Khi nào dùng cái nào?</summary>

All-at-once: chuyển 100% một lần. Nhanh, hợp cho môi trường dev. Canary: một phần nhỏ trước, chờ, rồi chuyển hết. Hợp cho production có alarm tốt. Linear: tăng đều theo bước. Rủi ro được dàn đều hơn, nhưng thời gian deploy dài hơn. Cả ba đều giữ bản cũ để rollback nhanh.
</details>

<details><summary>2. Vì sao lab tăng service lên 4 task?</summary>

Để bộ Green có đủ task nhận 25% traffic một cách ổn định và để quan sát dễ hơn. Thực ra ALB chia theo trọng số target group chứ không theo số task, nhưng có nhiều task thì kết quả đếm `curl` ít bị lệch hơn.
</details>

## Lab9 · Manual Approval, dọn dẹp và tổng kết {022-024}

**Khái niệm cốt lõi**

**Manual approval** là một action đặc biệt trong CodePipeline: pipeline **dừng lại** và chờ người có quyền bấm *Approve* hoặc *Reject*. Đây là ranh giới giữa *Continuous Delivery* (có người duyệt) và *Continuous Deployment* (tự động hoàn toàn).

```
Source ─▶ Build ─▶ Deploy-Dev ─▶ [Manual approval] ─▶ Deploy-Prod
                                     │ SNS → email "Có bản mới chờ duyệt"
                                     └ người duyệt xem link review, ghi comment
```

Cách thêm (console): Pipeline → Edit → *Add stage* "Approval" (đặt trước stage Deploy) → *Add action group* → Action provider: **Manual approval**. Có thể điền:
- **SNS topic ARN:** gửi email/Slack cho người duyệt.
- **URL for review:** link tới môi trường test (ví dụ `http://<alb>:81`).
- **Comments:** hướng dẫn cho người duyệt.

**Đi sâu hơn**

- **Quá hạn 7 ngày:** không ai duyệt trong 7 ngày thì action tự *Failed*.
- **Phân quyền:** ai được duyệt? Dùng IAM, cho phép `codepipeline:PutApprovalResult` trên đúng ARN của action approval. Dev thường không được tự duyệt lên production.
- **Không tính phút ở V2:** thời gian chờ duyệt không bị tính tiền. Nhưng nếu dùng *Superseded*, một commit mới có thể "vượt" bản đang chờ duyệt.
- **Duyệt bằng CLI:**

  ```bash
  aws codepipeline get-pipeline-state --name <pipeline> \
    --query "stageStates[?stageName=='Approval'].actionStates[0].latestExecution.token" --output text
  aws codepipeline put-approval-result --pipeline-name <pipeline> --stage-name Approval \
    --action-name ManualApproval --token <token> \
    --result summary="Đã test port 81 OK",status=Approved
  ```
- **Lựa chọn thay thế:** stage *conditions* của V2 (tự chặn hoặc rollback stage dựa trên CloudWatch alarm), hoặc approval bằng environment protection rule của GitHub Actions (chương 13).

**Tổng kết chương: chọn chiến lược deploy**

| Chiến lược | Ai làm | Downtime | Rollback | Chi phí thêm khi deploy |
|---|---|---|---|---|
| All at once (EB) | Beanstalk | Có | Deploy lại bản cũ | Không |
| Rolling (ECS) | ECS | Không | Circuit breaker / deploy lại | Thêm tối đa `maximumPercent` |
| Blue/Green | CodeDeploy hoặc ECS built-in | Không | Đổi listener, vài giây | Gấp đôi số task tạm thời |
| Canary / Linear | CodeDeploy hoặc ECS built-in | Không | Tự động theo alarm | Gấp đôi số task tạm thời |

**Lỗi hay gặp & cách sửa**

- Người duyệt không nhận email → chưa bấm *Confirm subscription* trong email đầu tiên từ SNS, hoặc topic khác region với pipeline.
- `AccessDenied ... codepipeline:PutApprovalResult` → IAM user của người duyệt thiếu quyền.
- Bấm Approve rồi mà Deploy chạy bản khác bản đã test → execution mode *Superseded* đã cho một commit mới vượt lên. Với production, cân nhắc *Queued*.
