# Chương 16 · Final Assignment (dự án cuối khoá)

Đây là chương **bạn tự làm**. Bạn ghép mọi thứ đã học thành một dự án hoàn chỉnh: chạy ứng dụng bằng Docker Compose ở máy mình, đẩy image lên ECR, dựng hạ tầng AWS bằng Terraform, viết pipeline CI/CD cho frontend và backend (sau đó làm lại bằng CodePipeline), chụp evidence (bằng chứng) để nộp bài, và dọn sạch tài nguyên.

> ⚠️ **Cách học chương này:** đọc phần lý thuyết bên dưới, **tự thiết kế và làm trước**, chỉ mở video lời giải khi bị kẹt thật sự hoặc khi đã xong để so sánh. Phần lý thuyết này hướng dẫn *phương pháp*, không đưa đáp án.

Quy trình bạn sẽ đi qua:

```
Đọc đề → Phân tích yêu cầu → Vẽ kiến trúc → Docker Compose (local)
   → ECR → Terraform (network → data → compute) → CI/CD FE/BE
   → Evidence & README → CodePipeline → Evidence → terraform destroy
```

## Giới thiệu và phân tích đề bài {001-002}

**Khái niệm cốt lõi**

Lỗi lớn nhất khi làm dự án là **viết code trước khi hiểu đề**. Hãy dành 30–60 phút để biến đề bài thành một danh sách yêu cầu rõ ràng.

**Bước 1: Tách yêu cầu thành hai loại**

| Loại | Câu hỏi | Ví dụ |
|---|---|---|
| **Functional** (chức năng) | Hệ thống *làm gì*? | Frontend gọi API `/api/...`, backend đọc ghi database |
| **Non-functional** (phi chức năng) | Hệ thống *tốt đến mức nào*? | Chạy trên ≥ 2 AZ, có HTTPS, tự triển khai khi push code, không lộ secret, chi phí thấp |

**Bước 2: Viết lại đề thành bảng "yêu cầu → bằng chứng"**

Mỗi yêu cầu phải trả lời được câu hỏi: *"Làm sao chứng minh mình đã làm xong?"* Bảng này chính là checklist nộp bài sau này.

```markdown
| # | Yêu cầu (trích đề)            | Thành phần AWS / công cụ | Bằng chứng sẽ chụp                     |
|---|-------------------------------|--------------------------|----------------------------------------|
| 1 | Ứng dụng chạy được ở local    | Docker Compose           | `docker compose ps` + ảnh trình duyệt  |
| 2 | Image lưu trên registry riêng | ECR                      | Danh sách image + tag theo commit SHA  |
| 3 | Hạ tầng tạo bằng IaC          | Terraform                | `terraform plan/apply` output          |
| 4 | Push code thì tự deploy       | CI/CD                    | Lịch sử pipeline chạy xanh             |
| … | …                             | …                        | …                                      |
```

**Bước 3: Liệt kê câu hỏi chưa rõ và tự ra giả định**

Trong công việc thật, bạn sẽ hỏi lại người giao việc. Ở đây, hãy **ghi giả định vào README** để người chấm hiểu lý do bạn chọn như vậy. Ví dụ: "Đề không yêu cầu domain riêng, nên tôi dùng DNS của ALB."

Các câu hỏi nên tự đặt ra:
- Frontend là SPA tĩnh (build ra HTML/JS) hay server Node.js? Cách đóng gói và phục vụ khác nhau.
- Backend cần biến môi trường gì? Chuỗi kết nối database lấy từ đâu?
- Database là loại gì (SQL hay NoSQL)? Dùng dịch vụ managed hay tự chạy container?
- Bao nhiêu môi trường (dev, prod)? Một region hay nhiều region?
- Ngân sách: bạn chấp nhận tốn bao nhiêu USD cho cả dự án?

**Đi sâu hơn: chia nhỏ công việc**

Chia thành các **mốc có thể kiểm chứng** (milestone). Mỗi mốc kết thúc bằng một thứ chạy được:

1. M1: Chạy local bằng Compose.
2. M2: Image nằm trên ECR.
3. M3: Hạ tầng mạng và database lên bằng Terraform.
4. M4: Ứng dụng chạy trên AWS, truy cập qua ALB.
5. M5: CI/CD tự deploy.
6. M6: README, sơ đồ, evidence, dọn dẹp.

Mỗi mốc nên là một nhánh hoặc pull request riêng trong Git. Lịch sử commit sạch cũng là một bằng chứng tốt khi đưa vào CV.

## Thiết kế hệ thống {003}

**Khái niệm cốt lõi**

Trước khi viết Terraform, hãy vẽ sơ đồ. Một kiến trúc container chuẩn trên AWS thường trông như sau:

```
                         Internet
                            │
                     ┌──────┴──────┐  (tuỳ chọn) Route 53 + ACM cho HTTPS
                     │     ALB     │  public subnet AZ a + AZ b
                     └──┬───────┬──┘
              path "/"  │       │  path "/api/*"
 ┌──────────────────────┼───────┼───────────────── VPC (≥ 2 AZ) ──────────┐
 │   private subnet     ▼       ▼                                          │
 │            [Frontend task/pod] [Backend task/pod]  ← ECS Fargate hoặc EKS │
 │                                   │                                     │
 │   private subnet (data)           ▼                                     │
 │                         [RDS / DocumentDB / ...] Multi-AZ nếu cần        │
 │                                                                         │
 │   NAT Gateway (hoặc VPC endpoint cho ECR, S3, Logs)                      │
 └─────────────────────────────────────────────────────────────────────────┘
   ECR (image)   CloudWatch Logs/Alarms   Secrets Manager / SSM Parameter Store
```

**Đi sâu hơn: các quyết định thiết kế quan trọng**

| Quyết định | Lựa chọn A | Lựa chọn B | Tiêu chí chọn |
|---|---|---|---|
| Chạy container | **ECS Fargate**: đơn giản, không quản node, không phí control plane | **EKS**: chuẩn Kubernetes, linh hoạt, nhưng có phí control plane 0,10 USD/giờ và phức tạp hơn | Đề yêu cầu gì? Ngân sách? Bạn muốn khoe kỹ năng gì? |
| Database | **Dịch vụ managed** (RDS, DocumentDB): có backup, Multi-AZ | **Container DB** + volume | Production gần như luôn dùng managed. Container DB chỉ hợp cho demo |
| Đi ra Internet từ private subnet | **NAT Gateway**: đơn giản, khoảng 1–1,5 USD/ngày | **VPC endpoint** cho ECR/S3/Logs | Học thì 1 NAT là đủ. Ghi rõ "production nên dùng 1 NAT mỗi AZ" |
| Frontend | Container sau ALB | S3 + CloudFront (nếu là SPA tĩnh) | Theo đề và kiến trúc đã học |
| Secret | Secrets Manager | SSM Parameter Store (SecureString, rẻ hơn) | Tuyệt đối không ghi trong code hay image |

**Nguyên tắc bảo mật mạng** (vẽ được thành mũi tên trên sơ đồ):
- SG của ALB: mở 80/443 từ `0.0.0.0/0`.
- SG của app: chỉ nhận traffic **từ SG của ALB**, đúng port của app.
- SG của database: chỉ nhận traffic **từ SG của backend**, đúng port DB.
- Không có gì trong private subnet có IP public.

**Ước lượng chi phí trước khi làm**

Dùng **AWS Pricing Calculator**, hoặc ước lượng nhanh theo giờ, rồi ghi con số vào README:

```
ALB           ~0,025 USD/giờ + LCU
NAT Gateway   ~0,05–0,06 USD/giờ + dữ liệu
Fargate       theo vCPU-giờ và GB-giờ (task 0,25 vCPU / 0,5 GB rất rẻ)
EKS           +0,10 USD/giờ control plane + node EC2
RDS/DocDB     instance nhỏ nhất + storage; DocumentDB đắt hơn RDS khá nhiều
IPv4 public   0,005 USD/giờ mỗi địa chỉ
```

> 💰 Hãy đặt **AWS Budget** (ví dụ 10 USD, cảnh báo ở 50% và 80%) trước khi `terraform apply` lần đầu.

**Công cụ vẽ sơ đồ:** draw.io (diagrams.net) có sẵn bộ icon AWS. Mermaid hoặc Python `diagrams` cho phép vẽ bằng code, lưu được trong Git.

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao SG của database nên tham chiếu SG của backend thay vì CIDR của subnet private?</summary>

Tham chiếu SG nghĩa là "chỉ những gì gắn SG backend mới vào được". Dùng CIDR thì *mọi thứ* trong subnet đó (kể cả frontend, hay một máy bị chiếm quyền) đều kết nối được DB. Ngoài ra, khi IP của task thay đổi, quy tắc dựa trên SG vẫn đúng.
</details>

<details><summary>2. Tại sao cần ít nhất 2 AZ, và ALB yêu cầu gì?</summary>

Một AZ có thể gặp sự cố. Hai AZ giúp ứng dụng vẫn chạy. ALB **bắt buộc** chọn subnet ở ít nhất 2 AZ, nên dù ứng dụng chỉ có 1 task, bạn vẫn phải có 2 public subnet.
</details>

## Docker Compose tại local và đẩy image lên ECR {004-005}

**Khái niệm cốt lõi**

**Chạy được ở local trước rồi mới lên cloud.** Mỗi lỗi sửa ở local mất vài giây. Cùng lỗi đó trên AWS mất vài phút và tốn tiền.

Docker Compose mô tả cả hệ thống (frontend, backend, database) trong một file:

```yaml
# compose.yaml (khung tham khảo, KHÔNG phải lời giải; tên service, port, biến môi trường lấy theo đề)
services:
  db:
    image: <image-database>:<version-cố-định>
    volumes: [db-data:/data]           # dữ liệu không mất khi container bị xoá
    healthcheck: { test: [...], interval: 10s, retries: 5 }
  backend:
    build: ./backend
    environment:
      DB_URL: ${DB_URL}                # đọc từ file .env (không commit)
    depends_on:
      db: { condition: service_healthy }
  frontend:
    build: ./frontend
    ports: ["8080:80"]
    depends_on: [backend]
volumes:
  db-data:
```

```bash
docker compose up -d --build
docker compose ps
docker compose logs -f backend
docker compose down -v          # -v xoá luôn volume dữ liệu
```

**Checklist Dockerfile tốt** (người chấm và nhà tuyển dụng sẽ nhìn vào):
- **Multi-stage build:** stage build có compiler và devDependencies, stage chạy chỉ có thứ cần thiết.
- Image nền nhỏ và ghim version (`node:20-alpine`, `nginx:1.27-alpine`), không dùng `latest`.
- Có `.dockerignore` (loại `node_modules`, `.git`, `.env`).
- Chạy bằng **user không phải root** (`USER node`).
- Không `COPY .env` vào image, không ghi secret bằng `ENV`.
- Có `HEALTHCHECK` hoặc endpoint `/health` để ALB và ECS/EKS kiểm tra.

**Đẩy image lên ECR**

```bash
AWS_REGION=ap-southeast-1
ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
REGISTRY=$ACCOUNT_ID.dkr.ecr.$AWS_REGION.amazonaws.com

aws ecr create-repository --repository-name <tên-repo> \
  --image-scanning-configuration scanOnPush=true --region $AWS_REGION
aws ecr get-login-password --region $AWS_REGION | \
  docker login --username AWS --password-stdin $REGISTRY

TAG=$(git rev-parse --short HEAD)             # tag theo commit, truy vết được
docker build -t $REGISTRY/<tên-repo>:$TAG ./backend
docker push $REGISTRY/<tên-repo>:$TAG
```

**Đi sâu hơn**

- **Tag bất biến:** bật `imageTagMutability = IMMUTABLE` trên ECR để không ai ghi đè tag `v1.0.0`. Tag theo commit SHA giúp biết chính xác code nào đang chạy và rollback dễ dàng.
- **Lifecycle policy:** tự xoá image cũ (ví dụ chỉ giữ 10 image gần nhất). ECR tính phí lưu trữ theo GB-tháng.
- **Kiến trúc CPU:** build trên Mac M1/M2 ra image `arm64`. Chạy trên Fargate hay node x86 sẽ báo `exec format error`. Dùng `docker buildx build --platform linux/amd64`. Trên Fedora x86_64 thì mặc định đã là amd64.
- Có thể tạo repo ECR bằng Terraform (`aws_ecr_repository`). Nhưng nếu `terraform destroy` xoá repo còn image thì sẽ lỗi, trừ khi đặt `force_delete = true`.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `no basic auth credentials` khi push | Chưa login ECR, hoặc token (12 giờ) đã hết hạn | Chạy lại `aws ecr get-login-password ...` |
| `name unknown: The repository with name '...' does not exist` | Chưa tạo repo hoặc sai region | Tạo repo, kiểm tra region trong URL |
| Backend báo `ECONNREFUSED 127.0.0.1:<port-db>` trong Compose | Dùng `localhost` thay vì tên service | Trong Compose, host của DB là **tên service** (`db`) |
| Frontend gọi API bị lỗi CORS / 404 | URL API được "nướng" vào bundle lúc build | Dùng đường dẫn tương đối `/api` và để reverse proxy/ALB định tuyến |

**Bài tập**

🟢 *Cơ bản*: Chạy ứng dụng bằng Compose, chụp `docker compose ps` và trình duyệt làm evidence M1. Push cả hai image lên ECR với tag là commit SHA.

🟡 *Thực hành*: Tối ưu Dockerfile backend bằng multi-stage và user không phải root. Ghi lại kích thước image trước và sau (`docker images`) vào README.

🔴 *Thử thách*: Chạy `trivy image <image>` (hoặc xem kết quả scan trên ECR), sửa ít nhất một lỗ hổng mức HIGH bằng cách đổi base image hoặc nâng dependency. Ghi lại vào README như một mục "Security hardening".

<details><summary>Gợi ý</summary>

Trên Fedora có thể chạy Trivy bằng container: `docker run --rm -v /var/run/docker.sock:/var/run/docker.sock aquasec/trivy:latest image <image>`. Thường chỉ cần đổi sang bản `-alpine` hoặc `-slim` mới hơn là giảm mạnh số CVE. Ghi lại cả con số trước và sau.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao không nên deploy bằng tag <code>latest</code>?</summary>

`latest` không cho biết code nào đang chạy. Rollback không được vì tag cũ đã bị ghi đè. Ngoài ra, ECS/EKS có thể không kéo image mới nếu tag không đổi. Tag theo commit SHA hoặc version giải quyết cả ba vấn đề.
</details>

## Cấu trúc và triển khai Terraform {006-008}

**Khái niệm cốt lõi**

Đây là lúc dùng lại toàn bộ chương 05. Tổ chức code theo **tầng**, mỗi tầng là một module:

```
infra/
├── backend.tf            # S3 backend + khoá state
├── providers.tf          # provider aws, ghim version, default_tags
├── variables.tf / terraform.tfvars
├── main.tf               # gọi các module theo thứ tự phụ thuộc
├── outputs.tf            # DNS của ALB, URL ECR, endpoint DB...
└── modules/
    ├── network/          # VPC, subnet 2 AZ, IGW, NAT, route table
    ├── security/         # các Security Group tham chiếu lẫn nhau
    ├── data/             # database + subnet group + secret
    ├── compute/          # ECS cluster/service/task definition hoặc EKS
    └── loadbalancer/     # ALB, listener, target group, rule /api
```

**Thứ tự apply nên đi từng bước** (có thể dùng `-target` khi đang phát triển, nhưng bản cuối phải `apply` một lần là chạy):

1. `network` → kiểm tra subnet, route table trên console.
2. `security` + `data` → kiểm tra database đã `available`.
3. `loadbalancer` + `compute` → kiểm tra target group `healthy`.

**Checklist Terraform** (tự chấm trước khi nộp)

- [ ] State lưu trên **S3** có khoá (`use_lockfile = true` hoặc DynamoDB), bucket bật versioning.
- [ ] Không có access key, mật khẩu DB hay webhook trong `.tf` / `.tfvars` được commit.
- [ ] Mật khẩu DB được sinh bằng `random_password` hoặc `manage_master_user_password = true` (RDS tự lưu vào Secrets Manager).
- [ ] Biến có `type` và `description`. Giá trị theo môi trường nằm trong `tfvars`.
- [ ] Provider và module **ghim version**.
- [ ] `default_tags { tags = { Project = "...", Owner = "...", Env = "..." } }`, để lọc chi phí theo tag.
- [ ] Output đủ dùng cho CI/CD (tên cluster/service, URL ECR).
- [ ] `terraform fmt -check` và `terraform validate` đều qua. Có thể thêm `tflint` và `checkov` hoặc `trivy config`.
- [ ] `terraform destroy` xoá sạch, không cần xoá tay thứ gì.

**Đi sâu hơn**

- **Ranh giới giữa Terraform và CI/CD:** Terraform tạo *hạ tầng* (cluster, service, ALB). CI/CD chỉ đổi *phiên bản image*. Nếu cả hai cùng quản lý tag image, `terraform apply` lần sau sẽ "kéo lùi" về image cũ. Cách phổ biến: dùng `lifecycle { ignore_changes = [...] }` cho phần do pipeline quản lý, hoặc để pipeline cập nhật task definition/manifest.
- **Health check là điểm hay gãy nhất:** port của container, port của target group, health check path, SG và `target_type` (`ip` cho Fargate) phải khớp nhau.
- **Thời gian tạo:** database và NAT mất vài phút, EKS mất 10–15 phút. Hãy kiên nhẫn đọc `plan` thay vì apply đi apply lại.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `Error acquiring the state lock` | Lần chạy trước bị ngắt giữa chừng | Chắc chắn không ai đang chạy, rồi `terraform force-unlock <LOCK_ID>` |
| Target group toàn `unhealthy`, ALB trả 503 | Sai port hoặc health check path, SG chặn | Xem mục "Health checks" của target group, log của task/pod |
| Task ECS dừng: `CannotPullContainerError` | Subnet private không có NAT/endpoint, hoặc execution role thiếu quyền ECR | Kiểm tra route `0.0.0.0/0 → NAT`, gắn `AmazonECSTaskExecutionRolePolicy` |
| `DependencyViolation` khi destroy VPC | Còn ENI hoặc ALB do dịch vụ khác tạo (ví dụ controller của EKS) | Xoá tài nguyên do Kubernetes tạo trước, rồi destroy lại |

💰 Hạ tầng của dự án có thể tốn **3–10 USD/ngày**, tuỳ kiến trúc. Làm theo phiên: `apply` buổi sáng, chụp evidence, `destroy` buổi tối. Terraform giúp dựng lại trong vài phút.

**Bài tập**

🟢 *Cơ bản*: Viết module `network` và `security`, apply và chụp sơ đồ **Resource map** của VPC trên console làm evidence.

🟡 *Thực hành*: Thêm CI cho chính Terraform: một workflow chạy `terraform fmt -check`, `validate` và `plan` khi mở pull request, rồi in kết quả plan vào summary của job.

<details><summary>Gợi ý</summary>

Dùng action `hashicorp/setup-terraform`. Với `plan`, CI cần quyền đọc AWS, nên dùng OIDC (xem phần CI/CD bên dưới) với một role chỉ đọc. Ghi plan vào `$GITHUB_STEP_SUMMARY` để người review đọc ngay trên trang PR.
</details>

🔴 *Thử thách*: Chạy `checkov -d infra/` hoặc `trivy config infra/`. Chọn 3 cảnh báo, sửa 2 cái, và giải thích bằng văn bản vì sao chấp nhận cái thứ ba (ví dụ "ALB không bật access log vì đây là môi trường học").

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao nên tách module network và compute, thay vì để mọi thứ trong một file main.tf?</summary>

Mỗi module có input và output rõ ràng, dễ đọc, dễ test riêng và dễ dùng lại cho môi trường khác. Khi lỗi xảy ra, bạn biết ngay nên tìm ở tầng nào. Người chấm cũng thấy được tư duy thiết kế theo tầng của bạn.

## CI/CD cho Frontend, Backend và nộp kết quả {009-012}

**Khái niệm cốt lõi**

Mỗi service (frontend, backend) có **pipeline riêng**, chỉ chạy khi code của service đó thay đổi:

```
push / merge vào main (chỉ thay đổi trong backend/**)
   │
   ├─ 1. Checkout + cài dependency (có cache)
   ├─ 2. Lint + unit test               ← fail thì dừng, không deploy
   ├─ 3. docker build, tag = commit SHA
   ├─ 4. Scan image (ECR scan / Trivy)
   ├─ 5. docker push lên ECR
   └─ 6. Deploy: cập nhật service sang image mới
         (ECS: task definition mới → update service; EKS: set image / apply manifest)
         → chờ rollout ổn định → smoke test (curl qua ALB)
```

**Checklist CI/CD**

- [ ] Pipeline tách cho FE và BE, lọc theo đường dẫn (`paths:` trong GitHub Actions).
- [ ] Image tag = commit SHA. Không deploy `latest`.
- [ ] **Không có access key dài hạn trong secret của CI.** Dùng **OIDC**: GitHub Actions assume IAM role bằng token tạm thời.
- [ ] Role của CI theo least privilege: chỉ push đúng repo ECR, chỉ cập nhật đúng service.
- [ ] Bước deploy **chờ rollout thành công** (ECS: `wait-for-service-stability`; EKS: `kubectl rollout status`), không "bắn rồi quên".
- [ ] Có cơ chế rollback: deploy lại SHA trước đó, hoặc ECS deployment circuit breaker với rollback.
- [ ] Badge trạng thái pipeline gắn trong README.

**Đi sâu hơn: OIDC cho GitHub Actions**

```yaml
# .github/workflows/backend.yml (khung, thay giá trị theo dự án)
on:
  push:
    branches: [main]
    paths: ["backend/**"]
permissions:
  id-token: write        # bắt buộc để xin OIDC token
  contents: read
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: arn:aws:iam::<ACCOUNT_ID>:role/<tên-role-ci>
          aws-region: ap-southeast-1
      - uses: aws-actions/amazon-ecr-login@v2
      # ... build, push, deploy
```

Trust policy của role chỉ tin đúng repo và nhánh của bạn:

```json
"Condition": {
  "StringEquals": { "token.actions.githubusercontent.com:aud": "sts.amazonaws.com" },
  "StringLike":   { "token.actions.githubusercontent.com:sub": "repo:<user>/<repo>:ref:refs/heads/main" }
}
```

**Evidence và README cho CV** (video 012)

Một README tốt giúp người khác (và nhà tuyển dụng) hiểu dự án trong 2 phút:

```markdown
# <Tên dự án> — Ứng dụng container trên AWS
![CI](badge-url)
### Kiến trúc
(ảnh sơ đồ) + 3–5 dòng giải thích luồng request
### Công nghệ
Docker, ECR, Terraform, ECS Fargate / EKS, ..., GitHub Actions, CodePipeline
### Cách chạy
Local: `docker compose up` · AWS: `cd infra && terraform apply`
### CI/CD
Sơ đồ pipeline, cách cấu hình OIDC
### Bảo mật & chi phí
SG nhiều lớp, secret trong Secrets Manager; chi phí ước lượng X USD/ngày
### Evidence
Ảnh chụp có chú thích (xem bảng bên dưới)
### Bài học & hướng phát triển
Những lỗi đã gặp, cách sửa; sẽ thêm HTTPS, autoscaling, alarm...
```

**Bộ evidence nên có** (đặt tên ảnh có thứ tự: `01-compose-ps.png`, `02-ecr-images.png`…):
1. Ứng dụng chạy ở local.
2. Image trên ECR (thấy tag SHA và kết quả scan).
3. Output `terraform apply` (hoặc phần cuối của nó) và `terraform output`.
4. Resource map của VPC, target group `healthy`.
5. Trình duyệt mở DNS của ALB, thao tác thành công cả frontend và API.
6. Pipeline FE và BE chạy xanh, kèm commit đã kích hoạt nó.
7. Một thay đổi nhỏ (đổi màu chữ, đổi chuỗi version) được tự deploy, ảnh "trước" và "sau".

> ⚠️ Trước khi chụp: **che account ID, ARN, URL webhook, IP cá nhân**. Không bao giờ chụp màn hình có access key hay mật khẩu.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `Not authorized to perform sts:AssumeRoleWithWebIdentity` | Trust policy sai `sub` (tên repo hoặc nhánh), hoặc thiếu `id-token: write` | So khớp chuỗi `repo:owner/name:ref:refs/heads/main` |
| `Could not load credentials from any providers` | Chưa có bước `configure-aws-credentials` | Thêm bước này trước mọi lệnh AWS |
| Pipeline xanh nhưng web vẫn bản cũ | Deploy cùng tag nên không kéo image mới, hoặc trình duyệt cache | Dùng tag SHA, chờ rollout, hard refresh |

**Bài tập**

🟢 *Cơ bản*: Viết pipeline cho backend: build → push ECR → deploy. Đổi một chuỗi trong API, push code và chụp evidence "trước/sau".

🟡 *Thực hành*: Thay access key trong secret của CI bằng **OIDC**. Xoá access key cũ trong IAM và chứng minh pipeline vẫn chạy.

<details><summary>Gợi ý</summary>

Tạo identity provider `token.actions.githubusercontent.com` (audience `sts.amazonaws.com`) trong IAM, tạo role với trust policy như trên, rồi gắn policy tối thiểu: `ecr:GetAuthorizationToken`, các action push trên đúng ARN repo, và quyền deploy cho đúng service. Xem log của job: dòng `Assuming role with OIDC` là bằng chứng.
</details>

🔴 *Thử thách*: Thêm bước **smoke test** sau deploy (`curl -f http://<alb>/api/health` thử lại 5 lần). Nếu fail thì tự rollback về SHA trước đó. Cố tình deploy một bản lỗi để chứng minh rollback hoạt động.

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao OIDC an toàn hơn lưu access key trong GitHub Secrets?</summary>

Access key sống rất lâu: lộ một lần (log, fork, người có quyền admin repo) là kẻ xấu dùng được mãi đến khi bạn phát hiện. OIDC cấp credential tạm thời (mặc định 1 giờ) cho đúng repo và nhánh đã khai báo trong trust policy, và không có gì để lộ.
</details>

## CodePipeline cho Frontend/Backend, evidence và dọn dẹp {013-016}

**Khái niệm cốt lõi**

Phần này làm lại CI/CD bằng dịch vụ của AWS, để bạn so sánh hai cách tiếp cận:

```
Source (GitHub qua CodeConnections)  →  Build (CodeBuild: buildspec.yml)  →  Deploy (ECS / EKS)
        trigger theo nhánh/đường dẫn          build, push ECR, sinh artifact       cập nhật service
```

| | GitHub Actions | AWS CodePipeline + CodeBuild |
|---|---|---|
| Nằm ở đâu | Cạnh code trên GitHub | Trong tài khoản AWS |
| Quyền AWS | OIDC → IAM role | **Service role** của CodeBuild/CodePipeline, không cần key |
| Kết nối mã nguồn | Sẵn có | Qua **CodeConnections** (tên cũ CodeStar Connections), phải bấm xác nhận trên GitHub |
| Chi phí | Có quota phút miễn phí cho repo public/cá nhân | Pipeline V2 tính theo phút chạy action, CodeBuild tính theo phút build |

> AWS CodeCommit đã ngừng nhận khách hàng mới từ 7/2024. Hãy để mã nguồn trên GitHub và kết nối qua CodeConnections.

**Checklist CodePipeline**
- [ ] `buildspec.yml` nằm trong repo, các phase `pre_build` (login ECR), `build`, `post_build` (push và sinh artifact cho bước deploy).
- [ ] Dùng biến `CODEBUILD_RESOLVED_SOURCE_VERSION` làm tag image.
- [ ] Service role của CodeBuild có quyền ECR. Nếu deploy lên EKS, role đó cần **access entry** trong cluster (xem chương 15).
- [ ] Biến bí mật lấy từ Parameter Store hoặc Secrets Manager (`env: parameter-store:` / `secrets-manager:`), không ghi thẳng trong buildspec.
- [ ] Nếu build image Docker: bật **privileged mode** cho project CodeBuild.
- [ ] Artifact bucket (S3) và log group (CloudWatch) có trong danh sách dọn dẹp.

**Lỗi hay gặp & cách sửa**

| Thông báo | Nguyên nhân | Cách sửa |
|---|---|---|
| `Cannot connect to the Docker daemon` trong CodeBuild | Chưa bật privileged mode | Bật "Privileged" trong environment của project |
| Source stage báo connection `PENDING` | Kết nối GitHub chưa được xác nhận | Vào Developer Tools → Connections → "Update pending connection" |
| `error: You must be logged in to the server` ở bước deploy EKS | Role của CodeBuild chưa có access entry | Tạo access entry cho ARN của role đó |

**Dọn dẹp tài nguyên** (video 016) — làm theo thứ tự ngược với lúc tạo:

```bash
# 1. Dừng pipeline (CodePipeline, project CodeBuild; tắt workflow nếu không dùng nữa)
# 2. Xoá tài nguyên do Kubernetes hoặc ECS tạo ngoài Terraform (Ingress/ALB, PVC/EBS) nếu có
# 3. Xoá hạ tầng chính
cd infra && terraform destroy
# 4. Xoá thủ công những gì nằm ngoài Terraform:
#    ECR repo (hoặc force_delete), S3 artifact bucket, CloudWatch log group,
#    CodeConnections, IAM role/OIDC provider của CI, secret trong Secrets Manager
#    (secret bị xoá có thời gian chờ 7–30 ngày, có thể --force-delete-without-recovery)
# 5. Cuối cùng mới xoá bucket S3 chứa state (nếu không dùng nữa)
```

Sau đó dùng **Tag Editor / Resource Groups** của AWS, lọc theo tag `Project=<tên>` ở mọi region, để chắc chắn không còn gì. Hôm sau kiểm tra **Billing**.

**Bài tập mở rộng** (làm sau khi nộp bài, để dự án nổi bật hơn trên CV)

🟢 *Cơ bản*: Làm pipeline CodePipeline cho frontend và backend. Chụp evidence một lần chạy thành công của mỗi pipeline. Ghi vào README bảng so sánh GitHub Actions và CodePipeline theo trải nghiệm thật của bạn.

🟡 *Thực hành*:
- **HTTPS bằng ACM:** nếu có domain, xin chứng chỉ ACM (xác thực bằng DNS), thêm listener 443 cho ALB, chuyển hướng 80 sang 443. Chứng chỉ ACM public miễn phí khi dùng với ALB.
- **Alarm:** tạo CloudWatch Alarm cho `HTTPCode_Target_5XX_Count` và `UnHealthyHostCount` của ALB, gửi qua SNS về email. Cố tình làm backend lỗi để alarm bắn.

<details><summary>Gợi ý</summary>

Cả hai làm được bằng Terraform: `aws_acm_certificate` + `aws_acm_certificate_validation` + `aws_route53_record`; và `aws_cloudwatch_metric_alarm` với namespace `AWS/ApplicationELB`, dimension `LoadBalancer` (lấy từ `arn_suffix` của ALB). Không có domain thì bỏ phần HTTPS và ghi rõ trong README. Alarm và SNS email nằm trong Free Tier ở mức nhỏ.
</details>

🔴 *Thử thách*:
- **Môi trường thứ hai:** thêm môi trường `dev` dùng cùng module, khác `tfvars` và state key. Pipeline deploy tự động lên dev, còn prod cần **phê duyệt thủ công** (GitHub Environments với required reviewers, hoặc Manual approval stage trong CodePipeline).
- **Quan sát:** đưa log ứng dụng về CloudWatch Logs với retention 7 ngày, tạo dashboard có request count, latency p95 và lỗi 5xx. Kết hợp với chương 17 nếu chạy trên EKS.

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao không xoá bucket state trước khi <code>terraform destroy</code>?</summary>

Terraform cần state để biết phải xoá những tài nguyên nào. Mất state thì mọi tài nguyên thành "mồ côi": vẫn chạy và tính tiền, nhưng Terraform không còn biết tới, và bạn phải xoá tay từng thứ.
</details>

<details><summary>2. Sau <code>terraform destroy</code> báo thành công, những gì có thể vẫn đang tính tiền?</summary>

Những thứ tạo ngoài Terraform: ALB và EBS do controller Kubernetes tạo, ECR image, S3 artifact bucket, CloudWatch log group (phí lưu trữ), secret trong Secrets Manager, EIP chưa giải phóng, snapshot. Đó là lý do cần kiểm tra lại bằng Tag Editor và Billing.
</details>
