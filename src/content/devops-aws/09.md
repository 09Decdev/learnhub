# Chương 09 · CICD sử dụng Jenkins

Học xong chương này, bạn **tự dựng một server Jenkins** trên EC2 Ubuntu và viết pipeline đưa code từ GitHub đi tới production: build Java/Node.js, build Docker image, đẩy lên ECR, deploy lên ECS, tự chạy khi có `git push`, release thủ công theo tag và báo kết quả sang Slack.

Bộ khung pipeline bạn sẽ viết đi viết lại cả chương:

```groovy
pipeline {
    agent any                       // chạy trên máy nào
    environment { REGION = 'ap-southeast-1' }
    stages {
        stage('Checkout') { steps { git 'https://github.com/<bạn>/<repo>.git' } }
        stage('Build')    { steps { sh 'docker build -t app:${BUILD_ID} .' } }
        stage('Deploy')   { steps { sh 'aws ecs update-service ...' } }
    }
    post { always { echo "Kết quả: ${currentBuild.currentResult}" } }
}
```

## Jenkins là gì và kiến trúc controller/agent {001-002}

**CI/CD** là tự động hoá con đường từ lúc dev `git push` tới lúc người dùng thấy tính năng mới:

- **CI (Continuous Integration, tích hợp liên tục):** mỗi lần push, máy tự lấy code, build, chạy test. Lỗi được phát hiện trong vài phút chứ không phải vài tuần.
- **CD (Continuous Delivery/Deployment):** build xong thì tự đóng gói và đưa lên môi trường. *Delivery* là sẵn sàng deploy nhưng cần người bấm nút. *Deployment* là tự deploy luôn tới production.

**Jenkins** là CI/CD server mã nguồn mở, viết bằng Java, ra đời từ 2011 (tách ra từ Hudson). Điểm mạnh là **hơn 1.800 plugin** và bạn tự host được, toàn quyền kiểm soát. Điểm yếu là bạn phải tự vận hành: cập nhật, sao lưu, vá bảo mật.

**Kiến trúc controller/agent:**

```
            ┌───────────────── Jenkins controller ─────────────────┐
 GitHub ──► │ Web UI :8080 · lịch build · lưu cấu hình job (XML)   │
 webhook    │ credentials store · plugin · lịch sử build          │
            └──────────┬───────────────────────┬───────────────────┘
                       │ giao việc (SSH/JNLP)  │
               ┌───────▼──────┐        ┌───────▼──────┐
               │ agent linux  │        │ agent docker │   ← mỗi agent có N executor
               │ 2 executor   │        │ (container   │
               │ workspace/   │        │  tạm thời)   │
               └──────────────┘        └──────────────┘
```

- **Controller** (trước đây gọi là *master*): bộ não. Giữ cấu hình, giao diện web, lên lịch build, lưu kết quả. Thư mục dữ liệu là `JENKINS_HOME` (trên Ubuntu: `/var/lib/jenkins`).
- **Agent** (trước đây gọi là *slave*): máy thực sự chạy lệnh build. Có thể là EC2, container, Pod Kubernetes.
- **Executor:** một "khe" chạy build trên một node. Agent có 2 executor thì chạy được 2 build cùng lúc.
- **Built-in node:** chính controller cũng có executor. Trong khoá học, mọi build chạy luôn trên controller cho đơn giản.
- **Workspace:** thư mục làm việc của mỗi job, ví dụ `/var/lib/jenkins/workspace/Buildjob3-simple-Java-project`.

**Đi sâu hơn**

- Tài liệu bảo mật của Jenkins khuyên đặt **số executor của built-in node = 0** và chạy build trên agent. Lý do: build chạy trên controller có quyền đọc toàn bộ `JENKINS_HOME`, kể cả file chứa credentials đã mã hoá và khoá giải mã. Ai sửa được Jenkinsfile là có thể đọc chúng.
- Hệ thống **Agent → Controller Access Control** luôn bật từ Jenkins 2.326, chặn agent bị chiếm quyền gửi lệnh độc hại ngược lên controller.
- **Các lựa chọn thay thế Jenkins** (2025–2026): GitHub Actions, GitLab CI, AWS CodePipeline/CodeBuild, CircleCI. Các dịch vụ này không cần tự vận hành server. Jenkins vẫn rất phổ biến ở doanh nghiệp vì linh hoạt và chạy được trong mạng nội bộ.
- **Các loại job hay gặp:** *Freestyle* (cấu hình bằng form, lab1–2), *Pipeline* (viết bằng code, lab3 trở đi), *Multibranch Pipeline* (tự tạo job cho mỗi nhánh có Jenkinsfile), *Organization Folder* (quét cả tổ chức GitHub).

**Câu hỏi tự kiểm tra**

<details><summary>1. Controller và agent khác nhau thế nào? Vì sao không nên build trên controller?</summary>

Controller điều phối: giữ cấu hình, UI, lịch build, credentials. Agent chạy lệnh build thật. Build trên controller có quyền truy cập file hệ thống của chính Jenkins. Một script build độc hại (hoặc lỗi) có thể đọc secret, xoá cấu hình, làm sập Jenkins. Tách ra agent thì hỏng agent vẫn thay được, controller an toàn.
</details>

<details><summary>2. Continuous Delivery khác Continuous Deployment ở điểm nào?</summary>

Cả hai đều tự build, test, đóng gói. *Delivery* dừng ở trạng thái "sẵn sàng deploy", cần người duyệt bấm nút lên production (giống lab9). *Deployment* tự đẩy thẳng lên production nếu mọi bước pass (giống lab8 với nhánh develop).
</details>

## Cài đặt Jenkins trên Ubuntu server {003}

Code lab: `cicd-using-jenkins/1.install-jenkins.sh` (chỉ trỏ sang hướng dẫn chính thức) và `2.troubleshoot-jenkins-failed-start.sh`.

**Khái niệm cốt lõi**

Jenkins là ứng dụng Java, nên thứ tự luôn là: **cài Java trước → cài Jenkins → mở trình duyệt vào port 8080 → nhập mật khẩu admin ban đầu → cài plugin gợi ý → tạo user admin**.

```bash
# 1. Java (Jenkins LTS hiện hành cần Java 21 hoặc 25)
sudo apt update
sudo apt install -y fontconfig openjdk-21-jre
java -version

# 2. Repo Jenkins LTS (bản "debian-stable"); khoá ký repo được đổi định kỳ, bản 2026 là jenkins.io-2026.key
sudo wget -O /etc/apt/keyrings/jenkins-keyring.asc \
  https://pkg.jenkins.io/debian-stable/jenkins.io-2026.key
echo "deb [signed-by=/etc/apt/keyrings/jenkins-keyring.asc] https://pkg.jenkins.io/debian-stable binary/" \
  | sudo tee /etc/apt/sources.list.d/jenkins.list > /dev/null
sudo apt update
sudo apt install -y jenkins

# 3. Kiểm tra dịch vụ và lấy mật khẩu ban đầu
sudo systemctl status jenkins
sudo cat /var/lib/jenkins/secrets/initialAdminPassword
```

Truy cập `http://<public-ip>:8080`, dán mật khẩu, chọn **Install suggested plugins**.

**Đi sâu hơn**

- **LTS hay Weekly?** Weekly ra bản mỗi tuần. **LTS** (Long-Term Support) chọn một bản ổn định mỗi ~12 tuần và vá lỗi cho nó. Server thật luôn dùng LTS.
- **Java:** theo chính sách Java của Jenkins, Java 17 đã hết hỗ trợ (bản LTS cuối dùng được Java 17 là 2.541.3, tháng 3/2026). Jenkins mới cần **Java 21** hoặc **Java 25**. Script troubleshoot trong repo ghi "Jenkins yêu cầu version 17" là thông tin **đã cũ**.
- **Cấu hình máy:** tài liệu chính thức nêu tối thiểu 256 MB RAM, nhưng khi build Maven + Docker thì nên có từ 2–4 GB RAM. Dùng `t3.small` hoặc `t3.medium` thay vì `t3.micro`, nếu không Jenkins sẽ bị kill vì hết RAM.
- **Đổi port:** `sudo systemctl edit jenkins`, thêm `[Service]` và `Environment="JENKINS_PORT=8081"`, rồi `sudo systemctl restart jenkins`.
- **Chọn Java cho riêng Jenkins** mà không đổi Java mặc định của cả máy: trong `systemctl edit jenkins` thêm `Environment="JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64"`.
- **Cách cài khác:** Docker image `jenkins/jenkins:lts-jdk21`, Helm chart trên Kubernetes, hoặc file `jenkins.war`.

**Bảo mật ngay từ đầu**

- ⚠️ **Không mở port 8080 cho `0.0.0.0/0`.** Jenkins là mục tiêu quét tự động rất phổ biến. Chỉ mở cho `<ip-của-bạn>/32`. Lab8 cần GitHub gọi vào thì chỉ thêm dải IP webhook của GitHub (xem phần Lab8).
- Gắn **IAM Role** cho EC2 Jenkins (Instance Profile) để gọi AWS. Không chạy `aws configure` với access key trên server.
- **Cập nhật Jenkins và plugin thường xuyên** (Manage Jenkins → Plugins → Updates). Phần lớn lỗ hổng Jenkins nằm ở plugin. Theo dõi trang Security Advisories của jenkins.io.
- Không cài plugin thừa. Mỗi plugin là thêm một bề mặt tấn công.

**Lỗi hay gặp & cách sửa**

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| `Job for jenkins.service failed` sau khi cài thêm JDK cho lab Java | `update-alternatives` trỏ `java` sang bản Jenkins không hỗ trợ | Xem log `sudo journalctl -u jenkins -n 50` hoặc `/var/log/jenkins/jenkins.log`. Chạy `sudo update-alternatives --config java` chọn bản 21, hoặc đặt `JAVA_HOME` riêng cho service, rồi `sudo systemctl restart jenkins` |
| `jenkins: failed to find a valid Java installation` | Cài Jenkins trước khi cài Java | Cài `openjdk-21-jre` rồi restart |
| `NO_PUBKEY ...` khi `apt update` | Dùng khoá repo cũ (2023) sau khi Jenkins đổi khoá | Tải lại khoá mới theo trang cài đặt chính thức |
| Trình duyệt quay mãi, không vào được | Security Group chưa mở 8080 cho IP của bạn, hoặc máy hết RAM | Kiểm tra SG; `free -h`; nâng instance type |

💰 **Chi phí / an toàn:** EC2 `t3.medium` ở Singapore khoảng 0,05 USD/giờ (ước lượng), cộng EBS và IPv4 public (~0,005 USD/giờ). Không học thì **Stop** instance. Lưu ý Public IP đổi sau khi start lại, nên webhook lab8 phải cập nhật URL (hoặc dùng Elastic IP).

**Bài tập**

🟢 *Cơ bản:* Cài Jenkins LTS trên EC2 Ubuntu `t3.small`, SG chỉ mở 22 và 8080 cho IP của bạn. Đăng nhập, tạo user admin riêng.

🟡 *Thực hành:* Đổi Jenkins sang port 8081 bằng `systemctl edit`, và ép Jenkins dùng Java 21 qua `JAVA_HOME` trong khi `java -version` của máy vẫn là bản khác.

<details><summary>Gợi ý</summary>

```bash
sudo systemctl edit jenkins
# thêm:
# [Service]
# Environment="JENKINS_PORT=8081"
# Environment="JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64"
sudo systemctl daemon-reload && sudo systemctl restart jenkins
sudo ss -tlnp | grep java        # phải thấy :8081
```

Nhớ sửa Security Group sang port 8081.
</details>

🔴 *Thử thách:* Chạy Jenkins bằng Docker trên chính máy Fedora của bạn, dữ liệu nằm trong volume để xoá container không mất job.

<details><summary>Lời giải</summary>

```bash
docker volume create jenkins_home
docker run -d --name jenkins -p 127.0.0.1:8080:8080 \
  -v jenkins_home:/var/jenkins_home jenkins/jenkins:lts-jdk21
docker exec jenkins cat /var/jenkins_home/secrets/initialAdminPassword
```

Bind vào `127.0.0.1` để chỉ máy bạn truy cập được. Dọn dẹp: `docker rm -f jenkins && docker volume rm jenkins_home`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao nên gắn IAM Role cho EC2 Jenkins thay vì <code>aws configure</code>?</summary>

IAM Role cấp credentials tạm thời, tự xoay vòng, không nằm trong file nào trên đĩa. Access key cố định nếu lộ (qua log build, qua plugin lỗi) thì dùng được mãi cho tới khi bạn xoá.
</details>

Cài maven kéo theo một JDK khác và có thể đổi `java` mặc định. Xem `journalctl -u jenkins` để thấy lỗi phiên bản Java, rồi `update-alternatives --config java` hoặc đặt `JAVA_HOME` cho service.
</details>

## Lab1 · Job Freestyle đầu tiên "Hello" {005}

Code lab: `cicd-using-jenkins/lab1/lab1.sh`.

**Khái niệm cốt lõi**

**Freestyle job** là loại job cấu hình hoàn toàn bằng form trên giao diện: chọn nguồn code, trigger, các bước build (Build Steps) và hành động sau build (Post-build Actions).

```bash
# Build Steps → Execute shell
echo "Build Step 01-Hello world"
echo "Devops for beginner on AWS"
```

Bấm **Build Now** rồi mở **Console Output** để xem log. Mỗi lần chạy là một **build** có số thứ tự `#1`, `#2`…

- Lệnh shell chạy dưới user hệ điều hành **`jenkins`**, không phải `ubuntu` hay `root`. Vì vậy đường dẫn `~` là `/var/lib/jenkins`.
- Shell mặc định chạy với `-xe`: in từng lệnh (`+ echo ...`) và **dừng ngay khi một lệnh trả về mã lỗi khác 0**. Build khi đó có trạng thái **FAILURE**.
- Trạng thái build: SUCCESS (xanh), UNSTABLE (vàng, thường do test fail), FAILURE (đỏ), ABORTED (xám).

**Đi sâu hơn**

- Freestyle dễ bắt đầu nhưng **cấu hình nằm trong Jenkins** (file `config.xml`), không nằm trong Git: không review được, khó tái tạo. Đó là lý do từ lab3 chuyển sang Pipeline.
- Nên bật **Discard old builds** (giữ 10–20 build) để `JENKINS_HOME` không đầy đĩa.

**Lỗi hay gặp**

- `Build step 'Execute shell' marked build as failure` kèm `command not found`: công cụ chưa cài trên máy Jenkins, hoặc không nằm trong `PATH` của user `jenkins`.
- `Permission denied` khi ghi file ngoài workspace: user `jenkins` không có quyền. Hãy ghi trong `$WORKSPACE`.

**Bài tập**

🟢 *Cơ bản:* Tạo job in ra `whoami`, `pwd`, `hostname` và `date`. Giải thích vì sao `whoami` là `jenkins`.

🟡 *Thực hành:* Thêm bước `exit 1` vào giữa job. Quan sát trạng thái build và các lệnh phía sau có chạy không. Sau đó cấu hình **Build periodically** với `H/15 * * * *` và tìm hiểu chữ `H` nghĩa là gì.

<details><summary>Gợi ý</summary>

`H` (hash) để Jenkins tự rải thời điểm chạy theo tên job, tránh mọi job cùng chạy đúng phút 00 gây quá tải. Nhớ tắt trigger sau khi thử để tránh build liên tục.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Lệnh thứ 2 trong 3 lệnh shell bị lỗi. Lệnh thứ 3 có chạy không?</summary>

Không. Jenkins chạy shell với `-e`, gặp mã lỗi khác 0 là dừng và đánh dấu FAILURE.
</details>

## Lab2 · Biến môi trường và Credentials {006}

Code lab: `cicd-using-jenkins/lab2/lab2.sh`.

**Khái niệm cốt lõi**

**Biến có sẵn của Jenkins** (xem đầy đủ tại `http://<jenkins>:8080/env-vars.html`):

| Biến | Ý nghĩa |
|---|---|
| `BUILD_ID` / `BUILD_NUMBER` | Số thứ tự build: 1, 2, 3… |
| `JOB_NAME` | Tên job |
| `WORKSPACE` | Thư mục làm việc của job |
| `BUILD_URL` | Link tới trang build |
| `GIT_COMMIT`, `GIT_BRANCH` | Có khi job checkout từ Git |

**Credentials store** là kho lưu bí mật mã hoá của Jenkins (Manage Jenkins → Credentials). Các kiểu hay dùng: *Username with password*, *Secret text* (token), *SSH Username with private key*, *Secret file*. Mỗi credential có một **ID** (ví dụ `dblogin`) để pipeline tham chiếu.

```groovy
withCredentials([usernamePassword(credentialsId: 'dblogin',
                                  usernameVariable: 'USERNAME',
                                  passwordVariable: 'PASSWORD')]) {
    sh '''
        echo "Username: $USERNAME"
        echo "Password: $PASSWORD"     # Jenkins sẽ che thành ****
    '''
}
```

- Bên trong khối `withCredentials`, secret nằm trong biến môi trường. Ra khỏi khối là biến biến mất.
- Jenkins tự **che (mask)** giá trị secret trong Console Output thành `****`.

**Đi sâu hơn**

- ⚠️ **Không hard-code secret** trong job hay Jenkinsfile. Jenkinsfile nằm trong Git, ai đọc được repo là thấy.
- ⚠️ **Dùng nháy đơn `'...'` cho lệnh `sh` có secret.** Với nháy kép `"... $PASSWORD"`, Groovy chèn giá trị *trước* khi chạy shell, secret có thể lộ qua danh sách tiến trình. Jenkins sẽ cảnh báo "A secret was passed to "sh" using Groovy String interpolation". Nháy đơn để shell tự đọc biến môi trường, an toàn hơn.
- Masking chỉ che *đúng chuỗi* đó. Nếu bạn `echo $PASSWORD | base64` thì giá trị đã biến đổi **không bị che**. Lab in password ra chỉ để minh hoạ, đừng làm vậy ở job thật.
- Trong Declarative có cách viết gọn: `environment { DB = credentials('dblogin') }` tạo ra `DB`, `DB_USR`, `DB_PSW`.
- Credentials có **scope**: *Global* (mọi job), *System* (chỉ Jenkins dùng nội bộ, ví dụ kết nối agent). Có thể đặt credentials trong **Folder** để chỉ job trong folder đó dùng được.
- Doanh nghiệp thường không lưu secret trong Jenkins mà lấy từ **AWS Secrets Manager** hoặc **HashiCorp Vault** qua plugin, hoặc dùng IAM Role.

**Lỗi hay gặp**

- `ERROR: Could not find credentials entry with ID 'dblogin'`: ID gõ sai, hoặc credential nằm trong folder khác/scope System.
- Thấy secret in ra rõ ràng trong log: secret đã bị biến đổi (cắt chuỗi, encode) trước khi in.

**Bài tập**

🟢 *Cơ bản:* Tạo job Pipeline in ra `BUILD_NUMBER`, `JOB_NAME`, `WORKSPACE`, `BUILD_URL`.

🟡 *Thực hành:* Tạo credential kiểu *Secret text* ID `api-token`. Viết pipeline dùng `environment { TOKEN = credentials('api-token') }` rồi chạy `sh 'test -n "$TOKEN" && echo "co token"'`. Thử đổi sang nháy kép và đọc cảnh báo trong log.

<details><summary>Lời giải</summary>

```groovy
pipeline {
    agent any
    environment { TOKEN = credentials('api-token') }
    stages {
        stage('Use token') {
            steps { sh 'test -n "$TOKEN" && echo "co token"' }
        }
    }
}
```
</details>

🔴 *Thử thách:* Chứng minh vì sao masking không đủ an toàn: in secret qua `rev` hoặc `base64` và thấy giá trị lộ ra. Rút ra quy tắc cho team. (Dùng secret giả, xoá build sau khi thử.)

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao <code>sh "curl -H 'Auth: ${TOKEN}' ..."</code> bị Jenkins cảnh báo?</summary>

Nháy kép khiến Groovy chèn giá trị secret vào chuỗi lệnh trước khi gửi cho shell. Secret khi đó nằm trong tham số tiến trình và có thể lộ. Viết `sh 'curl -H "Auth: $TOKEN" ...'` để shell tự đọc biến môi trường.
</details>

- [Using credentials (jenkins.io)](https://www.jenkins.io/doc/book/using/using-credentials/)

## Khái niệm Pipeline trong Jenkins {007}

**Khái niệm cốt lõi**

Một luồng CI/CD điển hình mà các lab sau sẽ ghép dần:

```
git push ──► Checkout ──► Build ──► Test ──► Đóng gói ──► Lưu artifact ──► Deploy ──► Thông báo
               lab3        lab3-4             lab5         S3 / ECR         lab6       lab11
               └──── trigger tự động: lab8 (webhook) · thủ công theo tag: lab9 ────┘
```

- **Pipeline** = toàn bộ quy trình, viết bằng code (Groovy DSL) thay vì click form.
- **Stage** = một giai đoạn có tên (Build, Test, Deploy). Hiện thành cột trên giao diện.
- **Step** = một lệnh cụ thể trong stage: `sh`, `git`, `echo`, `withCredentials`.
- **Artifact** = sản phẩm của build: file `.jar`, thư mục `dist/`, Docker image.
- **Jenkinsfile** = file chứa pipeline, đặt trong repo (lab7).

**Hai cú pháp Pipeline:**

| | Declarative | Scripted |
|---|---|---|
| Bắt đầu bằng | `pipeline { ... }` | `node { ... }` |
| Cấu trúc | Cố định: `agent`, `stages`, `steps`, `post` | Tự do, là code Groovy |
| Kiểm tra cú pháp | Có, báo lỗi trước khi chạy | Ít, lỗi lộ ra lúc chạy |
| Khi nào dùng | **Mặc định cho mọi pipeline mới** | Logic phức tạp, vòng lặp động (lab10) |

**Đi sâu hơn**

- **Nguyên tắc "build một lần, deploy nhiều nơi":** build ra artifact *một lần*, gắn version (ví dụ `ver-${BUILD_ID}` hoặc Git tag), rồi đưa *cùng artifact đó* lên dev, staging, production. Không build lại cho mỗi môi trường.
- **Pipeline as Code** cho phép review pipeline qua Pull Request giống như code ứng dụng.
- Giao diện xem pipeline: **Blue Ocean** đã bị đánh dấu deprecated và ngừng phát triển. Jenkins khuyên dùng plugin **Pipeline Graph View** (hoặc *Pipeline: Stage View*). Đừng mất công cài Blue Ocean theo các video cũ.
- **Snippet Generator** (link "Pipeline Syntax" ở trang cấu hình job) sinh code mẫu cho bất kỳ step nào. Đây là công cụ tra cứu số 1 khi viết pipeline.

**Câu hỏi tự kiểm tra**

<details><summary>Vì sao nên gắn tag version cho artifact thay vì luôn dùng <code>latest</code>?</summary>

`latest` thay đổi theo thời gian nên không biết production đang chạy bản nào, và không rollback được về "bản trước". Tag cố định (`v1.0.1`, `ver-42`) cho phép truy vết từ image về commit và deploy lại chính xác bản cũ.
</details>

## Lab3 · Build Java với Maven và cú pháp Declarative {008-010}

Code lab: `cicd-using-jenkins/lab3/lab3.sh` (phần 1–2: Freestyle + Maven + upload S3) và `lab3/lab3.groovy` (phần 3: viết lại bằng Declarative).

**Khái niệm cốt lõi**

- **Maven** là công cụ build Java: đọc `pom.xml`, tải thư viện, compile, test, đóng gói thành `target/*.jar`.
- **Global Tool Configuration** (Manage Jenkins → Tools): khai báo JDK và Maven để job gọi theo tên. Lab chọn *Install from Apache* để Jenkins tự tải Maven.
- Upload artifact lên **S3** để lưu lâu dài, mỗi build một thư mục `${BUILD_ID}`.

```groovy
pipeline {
    agent any
    tools { maven 'M3' }                          // tên Maven đã khai báo ở Tools
    stages {
        stage('Checkout') {
            steps { git 'https://github.com/<bạn>/simple-java-maven-app.git' }
        }
        stage('Build') {
            steps { sh 'mvn -B -DskipTests clean package' }   // -B: batch mode, log gọn
        }
        stage('Upload Artifacts') {
            steps {
                sh 'aws s3 cp ${WORKSPACE}/target/my-app-1.0-SNAPSHOT.jar s3://<bucket-của-bạn>/buildjob3/${BUILD_ID}/'
            }
        }
    }
}
```

> Bucket `udemy-jenkins-linh` trong repo là của giảng viên. Bạn phải tạo bucket của mình (tên duy nhất toàn cầu).

**Các khối của Declarative Pipeline (đi sâu hơn)**

```groovy
pipeline {
    agent any
    options {
        timeout(time: 30, unit: 'MINUTES')          // build treo quá 30 phút thì huỷ
        buildDiscarder(logRotator(numToKeepStr: '20'))
        disableConcurrentBuilds()                   // không chạy 2 build cùng lúc
        timestamps()                                // thêm giờ vào mỗi dòng log (cần plugin Timestamper)
    }
    parameters {
        string(name: 'VERSION', defaultValue: 'v0.0.1')
        choice(name: 'ACTION', choices: ['BuildAndDeploy', 'OnlyBuild', 'OnlyDeploy'])
        booleanParam(name: 'RUN_TESTS', defaultValue: true)
    }
    environment { REGION = 'ap-southeast-1' }
    triggers { pollSCM('H/5 * * * *') }             // hoặc cron(...), upstream(...)
    stages {
        stage('Test') {
            when { expression { params.RUN_TESTS } } // chỉ chạy khi điều kiện đúng
            steps { sh 'mvn -B test' }
            post { always { junit 'target/surefire-reports/*.xml' } }
        }
    }
    post {
        success { echo 'OK' }
        failure { echo 'Hỏng rồi' }
        always  { cleanWs() }                       // dọn workspace (plugin Workspace Cleanup)
    }
}
```

- `post` có các điều kiện: `always`, `success`, `failure`, `unstable`, `aborted`, `changed`, `fixed`, `regression`, `unsuccessful`, `cleanup`.
- `when` có sẵn: `branch`, `tag`, `buildingTag()`, `changeRequest()`, `environment`, `expression`, `triggeredBy`, kết hợp bằng `allOf`/`anyOf`/`not`.
- Đọc tham số qua `params.VERSION` (Groovy) hoặc `$VERSION` (shell).
- **`agent docker`**: chạy stage trong container, không cần cài Maven lên server. Cần plugin *Docker Pipeline* và Docker trên agent:

```groovy
pipeline {
    agent { docker { image 'maven:3.9-eclipse-temurin-21' } }
    stages { stage('Build') { steps { sh 'mvn -B clean package' } } }
}
```

Mỗi build có môi trường sạch, đúng phiên bản. Đây là cách làm hiện đại thay cho việc cài tay JDK/Maven/Node lên server Jenkins (nguồn gốc của lỗi Java ở trên).

**Lỗi hay gặp & cách sửa**

- `mvn: not found`: chưa có khối `tools { maven 'M3' }`, hoặc tên `M3` không khớp tên ở Tools.
- `upload failed ... AccessDenied`: EC2 Jenkins chưa có IAM Role, hoặc role không có quyền `s3:PutObject` trên bucket.
- `Unable to locate credentials`: chưa gắn Instance Profile cho EC2. Kiểm tra bằng `aws sts get-caller-identity` khi chạy dưới user jenkins.
- Jenkins không start lại sau lab này: xem phần cài đặt (Java bị đổi).

💰 **Chi phí / an toàn:** S3 gần như miễn phí với vài file jar. Lab dùng `AmazonS3FullAccess` cho nhanh. Làm đúng là policy chỉ cho `s3:PutObject` trên `arn:aws:s3:::<bucket>/buildjob3/*`. Học xong xoá bucket: `aws s3 rb s3://<bucket> --force`.

**Bài tập**

🟢 *Cơ bản:* Chạy lại lab3 với bucket của bạn. Mở S3 kiểm tra mỗi build tạo một thư mục số.

🟡 *Thực hành:* Bỏ `-DskipTests`, thêm stage `Test` chạy `mvn -B test` và publish kết quả bằng `junit`. Thêm `options { timeout(...); buildDiscarder(...) }`.

<details><summary>Gợi ý</summary>

Báo cáo test của Maven nằm ở `target/surefire-reports/*.xml`. Đặt `junit` trong `post { always { ... } }` của stage Test để test fail vẫn có báo cáo. Khi có test fail, `junit` đánh dấu build UNSTABLE.
</details>

🔴 *Thử thách:* Viết lại lab3 dùng `agent { docker { image 'maven:3.9-eclipse-temurin-21' } }` để không cần khai báo Maven trong Tools. Upload jar lên S3 trong stage riêng chạy bằng `agent any` (vì image Maven không có AWS CLI).

<details><summary>Gợi ý</summary>

Dùng `agent none` ở cấp pipeline, mỗi stage tự khai báo agent. Chuyển file giữa các stage bằng `stash includes: 'target/*.jar', name: 'jar'` và `unstash 'jar'`. Agent docker cần user `jenkins` có quyền chạy Docker (xem lab5).
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>post { always { ... } }</code> ở cấp pipeline chạy khi nào?</summary>

Chạy sau khi mọi stage kết thúc, **bất kể** thành công, thất bại hay bị huỷ. Thích hợp để dọn workspace và gửi thông báo.
</details>

<details><summary>2. Ưu điểm của <code>agent docker</code> so với cài Maven lên server Jenkins?</summary>

Mỗi job tự chọn phiên bản công cụ, không xung đột nhau (job A cần Java 17, job B cần Java 21). Server Jenkins gọn, ít thứ phải cập nhật. Môi trường build tái tạo được ở bất kỳ agent nào có Docker.
</details>

## Lab5 · Build Docker image và push lên ECR {013}

Code lab: `cicd-using-jenkins/lab5/lab5.groovy`, `lab5/lab5.sh`.

**Khái niệm cốt lõi**

```
Jenkins ── docker build ──► image nodejs-random-color:ver-7
        ── docker login ──► ECR (bằng token tạm từ IAM Role)
        ── docker tag/push ► <ACCOUNT_ID>.dkr.ecr.ap-southeast-1.amazonaws.com/nodejs-random-color:ver-7
```

```groovy
environment {
    REGISTRY = '<ACCOUNT_ID>.dkr.ecr.ap-southeast-1.amazonaws.com'   // thay bằng account của bạn
    IMAGE    = "${REGISTRY}/nodejs-random-color"
}
stages {
    stage('Build') { steps { sh 'docker build -t nodejs-random-color:ver-${BUILD_ID} .' } }
    stage('Upload image to ECR') {
        steps {
            sh 'aws ecr get-login-password --region ap-southeast-1 | docker login --username AWS --password-stdin $REGISTRY'
            sh 'docker tag nodejs-random-color:ver-${BUILD_ID} $IMAGE:ver-${BUILD_ID}'
            sh 'docker push $IMAGE:ver-${BUILD_ID}'
        }
    }
}
```

- Repo lab hard-code account `430950558682` ở nhiều chỗ. Gom vào `environment` như trên để chỉ sửa **một** dòng.
- `aws ecr get-login-password` lấy token có hiệu lực **12 giờ**, nên mỗi build login lại là đúng.
- Repository ECR `nodejs-random-color` phải **tạo trước**: `aws ecr create-repository --repository-name nodejs-random-color`.

**Đi sâu hơn**

- ⚠️ `sudo usermod -aG docker jenkins` giải quyết lỗi permission, nhưng **nhóm `docker` tương đương quyền root** trên máy: ai viết được Jenkinsfile là chạy được `docker run -v /:/host` và làm chủ server. Chấp nhận được trong lab. Thực tế nên build trên agent riêng, tách khỏi controller.
- Bật **Tag immutability** trên ECR để không ai ghi đè được tag `v1.0.0` đã phát hành. Bật **scan on push** để quét lỗ hổng.
- Đặt **Lifecycle policy** cho ECR (ví dụ chỉ giữ 20 image gần nhất) để không tốn tiền lưu trữ.
- Dọn image trên máy Jenkins: `docker image prune -af --filter "until=24h"`, nếu không đĩa sẽ đầy sau vài chục build.

**Lỗi hay gặp & cách sửa**

| Lỗi | Cách sửa |
|---|---|
| `permission denied while trying to connect to the Docker daemon socket` | `sudo usermod -aG docker jenkins && sudo systemctl restart jenkins` (phải restart để nhận nhóm mới) |
| `no basic auth credentials` khi push | Chưa login, hoặc login sai region/account |
| `name unknown: The repository with name '...' does not exist` | Chưa tạo repository ECR |
| `AccessDeniedException ... ecr:GetAuthorizationToken` | IAM Role của EC2 thiếu quyền ECR (ví dụ policy `AmazonEC2ContainerRegistryPowerUser`) |

💰 **Chi phí / an toàn:** ECR tính khoảng 0,10 USD/GB/tháng lưu trữ (ước lượng). Vài image Node.js nhỏ chỉ tốn vài cent. Xoá image cũ khi học xong.

**Bài tập**

🟢 *Cơ bản:* Tạo ECR repo, sửa pipeline dùng account của bạn qua `environment`, chạy 2 lần và thấy 2 tag `ver-N` trên ECR.

🟡 *Thực hành:* Push thêm tag thứ hai là 7 ký tự đầu của commit (`GIT_COMMIT`). Đặt lifecycle policy giữ 10 image.

## Lab6 · Deploy Docker image lên ECS Cluster {015-016}

Code lab: `cicd-using-jenkins/lab6/lab6.groovy`, `lab6/lab6.sh`, Terraform ở `lab6/terraform/` (VPC + NAT, SG, ALB, Target Group, ECS Fargate cluster, task definition, service 3 task).

**Khái niệm cốt lõi**

```
Terraform tạo hạ tầng 1 lần:  VPC ─ ALB:80 ─ Target Group ─ ECS Service (3 task Fargate, private subnet)
Jenkins deploy mỗi lần:       đọc task definition cũ ─► thay image ─► đăng ký revision mới ─► update-service
```

- **Task definition** là "bản thiết kế" container: image, CPU/RAM, port, log. Mỗi lần sửa là một **revision** mới (`nodejs-task-definition:5`). Revision cũ không bị sửa.
- **Service** giữ đủ số task đang chạy và gắn chúng vào Target Group của ALB.
- Job Jenkins nhận tham số `version` (String Parameter), ví dụ `ver-3`.

```bash
TASK_DEFINITION=$(aws ecs describe-task-definition --task-definition ${TASK_FAMILY} --region ap-southeast-1)
# Thay image, xoá các trường chỉ-đọc mà register-task-definition không chấp nhận
NEW_TASK_DEFINITION=$(echo $TASK_DEFINITION | jq --arg IMAGE "${FULL_IMAGE}" \
  '.taskDefinition | .containerDefinitions[0].image = $IMAGE
   | del(.taskDefinitionArn) | del(.revision) | del(.status) | del(.requiresAttributes)
   | del(.compatibilities) | del(.registeredAt) | del(.registeredBy)')
NEW_TASK_INFO=$(aws ecs register-task-definition --region ap-southeast-1 --cli-input-json "$NEW_TASK_DEFINITION")
NEW_REVISION=$(echo $NEW_TASK_INFO | jq '.taskDefinition.revision')
aws ecs update-service --cluster udemy-devops-ecs-cluster --service nodejs-service \
  --task-definition ${TASK_FAMILY}:${NEW_REVISION} --force-new-deployment
```

**Đi sâu hơn**

- `update-service` **không chờ** deploy xong. Job xanh chỉ nghĩa là "đã gửi yêu cầu". Thêm dòng sau để job chờ tới khi service ổn định (hoặc fail sau khoảng 10 phút):

  ```bash
  aws ecs wait services-stable --cluster udemy-devops-ecs-cluster --services nodejs-service
  ```

- Mặc định ECS dùng **rolling update** với `minimumHealthyPercent=100`, `maximumPercent=200`: bật task mới trước, task mới healthy rồi mới tắt task cũ, không downtime. Chương 10 sẽ phân tích kỹ.
- Bật **deployment circuit breaker** (`deploymentCircuitBreaker { enable = true, rollback = true }` trong `aws_ecs_service`) để ECS tự rollback khi task mới không khởi động được.
- Lỗi kinh điển: Terraform quản lý task definition, Jenkins lại đăng ký revision mới. Lần `terraform apply` sau Terraform thấy service lệch và **kéo về revision cũ**. Cách xử lý phổ biến: `lifecycle { ignore_changes = [task_definition] }` trên `aws_ecs_service`.

**Lỗi hay gặp & cách sửa**

- `jq: not found`: `sudo apt-get install -y jq` trên máy Jenkins.
- `ClientException: Unknown parameter in input: "registeredAt"`: chưa xoá hết trường chỉ-đọc. Kiểm tra lại câu `jq`. AWS CLI mới có thể thêm trường mới, cần `del()` thêm.
- Task cứ `PENDING` rồi `STOPPED` với `CannotPullContainerError`: image/tag không tồn tại trên ECR, hoặc private subnet không ra được Internet (NAT Gateway hỏng).
- `AccessDeniedException ... iam:PassRole`: IAM Role của Jenkins cần quyền `iam:PassRole` cho execution role của task khi đăng ký task definition.

## Lab7 · Pipeline from SCM: Jenkinsfile nằm trong repo {017}

Code lab: `cicd-using-jenkins/lab7/lab7.sh`, `lab7/lab7-Jenkinsfile.groovy`.

**Khái niệm cốt lõi**

Thay vì dán pipeline vào ô *Pipeline script* trên Jenkins, bạn commit file **`Jenkinsfile`** vào gốc repo và chọn **Pipeline script from SCM**. Jenkins tự clone repo, đọc Jenkinsfile và chạy.

```
Repo GitHub (private)
├── Dockerfile
├── app.js
└── Jenkinsfile   ← pipeline nằm cạnh code, được review qua Pull Request
```

- Jenkinsfile của lab7 **bỏ stage Checkout** vì Jenkins đã tự checkout repo trước khi chạy pipeline (bước "Declarative: Checkout SCM").
- Repo private → Jenkins cần credentials. Lab dùng **SSH key**:

```bash
ssh-keygen -t ed25519 -C "jenkins@lab" -f ~/.ssh/jenkins_github   # tạo cặp khoá riêng cho Jenkins
cat ~/.ssh/jenkins_github.pub   # dán vào GitHub
```

  Private key đưa vào Jenkins dạng credential **SSH Username with private key** (username `git`). URL repo dùng dạng SSH: `git@github.com:<bạn>/nodejs-random-color.git`.
- **Git Host Key Verification** (Manage Jenkins → Security): Jenkins phải tin host key của github.com. Lab chọn *Accept first connection*. Cách chặt hơn là *Manually provided keys* với host key công bố trên docs.github.com.

**Đi sâu hơn**

- **Deploy key thay vì SSH key của tài khoản:** gắn public key vào *Settings → Deploy keys* của **một repo**, chỉ quyền read. Lộ key chỉ ảnh hưởng một repo, không phải mọi repo của bạn. Hoặc dùng **GitHub App** với plugin GitHub Branch Source (token ngắn hạn, được Jenkins khuyên dùng cho tổ chức).
- **Multibranch Pipeline:** Jenkins quét repo, mỗi nhánh/PR có Jenkinsfile thành một job riêng. Khi đó `when { branch 'main' }` mới có tác dụng.
- **Shared Library:** khi nhiều repo lặp lại cùng đoạn "build + push ECR", gom vào một repo thư viện:

  ```
  jenkins-shared-lib/
  └── vars/
      └── buildAndPushEcr.groovy   // def call(String repo) { sh "docker build ..." }
  ```

  Khai báo ở Manage Jenkins → System → Global Pipeline Libraries, rồi trong Jenkinsfile:

  ```groovy
  @Library('jenkins-shared-lib') _
  pipeline { agent any; stages { stage('Image') { steps { buildAndPushEcr('nodejs-random-color') } } } }
  ```

- **Replay** (trên trang build) cho phép sửa thử Jenkinsfile và chạy lại mà không cần commit, rất tiện khi gỡ lỗi.

**Lỗi hay gặp & cách sửa**

- `No ED25519 host key is known for github.com and you have requested strict checking`: chưa cấu hình Git Host Key Verification.
- `Permission denied (publickey)`: chưa chọn credential trong job, public key chưa thêm vào GitHub, hoặc dùng URL HTTPS với SSH key.
- `Unable to find Jenkinsfile from git`: sai *Script Path* hoặc sai nhánh (`*/main` vs `*/master`).

## Lab8 · Tự động build khi push code: GitHub webhook {018}

Code lab: `cicd-using-jenkins/lab8/lab8.sh`, `lab8/lab8.groovy` (file `Jenkinsfile-auto` trong repo: build → push tag `latest` → deploy ECS).

**Khái niệm cốt lõi**

**Polling** và **webhook** là hai cách để Jenkins biết có code mới:

```
Polling:  Jenkins ── 5 phút hỏi 1 lần "có commit mới không?" ──► GitHub     (chậm, tốn tài nguyên)
Webhook:  GitHub  ── ngay khi push: POST /github-webhook/ ──────► Jenkins   (tức thì)
```

Các bước trong lab:
1. Cài plugin **GitHub** (thường có sẵn trong bộ suggested).
2. Job: tick **GitHub hook trigger for GITScm polling**, Pipeline from SCM, *Branches to build* `*/develop`, *Script Path* `Jenkinsfile-auto`.
3. GitHub repo → Settings → Webhooks → Payload URL `http://<jenkins>:8080/github-webhook/` (**phải có `/` cuối**), Content type `application/json`, chọn sự kiện Pushes.
4. `git push origin develop` → job tự chạy.

Xem lịch sử gọi webhook ở GitHub: Settings → Webhooks → **Recent Deliveries** (mã phản hồi, payload, nút *Redeliver*).

**Đi sâu hơn**

- Tên tuỳ chọn "GitHub hook trigger for **GITScm polling**" nói lên cơ chế: webhook đến thì Jenkins **chạy polling ngay lập tức** cho các job khớp URL repo. Vì vậy URL repo trong job phải khớp với repo gửi webhook.
- ⚠️ **Lab yêu cầu mở 8080 cho mọi IP, đừng làm vậy lâu dài.** Cách tốt hơn:
  - Chỉ mở cho dải IP webhook của GitHub: lấy từ `curl -s https://api.github.com/meta | jq -r '.hooks[]'`, cộng IP của bạn.
  - Đặt Jenkins sau ALB/Nginx có HTTPS, chỉ cho phép đường dẫn `/github-webhook/` từ Internet.
  - Dùng **webhook secret** để Jenkins xác minh request thật sự từ GitHub (cấu hình *Shared secret* trong phần GitHub của Manage Jenkins → System).
- Job lab8 deploy image `latest` với `--force-new-deployment`. ECS phân giải tag thành **digest** lúc deploy, nên force deploy sẽ lấy đúng image `latest` mới. Nhưng bạn mất khả năng biết đang chạy bản nào. Kết hợp thêm tag `ver-${BUILD_ID}` hoặc SHA commit.
- Webhook chỉ tới được khi Jenkins có địa chỉ public. Jenkins trong mạng nội bộ thì dùng polling, hoặc dịch vụ chuyển tiếp webhook.

**Lỗi hay gặp & cách sửa**

| Triệu chứng | Nguyên nhân | Cách sửa |
|---|---|---|
| Recent Deliveries báo timeout | SG không cho GitHub vào 8080, hoặc IP Jenkins đã đổi sau khi stop/start | Sửa SG; cập nhật Payload URL; dùng Elastic IP |
| Mã `302` hoặc `404` | Thiếu `/` cuối URL, hoặc sai đường dẫn | Dùng đúng `/github-webhook/` |
| Webhook `200` nhưng job không chạy | Chưa tick trigger, hoặc URL repo trong job khác repo gửi webhook, hoặc push nhánh khác `develop` | Kiểm tra cấu hình job; xem *GitHub Hook Log* trong job |
| Job chạy 2 lần mỗi lần push | Bật cả Poll SCM và webhook | Chỉ giữ một |

💰 **Chi phí / an toàn:** Job này deploy thật lên ECS, nên cần stack Terraform lab6 đang chạy (tốn tiền theo giờ). Gom thời gian thực hành lab6–9 vào một buổi rồi destroy.

🟡 *Thực hành:* Thu hẹp SG port 8080: chỉ IP của bạn + các dải `hooks` của GitHub. Thêm webhook secret. Kiểm tra webhook vẫn hoạt động.

## Lab9 · Job release thủ công theo Git tag và dọn dẹp {019-020}

Code lab: `cicd-using-jenkins/lab9/lab9.groovy`, `lab9/lab9.sh`. Video 020 là xoá stack Terraform của lab6.

**Khái niệm cốt lõi**

Production cần **kiểm soát**: không tự deploy mỗi lần push, mà người release chọn đúng phiên bản đã gắn **tag** trên `master`.

- Job tick **This project is parameterized**: `VERSION` (String, ví dụ `v1.0.0`) và `ACTION` (Choice: `BuildAndDeploy`, `OnlyBuild`, `OnlyDeploy`).
- Checkout theo tag thay vì nhánh:

```groovy
checkout([$class: 'GitSCM',
    branches: [[name: 'refs/tags/${VERSION}']],
    userRemoteConfigs: [[url: 'git@github.com:<bạn>/nodejs-random-color.git',
                         credentialsId: '<id-ssh-key-của-bạn>']]])
```

- Stage chạy có điều kiện bằng `when`:

```groovy
stage('Build') {
    when { expression { env.ACTION == 'BuildAndDeploy' || env.ACTION == 'OnlyBuild' } }
    steps { sh 'docker build -t nodejs-random-color:${VERSION} .' }
}
```

  Stage bị bỏ qua hiện màu xám "skipped due to when conditional".

```bash
# Người release tạo tag
git checkout master && git pull
git tag -a v1.0.0 -m "Release v1.0.0"
git push origin v1.0.0
```

**Đi sâu hơn**

- **Annotated tag** (`-a`) lưu người tạo, ngày, thông điệp. Release nên dùng annotated tag. Theo quy ước **Semantic Versioning**: `MAJOR.MINOR.PATCH`.
- **OnlyDeploy** chính là **rollback**: chạy lại với `VERSION=v1.0.0` cũ là đưa image cũ (đã có trên ECR) lên lại, không cần build.
- Viết gọn hơn bằng `when { anyOf { environment name: 'ACTION', value: 'BuildAndDeploy'; environment name: 'ACTION', value: 'OnlyBuild' } }`.
- Khai báo tham số trong Jenkinsfile bằng khối `parameters { ... }` thay vì click form. Lưu ý: lần chạy đầu tiên Jenkins mới "học" được tham số.
- **Cổng duyệt:** thêm `input message: 'Deploy lên production?', submitter: 'release-managers'` trước stage Deploy để bắt buộc người có quyền bấm xác nhận.
- Một số tổ chức dùng Multibranch với `when { buildingTag() }` để tự chạy khi có tag mới. Lab9 cố ý làm thủ công để có người chịu trách nhiệm.

**Lỗi hay gặp**

- `Couldn't find any revision to build`: tag chưa được push (`git push origin v1.0.0`), hoặc gõ sai tên tag.
- `OnlyDeploy` bị lỗi `CannotPullContainerError`: image tag đó chưa từng được build và push.
- Tham số `ACTION` không có giá trị trong `when`: dùng `params.ACTION` hoặc `env.ACTION`, đừng viết `ACTION` trần trong Groovy.

## Lab10 · Scripted Pipeline {021}

Code lab: `cicd-using-jenkins/lab10/lab10.groovy`.

**Khái niệm cốt lõi**

Cùng pipeline lab5, viết bằng cú pháp **Scripted**:

```groovy
node {                                   // xin 1 executor trên 1 node bất kỳ (≈ agent any)
    stage('Checkout') {
        git 'https://github.com/<bạn>/nodejs-random-color.git'
    }
    stage('Build') {
        sh 'docker build -t nodejs-random-color:ver-${BUILD_ID} .'
    }
    stage('Upload image to ECR') {
        sh 'aws ecr get-login-password --region ap-southeast-1 | docker login --username AWS --password-stdin $REGISTRY'
        // ...tag và push như lab5
    }
}
```

- Không có `pipeline {}`, `stages {}`, `steps {}`. Trong `node {}` là **code Groovy thật**: biến, `if`, vòng lặp, hàm, `try/catch`.
- Không có `post {}`. Muốn làm việc "luôn chạy cuối cùng" thì tự viết `try/catch/finally`:

```groovy
node {
    try {
        stage('Build') { sh 'make build' }
        currentBuild.result = 'SUCCESS'
    } catch (err) {
        currentBuild.result = 'FAILURE'
        throw err
    } finally {
        echo "Kết thúc với: ${currentBuild.result}"   // tương đương post { always }
    }
}
```

**Đi sâu hơn**

- **Declarative cũng chạy trên engine của Scripted.** Muốn dùng Groovy trong Declarative thì bọc trong `script { ... }`. Khuyến nghị: viết Declarative, chỉ dùng `script {}` cho đoạn nhỏ cần logic; logic lớn đưa vào Shared Library.
- Scripted mạnh khi cần **tạo stage động**, ví dụ build song song cho danh sách service:

```groovy
def services = ['api', 'web', 'worker']
def jobs = [:]
services.each { s -> jobs[s] = { node { sh "docker build -t ${s} ./${s}" } } }
parallel jobs
```

- Code Groovy trong pipeline chạy trong **sandbox** (Script Security). Gọi API Java lạ sẽ bị chặn với lỗi `Scripts not permitted to use method ...` và cần admin duyệt (In-process Script Approval). Đừng duyệt bừa: duyệt là cho phép code đó chạy với quyền của controller.
- Pipeline phải **tuần tự hoá được (CPS)** để sống sót khi Jenkins restart. Một số đối tượng Groovy không serializable gây lỗi `NotSerializableException`. Đánh dấu hàm thuần bằng `@NonCPS` khi cần.

**Lỗi hay gặp**

- `groovy.lang.MissingPropertyException: No such property: VERSION`: trong Groovy phải viết `params.VERSION` hoặc `env.VERSION`. Bên trong chuỗi `sh '...'` nháy đơn thì shell mới hiểu `$VERSION`.
- `java.io.NotSerializableException`: giữ đối tượng như `Matcher` qua một step. Tách xử lý vào hàm `@NonCPS`.

**Bài tập**

🟢 *Cơ bản:* Chạy lab10, so sánh giao diện và log với lab5. Ghi ra 3 điểm khác nhau của cú pháp.

🟡 *Thực hành:* Thêm `try/catch/finally` để in kết quả cuối cùng, cố tình làm stage Build fail và kiểm tra `finally` vẫn chạy.

🔴 *Thử thách:* Viết lại lab9 (tham số + điều kiện) bằng Scripted, dùng `properties([parameters([...])])` và `if`. Sau đó tự nhận xét bản nào dễ đọc hơn cho người mới vào team.

<details><summary>Gợi ý</summary>

```groovy
properties([parameters([
    string(name: 'VERSION', defaultValue: 'v0.0.1'),
    choice(name: 'ACTION', choices: ['BuildAndDeploy', 'OnlyBuild', 'OnlyDeploy'])
])])
node {
    if (params.ACTION in ['BuildAndDeploy', 'OnlyBuild']) {
        stage('Build') { sh 'docker build -t app:$VERSION .' }
    }
}
```

Stage nằm trong `if` sẽ không hiện ra khi bị bỏ qua, khác với `when` của Declarative hiện "skipped".
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Khi nào chọn Scripted thay vì Declarative?</summary>

Khi cần logic mà Declarative không diễn đạt gọn: số stage thay đổi theo dữ liệu, vòng lặp phức tạp, xử lý lỗi chi tiết. Còn lại nên dùng Declarative vì có cấu trúc chuẩn, kiểm tra cú pháp sớm, dễ đọc.
</details>

## Lab11 · Thông báo kết quả sang Slack và tổng kết chương {022-023}

Code lab: `cicd-using-jenkins/lab11/lab11.groovy`, `lab11/lab11.sh`.

**Khái niệm cốt lõi**

Build xong mà không ai biết thì vô ích. Lab11 gửi kết quả mỗi build vào một kênh Slack.

1. Cài plugin **Slack Notification**.
2. Lấy token từ Slack, lưu vào Jenkins dạng credential **Secret text** (ví dụ ID `slacktoken`). **Không** dán token vào Jenkinsfile.
3. Manage Jenkins → System → Slack: workspace, credential, kênh mặc định → **Test Connection**.
4. Gọi `slackSend` trong `post`:

```groovy
def COLOR_MAP = [
    'SUCCESS' : 'good',      // xanh
    'FAILURE' : 'danger',    // đỏ
    'UNSTABLE': 'warning',   // vàng (lab gốc thiếu dòng này)
    'ABORTED' : '#808080',
]
pipeline {
    agent any
    stages { /* ...giống lab5... */ }
    post {
        always {
            slackSend channel: '#udemy-devops-demo',
                color: COLOR_MAP[currentBuild.currentResult],
                message: "*${currentBuild.currentResult}:* Job ${env.JOB_NAME} build ${env.BUILD_NUMBER}\nXem thêm: ${env.BUILD_URL}"
        }
    }
}
```

**Đi sâu hơn**

- Lab dùng app **"Jenkins CI"** trong Slack App Directory. Tài liệu plugin hiện hướng dẫn **tạo Slack app riêng** (từ manifest), lấy **Bot User OAuth Token**, tick *Custom slack app bot user* và mời bot vào kênh. Bot cần ít nhất scope `chat:write`.
- Thông báo `always` dễ thành "spam" khiến mọi người tắt kênh. Thực tế hay dùng `failure` và `fixed` (báo khi hỏng và khi vừa sửa xong).
- Cấu hình Slack ở trang System có thể quản lý bằng code với **JCasC**.

**Tổng kết chương: quản lý Jenkins như code (JCasC)**

Sau 11 lab, server Jenkins của bạn có cả chục mục cấu hình click tay (Tools, Credentials, Slack, Security). Mất server là phải làm lại từ đầu. **Jenkins Configuration as Code (JCasC)** mô tả toàn bộ cấu hình trong một file YAML:

```yaml
# jenkins.yaml — plugin "Configuration as Code"; trỏ biến môi trường CASC_JENKINS_CONFIG tới file này
jenkins:
  systemMessage: "Jenkins lab DevOps AWS"
  numExecutors: 0                      # không build trên controller
unclassified:
  slackNotifier:
    teamDomain: "myworkspace"
    tokenCredentialId: "slacktoken"
    botUser: true
tool:
  maven:
    installations:
      - name: "M3"
        properties:
          - installSource:
              installers:
                - maven:
                    id: "3.9.6"
```

Kết hợp **JCasC + Jenkinsfile trong repo + Shared Library + agent Docker** là bạn dựng lại được toàn bộ Jenkins trong vài phút. Xuất cấu hình hiện tại ở Manage Jenkins → Configuration as Code → *View Configuration* để học cú pháp.

**Checklist bảo mật Jenkins** để mang theo sau khoá học:
- Không mở 8080 ra `0.0.0.0/0`; đặt sau HTTPS.
- Cập nhật Jenkins LTS và plugin định kỳ; gỡ plugin không dùng.
- Built-in node 0 executor; build trên agent.
- Secret trong Credentials store (hoặc Secrets Manager/Vault), không hard-code; dùng IAM Role thay access key.
- Phân quyền theo user/nhóm (Matrix Authorization), tắt đăng ký tự do.
- Sao lưu `JENKINS_HOME` hoặc quản lý cấu hình bằng JCasC.

**Lỗi hay gặp & cách sửa**

- Test Connection báo `Failure`: sai token, sai workspace, hoặc bot chưa được mời vào kênh (`not_in_channel`).
- Tin nhắn không có màu khi build UNSTABLE/ABORTED: `COLOR_MAP` thiếu khoá đó nên trả về `null`.
- `No such DSL method 'slackSend'`: chưa cài plugin Slack Notification hoặc chưa restart sau khi cài.

**Bài tập**

🟢 *Cơ bản:* Gửi thông báo Slack cho job lab5. Làm build fail một lần để thấy tin nhắn màu đỏ.

🟡 *Thực hành:* Chỉ thông báo khi `failure` và `fixed`. Thêm tên người/commit gây ra build vào tin nhắn (gợi ý: `git log -1 --pretty=%an` qua `sh(returnStdout: true)`).

🔴 *Thử thách:* Viết `jenkins.yaml` cho Jenkins chạy Docker trên máy Fedora (bài tập phần cài đặt): tạo sẵn user admin lấy mật khẩu từ biến môi trường, cài sẵn Maven `M3`, đặt 0 executor cho built-in node. Xoá container, chạy lại, cấu hình vẫn y nguyên.

<details><summary>Gợi ý</summary>

```yaml
jenkins:
  numExecutors: 0
  securityRealm:
    local:
      allowsSignup: false
      users:
        - id: "admin"
          password: "${ADMIN_PASSWORD}"   # JCasC tự thay biến môi trường
```

Chạy container với `-e CASC_JENKINS_CONFIG=/var/jenkins_home/casc/jenkins.yaml -e ADMIN_PASSWORD=...` và mount file YAML vào. Plugin `configuration-as-code` phải được cài sẵn (dùng `jenkins-plugin-cli` trong Dockerfile tự build). Không commit mật khẩu thật vào Git.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao token Slack phải là credential Secret text, không viết vào Jenkinsfile?</summary>

Jenkinsfile nằm trong Git, ai đọc được repo là có token để gửi tin nhắn giả danh vào workspace. Credential được mã hoá trong Jenkins và bị che trong log.
</details>

<details><summary>2. JCasC giải quyết vấn đề gì mà Jenkinsfile không giải quyết?</summary>

Jenkinsfile mô tả *từng pipeline*. JCasC mô tả *chính server Jenkins*: bảo mật, tool, plugin config, credentials, agent. Có cả hai thì cả pipeline lẫn server đều tái tạo được từ Git.
</details>
