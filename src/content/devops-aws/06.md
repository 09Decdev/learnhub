## Linux là gì và kết nối tới server đầu tiên {002-004}

**Hệ điều hành (OS)** là lớp phần mềm đứng giữa phần cứng và ứng dụng: quản lý CPU, RAM, ổ đĩa, mạng và cho chương trình dùng chung các tài nguyên đó. **Linux** thực chất là tên của *kernel* (nhân). Kernel + bộ công cụ (bash, coreutils, trình quản lý gói…) đóng gói lại thành một **distro** (bản phân phối).

```
┌───────────── Ứng dụng (nginx, java, python…) ─────────────┐
│  Shell (bash) · tiện ích (ls, cp, grep) · systemd         │  ← user space
├───────────────────────────────────────────────────────────┤
│  Kernel Linux: process, bộ nhớ, file system, mạng, driver │  ← kernel space
├───────────────────────────────────────────────────────────┤
│  Phần cứng (trên EC2 là máy ảo do AWS Nitro cung cấp)     │
└───────────────────────────────────────────────────────────┘
```

**Vì sao DevOps phải biết Linux:** phần lớn server trên cloud, gần như mọi container và mọi node Kubernetes đều chạy Linux. Khi có sự cố lúc 2 giờ sáng, bạn sẽ SSH vào máy và đọc log bằng dòng lệnh, không có giao diện đồ hoạ.

**Đi sâu hơn: các họ distro bạn sẽ gặp**

| Họ | Distro tiêu biểu | Trình quản lý gói | User mặc định trên EC2 |
|---|---|---|---|
| Red Hat | **Amazon Linux 2023**, Fedora, RHEL, Rocky | `dnf` (`yum` chỉ là tên gọi tắt trỏ sang `dnf`) | `ec2-user` |
| Debian | **Ubuntu**, Debian | `apt` | `ubuntu` (Debian: `admin`) |
| Khác | Alpine (rất nhỏ, hay dùng làm image Docker) | `apk` | – |

- Bài lab trong khoá dùng `yum` vì quay trên Amazon Linux 2. Trên **Amazon Linux 2023 (AL2023)** hãy dùng `dnf`. Máy Fedora của bạn cũng là họ Red Hat, nên lệnh gần như giống hệt AL2023.
- Xem đang chạy distro nào: `cat /etc/os-release` (AL2023 không còn lệnh `lsb_release`).

**Cây thư mục chuẩn (FHS – Filesystem Hierarchy Standard)**

Linux không có ổ `C:`, `D:`. Mọi thứ bắt đầu từ thư mục gốc `/`:

| Thư mục | Chứa gì | Ví dụ |
|---|---|---|
| `/etc` | File **cấu hình** của hệ thống | `/etc/ssh/sshd_config`, `/etc/fstab` |
| `/home/<user>` | Thư mục riêng của từng user | `/home/ec2-user` |
| `/root` | Thư mục riêng của user `root` | |
| `/var` | Dữ liệu **thay đổi liên tục**: log, web, cache | `/var/log`, `/var/www/html` |
| `/usr/bin`, `/usr/sbin` | Chương trình đã cài | `/usr/bin/git` |
| `/tmp` | File tạm, có thể bị xoá khi reboot | |
| `/dev` | Thiết bị phần cứng dưới dạng file | `/dev/nvme1n1` (ổ EBS) |
| `/proc`, `/sys` | File "ảo" do kernel sinh ra để xem trạng thái | `/proc/cpuinfo` |
| `/opt` | Phần mềm bên thứ ba cài thủ công | |

Triết lý quan trọng: **"mọi thứ đều là file"**. Ổ đĩa, thông tin CPU, thậm chí process đều đọc được như file.

**Lab1 · Tạo EC2 và SSH vào**

1. Console EC2 → *Launch instance* → AMI **Amazon Linux 2023**, loại `t3.micro` (hoặc `t2.micro` tuỳ region có Free Tier).
2. Tạo hoặc chọn **key pair**, tải file `.pem` về.
3. Security Group (tường lửa của EC2): mở port 22 **chỉ cho IP của bạn** (chọn *My IP*).

```bash
chmod 400 ~/Downloads/udemy-key.pem            # bắt buộc, nếu không ssh sẽ từ chối key
ssh -i ~/Downloads/udemy-key.pem ec2-user@<public-ip-hoặc-public-dns>
whoami; hostname; cat /etc/os-release           # đang là ai, ở máy nào, distro gì
```

- Thay vì nhớ lệnh dài, khai báo trong `~/.ssh/config` rồi chỉ cần gõ `ssh lab`:

```bash
# ~/.ssh/config
Host lab
    HostName 13.250.x.x
    User ec2-user
    IdentityFile ~/.ssh/udemy-key.pem
```

- Không muốn mở port 22? Dùng **EC2 Instance Connect** hoặc **SSM Session Manager** (đăng nhập từ console, không cần key, không cần mở port).

**Lỗi hay gặp & cách sửa**

- `WARNING: UNPROTECTED PRIVATE KEY FILE! … Permissions 0644 … are too open` → chạy `chmod 400 key.pem`.
- `Permission denied (publickey)` → sai user (Ubuntu dùng `ubuntu`, không phải `ec2-user`), hoặc sai file key.
- `Connection timed out` → Security Group chưa mở port 22 cho IP hiện tại của bạn (IP nhà mạng có thể đổi), hoặc EC2 nằm ở subnet không có route ra Internet Gateway.
- `REMOTE HOST IDENTIFICATION HAS CHANGED` → bạn tạo máy mới trùng IP cũ. Xoá dòng cũ: `ssh-keygen -R <ip>`.

💰 **Chi phí:** `t3.micro` khoảng 0,01–0,013 USD/giờ tuỳ region, và AWS tính thêm phí cho mọi IPv4 public (khoảng 0,005 USD/giờ). Tài khoản có Free Tier thường được miễn phí phần lớn. Học xong buổi nào thì **Stop** máy, học xong chương thì **Terminate**.

**Bài tập**

🟢 *Cơ bản*: Tạo EC2 AL2023, SSH vào, ghi lại kết quả `cat /etc/os-release`, `uname -r` (phiên bản kernel), `df -h` và `free -h`.

🟡 *Thực hành*: Tạo file `~/.ssh/config` để SSH bằng `ssh lab`. Sau đó stop/start EC2 một lần: public IP có đổi không? Sửa lại config cho đúng.

<details><summary>Gợi ý</summary>

</details>

🔴 *Thử thách*: Gỡ rule port 22 khỏi Security Group, rồi vẫn vào được máy bằng **SSM Session Manager**. Bạn cần gắn IAM role nào cho EC2?

<details><summary>Gợi ý</summary>

</details>

**Câu hỏi tự kiểm tra**

## Lab2 · Làm quen với VIM và NANO {005-006}

Trên server không có VS Code. Bạn sẽ sửa file cấu hình bằng trình soạn thảo trong terminal. Hai trình phổ biến:

- **nano**: dễ dùng, phím tắt hiện sẵn ở cuối màn hình. `^O` nghĩa là `Ctrl+O`.
- **vim** (hoặc `vi`): mạnh, có mặt ở *mọi* server, nhưng phải hiểu khái niệm **mode** (chế độ).

**Các mode của vim**

```
            i / a / o                     :
 NORMAL ───────────────▶ INSERT    NORMAL ─────▶ COMMAND (:w, :q, :wq, /tìm)
   ▲                         │        ▲                │
   └──────── Esc ────────────┘        └──── Enter ─────┘
```

- Mở file xong, vim đang ở **NORMAL mode**: gõ phím là *ra lệnh*, không phải gõ chữ. Đây là lý do người mới hay "kẹt" trong vim.
- Nhấn `i` để vào **INSERT mode** mới gõ chữ được. Nhấn `Esc` để quay về NORMAL.

**Bảng lệnh vim tối thiểu cần thuộc**

| Mục đích | Phím |
|---|---|
| Lưu và thoát | `Esc` rồi `:wq` Enter (hoặc `:x`) |
| Thoát không lưu | `Esc` rồi `:q!` Enter |
| Bắt đầu gõ chữ | `i` (trước con trỏ), `a` (sau con trỏ), `o` (dòng mới bên dưới) |
| Xoá một dòng / copy / dán | `dd` / `yy` / `p` |
| Hoàn tác / làm lại | `u` / `Ctrl+r` |
| Về đầu file / cuối file | `gg` / `G` |
| Tìm chữ | `/PasswordAuthentication` Enter, `n` để tới kết quả tiếp |
| Hiện số dòng | `:set number` |
| Thay thế cả file | `:%s/cũ/mới/g` |

**Bảng lệnh nano**

| Mục đích | Phím |
|---|---|
| Lưu | `Ctrl+O` rồi Enter |
| Thoát | `Ctrl+X` |
| Tìm | `Ctrl+W` |
| Cắt / dán dòng | `Ctrl+K` / `Ctrl+U` |

**Đi sâu hơn**

- Sửa file hệ thống thì phải có `sudo`: `sudo vim /etc/ssh/sshd_config`. Nếu quên `sudo`, khi `:wq` bạn nhận lỗi `E45: 'readonly' option is set` hoặc `E212: Can't open file for writing`. Mẹo cứu: `:w !sudo tee %` rồi `:q!`.
- **Đặt trình soạn thảo mặc định** cho các lệnh như `crontab -e`, `visudo`, `git commit`: thêm `export EDITOR=nano` (hoặc `vim`) vào `~/.bashrc`.
- **Luôn sao lưu trước khi sửa file cấu hình quan trọng**: `sudo cp /etc/fstab /etc/fstab.bak`.
- Xem file mà không sửa: `cat` (file ngắn), `less` (file dài, `q` để thoát, `/` để tìm), `tail -f` (theo dõi log đang ghi).
- AL2023 bản tối giản có thể chỉ có `vi`. Cài thêm: `sudo dnf install -y vim nano`.

```bash
vimtutor            # bài học vim tương tác ~30 phút, có sẵn khi cài vim
```

**Lỗi hay gặp & cách sửa**

- Gõ chữ mà vim nhảy lung tung, xoá mất dòng → bạn đang ở NORMAL mode. Nhấn `Esc`, gõ `u` vài lần để hoàn tác, rồi nhấn `i` trước khi gõ.
- `E37: No write since last change (add ! to override)` → bạn gõ `:q` khi file đã sửa. Dùng `:wq` để lưu hoặc `:q!` để bỏ.
- `Found a swap file by the name ".sshd_config.swp"` → lần trước vim bị đóng đột ngột. Chọn `(R)ecover` nếu muốn khôi phục, hoặc `(D)elete it` nếu chắc chắn không cần.

**Bài tập**

🟢 *Cơ bản*: Dùng vim tạo file `~/notes.txt` gồm 5 dòng. Xoá dòng 3 bằng `dd`, hoàn tác bằng `u`, lưu và thoát. Làm lại bằng nano.

🟡 *Thực hành*: Trong vim, mở `/etc/ssh/sshd_config` **chỉ để đọc** (`view /etc/ssh/sshd_config`). Tìm các dòng `PasswordAuthentication`, `PermitRootLogin` và `Include`. Ghi lại giá trị đang có.

<details><summary>Gợi ý</summary>

Gõ `/Include` Enter. Bạn sẽ thấy dòng `Include /etc/ssh/sshd_config.d/*.conf` ở gần đầu file. Điều này có nghĩa là cấu hình thật còn nằm trong thư mục `sshd_config.d/`. Bạn sẽ cần thông tin này ở Lab3.
</details>

🔴 *Thử thách*: Chỉ dùng một lệnh vim `:%s`, đổi tất cả `http://` thành `https://` trong một file. Sau đó làm lại bằng `sed -i` không cần mở vim.

<details><summary>Lời giải</summary>

Trong vim: `:%s#http://#https://#g` (dùng `#` làm dấu phân cách để khỏi phải escape `/`). Bằng sed: `sed -i 's#http://#https://#g' file.txt`. Nên chạy thử `sed` *không* có `-i` trước để xem kết quả.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>Bạn đang trong vim, đã sửa file sai bét và muốn thoát mà không lưu gì. Gõ gì?</summary>

`Esc` rồi `:q!` Enter.
</details>

## Lab3 · User, Group và sudo {007-008}

**Khái niệm cốt lõi**

- Mỗi người (hoặc mỗi chương trình) dùng máy là một **user**, có **UID** (số định danh). `root` có UID 0 và có toàn quyền.
- **Group** gom nhiều user lại để phân quyền một lần cho cả nhóm. Mỗi user có một *primary group* và có thể thuộc nhiều *supplementary group*.
- **sudo** cho phép user thường chạy *từng lệnh* với quyền root, có ghi log ai làm gì. An toàn hơn nhiều so với đăng nhập thẳng bằng root.

Ví dụ đời thường: công ty có nhân viên (user), phòng ban (group), và giám đốc ký uỷ quyền cho một số người được mở kho (sudoers).

**User được lưu ở đâu**

| File | Nội dung |
|---|---|
| `/etc/passwd` | Danh sách user: tên, UID, GID, thư mục home, shell |
| `/etc/shadow` | Mật khẩu đã băm (chỉ root đọc được) |
| `/etc/group` | Danh sách group và thành viên |
| `/etc/sudoers`, `/etc/sudoers.d/` | Ai được dùng sudo, được chạy lệnh gì |

```bash
id developer1                 # uid=1001(developer1) gid=1001(developer1) groups=1001(developer1),1002(developer_group)
getent passwd developer1      # dòng tương ứng trong /etc/passwd
```

**Lệnh của lab (`lab3-user-and-group-operation.sh`)**

```bash
sudo useradd developer1                         # tạo user (AL2023 tự tạo /home/developer1)
sudo passwd developer1                          # đặt mật khẩu
sudo groupadd developer_group
sudo usermod -a -G developer_group developer1   # -a = append; THIẾU -a sẽ xoá user khỏi các group khác
sudo visudo                                     # sửa sudoers an toàn (kiểm tra cú pháp trước khi lưu)
#   %developer_group ALL=(ALL) ALL              # % = group; mọi máy; chạy như mọi user; mọi lệnh
sudo userdel -r developer1                      # -r xoá luôn thư mục home
sudo groupdel developer_group
```

Đọc dòng sudoers `%developer_group ALL=(ALL) ALL`:

```
%developer_group   ALL      =(ALL)            ALL
└─ ai (group)      └─ trên host nào  └─ chạy với tư cách user nào  └─ được chạy lệnh nào
```

**Đi sâu hơn**

- **Đừng sửa thẳng `/etc/sudoers`.** Tạo file riêng trong `/etc/sudoers.d/`, luôn qua `visudo`:

```bash
sudo visudo -f /etc/sudoers.d/developers
#   %developer_group ALL=(ALL) ALL
sudo visudo -c        # kiểm tra cú pháp toàn bộ
```

  File sudoers sai cú pháp có thể làm *không ai dùng được sudo nữa*. `visudo` chặn lưu khi sai, `vim /etc/sudoers` thì không.
- Trên họ Red Hat đã có sẵn group **`wheel`** được dùng sudo. Cách gọn nhất: `sudo usermod -aG wheel developer1`. Trên Ubuntu group tương ứng là `sudo`.
- `ec2-user` dùng sudo không cần mật khẩu nhờ file `/etc/sudoers.d/90-cloud-init-users` (dòng có `NOPASSWD:ALL`).
- **Least privilege với sudo**: có thể chỉ cho phép đúng một lệnh, ví dụ `%developer_group ALL=(root) /usr/bin/systemctl restart httpd`.
- `sudo su` / `sudo -i` mở shell root. Tiện nhưng nguy hiểm, mọi lệnh sau đều là root. Làm xong `exit` ngay.
- Thay đổi group chỉ có hiệu lực ở **phiên đăng nhập mới**. Đăng xuất, vào lại rồi chạy `id` để kiểm tra.
- Ubuntu: `useradd` mặc định *không* tạo home. Dùng `useradd -m -s /bin/bash` hoặc lệnh thân thiện hơn `adduser`.

**Bật đăng nhập bằng mật khẩu (phần đầu lab)**

Lab sửa `PasswordAuthentication yes` để `developer1` SSH bằng mật khẩu. Trên AL2023 và Ubuntu mới, sửa mỗi file chính có thể **không có tác dụng**. Lý do: `sshd_config` có dòng `Include /etc/ssh/sshd_config.d/*.conf` ở đầu, và với sshd, **giá trị đọc được đầu tiên sẽ thắng**. Nếu một file trong thư mục đó ghi `PasswordAuthentication no`, giá trị của bạn ở dưới bị bỏ qua.

```bash
sudo sshd -T | grep -i passwordauthentication    # giá trị sshd ĐANG thực sự dùng
grep -ri passwordauthentication /etc/ssh/sshd_config.d/
sudo sshd -t && sudo systemctl restart sshd      # -t kiểm tra cú pháp trước khi restart
```

> ⚠️ Cho phép SSH bằng mật khẩu trên máy có IP public là mời bot dò mật khẩu. Chỉ bật để học, làm xong **tắt lại ngay** (Lab9 sẽ dùng SSH key thay thế).

**Lỗi hay gặp & cách sửa**

- `developer1 is not in the sudoers file. This incident will be reported.` → user chưa thuộc group có quyền sudo, hoặc chưa đăng nhập lại sau khi thêm group.
- `>>> /etc/sudoers: syntax error near line 120 <<<` khi lưu trong visudo → gõ `e` để sửa lại, đừng chọn `Q` (lưu dù lỗi).
- Đặt `PasswordAuthentication yes` rồi vẫn `Permission denied (publickey)` → xem lại phần `sshd_config.d` ở trên.
- `userdel: user developer1 is currently used by process 1234` → user đang đăng nhập. Cho thoát phiên đó (`sudo pkill -u developer1`) rồi xoá.

**Bài tập**

🟢 *Cơ bản*: Tạo user `developer1`, `developer2`, group `developer_group`, thêm cả hai vào group. Chứng minh bằng `id` và `getent group developer_group`.

## Lab4 · Phân quyền file và thư mục {009-010}

**Khái niệm cốt lõi**

Mỗi file có **một owner (user)**, **một group** và **3 bộ quyền** cho 3 đối tượng:

```
-rwxr-x---  1 ec2-user ec2-user  42 Jan 10 10:00 test_file.txt
│└┬┘└┬┘└┬┘    └──┬───┘ └──┬───┘
│ │  │  │     owner     group
│ │  │  └── others (mọi người còn lại): ---  không có quyền
│ │  └───── group:                     r-x  đọc + thực thi
│ └──────── owner (user):              rwx  đọc + ghi + thực thi
└────────── loại: - file thường, d thư mục, l symlink
```

**r, w, x có nghĩa khác nhau với file và thư mục**

| Quyền | Với file | Với thư mục |
|---|---|---|
| `r` (4) | Đọc nội dung | Liệt kê tên file bên trong (`ls`) |
| `w` (2) | Sửa nội dung | Tạo, xoá, đổi tên file bên trong |
| `x` (1) | Chạy như chương trình | **Đi vào** thư mục (`cd`) và truy cập file bên trong |

Đây là chìa khoá để hiểu Lab4: `developer1` không đọc được `/home/ec2-user/test_folder/test_file.txt` vì **thư mục `/home/ec2-user` có quyền 700**, others không có `x` nên không "đi xuyên qua" được, dù file bên trong có quyền gì đi nữa. Muốn vào một file, bạn cần quyền `x` trên **mọi thư mục** trên đường dẫn.

**chmod dạng số và dạng ký hiệu**

Cộng điểm: r=4, w=2, x=1. Mỗi chữ số ứng với owner, group, others.

| Số | Ký hiệu | Hay dùng cho |
|---|---|---|
| `755` | `rwxr-xr-x` | Thư mục, script mọi người chạy được |
| `644` | `rw-r--r--` | File thường, file cấu hình |
| `750` | `rwxr-x---` | Chỉ owner và group |
| `700` | `rwx------` | Thư mục riêng tư (`~/.ssh`) |
| `600` | `rw-------` | File bí mật (`authorized_keys`, private key) |
| `400` | `r--------` | File `.pem` chỉ đọc |

```bash
chmod 750 test_file.txt        # dạng số (lab)
chmod u+x deploy.sh            # dạng ký hiệu: thêm x cho owner
chmod g-w,o-rwx secret.txt     # bỏ w của group, bỏ hết quyền của others
chmod -R g+rX shared/          # X hoa: chỉ thêm x cho thư mục (và file vốn đã có x)
sudo chown developer1:developer_group test_file.txt   # đổi owner và group
stat -c '%A %a %U:%G %n' test_file.txt                # xem quyền dạng chữ và số
namei -l /home/ec2-user/test_folder/test_file.txt     # xem quyền của TỪNG thư mục trên đường dẫn
```

**Đi sâu hơn**

- **umask**: quyết định quyền mặc định của file mới. Thường là `0022`: file mới là `644`, thư mục mới là `755`. Một số distro dùng `0002` cho user thường (group được ghi). Xem bằng lệnh `umask`.
- **Quyền đặc biệt**:
  - **setuid** (`4xxx`, chữ `s` ở vị trí x của owner): chương trình chạy với quyền của *owner file*. Ví dụ `/usr/bin/passwd` là `-rwsr-xr-x`, nhờ vậy user thường đổi được mật khẩu trong `/etc/shadow`.
  - **setgid trên thư mục** (`2xxx`): file tạo bên trong tự thuộc group của thư mục. Rất hợp cho thư mục dùng chung của team.
  - **sticky bit** (`1xxx`, chữ `t`): trong thư mục ai cũng ghi được, chỉ owner mới xoá được file của mình. Ví dụ `/tmp` là `drwxrwxrwt`.
- **ACL** (`setfacl`/`getfacl`): khi cần cấp quyền cho *một user cụ thể* mà không muốn đổi group.
- Cũng có **SELinux** trên họ Red Hat (Fedora bật mặc định). Đôi khi quyền `rwx` đúng mà vẫn bị chặn: xem `ls -Z` và `sudo ausearch -m avc`. Đây là chủ đề nâng cao, chỉ cần biết là có.

**Nhận xét về lab**

Lab dùng `sudo chmod -R 755 /home/ec2-user`. Cách này *chạy được* nhưng không nên làm trên máy thật:
- `-R` gắn quyền `x` cho **mọi file**, kể cả file văn bản.
- Toàn bộ home của `ec2-user` (bao gồm `.bash_history`, file cấu hình) thành ai cũng đọc được.

Cách tốt hơn, chỉ mở đúng thứ cần:

```bash

chmod 711 /home/ec2-user                 # others chỉ được "đi qua", không liệt kê được
chmod 2750 /home/ec2-user/test_folder    # setgid, group đọc và vào được
chmod 640 /home/ec2-user/test_folder/test_file.txt
```

(Trong file lab còn lỗi đánh máy `cat tét_file.txt`, đúng phải là `test_file.txt`.)

**Lỗi hay gặp & cách sửa**

- `cat: /home/ec2-user/test_folder/test_file.txt: Permission denied` dù file là `644` → một thư mục cha thiếu quyền `x`. Dùng `namei -l <đường dẫn>` để thấy chỗ bị chặn.
- `./deploy.sh: Permission denied` → file chưa có `x`. Chạy `chmod u+x deploy.sh`, hoặc chạy `bash deploy.sh`.
- `chown: changing ownership of 'x': Operation not permitted` → chỉ root đổi được owner. Thêm `sudo`.
- Lỡ `chmod -R 777` cả thư mục `~/.ssh` → SSH bằng key bị từ chối (sshd bỏ qua key khi quyền quá rộng). Sửa: `chmod 700 ~/.ssh && chmod 600 ~/.ssh/authorized_keys`.

## Lab5 · Process {011}

**Khái niệm cốt lõi**

- **Program** là file nằm trên đĩa (ví dụ `/usr/sbin/httpd`). **Process** là chương trình *đang chạy*, có **PID** (số định danh), có owner, chiếm CPU và RAM.
- Mỗi process có một process cha (**PPID**). Process số 1 là `systemd`, cha của tất cả.
- Process giao tiếp với nhau bằng **signal** (tín hiệu). `kill` thực chất là lệnh *gửi signal*, không chỉ để "giết".

```
systemd (PID 1)
├── sshd ── sshd ── bash ── ps aux       ← lệnh bạn vừa gõ
├── httpd ── httpd (worker) × N
└── crond
```

**Lệnh của lab (`lab5-process.sh`) và hơn thế**

```bash
ps aux                        # mọi process, kiểu BSD: USER PID %CPU %MEM ... COMMAND
ps -ef                        # mọi process, kiểu chuẩn: UID PID PPID ... CMD
ps aux --sort=-%mem | head    # 10 process ăn RAM nhất
ps -ef --forest               # xem dạng cây cha-con
pgrep -a httpd                # tìm PID theo tên
top                           # theo dõi realtime (P: sort CPU, M: sort RAM, k: kill, q: thoát)
htop                          # bản đẹp hơn của top (Fedora: sudo dnf install htop)
kill <PID>                    # gửi SIGTERM (15): "làm ơn dừng lại"
kill -9 <PID>                 # gửi SIGKILL (9): kernel buộc dừng ngay
pkill -u developer1           # gửi SIGTERM cho mọi process của developer1
```

**Các signal cần biết**

| Signal | Số | Ý nghĩa | Bắt / bỏ qua được không |
|---|---|---|---|
| `SIGHUP` | 1 | Mất terminal; nhiều daemon hiểu là "đọc lại cấu hình" | Được |
| `SIGINT` | 2 | `Ctrl+C` | Được |
| `SIGKILL` | 9 | Dừng ngay lập tức | **Không** |
| `SIGTERM` | 15 | Yêu cầu dừng một cách lịch sự (mặc định của `kill`) | Được |
| `SIGSTOP` / `SIGCONT` | 19 / 18 | Tạm dừng / chạy tiếp (`Ctrl+Z`, `fg`) | Không / Được |

**Đi sâu hơn**

- **Luôn thử `kill` (SIGTERM) trước `kill -9`.** SIGTERM cho chương trình cơ hội ghi nốt dữ liệu, đóng kết nối database, xoá file tạm. `kill -9` cắt ngang, dễ để lại file khoá hoặc dữ liệu hỏng. Docker và Kubernetes cũng làm vậy: gửi SIGTERM, chờ một khoảng (mặc định 10 giây với `docker stop`, 30 giây với Kubernetes), rồi mới SIGKILL.
- **Load average** trong `top`/`uptime` (3 số: 1, 5, 15 phút): số process đang chạy hoặc chờ CPU. So với số CPU (`nproc`): load 2.0 trên máy 2 vCPU là đã "đầy".
- **Trạng thái process** (cột `STAT`): `R` đang chạy, `S` đang ngủ chờ việc, `D` chờ I/O không ngắt được, `Z` zombie (đã chết nhưng cha chưa "nhận xác"), `T` bị dừng.
- **Chạy ngầm**: `lệnh &` chạy nền, `jobs` xem danh sách, `fg` đưa lên lại. Đóng SSH là process chết theo (vì SIGHUP). Muốn chạy lâu dài thì **biến nó thành service** (Lab6), đừng dùng `nohup`.
- Ai đang chiếm port 80? `sudo ss -tlnp | grep :80`. Ai đang mở file? `sudo lsof /var/log/messages`.
- Process trong `/proc`: `cat /proc/<PID>/status` cho thấy RAM, UID, số thread…
- **Máy t3.micro chỉ có 1 GiB RAM.** Khi hết RAM, kernel kích hoạt **OOM killer** và giết process ăn nhiều RAM nhất. Xem dấu vết: `sudo journalctl -k | grep -i oom`.

**Lỗi hay gặp & cách sửa**

- `kill: (1234) - Operation not permitted` → process thuộc user khác. Dùng `sudo kill 1234`.
- `kill -9` mà process vẫn còn → nó đang ở trạng thái `D` (chờ I/O, thường do ổ đĩa mạng treo) hoặc `Z` (zombie, phải xử lý process cha).
- Kill process xong vài giây nó lại xuất hiện → nó được systemd quản lý với `Restart=always`. Dùng `sudo systemctl stop <service>`.

**Bài tập**


</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Khác nhau giữa <code>kill</code> và <code>kill -9</code>?</summary>

</details>

## Lab6 · Service với systemd {012}

**Khái niệm cốt lõi**

**Service** (hay *daemon*) là process chạy nền lâu dài: web server, database, SSH server. Trên hầu hết Linux hiện đại, **systemd** (PID 1) quản lý service: khởi động lúc boot, tự chạy lại khi chết, gom log, sắp xếp thứ tự phụ thuộc.

Mỗi service được mô tả bằng một **unit file** (`.service`). Lệnh `service httpd restart` trong video là cách cũ, trên máy hiện đại nó chỉ chuyển tiếp sang `systemctl`.

| Mục đích | Lệnh |
|---|---|
| Xem trạng thái, PID, vài dòng log cuối | `systemctl status httpd` |
| Bật / tắt / khởi động lại ngay | `sudo systemctl start` / `stop` / `restart httpd` |
| Đọc lại cấu hình, không ngắt kết nối | `sudo systemctl reload httpd` |
| Tự chạy khi boot | `sudo systemctl enable httpd` |
| Vừa enable vừa start | `sudo systemctl enable --now httpd` |
| Liệt kê service đang chạy / bị lỗi | `systemctl list-units --type=service` / `systemctl --failed` |
| Đọc log của service | `journalctl -u httpd -f` (`-f` = theo dõi liên tục) |

> `start` = chạy **bây giờ**. `enable` = chạy **lần boot sau**. Hai việc này độc lập: chỉ `enable` thì máy chưa chạy service; chỉ `start` thì reboot xong service không tự lên.

**Code lab (`lab6-service.sh`), viết lại cho AL2023**

```bash
sudo dnf install -y httpd git              # AL2023 dùng dnf
cd /var/www/html
sudo git clone https://github.com/cloudacademy/webgl-globe/ .
sudo cp -a src/* .
sudo rm -rf .git *.md src conf.d docs Dockerfile index.nginx-debian.html
sudo systemctl enable --now httpd
systemctl status httpd
curl -I http://localhost                   # kiểm tra từ chính máy đó: mong đợi HTTP/1.1 200 OK
```

Rồi mở `http://<public-ip>` trên trình duyệt. Nhớ mở **port 80** trong Security Group.

**Đi sâu hơn: tự viết một unit file**

Giả sử bạn có một app Python và muốn nó chạy như service thật sự:

```ini

[Service]

ExecStart=/usr/bin/python3 -m http.server 8080
Restart=on-failure          # chết bất thường thì tự chạy lại

Environment=APP_ENV=dev

[Install]
WantedBy=multi-user.target  # "enable" = gắn vào giai đoạn boot bình thường
```

```bash
mkdir -p ~/hello && echo "Xin chào từ systemd" > ~/hello/index.html
sudo systemctl daemon-reload          # BẮT BUỘC sau khi tạo/sửa unit file
sudo systemctl enable --now hello
journalctl -u hello -n 20             # 20 dòng log cuối
curl localhost:8080
```

- **`/etc/systemd/system/`** là nơi bạn đặt unit của mình. Unit do gói cài nằm ở `/usr/lib/systemd/system/`, **đừng sửa ở đó** (bản cập nhật gói sẽ ghi đè). Muốn chỉnh unit của gói, dùng `sudo systemctl edit httpd` để tạo file "override".
- **journald** gom stdout/stderr của mọi service. Lọc theo thời gian: `journalctl -u hello --since "10 min ago"`, chỉ lỗi: `journalctl -p err -b` (từ lần boot này).
- Lệnh `systemctl remove` ở cuối file lab **không tồn tại**. Gỡ một service bạn tự tạo: `sudo systemctl disable --now hello`, xoá file unit, rồi `sudo systemctl daemon-reload`. Service từ gói thì `sudo dnf remove httpd`.

**Đi sâu hơn: mạng cơ bản để kiểm tra service**

```bash
ip -br a                       # IP của các card mạng (EC2 chỉ thấy IP private!)
ip route                       # default gateway
sudo ss -tlnp                  # port TCP nào đang LISTEN, của process nào
curl -v http://localhost:8080  # gọi thử HTTP, -v hiện chi tiết
dig +short amazon.com          # tra DNS (cài: sudo dnf install bind-utils; Ubuntu: dnsutils)
```

- `ss` cho thấy `0.0.0.0:80` (nghe mọi IP) hay `127.0.0.1:80` (chỉ trong máy). App chỉ nghe `127.0.0.1` thì từ Internet sẽ không vào được dù Security Group mở.
- Quy trình gỡ lỗi "không vào được web": `systemctl status` → `ss -tlnp` → `curl localhost` trong máy → Security Group → NACL / route table.

**Lỗi hay gặp & cách sửa**

- `Failed to start hello.service: Unit hello.service not found.` → quên `daemon-reload`, hoặc file không nằm trong `/etc/systemd/system/`, hoặc đuôi file sai.
- `status=203/EXEC` trong `systemctl status` → `ExecStart` sai đường dẫn hoặc file không có quyền thực thi. Phải dùng **đường dẫn tuyệt đối** (`/usr/bin/python3`, không phải `python3`).
- `Job for httpd.service failed … See "journalctl -xeu httpd.service"` → làm đúng như nó gợi ý. Lỗi hay gặp nhất là sai cú pháp cấu hình (`sudo apachectl configtest`) hoặc port đã bị chiếm (`ss -tlnp`).
- Trình duyệt quay mãi rồi timeout, trong khi `curl localhost` vẫn chạy → Security Group chưa mở port 80.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab httpd trên AL2023 bằng `dnf`. Reboot máy (`sudo reboot`) và chứng minh httpd tự chạy lại.

🟡 *Thực hành*: Tạo `hello.service` như trên. Dùng `sudo kill -9 <PID của python>` để "giết" nó và quan sát systemd tự khởi động lại (`journalctl -u hello`). Đổi `Restart=on-failure` thành `Restart=no` và thử lại.

🔴 *Thử thách*: Có người báo "app chạy port 8080 không vào được từ Internet". Tự tạo lỗi này theo 3 cách (service chưa chạy, app chỉ nghe `127.0.0.1`, Security Group chưa mở 8080), rồi với mỗi cách ghi lại **lệnh nào** giúp bạn phát hiện ra.

<details><summary>Gợi ý</summary>

- Service chưa chạy: `systemctl status hello` báo `inactive (dead)`.
- Chỉ nghe localhost: đổi `ExecStart` thành `... http.server 8080 --bind 127.0.0.1`. `ss -tlnp` hiện `127.0.0.1:8080`.
- SG chưa mở: trong máy `curl localhost:8080` chạy được, còn từ Fedora `curl -m 5 http://<ip>:8080` bị timeout.
</details>

<details><summary>2. Khác nhau giữa <code>restart</code> và <code>reload</code>?</summary>

`restart` dừng hẳn rồi chạy lại process (ngắt các kết nối đang có). `reload` yêu cầu service đọc lại cấu hình mà không dừng (thường gửi SIGHUP). Không phải service nào cũng hỗ trợ `reload`.

## Lab7 · EBS: ổ đĩa, volume và mount point {013}

**Khái niệm cốt lõi**

- **EBS volume** là ổ đĩa mạng của AWS, gắn (attach) vào EC2. Nó tồn tại độc lập với máy: terminate EC2 thì volume thêm vào vẫn còn (trừ khi bật *Delete on termination*).
- Linux không tự dùng ổ mới. Có 3 bước: **(1) phân vùng** (tuỳ chọn) → **(2) tạo file system** (format) → **(3) mount** (gắn) vào một thư mục gọi là **mount point**.

```
AWS Console: Create volume (cùng AZ với EC2) → Attach to instance
        │
        ▼
/dev/nvme1n1  (ổ trống, chưa có gì)
        │ fdisk  → tạo phân vùng /dev/nvme1n1p1   (tuỳ chọn)
        │ mkfs.xfs → tạo file system
        │ mount  → gắn vào /data
        ▼
/data ← giờ bạn ghi file vào đây là ghi lên EBS
        │ /etc/fstab → tự mount lại sau reboot
```

**Code lab (`lab7-linux-disk-command.sh`)**

```bash
lsblk                                 # liệt kê ổ và phân vùng
df -h                                 # dung lượng đã dùng của các file system ĐÃ mount
sudo file -s /dev/nvme1n1             # in "data" nghĩa là chưa có file system
sudo fdisk /dev/nvme1n1               # n (new), p, Enter…, w (ghi)  → tạo /dev/nvme1n1p1
sudo mkfs -t xfs /dev/nvme1n1p1       # ⚠️ xoá sạch dữ liệu trên phân vùng
sudo mkdir /data
sudo mount /dev/nvme1n1p1 /data
sudo blkid                            # lấy UUID
sudo cp /etc/fstab /etc/fstab.bak     # sao lưu trước khi sửa
sudo vim /etc/fstab
#   UUID=2f8fae87-...  /data  xfs  defaults,nofail  0  2
sudo umount /data && sudo mount -a    # thử fstab NGAY, đừng đợi reboot
df -h /data
```

> ⚠️ **Tên thiết bị trong video là `/dev/xvdf`**, vì quay trên `t2`. Trên các loại máy **Nitro** như `t3`, `t4g`, `m5`…, EBS hiện ra dạng **NVMe**: ổ gốc `/dev/nvme0n1`, ổ thêm `/dev/nvme1n1`. Luôn chạy `lsblk` để biết tên thật, đừng chép tên từ video.

**Đi sâu hơn**

- **Vì sao dùng UUID trong `/etc/fstab`:** tên thiết bị (`nvme1n1`, `nvme2n1`) có thể đổi thứ tự sau reboot hoặc khi gắn thêm ổ. UUID gắn với file system nên không đổi. AWS khuyên dùng UUID.
- **`nofail` rất quan trọng:** nếu một ngày volume bị gỡ ra mà fstab không có `nofail`, máy có thể **không boot được** (kẹt ở emergency mode, không SSH vào được). Có `nofail` thì máy vẫn boot, chỉ thiếu `/data`.
- 6 cột của fstab: `thiết-bị  mount-point  loại-fs  tuỳ-chọn  dump  pass`. `pass=2` nghĩa là kiểm tra file system sau ổ gốc; `0` là không kiểm tra.
- **Có cần phân vùng không?** Với EBS dữ liệu, nhiều người format thẳng cả ổ (`mkfs -t xfs /dev/nvme1n1`) cho đơn giản. Khi mở rộng chỉ cần một bước, không phải `growpart`.
- **Mở rộng volume** (tăng từ 10 GB lên 20 GB trên console, không cần tắt máy):

```bash
lsblk                                   # thấy disk 20G nhưng partition vẫn 10G
sudo growpart /dev/nvme1n1 1            # nới partition số 1 (chỉ cần nếu có phân vùng)
sudo xfs_growfs -d /data                # nới file system XFS (tham số là MOUNT POINT)
# ext4 thì dùng: sudo resize2fs /dev/nvme1n1p1
df -h /data
```

  (Trong `note.txt` lệnh bị gõ thừa dấu cách `xfs _growfs`. Lệnh đúng là `xfs_growfs`.) EBS **chỉ tăng được, không giảm được** dung lượng. Sau một lần sửa volume, bạn phải chờ một khoảng thời gian (tài liệu AWS ghi khoảng 6 giờ) mới sửa tiếp được.
- **XFS hay ext4?** AL2023 và RHEL mặc định XFS, Ubuntu mặc định ext4. Cả hai đều ổn. Lưu ý XFS không thu nhỏ được.
- **Loại EBS**: dùng **gp3** (SSD đa dụng, rẻ hơn gp2 và chỉnh IOPS độc lập). Sao lưu bằng **snapshot**.
- **Instance store** (một số loại máy có sẵn ổ cục bộ) **mất dữ liệu khi stop máy**. Đừng nhầm với EBS.

**Lỗi hay gặp & cách sửa**

- Không thấy ổ mới trong `lsblk` → volume tạo ở **AZ khác** với EC2 (không attach được), hoặc chưa attach xong.
- `mount: /data: wrong fs type, bad option, bad superblock on /dev/nvme1n1` → chưa format, hoặc mount nhầm *cả ổ* trong khi file system nằm trên *phân vùng* (`nvme1n1p1`).
- `mount -a` báo `mount: /data: can't find UUID=...` → chép sai UUID. Sửa ngay trước khi reboot. Nếu đã lỡ reboot và máy không lên: stop máy, tháo ổ gốc, gắn vào một máy khác để sửa fstab (hoặc dùng EC2 Serial Console).
- `umount: /data: target is busy` → bạn (hoặc process nào đó) đang đứng trong `/data`. `cd ~` rồi thử lại; tìm thủ phạm bằng `sudo lsof +D /data`.

💰 **Chi phí / an toàn**
- gp3 khoảng 0,08–0,10 USD/GB-tháng tuỳ region (ước lượng; xem trang giá EBS). Volume 10 GB để quên một tháng chỉ vài chục cent, nhưng để quên nhiều volume và snapshot thì cộng dồn.
- Volume **đã detach vẫn bị tính tiền**. Học xong: `umount`, xoá dòng trong fstab, *Detach* rồi *Delete volume*.
- Tài khoản Free Tier kiểu cũ (tạo trước 15/7/2025) có 30 GB EBS miễn phí mỗi tháng trong 12 tháng. Tài khoản mới hơn dùng mô hình credit, hãy kiểm tra trong *Billing → Free Tier*.

**Bài tập**

🟢 *Cơ bản*: Tạo volume gp3 2 GB **cùng AZ** với EC2, attach, format XFS, mount vào `/data`, thêm vào fstab bằng UUID với `nofail`. Reboot và kiểm tra `df -h`.

🟡 *Thực hành*: Tăng volume lên 4 GB trên console, rồi mở rộng file system mà không cần umount. Ghi lại `lsblk` trước và sau.

🔴 *Thử thách*: Mô phỏng sự cố: xoá `nofail` khỏi fstab, **detach volume** trên console, rồi reboot. Quan sát máy có lên không (dùng *Actions → Monitor and troubleshoot → Get system log* hoặc EC2 Serial Console). Sau đó gắn lại volume và giải thích vì sao `nofail` cứu được tình huống này.

<details><summary>Gợi ý</summary>

Không có `nofail`, systemd coi mount `/data` là bắt buộc; thiếu thiết bị thì sau khoảng 90 giây chờ, máy rơi vào *emergency mode* và SSH không lên. Gắn lại volume (cùng AZ) và start máy là boot bình thường. Đây là lý do AWS ghi rõ `defaults,nofail` trong hướng dẫn. Thử thách này có rủi ro mất máy; chỉ làm trên EC2 học tập không có dữ liệu quan trọng.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao không nên ghi <code>/dev/nvme1n1p1</code> trong fstab?</summary>

Tên thiết bị NVMe được đánh số theo thứ tự phát hiện, có thể thay đổi khi reboot hoặc khi gắn thêm ổ. UUID gắn với chính file system nên không đổi.
</details>

<details><summary>2. Chạy <code>mkfs</code> lên một volume tạo từ snapshot thì sao?</summary>

Toàn bộ dữ liệu trong snapshot trên volume đó bị xoá (file system mới đè lên). Luôn kiểm tra `sudo file -s` hoặc `lsblk -f` trước khi `mkfs`.
</details>

## Lab8 · CronJob, systemd timer và bash script {014}

**Khái niệm cốt lõi**

**Cron** chạy lệnh theo lịch định sẵn: backup database lúc 2 giờ sáng, dọn log mỗi tuần, gọi API mỗi 5 phút. Mỗi dòng cron gồm **5 trường thời gian** + lệnh:

```
┌───────── phút        (0-59)
│ ┌─────── giờ         (0-23)
│ │ ┌───── ngày tháng  (1-31)
│ │ │ ┌─── tháng       (1-12)
│ │ │ │ ┌─ thứ         (0-7, 0 và 7 đều là Chủ nhật)
│ │ │ │ │
* * * * *  lệnh
```

| Biểu thức | Nghĩa |
|---|---|
| `* * * * *` | Mỗi phút (lab) |
| `*/5 * * * *` | Mỗi 5 phút |
| `0 2 * * *` | 2:00 sáng mỗi ngày |
| `30 8 * * 1-5` | 8:30 thứ Hai tới thứ Sáu |
| `0 0 1 * *` | 0:00 ngày mùng 1 hằng tháng |

Dùng **[crontab.guru](https://crontab.guru)** để dịch biểu thức sang tiếng người trước khi lưu.

**Hai nơi đặt cron**

| | `/etc/crontab` (lab dùng) | `crontab -e` (khuyên dùng) |
|---|---|---|
| Ai sửa | root | từng user tự sửa của mình |
| Có cột tên user? | **Có**: `* * * * * ec2-user /home/ec2-user/script.sh` | **Không**: `* * * * * /home/ec2-user/script.sh` |
| Kiểm tra cú pháp khi lưu | Không | Có |

Ngoài ra có `/etc/cron.d/` (giống `/etc/crontab`, mỗi ứng dụng một file) và các thư mục `/etc/cron.daily/`, `/etc/cron.weekly/`.

> ⚠️ **Amazon Linux 2023 không cài cron sẵn** (AL2 thì có). Nếu làm lab trên AL2023, bạn phải cài trước:
> `sudo dnf install -y cronie && sudo systemctl enable --now crond`
> AWS khuyến nghị chuyển sang **systemd timer** (phần Đi sâu bên dưới).

**Code lab (`lab8-linux-cronjob.sh`), sửa cho chắc chắn hơn**

```bash
cat > /home/ec2-user/script.sh <<'EOF'
#!/bin/bash
echo "Hello from Cronjob!!!" >> /home/ec2-user/log.txt
date >> /home/ec2-user/log.txt
EOF
chmod 755 /home/ec2-user/script.sh        # không cần sudo: file của chính bạn

crontab -e                                 # thêm dòng (không có cột user):
#   * * * * * /home/ec2-user/script.sh >> /home/ec2-user/cron.err 2>&1
crontab -l                                 # xem lại
sleep 120; cat /home/ec2-user/log.txt
```

Không cần restart `crond` sau khi sửa: cron tự phát hiện file thay đổi.

**Đi sâu hơn: bash script cơ bản**

Script chạy bằng cron không có ai nhìn màn hình, nên phải viết *cẩn thận hơn* script gõ tay:

```bash
#!/usr/bin/env bash
set -euo pipefail        # -e: lỗi là dừng; -u: dùng biến chưa khai báo là lỗi; pipefail: lỗi giữa pipe cũng tính

BACKUP_DIR="/data/backup"                    # biến: không có dấu cách quanh dấu =
TODAY="$(date +%F)"                          # $(...) lấy kết quả lệnh, ví dụ 2026-10-22
mkdir -p "$BACKUP_DIR"                       # luôn đặt biến trong dấu ""

if [[ ! -d /var/www/html ]]; then
  echo "Không thấy thư mục web" >&2          # in ra stderr
  exit 1                                     # exit code khác 0 = thất bại
fi

tar -czf "$BACKUP_DIR/web-$TODAY.tar.gz" -C /var/www html

for f in "$BACKUP_DIR"/*.tar.gz; do          # vòng lặp for
  echo "Có file: $f ($(du -h "$f" | cut -f1))"
done

find "$BACKUP_DIR" -name '*.tar.gz' -mtime +7 -delete   # xoá bản cũ hơn 7 ngày
echo "Xong, exit code của lệnh trước: $?"
```

- **Exit code**: `0` là thành công, khác `0` là lỗi. `$?` chứa exit code của lệnh vừa chạy. `cmd1 && cmd2` chỉ chạy cmd2 khi cmd1 thành công; `cmd1 || cmd2` chạy cmd2 khi cmd1 lỗi.
- Kiểm tra script trước khi đưa vào cron: `bash -n script.sh` (chỉ kiểm cú pháp), và công cụ **shellcheck** (`sudo dnf install ShellCheck` trên Fedora) bắt rất nhiều lỗi kinh điển.

**Đi sâu hơn: môi trường của cron rất "nghèo"**

- `PATH` của cron chỉ có vài thư mục cơ bản, không đọc `~/.bashrc`. Lệnh chạy tay được nhưng trong cron báo `command not found` là lỗi số một. Dùng đường dẫn tuyệt đối, hoặc khai báo `PATH=...` ở đầu crontab.
- Output không đi đâu cả (hoặc bị gửi "mail" cục bộ). Luôn chuyển hướng: `>> /var/log/myjob.log 2>&1`.
- Giờ của cron là giờ hệ thống. EC2 mặc định **UTC**, tức chậm hơn giờ Việt Nam 7 tiếng. Xem bằng `timedatectl`.
- Job chạy lâu có thể bị chồng lên lần chạy sau. Dùng `flock`: `*/5 * * * * flock -n /tmp/job.lock /path/job.sh`.

**Đi sâu hơn: systemd timer**

Cặp file `.service` (làm gì) + `.timer` (khi nào):

```ini
# /etc/systemd/system/hello-log.service
[Unit]
Description=Ghi log hello
[Service]
Type=oneshot
User=ec2-user
ExecStart=/home/ec2-user/script.sh
```

```ini
# /etc/systemd/system/hello-log.timer
[Unit]
Description=Chạy hello-log mỗi phút
[Timer]
OnCalendar=*-*-* *:*:00     # mỗi phút; "daily" = 0:00 hằng ngày; "Mon..Fri 08:30"
Persistent=true             # máy tắt lỡ lịch thì bật lên chạy bù
[Install]
WantedBy=timers.target
```

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now hello-log.timer
systemctl list-timers                       # lần chạy kế tiếp, lần chạy trước
journalctl -u hello-log.service -n 5        # log có sẵn, không cần tự redirect
systemd-analyze calendar "Mon..Fri 08:30"   # kiểm tra biểu thức lịch
```

| | cron | systemd timer |
|---|---|---|
| Cú pháp | 1 dòng, rất ngắn | 2 file, dài hơn |
| Log | Phải tự redirect | Tự vào journald |
| Chạy bù khi máy tắt | Không (trừ anacron) | `Persistent=true` |
| Có sẵn trên AL2023 | Không | Có |

**Lỗi hay gặp & cách sửa**

- `-bash: crontab: command not found` trên AL2023 → chưa cài `cronie`.
- Job không chạy, không có log → kiểm tra: `systemctl status crond`, `sudo journalctl -u crond`, quyền `x` của script, dòng trong `/etc/crontab` có đủ cột user chưa.
- Ghi dòng kiểu `/etc/crontab` (có `ec2-user`) vào `crontab -e` → cron hiểu `ec2-user` là *tên lệnh*, báo lỗi `ec2-user: command not found` trong log.
- Script chạy tay được, trong cron lỗi `command not found` → vấn đề `PATH` ở trên.

**Bài tập**

🟢 *Cơ bản*: Làm lại lab bằng `crontab -e` (không dùng `/etc/crontab`). Sau 3 phút, `log.txt` phải có 3 cặp dòng. Xong thì xoá job (`crontab -e` xoá dòng, hoặc `crontab -r`).

🟡 *Thực hành*: Chuyển chính job đó sang **systemd timer** chạy mỗi 2 phút. Chứng minh bằng `systemctl list-timers` và `journalctl`.

🔴 *Thử thách*: Viết script `backup-web.sh` (dùng `set -euo pipefail`) nén `/var/www/html` vào `/data/backup` (ổ EBS của Lab7), giữ 7 bản mới nhất, và trả exit code khác 0 nếu `/data` chưa mount. Lên lịch chạy 1:00 sáng **giờ Việt Nam** mỗi ngày trên máy đang chạy UTC.

<details><summary>Gợi ý</summary>

Kiểm tra mount: `mountpoint -q /data || { echo "/data chưa mount" >&2; exit 2; }`. 1:00 giờ Việt Nam (UTC+7) là 18:00 UTC hôm trước, nên cron là `0 18 * * *`. Với systemd timer có thể ghi thẳng múi giờ: `OnCalendar=*-*-* 01:00:00 Asia/Ho_Chi_Minh`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. <code>0 */6 * * *</code> chạy lúc nào?</summary>

Phút 0 của các giờ chia hết cho 6: 0:00, 6:00, 12:00, 18:00 mỗi ngày (theo giờ hệ thống).
</details>

<details><summary>2. Vì sao nên có <code>set -euo pipefail</code> trong script chạy tự động?</summary>

Không có nó, bash gặp lỗi vẫn chạy tiếp các lệnh sau, ví dụ `cd /sai/thư/mục` thất bại rồi `rm -rf *` chạy ngay trong thư mục hiện tại. Với `-e` script dừng tại lỗi đầu tiên; `-u` bắt lỗi gõ sai tên biến; `pipefail` không để lỗi bị "nuốt" giữa pipe.
</details>

## Lab9 · Thêm SSH key của thành viên dự án, tổng kết và dọn dẹp {015-016}

**Khái niệm cốt lõi**

Khi có thành viên mới, *không* gửi họ file `.pem` của bạn và cũng *không* dùng mật khẩu. Cách chuẩn:

```
Máy của dev01                               Server
ssh-keygen  → dev01      (private, GIỮ KÍN)
            → dev01.pub  (public) ──gửi──▶  /home/dev01/.ssh/authorized_keys
ssh -i dev01 dev01@server ───────────────▶  sshd so khớp chữ ký với public key → cho vào
```

- **Private key** không bao giờ rời máy của chủ nhân. **Public key** thì đưa cho ai cũng được.
- Mỗi người **một user, một key riêng**: khi có người nghỉ việc, chỉ cần xoá user hoặc xoá dòng key của họ, không ảnh hưởng người khác, và log ghi rõ ai đã đăng nhập.

**Code lab (`lab9-add-ssh-key.sh`)**

```bash
# Trên máy của thành viên (Fedora):
ssh-keygen -t ed25519 -C "dev01" -f ~/.ssh/dev01     # lab dùng rsa 4096, ed25519 ngắn và hiện đại hơn

# Trên server, với ec2-user:
sudo useradd dev01                                   # không đặt mật khẩu
sudo su - dev01                                      # dấu "-" để vào đúng home và môi trường của dev01
mkdir -p ~/.ssh && chmod 700 ~/.ssh
vim ~/.ssh/authorized_keys                           # dán MỘT dòng nội dung dev01.pub
chmod 600 ~/.ssh/authorized_keys
exit

# Trên máy thành viên:
ssh -i ~/.ssh/dev01 dev01@<public-ip>
```

Không cần restart sshd sau khi sửa `authorized_keys`: file được đọc ở mỗi lần đăng nhập.

**Đi sâu hơn**

- **Vì sao 700 và 600?** sshd có chế độ `StrictModes` (bật mặc định): nếu thư mục home, `~/.ssh` hoặc `authorized_keys` mà người khác *ghi được*, sshd sẽ **lặng lẽ bỏ qua key**. Owner cũng phải đúng là user đó.
- Nếu tạo file bằng `sudo` dưới quyền root (không `su - dev01`), file thuộc root và key không chạy. Sửa: `sudo chown -R dev01:dev01 /home/dev01/.ssh`.
- **ed25519 hay RSA?** ed25519 nhanh, key ngắn, an toàn; GitHub cũng khuyên dùng. RSA nên từ 3072 bit trở lên. Đặt **passphrase** cho private key và dùng `ssh-agent` để khỏi gõ lại.
- `ssh-copy-id -i ~/.ssh/dev01.pub dev01@server` tự làm hết phần trên, nhưng chỉ dùng được khi bạn *đã* vào được server bằng cách khác.
- Một dòng `authorized_keys` có thể thêm giới hạn, ví dụ `from="203.0.113.0/24" ssh-ed25519 AAAA... dev01` chỉ cho đăng nhập từ dải IP đó.

**Hardening SSH (gia cố an toàn)**

Tạo file `/etc/ssh/sshd_config.d/10-hardening.conf`:

```bash
PasswordAuthentication no     # chỉ cho đăng nhập bằng key
PermitRootLogin no            # không cho root đăng nhập thẳng
AllowUsers ec2-user dev01     # chỉ những user này được SSH
MaxAuthTries 3
```

```bash
sudo sshd -t                      # kiểm tra cú pháp; không in gì là OK
sudo systemctl reload sshd
```

> ⚠️ **Luôn giữ một phiên SSH đang mở** khi đổi cấu hình sshd, và thử đăng nhập ở *cửa sổ thứ hai*. Nếu cấu hình sai, bạn vẫn còn phiên cũ để sửa, không bị khoá ngoài server.

Ở mức hạ tầng: Security Group chỉ mở 22 cho IP cần thiết, hoặc bỏ hẳn port 22 và dùng SSM Session Manager.

> ⚠️ **Thư mục lab có file `dev01` (private key) nằm trong Git.** Bất kỳ ai đọc được repo đều đăng nhập được vào server nào đã thêm `dev01.pub`. Ở chương 07 bạn sẽ học cách gỡ secret đã lỡ commit; ngay bây giờ, đừng thêm `dev01.pub` vào server nào bạn giữ lâu dài, hãy tự sinh key mới.

**Lỗi hay gặp & cách sửa**

- `Permission denied (publickey)` → kiểm tra theo thứ tự: đúng user chưa; trên server `sudo ls -la /home/dev01/.ssh` (quyền 700/600, owner dev01); nội dung `authorized_keys` là **một dòng** liền (dán bằng vim hay bị xuống dòng giữa chừng); đọc log `sudo journalctl -u sshd -n 30`.
- Log server ghi `Authentication refused: bad ownership or modes for directory /home/dev01/.ssh` → sửa quyền và owner như trên.
- Chạy client với `ssh -v` (hoặc `-vvv`) để thấy key nào đang được thử và bị từ chối ở bước nào.
- `Too many authentication failures` → ssh-agent đang thử quá nhiều key. Thêm `-o IdentitiesOnly=yes -i <key>`.

**Tổng kết chương**

| Chủ đề | Lệnh / file nhớ nhất |
|---|---|
| Kết nối | `ssh -i key user@host`, `~/.ssh/config` |
| Soạn thảo | vim: `i`, `Esc`, `:wq`, `:q!` |
| User, quyền quản trị | `useradd`, `usermod -aG`, `visudo -f /etc/sudoers.d/...` |
| Phân quyền | `chmod 750`, `chown user:group`, `namei -l` |
| Process | `ps aux`, `top`, `kill` (rồi mới `kill -9`) |
| Service | `systemctl enable --now`, `journalctl -u` |
| Ổ đĩa | `lsblk`, `mkfs`, `mount`, fstab với `UUID` + `nofail` |
| Lịch chạy | `crontab -e`, systemd timer |
| SSH key | `authorized_keys` 600, `~/.ssh` 700, `PasswordAuthentication no` |

💰 **Dọn dẹp cuối chương** (làm đủ, theo thứ tự):
1. `umount /data`, xoá dòng `/data` trong fstab (nếu còn giữ máy).
2. **Terminate** EC2 (Stop thì ổ gốc EBS vẫn bị tính tiền).
3. *EC2 → Volumes*: xoá mọi volume trạng thái **available** (đã tách, vẫn tính tiền).
4. *Snapshots*: xoá snapshot đã tạo khi tập.
5. *Elastic IPs*: release nếu có. Xoá Security Group và key pair không dùng nữa.
6. Kiểm tra lại ở **đúng region** bạn đã dùng (ap-southeast-1 hoặc ap-southeast-2).

**Bài tập**

🟢 *Cơ bản*: Tự sinh cặp key ed25519 mới (không dùng file `dev01` trong repo), tạo user `dev01` trên server, cấu hình `authorized_keys` và đăng nhập được.

🟡 *Thực hành*: Thêm user `dev02` với key riêng. Sau đó "cho dev02 nghỉ việc": thu hồi quyền truy cập mà không ảnh hưởng `dev01`. Ghi lại 2 cách thu hồi và khác biệt giữa chúng.

<details><summary>Gợi ý</summary>

Cách 1: xoá dòng key của dev02 trong `authorized_keys` (user còn, file còn, chỉ mất quyền SSH). Cách 2: `sudo userdel -r dev02` (xoá cả user và home). Trước đó, `sudo pkill -u dev02` để cắt phiên đang mở, vì xoá key không đá phiên đang chạy ra ngoài. Thêm cách 3: `sudo usermod -L -e 1 dev02` để khoá tài khoản nhưng giữ dữ liệu cho việc kiểm tra sau.
</details>

🔴 *Thử thách*: Gia cố SSH của server: tắt mật khẩu, cấm root, chỉ cho phép `ec2-user` và `dev01`. Chứng minh bằng 3 lần thử đăng nhập thất bại có chủ đích (bằng mật khẩu, bằng root, bằng `dev02`) và chỉ ra dòng log tương ứng trong `journalctl -u sshd`. Không được tự khoá mình ngoài server.

<details><summary>Gợi ý</summary>

Dùng file trong `sshd_config.d/` như mẫu ở trên, `sudo sshd -t`, giữ phiên cũ mở rồi `reload`. Xác nhận giá trị thật bằng `sudo sshd -T | grep -Ei 'passwordauth|permitroot|allowusers'`. Thử từ cửa sổ khác: `ssh -o PubkeyAuthentication=no dev01@ip` (ép dùng mật khẩu) phải bị từ chối; log có dạng `User dev02 ... not allowed because not listed in AllowUsers`.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Bạn dán đúng public key nhưng vẫn bị từ chối, và quyền <code>~/.ssh</code> là <code>775</code>. Vì sao?</summary>

`775` cho group *ghi* vào `~/.ssh`. Với `StrictModes yes`, sshd coi như không an toàn và bỏ qua `authorized_keys`. Đổi về `700` (và file `600`).
</details>

<details><summary>2. Thành viên làm mất laptop chứa private key. Bạn làm gì?</summary>

Xoá ngay dòng public key tương ứng khỏi `authorized_keys` trên mọi server (và khỏi GitHub nếu dùng chung key), cắt các phiên đang mở của user đó, rồi để thành viên sinh cặp key mới có passphrase. Tốt nhất nên có danh sách server nào đã thêm key của ai, hoặc quản lý tập trung (IAM + SSM, EC2 Instance Connect).
</details>
