# Chương 05 · Infrastructure as Code với Terraform

Học xong chương này, bạn **mô tả hạ tầng AWS bằng code**: tạo, sửa và xoá EC2, VPC, ALB hay Auto Scaling chỉ bằng vài lệnh, cho nhiều môi trường và nhiều region, không cần click trên console.

Bốn lệnh bạn sẽ gõ nhiều nhất cả chương:

```bash
terraform init      # tải provider và module, kết nối backend
terraform plan      # xem trước sẽ tạo / sửa / xoá những gì
terraform apply     # thực hiện thay đổi
terraform destroy   # xoá hết tài nguyên do code này tạo
```

Ngoài ra, chương này giới thiệu thêm các công cụ dân Terraform dùng hằng ngày: `terraform fmt`, `terraform validate`, `tflint`, `trivy config`, các block `moved` / `import` / `removed`, `lifecycle`, `for_each`, file `.terraform.lock.hcl` và cách khoá state bằng S3 (`use_lockfile`).

> Phiên bản tại thời điểm viết (10/2026): Terraform **1.17**, AWS provider **6.x** (6.70), module VPC của Registry **6.x**, OpenTofu **1.13**. Code lab trong repo được viết cho Terraform 1.5+ và AWS provider 5.x, vẫn chạy được, nhưng chỗ nào khác biệt với bản mới sẽ được ghi chú.

## IaC là gì và vì sao dùng Terraform {002-008}

**Infrastructure as Code (IaC)** là viết hạ tầng (server, mạng, database…) thành file code, rồi để công cụ tự tạo ra đúng như vậy.

Click tay trên console có 4 vấn đề lớn:

| Vấn đề khi click tay | IaC giải quyết thế nào |
|---|---|
| Không nhớ đã cấu hình gì, ai sửa gì | Code nằm trong Git: có lịch sử, có review qua pull request |
| Dựng lại môi trường thứ hai rất lâu và dễ sai | Chạy lại cùng một bộ code là ra môi trường y hệt |
| Quên xoá tài nguyên, bị tính tiền | `terraform destroy` xoá sạch những gì code đã tạo |
| Mỗi người làm một kiểu | Module dùng chung, chuẩn hoá cho cả team |

**Các công cụ IaC thường gặp:**
- **Terraform / OpenTofu**: chạy được với nhiều cloud (AWS, Azure, GCP, Cloudflare…), viết bằng ngôn ngữ HCL. Đây là công cụ phổ biến nhất.
- **AWS CloudFormation / CDK**: của riêng AWS.
- **Pulumi**: viết hạ tầng bằng TypeScript hoặc Python.
- **Ansible**: chủ yếu để *cấu hình bên trong server* (cài gói, sửa file), không chuyên về *tạo hạ tầng*.

**Terraform hoạt động như thế nào:**

```
file .tf (trạng thái bạn MUỐN)
        │  terraform plan  → so sánh với
        ▼
terraform.tfstate (Terraform NHỚ đã tạo gì) + AWS thật
        │  terraform apply → gọi AWS API qua provider
        ▼
tài nguyên trên AWS
```

- **Declarative (khai báo):** bạn chỉ mô tả *kết quả cuối cùng* ("cần 1 EC2 t3.micro"), không viết *các bước*. Terraform tự tính phải tạo mới, sửa hay xoá.
- **Provider:** plugin để nói chuyện với từng nền tảng, ví dụ `hashicorp/aws`. `terraform init` tải provider về thư mục `.terraform/`.
- **State (`terraform.tfstate`):** file JSON ghi lại *tài nguyên nào trong code ứng với ID nào trên AWS*. Mất file state thì Terraform "quên" mọi thứ đã tạo.

> ⚠️ File state chứa thông tin nhạy cảm (IP, đôi khi cả mật khẩu). **Không commit state lên Git.** Repo của bạn đã có dòng `*.tfstate` trong `.gitignore`.

**Đi sâu hơn**

*Bên trong một lần `plan`.* Terraform đọc mọi file `.tf` trong thư mục (thứ tự file không quan trọng), dựng một **đồ thị phụ thuộc** (dependency graph) giữa các tài nguyên, rồi duyệt đồ thị đó. Tài nguyên không phụ thuộc nhau được xử lý **song song**, mặc định tối đa 10 việc cùng lúc (`-parallelism=10`). Đó là lý do EC2 và security group không liên quan có thể được tạo cùng lúc.

*Terraform core và provider là hai chương trình riêng.* `terraform` (core) chỉ biết đọc HCL, tính đồ thị và quản lý state. Mọi lời gọi AWS API do **provider** (một file chạy riêng trong `.terraform/providers/`) làm, hai bên nói chuyện qua gRPC. Vì vậy provider AWS có phiên bản riêng (5.x, 6.x) và lên phiên bản độc lập với Terraform.

*Ba lệnh "xem mà không sửa" nên tập thành phản xạ:*

```bash
terraform plan -out=tfplan          # lưu plan ra file
terraform show tfplan               # xem lại plan đã lưu
terraform apply tfplan              # apply ĐÚNG plan đã xem, không tính lại
terraform plan -refresh-only        # chỉ so state với AWS thật để phát hiện drift
terraform graph | dot -Tpng > graph.png   # vẽ đồ thị (cần: sudo dnf install graphviz)
```

`apply tfplan` rất quan trọng trong CI/CD: người duyệt xem plan nào thì máy chạy đúng plan đó. Nếu **state** đã thay đổi kể từ lúc tạo plan (ví dụ có người khác vừa apply), Terraform báo `Saved plan is stale` và từ chối chạy, bạn phải plan lại.

*Giấy phép và OpenTofu.* Tháng 8/2023 HashiCorp đổi giấy phép Terraform từ MPL (mã nguồn mở) sang BSL. Cộng đồng tách ra bản **OpenTofu** (thuộc Linux Foundation, lệnh `tofu`). OpenTofu dùng cùng cú pháp HCL, cùng provider, và có vài tính năng riêng như mã hoá state ngay trong công cụ. Với người học và với hầu hết công ty dùng nội bộ, Terraform vẫn dùng miễn phí; kiến thức chương này áp dụng được cho cả hai.

*IaC không chỉ là "tạo tài nguyên".* Quy trình thật trong công ty thường là: viết code → mở pull request → CI chạy `fmt`, `validate`, lint, quét bảo mật, `plan` và gắn plan vào PR → người khác duyệt → merge → CI chạy `apply`. Bạn sẽ gặp lại luồng này ở chương CI/CD.

**Lỗi hay gặp & cách sửa**

- **Sửa tay trên console rồi quên.** Lần `apply` sau Terraform "sửa lại" theo code, xoá mất thay đổi tay. Cách sửa: mọi thay đổi đi qua code. Nếu buộc phải sửa tay khi có sự cố, chạy `terraform plan -refresh-only` để thấy drift, rồi cập nhật code cho khớp.
- **Gõ `yes` mà không đọc plan.** Dòng cuối của plan, ví dụ `Plan: 1 to add, 0 to change, 3 to destroy.`, phải được đọc mỗi lần. Thấy `destroy` mà không hiểu vì sao thì dừng lại.
- **Chạy `terraform` ở sai thư mục.** Terraform chỉ đọc file `.tf` ở thư mục hiện tại (không đọc thư mục con trừ khi là module). Lỗi `Error: No configuration files` nghĩa là bạn đang đứng sai chỗ.

🔴 *Thử thách.* Viết script `safe-apply.sh` cho CI: tạo plan ra file, **dừng lại với mã lỗi 1** nếu plan có bất kỳ hành động xoá (`delete`) nào, ngược lại thì apply đúng plan đó. Thử với lab2: lần đầu (chỉ tạo) phải qua; đổi `ami` (gây replace) phải bị chặn.

<details><summary>Lời giải</summary>

```bash
#!/usr/bin/env bash
set -euo pipefail
terraform plan -input=false -out=tfplan
DELETES=$(terraform show -json tfplan \
  | jq -r '.resource_changes[] | select(.change.actions | index("delete")) | .address')
if [[ -n "$DELETES" ]]; then
  echo "Plan có xoá tài nguyên, cần người duyệt:"; echo "$DELETES"; exit 1
fi
terraform apply -input=false tfplan
```

Replace hiện trong JSON là `["delete","create"]` (hoặc `["create","delete"]` khi có `create_before_destroy`), nên `index("delete")` bắt được cả hai. Nhớ `terraform destroy` sau khi thử.
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. "Declarative" khác "imperative" thế nào? Cho ví dụ.</summary>

Imperative là viết *các bước*: "gọi API tạo EC2, rồi gắn SG, rồi…". Declarative là mô tả *đích đến*: "phải có 1 EC2 t3.micro gắn SG này". Chạy lại script imperative có thể tạo thêm EC2 thứ hai. Chạy lại `terraform apply` thì không, vì Terraform so với state và thấy đã đủ.
</details>

<details><summary>2. Nếu xoá EC2 bằng tay trên console rồi chạy <code>terraform plan</code>, chuyện gì xảy ra?</summary>

Lúc chạy plan, Terraform *refresh*, tức là hỏi AWS và thấy EC2 không còn. Vì code vẫn yêu cầu có EC2, plan sẽ báo **sẽ tạo lại 1 EC2** (`1 to add`). Hiện tượng hạ tầng thật lệch khỏi code như vậy gọi là **drift**.
</details>

<details><summary>3. Vì sao trong CI/CD nên dùng <code>terraform apply tfplan</code> thay vì <code>terraform apply -auto-approve</code>?</summary>

`apply tfplan` chạy **đúng** plan mà người duyệt đã xem. `apply -auto-approve` tính plan mới ngay lúc chạy; nếu trong lúc chờ duyệt có ai đổi hạ tầng hay code, thứ được apply có thể khác thứ đã được duyệt.
</details>

## Cài đặt môi trường làm việc {009-010}

Bạn cần 3 thứ: **Terraform CLI**, **AWS CLI** và **credentials** (thông tin xác thực) để Terraform gọi được AWS.

```bash
# Fedora
sudo dnf install -y dnf-plugins-core
sudo dnf config-manager addrepo --from-repofile=https://rpm.releases.hashicorp.com/fedora/hashicorp.repo
sudo dnf install -y terraform
terraform -version

aws configure          # nhập Access Key, Secret Key, region mặc định
aws sts get-caller-identity   # kiểm tra: đang đăng nhập AWS bằng user nào?
```

- Credentials lưu ở `~/.aws/credentials`. Terraform tự đọc file này, **không bao giờ viết access key vào file `.tf`**.
- Tạo một **IAM user riêng** cho việc học, đừng dùng root account. Sau khi học IAM ở tuần 2, thu hẹp quyền lại theo nguyên tắc least privilege.
- Extension **HashiCorp Terraform** trên VS Code: gợi ý code, tự format khi lưu, báo lỗi cú pháp.
- **GitHub Copilot / AI** viết code rất nhanh, nhưng **bạn phải đọc hiểu từng dòng trước khi `apply`**. AI có thể đề xuất mở `0.0.0.0/0` cho mọi port hoặc dùng loại instance đắt tiền.

**Đi sâu hơn**

*Provider AWS tìm credentials theo thứ tự.* Nếu không ghi gì trong block `provider "aws"`, nó thử lần lượt: biến môi trường (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_PROFILE`), rồi file `~/.aws/credentials` và `~/.aws/config` (kể cả profile SSO), rồi tới role gắn vào máy (EC2 instance profile, ECS task role). Muốn chọn profile cụ thể:

```bash
aws configure --profile learn          # tạo profile tên "learn"
AWS_PROFILE=learn terraform plan        # dùng profile đó cho lần chạy này
```

Nếu tài khoản của bạn dùng IAM Identity Center (SSO), `aws configure sso` rồi `aws sso login` cho credentials **tạm thời**, an toàn hơn access key dài hạn.

*Ghim phiên bản ngay từ đầu.* Thêm block `terraform` vào mỗi project để người khác (và chính bạn 6 tháng sau) chạy đúng phiên bản:

```hcl
terraform {
  required_version = ">= 1.11"            # Terraform CLI
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"                  # 6.x, không tự nhảy lên 7.0
    }
  }
}
```

Khi `init`, Terraform ghi phiên bản provider đã chọn và checksum vào **`.terraform.lock.hcl`**. **File này nên commit vào Git** (khác với `.terraform/` và `*.tfstate`). Muốn lên bản provider mới hơn trong khoảng cho phép thì chạy `terraform init -upgrade`. Lock file chỉ ghi **provider**, không ghi module.

*Bộ công cụ kiểm tra code trước khi plan:*

| Lệnh | Kiểm tra gì | Có gọi AWS không |
|---|---|---|
| `terraform fmt -recursive` | Định dạng chuẩn (thụt lề, căn dấu `=`). Thêm `-check` để CI báo lỗi thay vì sửa | Không |
| `terraform validate` | Cú pháp, tên thuộc tính, kiểu dữ liệu. Cần `init` trước (có thể `init -backend=false`) | Không |
| `tflint` + ruleset AWS | Lỗi mà validate bỏ qua: instance type không tồn tại, biến khai báo mà không dùng… | Không (mặc định) |
| `terraform plan` | So với AWS thật | Có |

```bash
# Cài tflint (đọc script trước khi chạy), rồi bật ruleset AWS
curl -sL https://raw.githubusercontent.com/terraform-linters/tflint/master/install_linux.sh -o install_tflint.sh
less install_tflint.sh && bash install_tflint.sh

cat > .tflint.hcl <<'EOF'
plugin "aws" {
  enabled = true
  version = "0.49.0"     # xem bản mới nhất trên GitHub tflint-ruleset-aws
  source  = "github.com/terraform-linters/tflint-ruleset-aws"
}
EOF
tflint --init && tflint
```

*Nhiều phiên bản Terraform trên một máy.* Repo cũ có thể cần Terraform 1.5, repo mới cần 1.17. Công cụ như `tenv` giúp chuyển phiên bản theo từng thư mục. Người mới thì chỉ cần một bản mới nhất từ repo HashiCorp là đủ.

**Lỗi hay gặp & cách sửa**

- **`Error: No valid credential sources found`** (đại ý, tên lỗi có thể khác theo phiên bản provider): chưa `aws configure`, hoặc đang dùng `AWS_PROFILE` trỏ tới profile không tồn tại. Kiểm tra bằng `aws sts get-caller-identity`.
- **`ExpiredToken` / `The security token included in the request is expired`**: credentials tạm (SSO, `assume-role`) đã hết hạn. Chạy lại `aws sso login`.
- **Tạo tài nguyên ở sai tài khoản / sai region.** Không có thông báo lỗi nào, chỉ là "không thấy EC2 trên console". Kiểm tra `aws sts get-caller-identity`, region trong `provider "aws"` và region đang chọn ở góc phải console.
- **`dnf config-manager` báo không hiểu tham số `--add-repo`**: Fedora 41 trở lên dùng dnf5, cú pháp mới là `addrepo --from-repofile=...` như ở trên. Hướng dẫn cũ trên mạng viết cho dnf4.

🟡 *Thực hành.* Cài `tflint` và ruleset AWS như trên. Trong một bản sao của lab3, đổi `instance_type` thành `"t3.micor"` (gõ sai). So sánh: `terraform validate` có bắt được lỗi không? `tflint` thì sao? Lỗi này nếu để tới `apply` thì AWS báo gì?

<details><summary>Lời giải</summary>

- `validate` **không** bắt được, vì với Terraform đây chỉ là một chuỗi hợp lệ.
- `tflint` với ruleset AWS báo luật `aws_instance_invalid_type`: `"t3.micor" is an invalid value as instance_type`.
- Tới `apply` thì AWS mới trả lỗi kiểu `InvalidParameterValue` cho instance type. Bắt lỗi sớm ở máy bạn rẻ hơn nhiều so với lúc apply giữa chừng.

Lưu ý: ở lab3, biến `instance_type` lấy từ `terraform.tfvars`, nên tflint cần đọc được tfvars (mặc định nó có đọc `terraform.tfvars`).
</details>

🔴 *Thử thách.* Tạo **git pre-commit hook** cho repo `devops-for-beginner`: mỗi lần commit, nếu có file `.tf` thay đổi thì chạy `terraform fmt -check -recursive iac-using-terraform` và chặn commit nếu chưa format. Thử commit một file `.tf` thụt lề sai để thấy hook chặn.

<details><summary>Lời giải</summary>

```bash
cat > .git/hooks/pre-commit <<'EOF'
#!/usr/bin/env bash
if git diff --cached --name-only | grep -q '\.tf$'; then
  if ! terraform fmt -check -recursive iac-using-terraform; then
    echo "Chưa format. Chạy: terraform fmt -recursive iac-using-terraform"
    exit 1
  fi
fi
EOF
chmod +x .git/hooks/pre-commit
```

Hook trong `.git/hooks/` không được commit lên Git. Ở công ty người ta thường dùng framework `pre-commit` với bộ hook `pre-commit-terraform` để cả team dùng chung (chạy fmt, validate, tflint, quét bảo mật).
</details>

**Câu hỏi tự kiểm tra**

<details><summary>1. Vì sao không được ghi access key thẳng vào provider "aws" { ... }?</summary>

File `.tf` được commit lên Git. Key lộ ra ngoài sẽ bị bot quét GitHub tìm thấy trong vài phút và dùng để đào coin, có khi tốn hàng nghìn USD. Hãy để key trong `~/.aws/credentials` hoặc biến môi trường; khi chạy trong CI/CD thì dùng IAM role/OIDC.
</details>

## Lab2 · EC2 đầu tiên bằng Terraform {011-014}

Lab này (`iac-using-terraform/lab2/main.tf`) tạo 3 tài nguyên: **key pair**, **security group** và **EC2 instance**.

```hcl
resource "aws_instance" "demo-instance" {
  #      └─ loại tài nguyên  └─ tên bạn đặt trong code
  ami           = "ami-0eeab0e1473986ffd"
  instance_type = "t3.micro"
  key_name      = aws_key_pair.udemy-keypair.key_name   # tham chiếu tài nguyên khác
  vpc_security_group_ids = [aws_security_group.test-security-group.id]
}
```

- **Cú pháp block:** `resource "<TYPE>" "<NAME>" { … }`. Địa chỉ của tài nguyên trong Terraform là `aws_instance.demo-instance`.
- **Tham chiếu tạo ra thứ tự:** vì `aws_instance` dùng `aws_key_pair.udemy-keypair.key_name`, Terraform biết phải tạo key pair *trước*. Đây là **implicit dependency** (phụ thuộc ngầm), bạn không cần tự sắp thứ tự.
- **Security Group = tường lửa của EC2.** `ingress` là chiều vào, `egress` là chiều ra. `protocol = "-1"` nghĩa là mọi giao thức.
- **AMI khác nhau theo từng region.** Một ID AMI chỉ tồn tại ở một region. Đổi region thì phải đổi AMI.
- **AMI phải cùng kiến trúc với instance type.** AMI `arm64` không chạy được trên `t3.micro` (x86_64), muốn dùng phải chọn `t4g.micro`. Bạn đã gặp lỗi `architecture … does not match` và viết `check-ami-arch.sh` để kiểm tra, đó là cách làm rất đúng.

**Về file keypair (bài 014):**
- `udemy-key` là **private key**, chỉ nằm trên máy bạn, **không commit**.
- `udemy-key.pub` là **public key**, đưa lên AWS qua `aws_key_pair`.
- Mỗi region chỉ có **một** key pair tên `udemy-keypair`. Lab sau mà tạo lại sẽ lỗi `InvalidKeyPair.Duplicate`. Cách xử lý: dùng `data "aws_key_pair"` để đọc lại key đã có (như bạn làm ở lab3), hoặc đặt tên khác.

```bash
ssh -i ./keypair/udemy-key ec2-user@<public-ip>     # Amazon Linux
ssh -i ./keypair/udemy-key ubuntu@<public-ip>       # Ubuntu
```

**Đi sâu hơn**

*Đọc ký hiệu trong plan.* `+` tạo mới, `-` xoá, `~` sửa tại chỗ, `-/+` xoá rồi tạo lại (replace), `+/-` tạo bản mới trước rồi mới xoá bản cũ, `<=` đọc data source. Dòng có chú thích `# forces replacement` cho biết thuộc tính nào gây ra replace. Muốn chủ động tạo lại một tài nguyên (ví dụ EC2 bị lỗi bên trong) mà không sửa code: `terraform apply -replace=aws_instance.demo-instance`. Lệnh `terraform taint` cũ làm việc tương tự nhưng đã bị khuyến cáo không dùng nữa.

*Block `lifecycle`: điều khiển cách Terraform thay đổi tài nguyên.*

```hcl
resource "aws_instance" "demo-instance" {
  # ...
  lifecycle {
    create_before_destroy = true      # replace: tạo máy mới xong mới xoá máy cũ
    prevent_destroy       = false     # true: mọi plan có xoá tài nguyên này đều bị từ chối
    ignore_changes        = [ami, tags["Owner"]]   # không đề xuất update khi các thuộc tính này lệch
  }
}
```

- `create_before_destroy` giảm thời gian gián đoạn, nhưng **xung đột với tên cố định**: security group `name = "test-security-group"` không thể có hai bản cùng tên trong một VPC. Khi cần, dùng `name_prefix = "test-sg-"` để AWS tự thêm hậu tố ngẫu nhiên.
- `prevent_destroy` chặn `terraform destroy` và chặn replace, nhưng **nếu bạn xoá hẳn block `resource` khỏi code thì tài nguyên vẫn bị xoá**, vì lúc đó Terraform không còn đọc được cài đặt lifecycle.
- `ignore_changes` hay dùng với `ami` khi AMI lấy từ `data "aws_ami"` có `most_recent = true`: không muốn mỗi lần Amazon ra AMI mới là EC2 bị tạo lại.
- Còn có `replace_triggered_by` (tạo lại khi tài nguyên khác đổi) và `precondition` / `postcondition` (kiểm tra điều kiện, báo lỗi rõ ràng).

*Security group: cách viết khuyến nghị hiện nay.* Tài liệu AWS provider khuyên **không** viết `ingress {}` / `egress {}` lồng trong `aws_security_group` nữa, mà tách mỗi rule thành một tài nguyên, mỗi rule một CIDR:

```hcl
resource "aws_security_group" "web" {
  name_prefix = "lab2-web-"
  description = "web server"
}
resource "aws_vpc_security_group_ingress_rule" "ssh_from_me" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = "203.0.113.10/32"    # IP của bạn
  from_port         = 22
  to_port           = 22
  ip_protocol       = "tcp"
}
resource "aws_vpc_security_group_egress_rule" "all_out" {
  security_group_id = aws_security_group.web.id
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1"
}
```

Không được trộn hai kiểu trên cùng một security group, sẽ bị "đánh nhau" và plan lúc nào cũng có thay đổi. Lab của khoá dùng kiểu inline, vẫn chạy đúng; kiểu mới dễ quản lý hơn khi số rule nhiều.

> ⚠️ Khi tạo security group trong VPC, AWS tự thêm rule egress "cho ra tất cả", nhưng **Terraform xoá rule mặc định đó**. Vì vậy lab phải tự khai báo `egress`. Quên khai báo là EC2 không ra Internet được.

## Lab3 · Biến, map và file tfvars {015-016}

Mục tiêu: **một bộ code dùng được cho nhiều region và nhiều cấu hình**, không phải sửa trực tiếp trong `main.tf`. Code lab: `iac-using-terraform/lab3/` (`main.tf`, `variable.tf`, `terraform.tfvars`).

```hcl
variable "region" {
  type    = string
  default = "ap-southeast-2"
}
variable "amis" {
  type = map(string)
  default = {
    "ap-southeast-1" = "ami-0e4b5d31e60aa0acd"
    "ap-southeast-2" = "ami-0eeab0e1473986ffd"
  }
}

resource "aws_instance" "demo-instance" {
  ami = var.amis[var.region]    # tra AMI theo region (mapping)
}
```

- **Kiểu biến:** `string`, `number`, `bool`, `list(...)`, `map(...)`, `object({...})`. Khai báo kiểu rõ ràng để Terraform báo lỗi sớm khi truyền sai.
- **Truyền giá trị cho biến**, nguồn sau ghi đè nguồn trước:
  `default` → biến môi trường `TF_VAR_x` → `terraform.tfvars` → `*.auto.tfvars` → `-var-file=...` và `-var "x=y"` trên dòng lệnh (cái nào viết sau thì thắng).
- `terraform.tfvars` được **tự động đọc**. Lệnh `--var-file "terraform.tfvars"` trong lab chỉ là ghi cho rõ ràng; với file tên khác (`prod.tfvars`) thì bắt buộc phải có.
- **`data` khác `resource`:**
  - `resource` là **tạo mới và quản lý** tài nguyên. `destroy` sẽ xoá nó.
  - `data` là **chỉ đọc** một tài nguyên đã có sẵn. `destroy` **không** xoá nó.
  - Ở lab3, bạn đọc lại key pair do lab2 tạo bằng `data "aws_key_pair"`, nhờ vậy không bị lỗi trùng tên.
- Mẹo: dùng `data "aws_ami"` với `filter` và `most_recent = true` để luôn lấy AMI mới nhất, thay vì chép tay ID AMI.

**Đi sâu hơn**

*`validation`: chặn giá trị sai ngay từ đầu.*

```hcl
variable "instance_type" {
  type    = string
  default = "t3.micro"
  validation {
    condition     = contains(["t3.micro", "t3.small", "t4g.micro"], var.instance_type)
    error_message = "Chỉ cho phép t3.micro, t3.small hoặc t4g.micro."
  }
}
```

*`locals`: biến nội bộ, tính một lần dùng nhiều nơi.* Khác `variable` ở chỗ người dùng **không truyền vào được**. Dùng để gom biểu thức lặp lại:

```hcl
locals {
  name_prefix = "udemy-${var.region}"
  common_tags = { Project = "udemy-devops", Region = var.region }
}

resource "aws_instance" "demo-instance" {
  # ...
  tags = merge(local.common_tags, { Name = "${local.name_prefix}-demo" })
}
```

*Kiểu `object` với thuộc tính tuỳ chọn* (Terraform 1.3+), hợp khi một biến chứa nhiều cấu hình:

```hcl
variable "server" {
  type = object({
    instance_type = string
    volume_size   = optional(number, 8)   # không truyền thì mặc định 8
  })
}
```

*`sensitive` và `ephemeral`.* `sensitive = true` chỉ ẩn giá trị khi in ra màn hình, **vẫn lưu trong state**. `ephemeral = true` (Terraform 1.10+) không ghi giá trị vào state và plan, nhưng chỉ dùng được ở một số chỗ (ví dụ thuộc tính write-only của provider).

*Thử biểu thức trước khi viết vào code:* `terraform console` mở REPL đọc được biến và state hiện tại:

```bash
terraform console
> var.amis[var.region]
> lookup(var.amis, "ap-northeast-1", "không có")
> merge({a = 1}, {b = 2})
```

*Về file lab3:* map `amis` trong lab viết dạng `"ap-southeast-2":"ami-..."` với dấu `:`. HCL chấp nhận cả `=` lẫn `:` trong object, nhưng `terraform fmt` và hầu hết code thực tế dùng `=`. Lab khai báo `map(any)`; `map(string)` chặt chẽ hơn.

**Lỗi hay gặp & cách sửa**

- **`Error: No value for required variable`**: biến không có `default` mà không được truyền. Ở lab3, `image_id` không có default; nếu bạn xoá dòng `image_id` trong `terraform.tfvars`, `plan` sẽ hỏi giá trị (hoặc báo lỗi khi chạy với `-input=false`). Sửa: truyền giá trị, thêm default, hoặc xoá biến không dùng.
- **`Error: Invalid index` / `The given key does not identify an element in this collection value`**: `var.amis[var.region]` với region không có trong map. Bạn sẽ gặp lỗi này ở **lab5 và lab9** nếu đổi region sang `ap-southeast-2`, vì map `amis` ở đó chỉ có Singapore và Tokyo. Sửa: thêm key cho region đó.
- **`Warning: Value for undeclared variable`**: tfvars có biến mà code không khai báo (thường do gõ sai tên). Riêng `-var` trên dòng lệnh với biến chưa khai báo thì là **lỗi**, không phải cảnh báo.
- **`data "aws_key_pair"` không tìm thấy key** (thông báo đại ý "no matching EC2 Key Pair found"): key `udemy-keypair` chưa có ở region đang chọn. Key pair là tài nguyên **theo region**. Sửa: tạo key ở region đó (chạy lab2 với region đó, hoặc `aws ec2 import-key-pair`).

## Lab4 · Output và Elastic IP {017}

**Output** in ra giá trị sau khi `apply`, và là cách để **module hoặc project khác lấy kết quả** của bạn. Code lab: `iac-using-terraform/lab4/main.tf`.

```hcl
resource "aws_eip" "demo-eip" {
  instance = aws_instance.demo-instance.id
}

output "instance_ip_addr_public" {
  value       = aws_eip.demo-eip.public_ip
  description = "IP tĩnh để SSH vào máy"
}
```

```bash
terraform output                          # xem mọi output
terraform output -raw instance_ip_addr_public
ssh -i ./keypair/udemy-key ec2-user@$(terraform output -raw instance_ip_addr_public)
```

- **Public IP thường** của EC2 **thay đổi** mỗi lần stop/start máy.
- **Elastic IP (EIP)** là IP tĩnh: giữ nguyên dù máy khởi động lại, và gắn sang máy khác được.
- 💰 AWS tính phí **mọi IPv4 public**, kể cả EIP, khoảng 0,005 USD/giờ. Học xong nhớ `destroy`.
- Output có `sensitive = true` sẽ bị ẩn khi in ra màn hình (nhưng vẫn nằm trong file state).

**Đi sâu hơn**

*Output nằm trong state.* Giá trị output được lưu trong `terraform.tfstate`, nên `terraform output` chạy được mà không cần gọi AWS. Đây cũng là lý do `sensitive = true` **không** phải là cách giấu bí mật: ai đọc được state là đọc được giá trị. Thêm nữa, `terraform output -json` và `-raw` **in thẳng** giá trị sensitive ra màn hình.

*Output kiểu phức tạp và `-json`:* output có thể là map hay object, rất tiện cho script:

```hcl
output "server" {
  value = {
    id         = aws_instance.demo-instance.id
    public_ip  = aws_eip.demo-eip.public_ip
    private_ip = aws_instance.demo-instance.private_ip
  }
}
```

```bash
terraform output -json server | jq -r .public_ip
```

*Kiểm tra điều kiện trên output.* Block `precondition` trong output báo lỗi rõ ràng nếu kết quả không như mong đợi:

```hcl
output "instance_ip_addr_public" {
  value = aws_eip.demo-eip.public_ip
  precondition {
    condition     = aws_eip.demo-eip.public_ip != ""
    error_message = "EIP chưa có địa chỉ public."
  }
}
```

*Chia sẻ kết quả giữa các project.* Project B đọc output của project A qua `data "terraform_remote_state"` (cần A dùng backend như S3, xem Lab9). Cách này buộc B phải đọc được **toàn bộ** state của A. Nhiều team thích cách khác: A ghi giá trị cần chia sẻ vào **SSM Parameter Store**, B đọc bằng `data "aws_ssm_parameter"`, hoặc B tra trực tiếp bằng data source (`data "aws_vpc"` lọc theo tag).

*Cú pháp EIP mới.* Với AWS provider 5.x trở lên, EIP không gắn instance ngay thì viết `domain = "vpc"` (thuộc tính cũ `vpc = true` đã bị bỏ). Lab gắn `instance = ...` nên không cần.

**Lỗi hay gặp & cách sửa**

- **`InvalidKeyPair.Duplicate` khi apply lab4**: lab4 lại **tạo mới** `aws_key_pair "udemy-keypair"` giống lab2. Nếu lab2 (hoặc lab khác) vẫn còn, sẽ trùng. Sửa: destroy lab cũ, hoặc đổi sang `data "aws_key_pair"` như bạn làm ở lab3.
- **`Error: Output refers to sensitive values`**: output dùng một giá trị đã bị đánh dấu sensitive (ví dụ mật khẩu DB) mà không khai báo `sensitive = true`. Sửa: thêm `sensitive = true` vào output, hoặc xem lại có thật cần xuất giá trị đó không.
- **`AddressLimitExceeded`**: mỗi region mặc định chỉ được khoảng 5 EIP. Thường là do EIP của các lab cũ chưa được giải phóng. Kiểm tra: `aws ec2 describe-addresses --region <region>`.
- **Output hiện `(known after apply)` trong plan**: không phải lỗi. IP chỉ có sau khi AWS tạo xong tài nguyên.

💰 **Chi phí / an toàn:** EIP **không gắn vào máy nào** vẫn bị tính 0,005 USD/giờ (giá public IPv4 hiện tại, gắn hay không đều tính). Destroy đúng thư mục để EIP được giải phóng cùng instance.

## Lab5 · Module: tái sử dụng code {018-019}

**Module** là một thư mục chứa các file `.tf`, có **input** (variable) và **output**. Bạn có thể hình dung nó như một *hàm* trong lập trình.

```
lab5/
├── main.tf              ← "root module" gọi các module con
├── modules/
│   ├── security/        ← main.tf, variable.tf, output.tf
│   └── compute/
```

```hcl
module "security" {
  source = "./modules/security"
}

module "compute" {
  source            = "./modules/compute"
  security_group_id = module.security.security_group_id   # output của module này → input của module kia
}
```

- Module con **không đọc được** biến của root. Mọi thứ phải truyền qua input rõ ràng.
- Thêm module mới, hoặc đổi `source`, thì phải chạy lại `terraform init`.
- Địa chỉ tài nguyên bên trong module có dạng `module.compute.aws_instance.this`.
- Chỉ nên tách module khi phần đó **được dùng lại** hoặc **có ranh giới rõ ràng** (mạng, bảo mật, máy chủ). Đừng tách module cho mỗi tài nguyên lẻ.

Trong code lab thật (`iac-using-terraform/lab5/main.tf`), tên input là `ec2_security_group_ids` (một list) và output là `public_security_group_id`:

```hcl
module "compute" {
  source                 = "./modules/compute"
  image_id               = var.amis[var.region]
  key_name               = aws_key_pair.udemy-keypair.key_name
  ec2_security_group_ids = [module.security.public_security_group_id]
}
```

**Đi sâu hơn**

*Không đặt block `provider` trong module con.* `lab5/modules/security/main.tf` có `provider "aws" { region = var.region }` ngay trong module. Tài liệu Terraform gọi đây là **legacy module**: module như vậy **không dùng được với `count`, `for_each`, `depends_on`**, và khi bạn xoá lời gọi module, Terraform mất luôn provider cần để xoá tài nguyên bên trong. Cách đúng: chỉ khai báo provider ở root; module con chỉ khai báo `required_providers`. Nếu module cần provider khác (region khác), truyền qua `providers = { aws = aws.tokyo }` (xem Lab10).

*Cấu trúc module chuẩn:*

```
modules/compute/
├── main.tf          # tài nguyên
├── variables.tf     # input, có description và type
├── outputs.tf       # output
├── versions.tf      # terraform { required_providers { aws = { source = "hashicorp/aws", version = ">= 5.0" } } }
└── README.md        # cách dùng
```

Với module dùng chung, tài liệu khuyên chỉ đặt **phiên bản tối thiểu** (`>=`) cho provider; còn root module mới đặt cả cận trên (`~>`).

*Các kiểu `source`:*

| `source` | Ví dụ |
|---|---|
| Thư mục local | `"./modules/compute"` (không có `version`) |
| Terraform Registry | `"terraform-aws-modules/vpc/aws"` + `version = "~> 6.0"` |
| Git | `"git::https://github.com/org/repo.git//modules/vpc?ref=v1.2.0"` (ghim bằng tag) |

*`for_each` và `count` trên module* (Terraform 0.13+): gọi cùng một module nhiều lần với tham số khác nhau. Kết hợp với **`for` expression** để gom output:

```hcl
module "compute" {
  source   = "./modules/compute"
  for_each = { web = "t3.micro", worker = "t3.micro" }

  instance_type          = each.value
  image_id               = var.amis[var.region]
  key_name               = aws_key_pair.udemy-keypair.key_name
  ec2_security_group_ids = [module.security.public_security_group_id]
}

output "public_ips" {
  value = { for name, m in module.compute : name => m.instance_ip_addr_public }
}
```

*`count` hay `for_each`?* `count` đánh số `[0]`, `[1]`, `[2]`. Xoá phần tử ở giữa list thì mọi phần tử phía sau **bị đánh số lại**, và Terraform sẽ xoá/tạo lại chúng. `for_each` dùng **key** (`["web"]`, `["worker"]`), xoá một key chỉ ảnh hưởng đúng phần tử đó. Quy tắc: tài nguyên giống hệt nhau thì `count`; có danh tính riêng thì `for_each`. Một trường hợp `count` rất hay dùng là bật/tắt: `count = var.enable_eip ? 1 : 0`.

*Chuyển code có sẵn vào module mà không tạo lại tài nguyên:* dùng `moved`:

```hcl
moved {
  from = aws_instance.demo-instance
  to   = module.compute.aws_instance.demo-instance
}
```

**Lỗi hay gặp & cách sửa**

- **`Error: Module not installed`**: thêm module mới hoặc đổi `source` mà chưa chạy `terraform init`. Sửa: `terraform init`.
- **`Error: Unsupported argument` / `An argument named "instance_typ" is not expected here`**: truyền input mà module không khai báo `variable` tương ứng (hoặc gõ sai tên). Sửa: khai báo trong `variables.tf` của module.
- **`Error: Unsupported attribute` / `This object does not have an attribute named ...`**: đọc `module.security.xxx` mà module không có `output "xxx"`.
- **`Error: Invalid index`** ở `var.amis[var.region]`: map `amis` trong `lab5/variable.tf` chỉ có `ap-southeast-1` và `ap-northeast-1`. Bạn chạy ở `ap-southeast-2` thì phải thêm key này (AMI Sydney bạn đã dùng ở lab2: `ami-0eeab0e1473986ffd`).
- **`Module is incompatible with count, for_each, and depends_on`**: bạn thêm `for_each` cho module có block `provider` bên trong (như `modules/security` của lab5). Sửa: xoá block provider trong module.

4. Cách cũ không cần sửa code: `terraform state mv aws_instance.demo-instance module.compute.aws_instance.demo-instance`. Block `moved` tốt hơn vì nằm trong code, được review và người khác apply cũng tự chuyển theo.
</details>

## Lab6 · Dựng một VPC hoàn chỉnh {020-021}

Code lab: `iac-using-terraform/lab6_part1/` (chỉ có module `networking`) và `lab6_part2/` (thêm `security`, `compute`, đặt EC2 vào public subnet).

```
                Internet
                   │
            Internet Gateway
                   │
 ┌──────────────── VPC 10.0.0.0/16 ─────────────────┐
 │  AZ a                         AZ b               │
 │  Public 10.0.1.0/24           Public 10.0.2.0/24 │ ← route 0.0.0.0/0 → IGW
 │     │ NAT Gateway                                │
 │  Private 10.0.3.0/24          Private 10.0.4.0/24│ ← route 0.0.0.0/0 → NAT
 └──────────────────────────────────────────────────┘
```

- **VPC:** mạng riêng của bạn trên AWS, có một dải CIDR, ví dụ `10.0.0.0/16` (65.536 IP).
- **Subnet:** một phần nhỏ của VPC, **nằm trong đúng một AZ**. Dùng 2 AZ để nếu một AZ sự cố thì hệ thống vẫn chạy.
- Một subnet được gọi là **public** khi *route table* của nó có đường `0.0.0.0/0 → Internet Gateway`. Bản thân subnet không có thuộc tính "public".
- **Private subnet** đi ra Internet (để cài gói, tải image) qua **NAT Gateway** đặt ở public subnet. Từ Internet thì không vào được private subnet.
- 💰 **NAT Gateway khá đắt**: khoảng 0,045–0,059 USD/giờ cộng phí dữ liệu, tức hơn 1 USD/ngày nếu quên tắt. Đây là khoản hay làm "cháy" tài khoản học nhất.
- Mỗi subnet AWS giữ lại **5 IP**, nên `/24` chỉ còn 251 IP dùng được.
- Thay vì copy-paste `public_subnet_1`, `public_subnet_2`, bạn có thể dùng `count` hoặc `for_each`, và hàm `cidrsubnet()` để chia CIDR tự động.

Lưu ý: tfvars của lab6 dùng private subnet `10.0.10.0/24` và `10.0.20.0/24`, sơ đồ trên chỉ là ví dụ.

**Đi sâu hơn**

*Viết subnet bằng `for_each` + `cidrsubnet()`.* `cidrsubnet(prefix, newbits, netnum)` cắt dải lớn thành dải nhỏ: `cidrsubnet("10.0.0.0/16", 8, 1)` là `10.0.1.0/24` (thêm 8 bit vào /16 thành /24, lấy dải số 1). Kết hợp với `data "aws_availability_zones"` để không viết cứng tên AZ:

```hcl
data "aws_availability_zones" "available" {
  state = "available"
}

locals {
  azs = slice(data.aws_availability_zones.available.names, 0, 2)   # 2 AZ đầu tiên
}

resource "aws_subnet" "public" {
  for_each                = { for i, az in local.azs : az => i }
  vpc_id                  = aws_vpc.my_vpc.id
  availability_zone       = each.key
  cidr_block              = cidrsubnet(var.cidr_block, 8, each.value + 1)    # 10.0.1.0/24, 10.0.2.0/24
  map_public_ip_on_launch = true
  tags = { Name = "public-${each.key}" }
}

resource "aws_route_table_association" "public" {
  for_each       = aws_subnet.public
  subnet_id      = each.value.id
  route_table_id = aws_route_table.public_route_table.id
}
```

Dùng AZ làm key của `for_each` (thay vì số thứ tự) giúp thêm/bớt AZ không làm các subnet khác bị tạo lại.

*`map_public_ip_on_launch`.* Subnet trong lab không bật thuộc tính này, nên EC2 tạo trong đó **không tự có public IP**. Lab6_part2 vẫn SSH được là nhờ gắn `aws_eip`. Bật thuộc tính trên (hoặc `associate_public_ip_address = true` ở instance) nếu không muốn dùng EIP.

*`depends_on` hợp lý duy nhất trong VPC.* Tài liệu `aws_nat_gateway` khuyên thêm `depends_on = [aws_internet_gateway.my_igw]` cho NAT Gateway, vì NAT cần IGW mới hoạt động nhưng code NAT không tham chiếu trực tiếp IGW. Đây là ví dụ đúng nghĩa của **phụ thuộc ẩn**: ngoài trường hợp này, hãy để tham chiếu tự tạo thứ tự. Tài liệu Terraform gọi `depends_on` là "phương án cuối cùng".

*NAT Gateway kiểu mới: regional.* AWS có thêm **regional NAT Gateway**: một NAT duy nhất tự mở rộng sang các AZ có workload, **không cần đặt trong public subnet**. Trong AWS provider mới, viết `availability_mode = "regional"` và `vpc_id` thay cho `subnet_id` / `allocation_id`. Kiểu truyền thống (mỗi AZ một NAT, đặt ở public subnet) gọi là **zonal**, chính là kiểu trong lab.

*Tiết kiệm NAT.* Nếu private subnet chỉ cần nói chuyện với S3 hoặc DynamoDB, dùng **gateway VPC endpoint** (miễn phí) thay vì đi qua NAT. Môi trường học thì có thể tắt hẳn NAT khi không cần cài gói trên máy private.

**Lỗi hay gặp & cách sửa**

- **`DependencyViolation` khi destroy** (VPC, subnet hay security group "has dependencies and cannot be deleted"): còn tài nguyên **ngoài Terraform** nằm trong VPC, ví dụ EC2 tạo tay, ENI của Load Balancer, hoặc security group tạo tay. Sửa: tìm và xoá thứ đó (`aws ec2 describe-network-interfaces --filters Name=vpc-id,Values=<vpc-id>`), rồi destroy lại.
- **`InvalidSubnet.Conflict`**: hai subnet có CIDR chồng lấn, hoặc CIDR subnet nằm ngoài CIDR VPC. Thử trước bằng `terraform console` với `cidrsubnet(...)`.
- **AZ không hợp lệ** (đại ý: "Value (ap-northeast-1b) for parameter availabilityZone is invalid"): không phải tài khoản nào cũng dùng được mọi AZ. Ví dụ ở Tokyo, tài khoản mới thường không có `ap-northeast-1b`, nên tfvars của lab10 dùng `1a` và `1c`. Dùng `data "aws_availability_zones"` để tránh.
- **Private EC2 không ra Internet dù đã có NAT**: route table private chưa được **associate** với subnet (quên `aws_route_table_association`), hoặc security group thiếu egress.

💰 **Chi phí / an toàn:** NAT Gateway 0,045 USD/giờ ở US East (Singapore, Sydney cao hơn một chút) **cộng** 0,045 USD/GB dữ liệu đi qua, **cộng** EIP của NAT. Mỗi lần học xong lab6 là `terraform destroy` ngay, kể cả khi định "mai làm tiếp". Kiểm tra: `aws ec2 describe-nat-gateways --region <region> --filter Name=state,Values=available`.

## Lab7 · Dùng module có sẵn để dựng VPC nhanh {022}

Không cần tự viết lại VPC từ đầu. **Terraform Registry** có các module đã được cộng đồng kiểm chứng:

```hcl
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"            # luôn ghim version

  name            = "learning-vpc"
  cidr            = "10.0.0.0/16"
  azs             = ["ap-southeast-1a", "ap-southeast-1b"]
  public_subnets  = ["10.0.1.0/24", "10.0.2.0/24"]
  private_subnets = ["10.0.3.0/24", "10.0.4.0/24"]
  enable_nat_gateway = true
  single_nat_gateway = true     # chỉ 1 NAT cho rẻ (môi trường học, dev)
}
```

- **Ghim `version`.** Không ghim thì lần `init` sau có thể tải bản mới với thay đổi phá vỡ (breaking change).
- `~> 5.0` nghĩa là chấp nhận `5.x` nhưng không lên `6.0`.
- Tự viết module (lab6) giúp bạn *hiểu bản chất*. Dùng module của Registry (lab7) giúp bạn *làm nhanh*. Trong công việc thực tế, người ta thường dùng module của Registry.

Code lab (`iac-using-terraform/lab7/modules/networking/main.tf`) ghim cứng `version = "5.0.0"` và **không** đặt `single_nat_gateway`.

**Đi sâu hơn**

*Phiên bản hiện tại.* Module VPC đã lên **6.x** (bản mới nhất lúc viết là 6.7.3) và yêu cầu AWS provider `>= 6.28`. Nhánh 5.x mới nhất là 5.21.0, cần AWS provider `>= 5.79`. Vì vậy hai con số phải đi đôi với nhau:

```hcl
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.79" }   # đi với module ~> 5.0
  }
}
```

Lab ghi provider `>= 5.0.0` (không có cận trên). Nếu bạn xoá `.terraform.lock.hcl` hay chạy `init -upgrade`, Terraform có thể chọn AWS provider 6.x trong khi module là 5.0.0, và bạn có thể gặp cảnh báo hoặc lỗi lạ. Hãy đặt cận trên cho provider ở root module.

*Lock file không ghi module.* `.terraform.lock.hcl` chỉ ghi phiên bản **provider**. Với module, Terraform luôn lấy bản mới nhất thoả ràng buộc `version`. Muốn chắc chắn tuyệt đối thì ghim chính xác (`version = "5.21.0"`), và nâng cấp có chủ đích.

*NAT trong module VPC: ba chế độ.*

| Thiết lập | Số NAT | Dùng khi |
|---|---|---|
| `enable_nat_gateway = true` (mặc định còn lại) | 1 NAT cho **mỗi private subnet** | Hiếm khi cần |
| `+ single_nat_gateway = true` | 1 NAT cho cả VPC | Học, dev: rẻ nhất |
| `+ one_nat_gateway_per_az = true` | 1 NAT mỗi AZ | Production: AZ này hỏng, AZ kia vẫn ra Internet |

Lab7 chỉ đặt `enable_nat_gateway = true` với 2 private subnet, nên **tạo 2 NAT Gateway**, tốn gấp đôi.

*Đọc module trước khi dùng.* Trên trang module ở Registry, xem tab **Inputs** (tham số), **Outputs** (ví dụ `vpc_id`, `public_subnets`, `private_subnets`), **Resources** (sẽ tạo những gì) và mục examples. Module tốt có tag phiên bản rõ ràng, nhiều lượt tải, cập nhật gần đây, và có changelog ghi rõ thay đổi phá vỡ.

*Comment `#tfsec:ignore:...` trong lab.* Đây là cách báo công cụ quét bảo mật tfsec bỏ qua một cảnh báo có chủ đích (ví dụ VPC học không cần flow log). tfsec hiện đã nhập vào **Trivy** (`trivy config`), Trivy vẫn hiểu kiểu comment này.

**Lỗi hay gặp & cách sửa**

- **`Error: Module not installed`** hoặc **`Module version requirements have changed`**: vừa thêm module hay đổi `version`. Sửa: `terraform init` (hoặc `terraform init -upgrade` khi nâng version).
- **`no available releases match the given constraints`**: ràng buộc provider giữa root và module mâu thuẫn, ví dụ root ghim `aws ~> 5.0` nhưng module VPC 6.x đòi `>= 6.28`. Sửa: chọn cặp phiên bản khớp nhau.
- **`Error: Unsupported argument`** sau khi nâng major version của module: input bị đổi tên hoặc bỏ. Sửa: đọc changelog / hướng dẫn nâng cấp của module trên GitHub trước khi đổi major.
- **Plan đòi xoá tạo lại hàng loạt tài nguyên sau khi nâng module**: địa chỉ bên trong module thay đổi. Module tốt thường kèm block `moved`; nếu không, đừng apply, quay lại version cũ và đọc kỹ.

💰 **Chi phí / an toàn:** cấu hình lab7 như trong repo tạo **2 NAT Gateway** (khoảng 0,09–0,12 USD/giờ chỉ riêng NAT, chưa kể dữ liệu và EIP). Thêm `single_nat_gateway = true` khi học, destroy ngay khi xong.

<details><summary>Gợi ý</summary>

## Lab8 · VPC + ALB + Auto Scaling + MongoDB {023-024}

Đây là kiến trúc web 3 tầng (3-tier) kinh điển. Code lab: `iac-using-terraform/lab8/` với 5 module `network`, `security`, `bastion`, `storage`, `application`.

```
User → ALB (public subnet) → Auto Scaling Group: các EC2 app (private subnet) → MongoDB (private subnet)
                    Bastion host (public subnet) → SSH vào các máy private
```

- **ALB (Application Load Balancer):** chia request cho nhiều EC2, và chỉ gửi tới máy *healthy* (qua health check của **Target Group**).
- **Launch Template + Auto Scaling Group:** khuôn mẫu để tạo EC2. ASG giữ số máy trong khoảng `min/desired/max`, tự thay máy hỏng và tự tăng giảm theo tải.
- **`user_data`:** script chạy **một lần** khi EC2 khởi động lần đầu, dùng để cài app.
- **Bastion host:** máy trung gian ở public subnet để SSH vào máy private. Ngày nay người ta hay thay bằng SSM Session Manager.
- **Security group tham chiếu lẫn nhau:** SG của app chỉ cho phép traffic *từ SG của ALB*, không mở cho `0.0.0.0/0`.

Trong lab, ALB có listener port 80 với hai rule theo đường dẫn: `/languages*` và `/ok` vào target group `api` (port 8080, health check `/ok`), còn lại vào target group `webserver` (port 80, health check `/`).

**Đi sâu hơn**

*Đổi Launch Template không thay máy đang chạy.* ASG dùng `version = "$Latest"`, nên máy **mới** sẽ lấy bản template mới, nhưng máy **đang chạy** giữ nguyên `user_data` cũ. Muốn ASG tự thay dần máy cũ, thêm `instance_refresh` **và** đổi `version` sang `latest_version`. Tài liệu AWS provider ghi rõ: với `"$Latest"`, refresh **không** được kích hoạt, vì giá trị chuỗi `"$Latest"` trong code không đổi.

```hcl
resource "aws_autoscaling_group" "asg" {
  # ...
  launch_template {
    id      = aws_launch_template.apptemplate.id
    version = aws_launch_template.apptemplate.latest_version   # số version thật, đổi mỗi lần sửa template
  }
  health_check_type         = "ELB"     # coi máy "hỏng" theo health check của ALB, không chỉ theo EC2
  health_check_grace_period = 300       # cho user_data 5 phút cài app trước khi bị kiểm tra

  instance_refresh {
    strategy = "Rolling"
    preferences {
      min_healthy_percentage = 50       # thay từng nửa, luôn còn máy phục vụ
    }
  }
}
```

Mặc định `health_check_type = "EC2"`: máy còn chạy là "healthy" dù app bên trong đã chết. Đặt `"ELB"` để ASG thay máy khi ALB thấy app không trả lời.

*Provider `hashicorp/template` đã bị lưu trữ (archived).* Module `application` dùng `data "template_cloudinit_config"` của provider `hashicorp/template` 2.2.0. Repo provider này đã archived, không có bản cho một số nền tảng mới (ví dụ Mac Apple Silicon). Thay bằng provider `hashicorp/cloudinit` (cùng cú pháp `part {}`) hoặc hàm có sẵn `templatefile()`:

```hcl
data "cloudinit_config" "config" {
  gzip          = false
  base64_encode = true
  part {
    content_type = "text/x-shellscript"
    content      = templatefile("${path.module}/app.sh.tftpl", {
      alb_dns    = aws_lb.alb1.dns_name
      mongodb_ip = var.mongodb_ip
    })
  }
}

resource "aws_launch_template" "apptemplate" {
  # ...
  user_data = data.cloudinit_config.config.rendered   # đã base64 sẵn
}
```

Tách script ra file `.tftpl` giúp đọc dễ hơn heredoc dài và tránh nhầm giữa `${...}` của Terraform với biến shell.

*`depends_on` trên module: dùng ít thôi.* `lab8/main.tf` đặt `depends_on = [module.network, module.security]` cho gần như mọi module, trong khi các module đã tham chiếu output của nhau (đủ để Terraform biết thứ tự). Tài liệu Terraform cảnh báo `depends_on` trên module làm plan "thận trọng" hơn: nhiều giá trị thành `(known after apply)` và có thể đề xuất thay thế nhiều hơn cần thiết. Thử xoá các `depends_on` thừa và xem `plan` vẫn đúng thứ tự.

*IMDSv2.* Comment `#tfsec:ignore:aws-ec2-enforce-launch-config-http-token-imds` cho biết lab đang bỏ qua cảnh báo bắt buộc IMDSv2. Trong thực tế nên thêm `metadata_options { http_tokens = "required" }` vào launch template; IMDSv2 chặn kiểu tấn công SSRF đánh cắp credentials của role trên máy.

*SSH qua bastion bằng một lệnh:* `ssh -J ubuntu@<bastion-ip> ubuntu@<app-private-ip>` (cần `ssh-agent` có key, hoặc cấu hình `~/.ssh/config` với `ProxyJump`). Đừng chép private key lên bastion.

**Lỗi hay gặp & cách sửa**

- **SSH vào bastion bị timeout**: `workstation_ip` trong `lab8/terraform.tfvars` là IP của **giảng viên** (`123.20.239.118/32`). Sửa: đặt IP của bạn, `"$(curl -s https://checkip.amazonaws.com)/32"`.
- **Target unhealthy với lý do `Target.Timeout` hoặc `Target.ResponseCodeMismatch`**: xem lý do bằng `aws elbv2 describe-target-health --target-group-arn <arn>`. `Timeout` thường là SG app không cho SG ALB vào port, hoặc app chưa chạy. `ResponseCodeMismatch` là app có trả lời nhưng không phải mã 200 ở đường dẫn health check.
- **`Provider registry.terraform.io/hashicorp/template v2.2.0 does not have a package available for your current platform`**: gặp trên máy ARM (ví dụ Mac M-series). Sửa: chuyển sang `cloudinit_config` như ở trên.
- **AMI không chạy ở region của bạn**: AMI trong tfvars là của Singapore (`ap-southeast-1`, provider cũng ghi cứng Singapore). Muốn chạy ở Sydney thì đổi cả `provider` lẫn ba AMI. AMI Ubuntu 20.04 cho app đã hết hỗ trợ tiêu chuẩn, nên chọn Ubuntu 22.04/24.04 khi làm lại.

Ước lượng tổng **0,15–0,25 USD/giờ**. Làm liền một buổi rồi `terraform destroy` ngay. Kiểm tra lại Load Balancer và NAT trên console sau khi destroy.

## Lab9 · Lưu Terraform state trên S3 {025}

Mặc định state nằm ở **máy bạn**. Khi làm việc nhóm hoặc chạy trong CI/CD, cách này gặp 3 vấn đề: người khác không thấy state, hai người cùng `apply` có thể ghi đè nhau, và mất máy là mất state.

```hcl
terraform {
  backend "s3" {
    bucket         = "udemy-terraform-state-singapore-<tên-bạn>"   # tên bucket là duy nhất toàn cầu
    key            = "lab9/terraform.tfstate"
    region         = "ap-southeast-1"
    dynamodb_table = "udemy-terraform-state"   # khoá state, primary key: LockID (kiểu String)
    encrypt        = true
  }
}
```

- **Bucket S3:** lưu file state. Nên **bật Versioning** để khôi phục được khi state bị hỏng.
- **State locking:** khi một người đang `apply`, người khác phải chờ.
  - Cách cũ là dùng **DynamoDB**, như repo đang làm.
  - Từ Terraform **1.10** (ổn định từ 1.11) có thể dùng `use_lockfile = true`, tức là khoá ngay trên S3, không cần DynamoDB.
- Bucket và bảng DynamoDB phải **tạo trước** (bằng tay hoặc bằng một project Terraform riêng). Backend không tự tạo được chính nó.
- Đổi backend thì chạy `terraform init -migrate-state` để chuyển state cũ lên S3.
- Các lệnh hay dùng với state: `terraform state list`, `terraform state show <địa chỉ>`, `terraform import`, `terraform state rm`.
- Bucket trong repo tên `...-linh` là của giảng viên, **bạn phải đổi sang tên của bạn**.

Code lab (`iac-using-terraform/lab9/main.tf`) dùng `key = "udemy-terraform"` và chưa có `encrypt`.

**Đi sâu hơn**

*Cách viết khuyến nghị hiện nay: S3 native locking.* Từ Terraform 1.11, `use_lockfile` đã ổn định và các tham số DynamoDB (`dynamodb_table`) bị đánh dấu **deprecated**: vẫn chạy, có cảnh báo, và tài liệu nói sẽ bị bỏ ở một bản minor sau này.

```hcl
terraform {
  backend "s3" {
    bucket       = "udemy-tfstate-<tên-bạn>-apse2"
    key          = "lab9/terraform.tfstate"
    region       = "ap-southeast-2"
    encrypt      = true
    use_lockfile = true      # tạo file lab9/terraform.tfstate.tflock cạnh state khi đang khoá
  }
}
```

Lock file tên `<key>.tflock`. IAM cần thêm quyền `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` trên file `.tflock` đó. Đang dùng DynamoDB muốn chuyển: đặt **cả hai** (`dynamodb_table` và `use_lockfile = true`) một thời gian để người dùng Terraform cũ vẫn được khoá, rồi bỏ `dynamodb_table`.

*Backend block không dùng được biến.* Viết `bucket = var.bucket` sẽ lỗi, vì backend được đọc **trước** khi Terraform xử lý biến. Cách làm phổ biến là **partial configuration**: để trống một phần trong code, truyền khi `init`:

```hcl
# main.tf
terraform {
  backend "s3" {}
}
```

```bash
# backend-dev.hcl
bucket       = "udemy-tfstate-<tên-bạn>-apse2"
key          = "dev/terraform.tfstate"
region       = "ap-southeast-2"
use_lockfile = true

terraform init -backend-config=backend-dev.hcl
```

(OpenTofu thì cho phép dùng biến và locals trong backend.)

*Project "bootstrap" tạo chính bucket state.* Bucket nên có: versioning, chặn public access, mã hoá (S3 đã tự mã hoá SSE-S3 mọi object mới từ 2023), và `prevent_destroy` để không lỡ tay xoá:

```hcl
resource "aws_s3_bucket" "state" {
  bucket = "udemy-tfstate-<tên-bạn>-apse2"
  lifecycle { prevent_destroy = true }
}
resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration { status = "Enabled" }
}
resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

Project bootstrap này thường giữ state **local** (hoặc sau khi tạo xong thì migrate chính nó lên bucket vừa tạo).

*Đưa tài nguyên có sẵn vào state: block `import`* (Terraform 1.5+). Thay vì lệnh `terraform import` (sửa state ngay, không qua review), viết vào code:

```hcl
import {
  to = aws_key_pair.udemy-keypair
  id = "udemy-keypair"            # ID theo tài liệu provider: với key pair là key_name
}
```

`terraform plan` sẽ báo `1 to import`. Chưa có block `resource`? Chạy `terraform plan -generate-config-out=generated.tf` để Terraform viết nháp giúp, rồi bạn đọc và chỉnh lại. Ngược lại, muốn **bỏ quản lý mà không xoá** tài nguyên thật, dùng block `removed`:

```hcl
removed {
  from = aws_key_pair.udemy-keypair
  lifecycle { destroy = false }
}
```

*Các lệnh state "nguy hiểm" cần biết:* `terraform state pull > backup.tfstate` (tải state về xem/sao lưu), `terraform force-unlock <LOCK_ID>` (gỡ khoá bị kẹt khi `apply` bị ngắt giữa chừng; chỉ dùng khi chắc chắn không ai đang chạy).

**Lỗi hay gặp & cách sửa**

- **`Error: Error acquiring the state lock`**: có người (hoặc chính bạn ở terminal khác, hoặc một lần chạy bị Ctrl+C) đang giữ khoá. Thông báo có `ID` của lock. Chờ người kia xong; nếu chắc chắn là khoá "mồ côi" thì `terraform force-unlock <ID>`.
- **`Error: Backend configuration changed`** (kèm gợi ý chạy `terraform init`): bạn đổi bucket/key/region trong block backend. Chạy `terraform init -migrate-state` để **chuyển** state sang chỗ mới, hoặc `terraform init -reconfigure` để **bỏ qua** state cũ (chỉ khi bạn biết chắc).
- **`Error: Variables not allowed`** trong block backend: dùng `var.` hay `local.` trong backend. Sửa: viết giá trị cố định hoặc dùng `-backend-config`.
- **Bucket không tồn tại / `AccessDenied` / `BucketAlreadyExists`** khi `init`: chưa tạo bucket, sai region, user IAM thiếu quyền, hoặc tên bucket đã bị người khác (ví dụ giảng viên) dùng trên toàn cầu. Sửa: tạo bucket tên riêng của bạn trước.

💰 **Chi phí / an toàn:** bucket state gần như miễn phí (vài KB). DynamoDB on-demand cho khoá state cũng gần như 0 đồng, nhưng `use_lockfile` giúp bạn khỏi phải quản lý thêm bảng. Phần tốn tiền là **lab9 vẫn tạo VPC có NAT Gateway** giống lab6: destroy khi xong. Lưu ý: `destroy` xoá tài nguyên, **không xoá** bucket state.

## Lab10 · Nhiều môi trường, nhiều region {026-027}

```
lab10/
├── modules/          ← code dùng chung (networking, security, compute)
├── singapore-dev/    ← main.tf gọi modules + terraform.tfvars của dev
└── tokyo-test/       ← cùng modules, tfvars khác, region khác
```

- **Mỗi môi trường một thư mục**, mỗi thư mục có **state riêng** (đặt `key` khác nhau trong backend S3). Nhờ vậy `destroy` môi trường dev không đụng tới môi trường test.
- Một cách khác là **`terraform workspace`**: cùng code, nhiều state. Cách này gọn hơn nhưng dễ nhầm môi trường. Với người mới, chia thư mục rõ ràng hơn.
- Region khác thì AMI khác và tên AZ khác. Những giá trị này nên để trong tfvars, không hard-code trong module.
- **Dọn dẹp cuối chương:** chạy `terraform destroy` ở **từng** thư mục môi trường. Sau đó mở console để kiểm tra EC2, EIP, NAT Gateway, Load Balancer và EBS volume ở **mọi region** bạn đã dùng.

Trong code lab, hai môi trường dùng **hai bucket khác nhau** (`...-singapore-linh` ở Singapore và `...-tokyo-linh` ở Tokyo) nhưng cùng `key = "udemy-terraform"`. Vị trí state = bucket + key, nên vẫn tách biệt.

**Đi sâu hơn**

*Thư mục hay workspace?*

| | Mỗi môi trường một thư mục | `terraform workspace` |
|---|---|---|
| State | Backend riêng (bucket/key riêng) | Cùng backend; S3 lưu ở `env:/<tên-workspace>/<key>` |
| Khác biệt giữa môi trường | Tự do (provider, version, tài nguyên khác nhau) | Chỉ qua biến và `terraform.workspace` |
| Phân quyền (dev/prod khác tài khoản) | Dễ | Tài liệu HashiCorp nói **không phù hợp** |
| Rủi ro | Lặp code `main.tf` (giảm bằng module) | Quên `workspace select`, apply nhầm prod |

Workspace hợp với các bản sao **tạm thời** của cùng một môi trường (ví dụ mỗi feature branch một stack thử nghiệm). Môi trường dev/test/prod thật thì nên tách thư mục (hoặc tách repo, tách tài khoản AWS).

```bash
terraform workspace new test        # tạo và chuyển sang workspace "test"
terraform workspace list            # dấu * là workspace hiện tại
terraform workspace select default
```

```hcl
locals {
  env = terraform.workspace                      # "default", "test"...
  instance_type = local.env == "prod" ? "t3.small" : "t3.micro"
}
```

*Nhiều region trong một cấu hình: provider alias.* Thay vì hai thư mục, đôi khi bạn cần một stack tạo tài nguyên ở hai region (ví dụ bucket nhân bản sang region khác):

```hcl
provider "aws" {
  region = "ap-southeast-1"                 # mặc định
}
provider "aws" {
  alias  = "tokyo"
  region = "ap-northeast-1"
}

resource "aws_security_group" "sg_tokyo" {
  provider = aws.tokyo
  name     = "demo-tokyo"
}

module "networking_tokyo" {
  source    = "../modules/networking"
  providers = { aws = aws.tokyo }           # module không cần (và không nên) có provider riêng
  # ...
}
```

AWS provider **6.x** còn cho phép đặt `region` ngay trên từng tài nguyên (thuộc tính `region` có ở hầu hết resource), nên nhiều trường hợp không cần alias nữa. Lưu ý: module lab10 có block `provider` bên trong (legacy), nên phải xoá block đó trước khi dùng `providers = {...}`.

*Giảm lặp code giữa các thư mục.* `singapore-dev/main.tf` và `tokyo-test/main.tf` gần như giống hệt nhau. Ngoài module, có thể dùng partial backend config (mỗi môi trường một file `backend-<env>.hcl`) và một file `<env>.tfvars`, chỉ còn **một** thư mục code. Công cụ như Terragrunt sinh ra để giải bài toán này ở quy mô lớn.

🔴 *Thử thách (dọn dẹp như người đi làm).* Viết script `leftovers.sh` quét **mọi region đang bật** của tài khoản và in ra các tài nguyên hay gây tốn tiền còn sót: EC2 đang chạy, NAT Gateway `available`, Elastic IP, Load Balancer, EBS volume `available` (không gắn vào máy nào). Chạy script sau khi destroy cả chương: kết quả phải rỗng.

<details><summary>Lời giải</summary>

```bash
#!/usr/bin/env bash
set -uo pipefail
for r in $(aws ec2 describe-regions --query 'Regions[].RegionName' --output text); do
  ec2=$(aws ec2 describe-instances --region "$r" \
        --filters Name=instance-state-name,Values=running,stopped \
        --query 'Reservations[].Instances[].InstanceId' --output text)
  nat=$(aws ec2 describe-nat-gateways --region "$r" \
        --filter Name=state,Values=available --query 'NatGateways[].NatGatewayId' --output text)
  eip=$(aws ec2 describe-addresses --region "$r" --query 'Addresses[].PublicIp' --output text)
  elb=$(aws elbv2 describe-load-balancers --region "$r" \
        --query 'LoadBalancers[].LoadBalancerName' --output text)
  ebs=$(aws ec2 describe-volumes --region "$r" \
        --filters Name=status,Values=available --query 'Volumes[].VolumeId' --output text)
  out="$ec2$nat$eip$elb$ebs"
  [[ -n "${out// /}" ]] && echo "[$r] EC2: $ec2 | NAT: $nat | EIP: $eip | ELB: $elb | EBS: $ebs"
done
echo "Quét xong."
```

EC2 `stopped` không tính phí giờ máy nhưng ổ EBS của nó vẫn tính tiền, nên script liệt kê luôn. Có thể nâng cấp: chạy script này hằng tuần bằng cron, và đặt **AWS Budgets** cảnh báo qua email khi chi phí vượt 5 USD.
</details>
